先定关系：SystemUI 与 WMS 是平级模块，不是它的子集。WMS 决定「窗口放哪、多大、谁在上面」，SystemUI 决定「这些系统窗口里画什么、怎么交互」。学过 WMS 再来，窗口树、Insets、输入分发、转场的地基可以直接复用。

一、先立住：五个版本事实

版本陷阱 ⚠ 网上讲 SystemUI 的文章大量基于 11/13/14，类名和职责差别很大。以下五点是本树（android-12.0.0_r32）实测，先记住能少走很多弯路。

  1. 没有 SystemBars.java，也没有 CentralSurfaces。状态栏就是 StatusBar，而且是启动组件之一（sysui/res/values/config.xml:319），不是被谁 new 出来的。讲 SystemBars 的基本是 Android 13+。
  2. 通知管线是新的：NotifPipeline（NotifPipeline.java:75）+ NotifCollection（NotifCollection.java:128）。本树没有 NotificationEntryManager，老文章那条链在 12 已被拆掉。
  3. WMShell 跑在 SystemUI 进程里：WMShell 本身就是 SystemUI 组件（sysui/wmshell/WMShell.java:93），Shell 的 Transitions/ShellTransitions 同进程加载。SystemUI 崩了，分屏/PIP/转场一起没。
  4. 两个方向的 binder 别搞反：IStatusBarService（system_server 的 StatusBarManagerService.java:95）是 SystemUI 调 system_server；IStatusBar（SystemUI 的 CommandQueue.java:81）是 system_server 调 SystemUI。
  5. Shell Transitions 有代码但不是默认主线：Transitions.java/ShellTransitions.java 都在，本树转场仍以 WMS 的 AppTransition + leash 为主（与 WMS 路线图一致）。排障先看 AppTransition，再确认有没有走 Shell。

二、阶段 0：启动链与工具箱（6 h）

启动链（已核实）

SystemServer.startSystemUi() — SystemServer.java:2931（定义 :3024），startServiceAsUser(SystemUIService)
SystemUIService.onCreate() — SystemUIService.java:66
SystemUIApplication.startServicesIfNeeded() — SystemUIService.java:70 → SystemUIApplication.java:161
读组件清单 — config_systemUIServiceComponents（config.xml:314）
反射实例化 + start() — SystemUIApplication.java:214，逐个 start() / onBootCompleted()

要点：

  • SystemUIApplication（:49）不是「一个 UI」，是组件容器；每个组件继承 SystemUI。
  • config_systemUIServiceComponentsPerUser（config.xml:348）只有 NotificationChannels 一项：换用户只重启这一部分，其余组件跟进程走。
  • SystemUIFactory（SystemUIFactory.java:42）+ Dagger：读 config_systemUIFactoryComponent（config.xml:311）决定实现类。定制 ROM 常在这里换工厂，而不是改 StatusBar。
  • SystemUI 能加 TYPE_STATUS_BAR/TYPE_NOTIFICATION_SHADE，是因为它持有 INTERNAL_SYSTEM_WINDOW 权限；普通 App 会被 WMS 直接拒。

三、阶段 1：状态栏与图标（20 h）

主线

电池 / 网络 / 时钟→ BatteryControllerImpl(:55)→ StatusBarIconControllerImpl(:59)→ icon slot（left/right）
  • StatusBar（StatusBar.java:268）是装配工：把窗口、面板、锁屏、图标、回调接在一起，本体近 5000 行，按功能跳读，不要从头读到尾。
  • 图标槽位：StatusBarIconControllerImpl 继承 StatusBarIconList，按 slot 管理；setIcon(slot, icon) / removeIcon(slot) 是入口。
  • 深浅色：system_server 通过 DisplayPolicy.java:2561 statusBar.onSystemBarAttributesChanged(...) 把 appearance 推给 SystemUI，CommandQueue 再分发，最终切 dark icon。图标看不清先查这条链，不要先改颜色。
  • StatusBarManager（core/java/android/app/StatusBarManager.java:48）是给 App 的公开 API（disable() :239、expandNotificationsPanel() :317），最终落到 StatusBarManagerService（:657 / :881）。
坑 图标重复/不消失 = slot 名冲突或 remove 没配对；深色页面图标不变白 = appearance 没传到，或被全屏窗口的 flag 覆盖；状态栏高度改了但内容没动 = 高度在 WMS 的 DisplayPolicy/Insets 侧，SystemUI 只负责画。
实验与验收 用 cmd statusbar 切 disable 标志观察图标区；动态加一个 system icon 再移除确认无残留。验收：能解释「图标为什么是黑/白」，并指出链路上任一环出错的现象。

四、阶段 2：通知管线（30 h，最值钱的一块）

主线（12 的新管线）

App postNotification → NotificationManagerService（system_server）
NotificationListener(:47) 收到 onNotificationPosted
NotifPipeline(:75) 收集
NotifCollection(:128) 去重/更新/取消
NotifCoordinators(:41)：RankingCoordinator(:43) / HeadsUpCoordinator(:59) / Media…
HeadsUpManager(:51) 决定弹不弹 → NotificationRowBinderImpl(:51) 绑 View
Shade / StatusBar 展示
  • NotifPipeline 是编排者，NotifCollection 是数据源。所有「通知为什么没出现」先确认它有没有进 NotifCollection。
  • 分组/折叠由 NotifCollection 的 group 逻辑与各 coordinator 共同决定（12 树里没有 GroupCoordinator.java，别照老文章找）；heads-up 由 HeadsUpManager + HeadsUpCoordinator 决策；排序在 RankingCoordinator。
  • 12 的 heads-up 实现是 HeadsUpManagerPhone（statusbar/phone/），抽象基类在 statusbar/policy/HeadsUpManager.java:51。
  • View 绑定是异步的（NotificationRowBinderImpl），「数据到了但界面晚一拍」是正常现象。
坑 不显示：channel 关了 / importance 太低 / 被压进折叠组 / App 被禁通知。重复：同 key 更新没走 update 路径，或两条不同 key。不弹 heads-up：灭屏、免打扰、前台服务、全屏窗口抑制，逐项排除。
实验与验收 用不同 importance 的 channel 各发一条，记录「是否 heads-up / 是否折叠 / 排序」；抓一次 dumpsys notification --noredact 讲清一条通知的字段变化。验收：给定「通知不显示」，10 分钟内用三层（NMS / NotifCollection / Shade）缩小范围。

五、阶段 3：Shade 与 QS（24 h）

  • 面板本体：NotificationPanelViewController（NotificationPanelViewController.java:181）负责手势、展开高度、折叠、与锁屏联动。
  • 面板状态机：ShadeControllerImpl（ShadeControllerImpl.java:41）负责「现在该不该展开/收起」，以及和 Keyguard、转场的协调。
  • 承载窗口：NotificationShadeWindowControllerImpl（:77）创建 TYPE_NOTIFICATION_SHADE 窗口（:211），mWindowManager.addView(mNotificationShadeView, mLp)（:232）——SystemUI 与 WMS 最直接的接触点之一。
  • 背景遮罩：ScrimController（ScrimController.java:75）管 scrim 透明度与前后层。
  • QS：QSTileHost（QSTileHost.java:78）管 tile 创建/排序/监听；QuickQSPanelController（QuickQSPanelController.java:42）管快捷面板那 6 个。
坑 拉不下来：锁屏状态、disable 标志、手势被上层窗口吃掉。收不回去：ShadeController 状态与 Keyguard/转场不同步，常见于解锁瞬间。tile 不显示：没在 QSTileHost 注册或 defaultTileList 没加。背景透明/黑块：ScrimController 的 alpha 被动画打断。
实验与验收 加一个自定义 QS tile（带长按跳转），重启后仍在；用 cmd statusbar expand-notifications / collapse 驱动面板观察状态变化。验收：能画出「手指下拉 → 展开 → 松手吸附/回弹」的状态机，并指出每个状态由谁维护。

六、阶段 4：Keyguard 与解锁（20 h）

灭屏/亮屏 → KeyguardViewMediator(:173) 决定 show/hide
KeyguardUpdateMonitor(:141) 收集凭据 / 生物识别 / SIM 状态
KeyguardBouncer(:57) 弹出密码 / PIN 界面
解锁成功 → hide → 通知 Shade / StatusBar / 转场
  • KeyguardViewMediator 是总调度，KeyguardUpdateMonitor 是状态源，KeyguardBouncer 是「要输密码时的那层」。
  • 与 WMS：锁屏是特殊窗口 + 一组可见性规则；showWhenLocked 的 Activity 能盖在锁屏上，但转场仍受 Keyguard 控制。
  • 与 Shade：锁屏上下拉是「锁屏面板」，解锁后才是「通知面板」，两者共用 NotificationPanelViewController 的不同配置。
  • 注意：KeyguardViewMediator、KeyguardUpdateMonitor 在 com/android/keyguard/ 包，不在 com/android/systemui/，find 时别漏。
坑 解锁后黑屏：Keyguard 已 hide 但下面窗口还没 drawn，是转场时序，不是锁屏 bug。锁屏不显示通知：visibility/isSensitive 策略，属正常。指纹解锁后仍停在锁屏：生物识别回调没触发 dismiss。多用户/工作资料异常：per-user 只重启 NotificationChannels，其他组件状态要自己处理。
实验与验收 adb shell input keyevent 26/82 走灭屏→亮屏→解锁，logcat 打时间戳；做一个 showWhenLocked 的 Activity 看层级。验收：能解释「解锁后黑屏」和「锁屏不显示通知」是两条完全不同的链路。

七、阶段 5：导航栏、手势、Recents（20 h）

  • 导航栏：NavigationBarController（NavigationBarController.java:85）按 display 创建/销毁 NavigationBarView（:101），支持三键/两键/手势三种模式。
  • 手势返回：SystemUI 侧 EdgeBackGestureHandler（EdgeBackGestureHandler.java:94）；WMS 侧 SystemGesturesPointerEventListener（SystemGesturesPointerEventListener.java:40）把系统手势事件送过来。边缘返回失效，两边都要查。
  • Recents：Recents（Recents.java:33）只是壳，真正实现由 Launcher/QuickStep 提供（RecentsImplementation，RecentsImplementation.java:26）；跨进程入口是 OverviewProxyService（OverviewProxyService.java:122）。
  • 与 WMS 的边界：导航栏高度决定 Insets；手势区域属于 WMS 的 system gesture exclusion；Recents 动画走 Shell。
坑 隐藏导航栏后手势失效：只改可见性，没同步 gesture inset / exclusion 区域。三键切手势后返回键位置错：NavigationBarView 没重建或 overlay 没生效。Recents 拉不起来：Launcher 死了或 OverviewProxy 没连上，不是 SystemUI 本身。
实验与验收 用 cmd overlay 切换手势/三键导航，观察 NavigationBarView 重建；复现一次「隐藏导航栏导致手势返回失效」，定位是 inset 还是 exclusion。验收：能说清一次边缘返回从触摸到 onBackPressed 的完整链路，以及 SystemUI 在哪一环。

九、阶段 7：与 WMS / WMShell 的交界（24 h，决定能不能排疑难）

这一阶段是把 WMS 知识变现的地方。四条交界线：

  1. 窗口类型与权限：TYPE_STATUS_BAR、TYPE_NOTIFICATION_SHADE、TYPE_NAVIGATION_BAR 由 SystemUI 添加；层级、焦点、触摸区域仍由 WMS 的 DisplayPolicy/InputMonitor 决定。
  2. Insets 与 SystemBarAttributes：SystemUI 画多高，WMS 就留多少 inset；DisplayPolicy.java:2561 把 appearance 推下来。状态栏遮挡 App 内容、全屏手势冲突，都在这条线上。
  3. 转场：WMShell（WMShell.java:93）在 SystemUI 进程里加载 Transitions/ShellTransitions；SystemUI 窗口要参与转场，否则「动画跳变/闪黑」。
  4. 冻屏/黑屏：SystemUI 的窗口没 draw，WMS 等 isDrawn，输入/转场就卡住。「隐藏 TaskBar 导致冻屏」就是典型：表面少画一帧，根因在绘制回调链。
排障顺序（建议固化成习惯）
现象（黑屏/冻屏/闪）
dumpsys window：窗口在不在、visible 吗、frame 对吗、mDrawState 是什么
dumpsys input：焦点窗口是谁、有没有 waitQueue
logcat --pid=$(pidof com.android.systemui)：异常 / ANR / 掉帧
Winscope：转场与层级随时间的变化
最后才怀疑业务逻辑
验收 拿一个真实的 SystemUI 冻屏/黑屏 case，写出「现象 → 三层 dump → 根因 → 修复/规避」的完整记录。
工具 用 Window Dump × 壁纸黑闪分析器 把 dumpsys 与 logcat 对齐：它会把壁纸窗口的 mDrawState、转场时间窗和 Surface 重建事件列在同一张时间线上。

十、阶段 8：定制、稳定性与面试（22 h）

定制三板斧

  • RRO/Overlay：改资源不改代码，cmd overlay list 验证；车机/ODM 最常用。
  • SystemUIFactory / Dagger：换实现类，适合深度定制；先看 config_systemUIFactoryComponent（config.xml:311）。
  • 直接改组件：前两条走不通才做，改完必须回归锁屏、通知、转场三条主线。

稳定性

  • SystemUI ANR：主线程被通知绑定/数据库/锁竞争阻塞；看 dumpsys activity processes + traces。
  • 内存：通知过多、图标缓存、壁纸；GarbageMonitor 是内置泄漏监控组件。
  • 进程重启：SysuiRestartReceiver / killall 后能否自愈，是判断「状态残留」最快的实验。

十一、四个实战项目（必须交付东西）

判断标准：有 patch / 有工具 / 有报告，能复现、能验证。跑两条 dumpsys 不算项目。

P1 通知全链路时间戳工具（3–5 天）

  • 做什么：监听 NotifPipeline/NotifCollection/RowBinder 的关键节点，输出一条通知从 post 到可见各阶段耗时。
  • 交付物：可重复运行的脚本或 debug 版 patch + 10 条通知的耗时表。
  • 验收：能解释「为什么这条通知比别人慢 100 ms」。

P2 QS Tile + 状态栏图标定制（3–5 天）

  • 做什么：加一个自定义 tile（带长按动作）+ 一个动态 system icon。
  • 交付物：patch + 截图 + 回归记录（重启、多用户、深浅色切换）。
  • 验收：三种场景都不崩、不残留。

P3 锁屏解锁时序与故障注入（5–7 天）

  • 做什么：抓一次完整解锁的时序图；人为注入 3 个故障（bouncer 不消失、指纹回调丢失、解锁后黑屏）。
  • 交付物：时序图 + 3 份「现象→根因→修复」记录。
  • 验收：每个故障都能在 15 分钟内定位到类。

P4 SystemUI × WMS 冻屏复现（5–7 天）

  • 做什么：复现「隐藏 TaskBar 导致冻屏」类问题，从 SystemUI 侧确认谁没 draw，再从 WMS 侧确认在等什么。
  • 交付物：完整 case 报告 + 两种修法对比。
  • 验收：能讲清「为什么少画一帧会冻住整个输入/转场」。

命令速查

adb / shell
# 进程与组件
adb shell dumpsys activity service com.android.systemui/.SystemUIService
adb shell ps -A | grep systemui

# 窗口
adb shell dumpsys window | grep -E "StatusBar|NotificationShade|NavigationBar"
adb shell dumpsys window windows

# 通知
adb shell dumpsys notification --noredact

# 系统栏控制
adb shell cmd statusbar help
adb shell cmd statusbar expand-notifications
adb shell cmd statusbar collapse

# 定制
adb shell cmd overlay list
adb shell cmd overlay enable <package>

# 重启验证
adb shell killall com.android.systemui

关键路径速记

frameworks/base/packages/SystemUI/src/com/android/systemui/
SystemUIApplication.java            组件容器
SystemUIService.java                入口 Service
statusbar/phone/StatusBar.java      装配工
statusbar/CommandQueue.java         system_server → SystemUI 回调入口
statusbar/phone/NotificationShadeWindowControllerImpl.java  Shade 窗口
statusbar/phone/NotificationPanelViewController.java        面板手势/展开
statusbar/notification/collection/NotifPipeline.java        通知编排
statusbar/notification/collection/NotifCollection.java      通知数据
keyguard/KeyguardViewMediator.java  锁屏总调度
wmshell/WMShell.java                Shell 接入点

注：KeyguardViewMediator、KeyguardUpdateMonitor 在 com/android/keyguard/ 包（不在 com/android/systemui/），AOSP 12 里两个包并存，find 时别漏。
