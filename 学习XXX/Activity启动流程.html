Activity 启动流程：一条链与四个岔路口

Activity 启动是 framework 里唯一一条同时穿过四个服务的链：app 侧的 Activity 把 Intent 交给 Instrumentation，binder 进 system_server 后由 ATMS 验身份、ActivityStarter 做全部准入与落栈决策，再由 AMS 决定要不要 fork 进程；新进程里 ActivityThread 反射构造 Activity、回调 onCreate/onResume，窗口经 ViewRootImpl 与 WMS 拿到第一帧。开发和定制里最常接到的四类反馈——「点了没反应」「白屏很久」「回到旧页面」「冷启动慢」——正好落在它的四个岔路口上，所以这条链的价值不在背流程，而在知道每个现象该往哪一行查。13 版有两个容易被 12 版经验带错的点：决策仍集中在 ActivityStarter，但「等 pause、预热 fork」这一段被移到 TaskFragment 里串行化；而 abort 的失败对外一律报成功，这意味着你只能信状态快照，不能信返回值。下面是一份 18 行、逐行现地核过的骨架，加上与另一份外部骨架的逐条对账：它有三处比我强，也有五处会让读者去查错的行。

3. 这份骨架怎么读

  1. 一句话定位：从 startActivity() 到第一帧上屏；中途会在 TaskFragment 里等一次 pause，再决定进程是复用、预热还是新 fork。
  2. 三个接力边界：binder ① execStartActivity()［app/Instrumentation.java:1798］；socket+fork startProcessAsync()［wm/ActivityTaskManagerService.java:4867］，新进程从 ActivityThread#main()［app/ActivityThread.java:7869］重新开始，调用栈在这里断；回环 attachApplicationLocked()［am/ActivityManagerService.java:4673］反向补发启动。
  3. 最小验证命令：adb shell am start -W -n 包/.Activity；精确分段用 events buffer：adb shell logcat -b events -v threadtime -d | grep -E "wm_create_activity|wm_restart_activity|am_proc_start|am_proc_bound|wm_on_create_called|wm_on_resume_called|wm_activity_launch_time"。main buffer 的 START u0/Start proc/Displayed 只能粗看有无新进程，不能定位。
  4. 本链最贵的一行：TaskFragment#resumeTopActivity()［wm/TaskFragment.java:1172］的 allPausedComplete 闸门——它决定这次启动是「等上一个 pause 完」还是「立刻走」，冷启动多出来的几百毫秒常落在这里。
  5. 可追问的三个名字：getReusableTask()［wm/ActivityStarter.java:2489］问复用判定的条件；startSpecificActivity()［wm/ActivityTaskSupervisor.java:1039］问「进程在但实例是新的」走哪条；attachApplicationLocked()［am/ActivityManagerService.java:4673］问进程起来后怎么把启动补回来。

4. 分块走读：闸门、预热、假成功、进程分叉

四块按「TaskFragment 决定何时能 resume → 等 pause 时先预热进程 → 拦下时对外怎么报 → 进程在不在」的顺序走。前三块都能用一条 logcat/dumpsys 命令验证，最后一块是唯一会换进程的地方。

块A｜第1跳：allPausedComplete 闸门

wm/TaskFragment.java:1181-1188

// 进入本块：next 已选定，上一跳可能仍停在 RESUMED
final boolean allPausedComplete = mRootWindowContainer.allPausedActivitiesComplete();
if (!allPausedComplete) {
    // ① why：pause 和 resume 必须串行，两个 Activity 同时 RESUMED 会让焦点/输入分裂
    ProtoLog.v(WM_DEBUG_STATES, "resumeTopActivity: Skip resume: some activity pausing.");
    return false;   // ② 不重试，等 pause 完成的回调再触发一次 resume
}

这段在干什么：进入时 next 已经是「该被 resume 的那一个」，但这一步不推进任何状态，只做一次全局检查：只要还有 Activity 在处理 pause，就直接返回 false。出去时的状态没变，等待方是 pause 完成后的下一次 resume 调用。

设计意图：用「返回 false + 外部重入」代替「阻塞等锁」。framework 不能在持 mGlobalLock 时睡等 app 回 pause 结果，否则整机窗口事务都停摆；所以它把等待变成「这次不做，下次再来」。代价是启动耗时里多出一段不可见的等待——这正是 TotalTime 里那几百毫秒的常见来源。

实战问题：冷启动偶发慢 300–800ms、且 trace 里 resumeTopActivity 被调用两次以上。因果：第一次撞上 allPausedComplete=false 提前返回，第二次才真正往下走。查法：adb shell dumpsys activity activities | grep -E "ResumedActivity|mResumedActivity" 看当时是否还有别的 Activity 处于 resumed/pausing；或在 wm/TaskFragment.java:1182 下断点，命中两次即为该路径。

🧠 思考（单块）
如果把这里改成「等 pause 完成再继续」，在哪些场景会立刻暴露问题？提示：想一下 mGlobalLock 是谁的锁、pause 的结果由谁送回来。

块B｜第2跳：pause 等待期提前 fork

wm/TaskFragment.java:1262-1274

if (next.attachedToProcess()) {
    next.app.updateProcessInfo(false, true, false, false);
} else if (!next.isProcessRunning()) {
    // ① why 原文注释：起进程是异步的，既然已经知道它没在跑，就提前起，
    //   省掉「等当前 Activity pause 完」的那段空转
    final boolean isTop = this == taskDisplayArea.getFocusedRootTask();
    mAtmService.startProcessAsync(next, false /* knownToBeDead */, isTop,
            isTop ? HostingRecord.HOSTING_TYPE_NEXT_TOP_ACTIVITY
                  : HostingRecord.HOSTING_TYPE_NEXT_ACTIVITY);
}

这段在干什么：进入时 next 还没进程；这一跳不 resume，只把 fork 请求发出去，让 zygote 在「等 pause」的同一段时间里把进程拉起来。出去时进程处于 starting，Activity 仍是 stopped。

设计意图：把两个独立耗时（pause 回环、进程 fork）重叠。反过来设计——等 pause 完再起进程——冷启动会稳定多花一次 fork+attach 的时间。注意这里的前提是 !isProcessRunning()：如果进程正在启动中，不会重复发。

实战问题：logcat 里 Start proc 出现得比 Displayed 早很多、但用户仍觉得慢。因果：进程已预热，慢在 app 侧 Application.onCreate 或首帧。查法：adb shell logcat -d | grep -E "Start proc|Displayed|ActivityTaskManager: START" 对齐三条时间戳；若 Start proc 与 START u0 几乎同时，说明走了本块预热；若 Start proc 明显晚于 pause 结束，说明预热没走（当时没有可 pause 的 Activity）。

🧠 思考（单块）
这里只预热、不 realStart，那么进程 attach 回来之后，是谁把「启动」这件事补上的？在骨架里找那一行。

块C｜第3跳：abort 对外一律报成功

wm/ActivityStarter.java:1262-1264

static int getExternalResult(int result) {
    // ① why：兼容老 API 语义——调用方拿到非 SUCCESS 会当异常处理，
    //   但启动被拦（后台限制/权限/Controller 否决）属于「正常拒绝」
    return result != START_ABORTED ? result : START_SUCCESS;
}

这段在干什么：进入时是内部结果码（可能 START_ABORTED，产生点在 :1096、:1789、:1828）；出去时被折成 START_SUCCESS。调用方完全看不出这次没起来。

设计意图：把「拒绝」和「出错」分开：出错要抛/返回错误，拒绝只是「不给你起」，对 app 表现为「已受理但什么也没发生」。这就是企业管控、儿童模式、后台启动限制能做到「静默」的原因。

实战问题：点了图标没反应，startActivity() 没抛异常、也没进 onCreate。因果：abort 被折叠成成功。查法：adb shell logcat -s ActivityTaskManager | grep "START u0" 有记录但无后续 Displayed；再看 adb shell logcat | grep -iE "abort|background start|denied"。判据是「有 START、无新 Task、无 Displayed」，三者同时成立才归因到本块。

🧠 思考（单块）
如果业务方非要区分「被拦」和「成功」，能拿到哪些信号？提示：想想 ActivityResult 回调、dumpsys activity activities 的 task 数量、以及 am start -W 的 Status 字段。

块D｜第4跳：进程分叉

wm/ActivityTaskSupervisor.java:1039-1052

void startSpecificActivity(ActivityRecord r, boolean andResume, boolean checkConfig) {
    final WindowProcessController wpc =
            mService.getProcessController(r.processName, r.info.applicationInfo.uid);
    boolean knownToBeDead = false;
    if (wpc != null && wpc.hasThread()) {
        // ① 有 binder 线程：直接发 ClientTransaction，本方法内完成
        realStartActivityLocked(r, wpc, andResume, checkConfig);
        return;
    }
    // … 省略：knownToBeDead 判定与参数整理（进程存在但线程未就绪时走这里）
    mService.startProcessAsync(r, knownToBeDead, isTop, hostingRecord);
    // ② 没线程：发 fork 请求就返回；真正的 realStart 发生在 attachApplication 回环里
}

这段在干什么：进入时拿到该 Activity 的进程记录；有 binder 线程就在本方法内直接 realStart（热启动），没有就只发 fork 请求然后返回（冷启动）。出去时两种情况形态完全不同：一个是「事务已发」，一个是「进程在起」。

设计意图：把「进程就绪」这件事抽成同一个入口，避免调用方到处判断。代价是读栈的人容易误以为 fork 是 startProcessAsync() 的调用子节点——它不是，真正的 realStart 在新进程 attach 之后从 RootWindowContainer 那一侧进来（:3611）。

实战问题：「图标闪一下消失」。因果：本方法走了 fork 分支，但进程起来后 attach 失败或 Application 崩溃，realStart 永远没发生。查法：adb shell logcat -d | grep -E "Start proc|am_proc_start|FATAL|am_crash"；判据是「有 Start proc、无对应 Displayed、有 crash 记录」。断点应打在 :1047（有线程）与 :1065（无线程）两处，看实际走哪条。

🧠 思考（单块）
热启动时 realStartActivityLocked() 在 TaskFragment 的 resume 流程里也会被调（:1382 那条分支之后）。同一个方法有两个入口，这会不会导致同一次启动发两次事务？靠什么字段防重？

支线｜Activity1 的 pause 为什么不在主干上

主干到「定 Task、起进程」为止都只关心 Activity2。Activity1 的 pause 是一条并发支线：它的终点不是 Activity2 的首帧，而是让 :1182 的闸门变成 true。把它画进主干会得出「pause 完才 fork」的错关系——实际两者是重叠的（这正是 :1271 提前预热的意义）。

TaskFragment#resumeTopActivity() → mResumedActivity 还活着，先暂停它 wm/TaskFragment.java:1172 └─ TaskFragment#startPausing() → 发 PauseActivityItem，记录转 PAUSING wm/TaskFragment.java:1571 └─ app 侧 ActivityThread#handlePauseActivity() → onPause() app/ActivityThread.java:4964 └─ 回执 ActivityRecord#activityPaused() ← 状态转 PAUSED wm/ActivityRecord.java:6238 └─ RootWindowContainer#allPausedActivitiesComplete() 为 true → 再进 resumeTopActivity wm/RootWindowContainer.java:3209

接力边界：第三行跨进程（binder 到 app），第四行是回执；回执由 ActivityClientController#activityPaused()［wm/ActivityClientController.java:184］接住，再落到 ActivityRecord。这条支线的主干只留两个接触点：入口 :1172、出口 :1182。

你的目的要不要展开这条支线
背名词表、回答「启动经过哪些方法」不要，主干留等待点即可
排查白屏 / 上屏慢要：Activity1 的界面在 pause 完成前一直显示，pause 慢会直接推迟 :1182 放行
排查「图标闪一下 / 点了没反应」不要，那是 abort 与起进程两条
做转场动画、启动保留上一页要：Activity1 的 pause 时机决定 transition 何时开始

同进程与跨进程的差别：同进程时 pause 只是一次本地事务，:1182 通常一次就过，感觉不到它存在；跨进程（Activity2 在新进程）时，Activity1 的 pause 与 Activity2 的 fork 并行——若 Start proc 明显早于 pause 结束，说明走了 :1271 的预热，属正常且更快。查当时有没有卡在 pause：adb shell dumpsys activity activities | grep -E "mResumedActivity|state=|pausing"；state=PAUSING 仍挂着且目标没 realStart，就是 :1182 在反复返回 false。

6. 两份骨架对账

外部那份骨架（另一个模型生成）同样基于 13 树，行号大部分真实存在。逐条核完的结论是：它的下半场比我第一版强，上半场有会让读者查错行的锚点，且终点缺失。下面只列有证据的差异，不评风格。

它赢的三处

内容为什么比我第一版强
wm/TaskFragment.java:1182 的 allPausedComplete 闸门我第一版把整段 resume 压成了一行，讲得出「走到哪」，讲不出「为什么冷启动慢」；这一行才是耗时的落点。
wm/TaskFragment.java:1271 的提前预热原文注释写明「start-process 是异步的，提前起以省掉等 pause 的时间」。这是 13 里冷启动真正省时间的一手，我漏了。
wm/RootWindowContainer.java:3611 + am/ActivityManagerService.java:4673 的 attach 回环把「fork 之后 realStart 从哪来」画出来了。没有这个回环，冷启动的栈在主路径上是断的。

它错/漏的五处

它的写法核对结果
startActivity(Intent) → app/Activity.java:5502:5502 是 startActivityForResult(Intent,int,Bundle)；startActivity(Intent) 在 :5929。差 427 行，按表去查会找不到。
null → setNewTask() 新建 Task @ :1627:1627 是 setNewTask(taskToAffiliate) 的调用点（定义 :2693），语义是「把记录关联到新 Task」。真正决定新建的是 computeTargetTask()——调用 :1578、定义 :1722，整份骨架里没出现。
三个同级 └─：复用 / setNewTask / startActivityLocked读起来像三选一，实际是「判断 → 两分支 → 汇合 → 再走一步」。第三个再用 └─，层级就断了。
「无进程 → startSpecificActivity()」@ :1045:1045 是 if (wpc != null && wpc.hasThread())，属有进程那条；startSpecificActivity 是统一入口（定义 :1039），1047 有线程直接 realStart，1065 才 fork。
终点停在 realStartActivityLocked() → ClientTransaction没有 handleLaunchActivity()、performLaunchActivity()、onResume、首帧。于是「启动完成」没有形态，白屏类问题在这份骨架上无处安放；也缺 abort 分支（:1096）与计时起点。

以后自己判骨架，四条就够：① 每个 File.java:行号 打开原文看方法名对不对；② 分支行是「并列」还是「汇合」，三个同级 └─ 就要问一句；③ 末尾有没有终点形态（首帧？事务？）；④ 有没有一条 25 分钟内能跑出来的判据。

🛠 三道判据题：症状 → 命令 → 归因

不出「请解释 X」这种题——那种题只验记忆。每题给一个真实症状，你要用命令把范围切到某一段，最后产出一句能写进笔记的归因。

判据（按相邻两个时间戳切段）：

段含义大了说明
wm_create_activity → am_proc_start准入/决策 → fork 完成（zygote 已回报 pid）等 pause、门禁、解析、fork 往返慢
am_proc_start → am_proc_bound进程初始化 → attachApplication 接回 system_server进程自身启动慢（so 加载、ART、多线程）
am_proc_bound → wm_on_create_calledbindApplication + Application.onCreate + 实例化Application/Provider 初始化重
wm_on_create_called → wm_on_resume_calledonCreate/onStart 自身app 初始化重（读配置、建 DB、DI）
wm_on_resume_called → wm_activity_launch_time布局 → 绘制 → 首帧布局层级深、主线程卡、GPU/SF

两个容易漏的标签：wm_restart_activity 是进程重建时的实际启动项（force-stop 之后再点最常见，此时 wm_create_activity 与它都会出现）；am_proc_bound 表示进程已 attach 完成，比 am_proc_start 更接近「进程可用」这个时刻。

顺带一个判据：am_proc_start 的第五个字段是 hosting type。看到 next-top-activity 就说明这次走了 TaskFragment.java:1271 的「pause 等待期提前 fork」；看到 top-activity 则是走 ActivityTaskSupervisor.java:1065 的正式起进程。不用读代码就能判断预热有没有生效。

产出：一句归因，如「慢在 am_proc_bound→on_create_called，属 Application 初始化而不是等 pause」。锚点：wm/ActivityStarter.java:1187（记录创建）、am/ProcessList.java:2599（fork 日志点）

为什么这题值得做：它把「冷启动优化」从一句口号变成四选一；选错方向，改代码就是白改。

题 3｜拿到一份 atrace / 一段堆栈，怎么判断这次是冷启动还是热启动，realStart 在哪一段？

触发：抓一份带 wm 与 am 类别的 trace（或直接用 events buffer 里的 am_proc_start 替代）：

adb shell atrace -t 5 wm am -a 包名 > t.txt
# 或
adb shell logcat -b events -v threadtime -d | grep -E "am_proc_start|wm_on_create_called"

判据：看有没有「新进程诞生」这一段，以及 realStart 相对它的位置：

形态结论
有 zygote fork / am_proc_start，且 realStart 出现在 attach 之后（跨进程的另一段）冷启动，realStart 由 attach 回环补发（wm/RootWindowContainer.java:3611）
没有 fork，realStart 在 resume 流程内立刻发生热启动，走已有 binder 线程（wm/ActivityTaskSupervisor.java:1047）

产出：一句归因，如「冷启动，realStart 在 attach 段，不在 resume 段」。锚点：wm/RootWindowContainer.java:3611

为什么这题值得做：读 trace 时最容易犯的错，就是在 fork 之后继续顺着同一段栈往下找 realStart——它根本不在那儿。

🛠 L0 实践题（25 分钟，零编译）

冷启动 vs 热启动：差在哪个分支
# 触发
adb shell am force-stop com.example.framworkcontent
adb logcat -c
adb shell am start -W -n com.example.framworkcontent/.WindowDemoActivity   # 冷
adb shell am start -W -n com.example.framworkcontent/.WindowDemoActivity   # 热
adb shell logcat -d | grep -iE "Start proc|Displayed"

判据：冷启动那轮出现 Start proc ... com.example.framworkcontent，热启动那轮没有；两次 TotalTime 差一个数量级。

锚点：wm/TaskFragment.java:1271、wm/ActivityTaskSupervisor.java:1065。

产出：一句结论——「冷热差落在 TaskFragment 的进程分支：冷启动在 pause 等待期预热 fork，热启动走 attachedToProcess() 直发 resume」。
