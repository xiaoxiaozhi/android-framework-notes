窗口上屏
从 vsync 到 SurfaceFlinger 的一帧

一次 vsync 只负责放行；app 先同步 binder 进 WMS 拿到 frame 和 Surface，再 measure / layout / draw，最后用 finishDrawing 交卷。WMS 的 placement 是另一条事件驱动的循环，relayout 只是强制插队一次。

骨架解说 · 这段在讲什么

这条链回答一个问题：一次 vsync 之后，一个窗口怎样从“要更新”变成屏幕上的像素。分六段看：

①
vsync 只是放行：Choreographer 在 doFrame 里执行已排队的 CALLBACK_TRAVERSAL，它不决定窗口多大，只决定“这一帧什么时候开始”。
②
先判要不要 relayout：performTraversals 用 mFirst || windowShouldResize || viewVisibilityChanged || params != null || mForceNextWindowRelayout 分流；纯 invalidate 不跨进程。
③
relayout 是同步 binder：app 线程在 mWindowSession.relayout 阻塞，system_server 的 WMS 接手这次请求。
④
WMS 在 relayout 内强制 placement：先 createSurfaceControl 确保 SurfaceControl 存在（已有 controller 就复用），再 performSurfacePlacement(true) 算 frame（insets 作输入），fillClientWindowFrames 把结果回填到 out 参数，然后 relayout 同步返回 app。
⑤
app 拿到 frame+Surface 才画：measure → layout → draw；像素由 RenderThread（或软件绘制）产生。
⑥
画完要交卷：reportDrawFinished(seqId) → finishDrawing 回到 WMS；WMS 再 requestTraversal，把 transaction 交给 SF，在下一个 vsync 合成。

一句话：WMS 只负责“量窗口、摆位置、发画布”，像素是 app 画的；但这两段被一次同步 binder 绑在同一帧里。

基线：AOSP 13（android-13.0.0_r84，/home/book/aosp13）。16 行全部现地 grep 核实；本轮锁 13，不使用 12 的行号。未核实：软件绘制路径下 reportDrawFinished 是否走同一 seqId 对账（本轮只核硬件路径）。

02

决策点

五处“这里必须做一个选择”的位置，也是排障时最先该看的地方。

DECISION 01

这帧要不要跨进程

守卫 mFirst || windowShouldResize || viewVisibilityChanged || params != null || mForceNextWindowRelayout（ViewRootImpl.java:3069）——不满足就只 measure/layout/draw，不碰 WMS。

DECISION 02

relayout 内要不要立刻算几何

performSurfacePlacement(true /* force */)（WindowManagerService.java:2495）——客户端马上要 out 值，不能等异步 placement；这一行是“relayout 才能返回 frame”的关键。

DECISION 03

画布什么时候新建

createSurfaceControl(...)（WindowManagerService.java:2481 → :2717）——mSurfaceController == null 才新建，否则直接复用；尺寸变化不在这个分支重建。

DECISION 04

什么时候算“画完”

reportDrawFinished(seqId)（ViewRootImpl.java:4379）——要等 RenderThread 的 frame complete 回调合并 transaction，不是一个 performDraw 返回就算完。

DECISION 05

WMS 什么时候交给 SF

finishDrawingWindow 里 requestTraversal()（WindowManagerService.java:2778）——不是立刻 commit，而是排一次 placement，和其他窗口变化一起提交。

CONTEXT

一句话记住这条链

vsync 是节拍器，不是开工命令；relayout 是 app 帧里的同步插曲，performSurfacePlacement 才是 WMS 自己的循环。

白话对照

读不懂代码时先看这一列。

代码白话
vsync屏幕的鼓点；告诉 app “下一帧可以开始了”，但不规定这一帧要做什么。
Choreographerapp 主线程的节拍器：把 input / animation / traversal / commit 排进同一个 vsync。
performTraversals一帧的总调度：先决定要不要 relayout，再 measure / layout / draw。
relayoutWindow向 WMS 要“窗口多大、放哪、画布在哪”；同步阻塞，拿到才继续。
SurfaceControlWMS 发给 app 的画布句柄；app 往它对应的 buffer 里画。
performSurfacePlacementWMS 的布局/摆位循环：算 frame、层级、动画，最后生成 transaction。
finishDrawingapp 交卷：告诉 WMS “这一帧画完了”，并带上 buffer 的 transaction。
transaction一组 Surface 变更的原子提交；SF 在下一个 vsync 应用并合成。
✦ ✦ ✦ 三个误读点

① “vsync 来了 WMS 就开始画”——错，vsync 只放行 app 的 traversal，WMS 不订阅 vsync。② “relayoutWindow 每帧都走”——错，守卫在 ViewRootImpl.java:3069。③ “finishDrawing 在 performDraw 里同步调用”——不准确，硬件路径要等 RenderThread 的 frame complete 回调。
