从 DecorView 到 WMS.addWindow

骨架解说 · 这段在讲什么

Activity 在 onResume 里把 DecorView 交给 WindowManager，最终变成 system_server 里一个被 WMS 认识的窗口。分五段看：

①
app 主线程：ActivityThread 拿到 PhoneWindow 和 DecorView，把类型固定成 TYPE_BASE_APPLICATION，然后调用 wm.addView。
②
仍在本进程：WindowManagerImpl.applyTokens 只看 mDefaultToken / mWindowContextToken（Activity 路径两者皆空，什么也不补）；真正的 Activity token 是紧接着 WindowManagerGlobal.addView 调 parentWindow.adjustLayoutParamsForSubWindow 时，由 Window.java:916 从 mAppToken 写进去的。WindowManagerGlobal 再为这个 View 建 ViewRootImpl，并把 View / Root / Params 记进三张平行表。
③
跨进程：ViewRootImpl.setView 把 mAdded 置 true、先排一次 traversal，再同步调用 mWindowSession.addToDisplayAsUser，binder 进 Session，Session 原样转给 WMS。
④
system_server：WMS.addWindow 先在锁外查权限，进锁后查 display、查重复、按 token 找归属（Activity 的 token 就是 ActivityRecord），再 new WindowState 并 mWindowMap.put 落库。
⑤
落库之后：下一次 performTraversals 调 relayout，WMS 算尺寸 / insets 并返回 Surface，窗口才真正有内容。

一句话：前四步决定「窗口存不存在」，最后一步决定「窗口长什么样」。

基线：AOSP 13（android-13.0.0_r84，/home/book/aosp13）。18 行全部现地 grep 核实。未核实：TYPE_APPLICATION_STARTING 启动窗口与本次 addView 的先后（走 ActivityRecord.attachStartingWindow，另一条支线）。

02

决策点

五处“这里必须做一个选择”的位置，也是排障时最先该看的地方。

DECISION 01

这是不是“主窗口”

l.type = TYPE_BASE_APPLICATION（ActivityThread.java:4842）——同一棵 DecorView，类型决定后面走应用 token 分支还是系统窗口分支。

DECISION 02

token 谁填的

Activity 的 token 不是这里填的：WindowManagerGlobal.addView 先调 parentWindow.adjustLayoutParamsForSubWindow（WindowManagerGlobal.java:323），后者写 wp.token = mAppToken（Window.java:916）。mDefaultToken 只在没有父窗口时生效，例如 AccessibilityService 的 overlay（AccessibilityService.java:2555）。

DECISION 03

权限门禁在哪一层

checkAddPermission 在 synchronized (mGlobalLock) 之前跑（WindowManagerService.java:1486 → PhoneWindowManager.java:2595），避免持锁做权限检查。

DECISION 04

同一个 client 能不能加两次

app 侧 findViewLocked 抛 IllegalStateException（WindowManagerGlobal.java:353-360），WMS 侧还有 mWindowMap.containsKey → ADD_DUPLICATE_ADD（WindowManagerService.java:1518）。

DECISION 05

失败为什么是 int 不是异常

addWindow 全程 return ADD_*（WindowManagerService.java:1477），由 setView 包成 RuntimeException("Adding window failed")（ViewRootImpl.java:1303）。

CONTEXT

一句话记住这条链

加窗发生在 onResume 返回之前；relayout 只算尺寸和 Surface。所以“窗口没出来”和“窗口没画出来”是两类问题。

03

三个实践问题

每题只给现象。答案必须落到一条能跑的命令和它的预期输出——答不出命令，就是没答对。

  1. 现象：启动必崩 Unable to add window。异常后半句可能是 token … is exiting、… has already been added、permission denied for window type。这三种各自对应 WMS 的哪个返回码？给出定位命令（logcat 抓哪一行、dumpsys 查哪个段），并指出哪一种根本到不了 WMS、先在 app 侧就被拦。
    锚点 ViewRootImpl.java:1338-1385 · WindowManagerGlobal.java:110-115 · WindowManagerService.java:1520 / :1542 / :1614
  2. 现象：Activity 已 resume，dumpsys window windows 里也能查到它，但屏幕是白的。分清两条路：relayout 没跑到，还是 Surface 有了却没画。各给一条命令和预期输出，并说明 addWindow 成功之后、首帧内容之前还差哪一步。
    锚点 ViewRootImpl.java:2806 · :3106 · :8204 / :8275
  3. 现象：改配置触发 relaunch 后崩 IllegalStateException: View … has already been added。用 mPreserveWindow 分支解释：正常 relaunch 为什么走不到第二次 addView，什么情况会让这层保护失效；再给一条确认“是不是这条路径”的命令。
    锚点 ActivityThread.java:4844-4859 · WindowManagerGlobal.java:353-360

三题对应三个分叉：加窗失败（还没进 mWindowMap）、加窗成功但没内容（进了但没 relayout）、加窗走了两次（复用窗口但没重挂回调）。排障先判在哪一段，再谈细节。

04

骨架阅读法

读完这五行，骨架才从“方法名清单”变成一条能讲的故事。

一句话定位
把 Activity 的 DecorView 注册成 WMS 认识的窗口；终点是 mWindowMap 里多一个 WindowState。
三个接力边界
同线程直调：ActivityThread.java:4859 → ViewRootImpl.java:1160（全程 app 主线程）；跨进程：ViewRootImpl.java:1281 → Session.java:209（同步等返回）；持锁区：WindowManagerService.java:1497 的 mGlobalLock 一直到 :1803。
最小验证命令
cd /home/book/aosp13 && grep -n "wm.addView(decor, l)" frameworks/base/core/java/android/app/ActivityThread.java && grep -n "mWindowMap.put(client.asBinder(), win)" frameworks/base/services/core/java/com/android/server/wm/WindowManagerService.java —— 应得 4859 与 1790。
最贵的一行
WindowManagerService.java:1790 mWindowMap.put(...)：在此之前系统里没有这个窗口，之后才有布局、合成、输入。
可追问的名字
mDefaultToken（户口谁给的）、ADD_DUPLICATE_ADD（什么情况撞车）、mRelayoutSeq（第一次 relayout 怎么和 addWindow 对上）。

WindowManagerImpl.java:146-168 — applyTokens 只补默认 / 上下文 token 
public void addView(View view, ViewGroup.LayoutParams params) {
    applyTokens(params);                                   // 只补默认 / 上下文 token
    mGlobal.addView(view, params, mContext.getDisplayNoVerify(),
            mParentWindow, mContext.getUserId());             // 再交给单例
}

private void applyTokens(ViewGroup.LayoutParams params) {
    final WindowManager.LayoutParams wparams = (WindowManager.LayoutParams) params;
    assertWindowContextTypeMatches(wparams.type);
    if (mDefaultToken != null && mParentWindow == null && wparams.token == null) {
        wparams.token = mDefaultToken;                        // 仅无父窗口的客户端命中（如 a11y overlay）
    }
    wparams.mWindowContextToken = mWindowContextToken;        // 指向 WindowContext，Activity 为空
}
WindowManagerService.java:1477-1790 — 判定顺序：先便宜后昂贵 
public int addWindow(Session session, IWindow client, LayoutParams attrs, ...) {
    int res = mPolicy.checkAddPermission(attrs.type, ...);   // :1486 锁外，可能要查 AppOps
    if (res != ADD_OKAY) return res;
    synchronized (mGlobalLock) {                               // :1497 持锁区开始
        DisplayContent displayContent = getDisplayContentOrCreate(displayId, attrs.token);
        if (mWindowMap.containsKey(client.asBinder())) {         // :1518 重复加窗
            return WindowManagerGlobal.ADD_DUPLICATE_ADD;
        }
        WindowToken token = displayContent.getWindowToken(attrs.token); // :1570 查表，不新建
        if (token == null) { ...new WindowToken.Builder(...)... }   // :1581-1607 Activity 走不到
        else if (rootType 是应用窗口) {
            activity = token.asActivityRecord();                  // :1610 就是 ActivityRecord 本人
            if (activity == null) return ADD_NOT_APP_TOKEN;       // :1614
        }
        final WindowState win = new WindowState(...);              // :1683 到这里才建对象
        win.attach();                                            // :1789
        mWindowMap.put(client.asBinder(), win);                    // :1790 ★ 真源
        win.mToken.addWindow(win);                              // :1802 挂成 token 的孩子
        displayPolicy.addWindowLw(win, attrs);                    // :1803
    }
    return res;
}

TASK 01

加窗是同步的，不是 relayout 时才加

触发

Activity 主窗口的 token 是 Activity 给的

06

白话对照

读不懂代码时先看这一列。

代码白话
DecorViewActivity 的整块画布（标题栏 + 内容都挂在它下面）
ViewRootImplapp 进程里这根“窗口的管子”：measure / layout / draw，同时负责跟 WMS 通讯
IWindowSession / Sessionapp 与 WMS 的专属客服；Session 是 system_server 里的接线员
IWindow / mWindowMap key窗口在 WMS 的身份证号（binder 引用）
WindowToken一组窗口的“户口”，决定属于哪个 Activity / 系统组件
WindowStateWMS 侧的窗口对象：尺寸、可见性、层级、输入通道都在它身上
✦ ✦ ✦ 三个误读点

① “addView 只是登记，真正加窗在 relayout”——错，setView 同步加。② “Activity 主窗口的 token 是 applyTokens 补的”——错，是 Window.java:916 从 mAppToken 写的；mDefaultToken 只服务无父窗口的 overlay。③ “addWindow 失败会抛异常”——它只返回码，异常是 setView 按码转成 BadTokenException 的。
