1一块屏怎么变成多个 Task

自由窗口不是“画一个框”，而是让同一块 display 上出现多个可独立配置的 Task。层级是 Display → TaskDisplayArea → root Task（容器） → leaf Task（窗口）→ Activity；全屏时 root 与 leaf 常重合：dumpsys activity activities 会并列显示 root 和 leaf（如 #1 home 下面挂 #96 launcher），dumpsys window containers 才会缩进成树；同一个 Task 在这两份输出里都出现，是同一个节点，不是两个。一个 app 可以有多 task，多个 app 也可以共用一个 task。

三条不变量（破了就出 bug）

① 窗口至少留一条可点的边

窗口可以挂到屏幕外，但不能整个消失。落地时 computeFreeformBounds() 先 intersect(stableBounds)，再用 MINIMUM_VISIBLE_WIDTH/HEIGHT_IN_DP 把窗口拉回可视区。
Task.java:2128–2160 · 破坏方式：am task resize 推到屏外

② config 与 bounds 必须一致

旋转、改密度、换显示区之后，Task 的 override bounds 必须重算；否则内容按旧尺寸排版。重算发生在 resolveLeafTaskOnlyOverrideConfigs()，不是 launch 时。
Task.java:2043 → :2066 · 破坏方式：旋转后看 bounds 与 app frame 是否同步

③ 改全局设置不重排已有 Task

settings put 只改能力 flag 和显示默认值（WindowManagerService.java:973/:976），不会把已经开着的窗口逐个搬一遍；已有 Task 继续按自己的 override bounds 活着，新启动才用新能力。
破坏方式：开着小窗改设置，看旧窗口是否原地不动

四个失败模式（“小窗没生效 / 点了没反应”先查这四个）

F1能力没开

01完整命令：--windowingMode 5 到底敲什么

最小可用的一条，直接复制就能跑；5 是整数常量，不是字符串 freeform。

bash · 最小命令
adb shell am start --windowingMode 5 -n com.android.settings/.Settings

解析--windowingMode 5

按整数读入 mWindowingMode（ActivityManagerShellCommand.java:429）。传字符串会 parseInt 失败。

常量5 = FREEFORM

WindowConfiguration.WINDOWING_MODE_FREEFORM = 5（:109）；随后写入 ActivityOptions.setLaunchWindowingMode(5)（:563）。

组件-n 包名/.Activity

换成自己的 demo 就是 -n com.example.myapplication/.MainActivity。

要“起之前先清干净 + 起完立刻验证”，用这一组：

bash · 完整可复现
# 0) 打开 freeform 能力（原值可能是 null）
adb shell settings put global enable_freeform_support 1

# 1) 杀掉旧任务，避免命中已有 task 而不重算模式
adb shell am force-stop com.android.settings

# 2) 以 freeform 启动，并等待启动结果
adb shell am start -W --windowingMode 5 -n com.android.settings/.Settings

# 3) 验证：应出现 mode=freeform 与 mBounds
adb shell dumpsys activity activities | grep -A1 "mode=freeform"
为什么要 force-stop：目标 Activity 已在前台时，am start 可能只把已有任务带到前台，不会重新走 launch 参数解析；不杀旧任务，--windowingMode 5 有时看不出效果。

带 -W 和不带，差在哪

先说结论：-W 不影响 freeform 的任何决策。它只加了一个布尔 mWaitOption（ActivityManagerShellCommand.java:389），改用另一条 Binder 入口，并让 shell 进程等首帧画完才返回。模式、bounds、root task 的代码路径完全一样。
维度带 -W不带 -W
shell 分支:599 if (mWaitOption) → :600:604 else → :605
Binder 入口ATMS.startActivityAndWait:1529ATMS.startActivityAsUser:1238
返回值WaitResult（含 Status / LaunchState / TotalTime / WaitTime）int（START_SUCCESS 等），只用来打错误信息

进程退出码都是 0（runStartActivity 末尾 :700 恒 return 0，只有参数错误才 return 1）

关键-W 等的是「首帧」，不是「代码跑完」

ActivityStarter:735 把结果塞进 waitResult 后调 waitResultIfNeeded（:825）；真正等的是 ATS.waitActivityVisibleOrLaunched 里的 mGlobalLock.wait() 循环。放行它的有四处：ActivityRecord.onWindowsDrawn（:6682，最常见）、reportFullyDrawnLocked（:6605）、idle 超时（ATS:1361）、记录被回收（cleanupActivity:606）。
所以 -W 返回时窗口已经存在、bounds 已经算好——这也是本文脚本都用 -W 的原因。

代价它会占住一个 system_server 线程

等待发生在处理这次 Binder 事务的 system_server 线程上（startActivityAndWait 是同步 AIDL）。上限是 IDLE_TIMEOUT = 10s × ro.hw_timeout_multiplier（ATS:174 / :2069），超时会打 Status: timeout。
这条 ActivityRecord.java:6605/:6682 与超时上限是纯代码核对，未在设备上构造“永不绘制”的场景验证。

两个实践坑：① 不带 -W 时 am start ... | grep 抓不到报错（走 stderr），要 2>&1；② 别用 echo $? 判断启动成功——两种写法都返回 0，判断得看 -W 打出的 Status: ok。
bash · 用 -W 当同步屏障
# 有 -W：返回即可 dump，不用 sleep
adb shell am start -W --windowingMode 5 -n com.android.settings/.Settings | tee /tmp/r.txt
grep -q "Status: ok" /tmp/r.txt && adb shell dumpsys activity activities | grep -A1 "mode=freeform"

# 无 -W：要自己等，而且报错在 stderr
adb shell am start --windowingMode 5 -n com.android.settings/.Settings 2>&1
sleep 0.5
adb shell dumpsys activity activities | grep -A1 "mode=freeform"
什么时候该去掉 -W：批量连起多个 Activity、或要测「启动后立刻再点一次」的竞态时——-W 会把每次启动串行化成 1 个往返，脚本会慢很多，也测不出并发时序。

03白话对照：这三个起点在说什么

记号：→ 这行产出什么、往哪流；← 这行的结果被谁决定；缩进 = 调用/归属层级；├─ └─ = 同一处的两个分支，不是先后；行号 = 打开文件跳过去的位置，不是时间轴。
  1. 启动有三个起点，先分清你在哪条：① am start ... -W；② am start 不带 -W；③ 最近任务里点「自由窗口」。
  2. ① 和 ② 都是把 5 塞进 ActivityOptions 走一次全新启动。区别只在 Binder 入口：-W 进 ATMS.startActivityAndWait(:1529)，不带进 ATMS.startActivityAsUser(:1238)；两者都落到 obtainStarter(...).execute()。
  3. ③ 走的是「把一个已存在的 task 再抬起来」，入口是 ATMS.startActivityFromRecents(:1786)；(Launcher 侧 makeLaunchOptions 顺手给了 mode=5 和一个 decor/2 的矩形)。
  4. ③ 里 task 还活着时，源码自己写明「不走 executeRequest 路径」(:2617)，直接 moveTaskToFrontLocked → findTaskToMoveToFront。所以 computeLaunchParams / TaskLaunchParamsModifier 这条链在 ③ 上根本不执行。
  5. 三条真正都过的是 TDA.getOrCreateRootTask(:942)，但 mode 来源不同：①② 用 launchParams.mWindowingMode(:948)，③ 用 options.getLaunchWindowingMode()(:952，因为 launchParams 为 null)。
  6. 开机时 system_server 读一次 feature 和 enable_freeform_support，算出内存 flag；三个起点都不会重跑它，只读它。
  7. 设置一改，WMS 的 SettingsObserver 重算并写回 ATMS 的 flag，再让 RootWindowContainer 重配显示（不重启）。
  8. ①② 上「真正放行」发生在 launch 解析：设备有能力 + 这次显式要 freeform，两个都满足才保留 5（canApplyFreeformWindowPolicy:565）。
  9. ③ 的放行是两个开关：Launcher 侧 supportsFreeformMultiWindow 决定菜单项出不出现；服务端 canUseActivityOptionsLaunchBounds:1517 依赖 mSupportsFreeformWindowManagement 决定 bounds 采不采纳。开关一关，表现是「点了没反应」而不是报错。
  10. bounds 的来源也不同：①② 由 modifier 给初值（getTaskBounds:728 → 应用配置时 computeFreeformBounds:2128 钳制）；③ 由 Launcher 客户端算好（decorW/2 × decorH/2，+50 偏移，:231–234），服务端 setBounds:1449 直接采用。
  11. 之后才汇到同一处：新建/复用 freeform root task（createRootTask:987）→ ShellTaskOrganizer.taskInfoToTaskListenerType(:801) 按 mode=5 选 FreeformTaskListener 装 caption。

一块显示区，决定“这屏里的任务默认什么窗口模式”。

Rectbounds vs frame

bounds 是 launch 阶段要求的大小/位置；frame 是 WMS 最终摆出来的，通常相等。

稳定区stable 区

扣掉状态栏/导航栏后的安全区，computeFreeformBounds 拿它做交集。

回调listener

WMShell 按窗口模式注册的回调，freeform 的 listener 管标题栏。

UIcaption / decoration

标题栏和边框，不在 app 里画，归 WMShell。

执行WMS 的角色

WMS 只执行 launch 的结果，不改写 freeform 的决策。

四个最容易误读的点

① :565 放行 ≠ 一定能 freeform，:286 还有一次“不可缩放 app”的策略分支。
② “手机能起自由窗口” ≠ “手机桌面是 freeform”：前者靠显式 5，后者要 mIsPc || forceDesktopMode()。
③ bounds 不是 WMS 布局算的；WMS 只执行，钳制在 Task.java:2128。而且 recents 入口的初始 bounds 是 Launcher 算的，不是系统算的。
④ 最近任务这条，只要 task 还活着就绕过整段 launch 参数解析：别拿 TaskLaunchParamsModifier 去解释「点自由窗口为什么是这个大小/位置」，那里没有它的代码。（task 已被回收 / 需要验凭据时，会退回慢路径重新走 launch 解析。）

先问这个这次从哪个入口进来

am start（带/不带 -W）走 launch 解析；最近任务走「抬已存在 task」，task 仍活着时绕过整段 TaskLaunchParamsModifier。先定入口，再谈后面几条。

feature 与开发者开关二选一；开机时 ATMS 算一次，运行时改设置由 WMS 观察者写回 flag。

Q1启动没生效，断在哪

Q2改完设置为什么没生效

settings put global enable_freeform_support 1 后立刻 am start 仍落回全屏，隔 0.3s 再试成功。指出哪一步是异步的，并设计一个不改代码的验证。

Q3bounds 回弹是谁干的

am task resize 把 freeform 推到屏幕外，bounds 被改回来。判断是 getTaskBounds 还是 computeFreeformBounds，给出改前 / 改后 bounds 与依据行。

Q4点「自由窗口」没反应

最近任务里长按/点击自由窗口，画面不动、也没报错。先分清是菜单项不存在（supportsFreeformMultiWindow 为 false）还是点了但 bounds 没被采纳（canUseActivityOptionsLaunchBounds 为 false）。给两条区分命令，并说明为什么这条链里 TaskLaunchParamsModifier 完全不该被怀疑。

06骨架阅读法

一句话定位
自由窗口不是 WMS 布局特性，而是 launch 阶段定 windowingMode + 初始 bounds，Shell 再加 caption 和转场。注意“launch 阶段”对最近任务入口不适用——那条只做 reparent + setBounds。
三个接力边界
① ATMS → TaskLaunchParamsModifier（仅 adb 线，:109）；② recents 线走 ActivityTaskSupervisor.findTaskToMoveToFront（:1427），不经 modifier；③ 跨进程 WMShell 走 TaskOrganizer（ShellTaskOrganizer.java:801）装 caption。三条都在 mGlobalLock 内完成。
最小验证
adb shell dumpsys activity activities | grep -A1 "mode=freeform"
recents 线额外看一眼：dumpsys activity recents | grep -i freeform（taskId 不变、windowingMode 变 5 才算走通）
最贵的一行
TaskLaunchParamsModifier.java:565 —— “为什么没进 freeform / 为什么被最大化”九成落这里。但只对 am start 入口成立；recents 入口根本没有这行代码。
可追问的名字
getTaskBounds、computeFreeformBounds、FreeformTaskListener。
