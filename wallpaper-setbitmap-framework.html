先记住一句话：setBitmap 本质是一个「文件写入协议」。Bitmap 不跨 Binder，App 把 PNG 写进 system_server 给的文件描述符；WPMS 监听到文件写完，裁剪成 wallpaper，再重启 ImageWallpaper 引擎；SystemUI 读图、画到 wallpaper surface，最后由 SurfaceFlinger 合成到 App 窗口下面。

一、全景：四个进程，五次交接

先把角色摆清楚。很多人以为「设壁纸」是 App 画了一张图交给系统，其实 App 只负责把原图编码成 PNG 写进文件；真正决定壁纸怎么显示的是 system_server 和 SystemUI。

关键认知 第三方 App 没有 wallpaper surface，也不直接和 SurfaceFlinger 打交道。它只把像素写进文件；绘制者是 SystemUI 的 ImageWallpaper。

二、五个阶段，逐步拆开

1

App 侧：从 API 到「写文件」

setBitmap(bitmap) 先走到三参数重载，默认 which = FLAG_SYSTEM | FLAG_LOCK；再走到带 userId 的五参数实现。它做三件事：校验裁剪矩形、通过 Binder 调 IWallpaperManager.setWallpaper()、拿到可写 FD 后用 Bitmap.compress(PNG, 90, fd) 把图写进去。

2

system_server：只发 FD，不收 Bitmap

WPMS.setWallpaper() 做用户校验、SET_WALLPAPER 权限校验、设备策略校验；然后 updateWallpaperBitmapLocked() 打开 /data/system/users/<uid>/wallpaper_orig，把写端 FD 返回给 App，并记录 imageWallpaperPending、whichPending 和完成回调。

3

文件写完：FileObserver 接手

App 关闭 FD 后，WPMS 里的 WallpaperObserver 收到 CLOSE_WRITE；它调用 generateCrop() 解码 wallpaper_orig，按屏幕尺寸/裁剪提示生成 wallpaper，恢复 SELinux 标签并保存设置。系统壁纸变化时，再触发 bindWallpaperComponentLocked(mImageWallpaper, force=true, ...)。

WallpaperManagerService.java:252、314、328
4

重新绑定：WMS 建 token，Engine 建窗口

WallpaperConnection.connectLocked() 先让 WMS 创建 TYPE_WALLPAPER 的 WallpaperWindowToken，再通过 IWallpaperService.attach() 把 token 交给 SystemUI。SystemUI 创建 ImageWallpaper.CanvasEngine，Engine.attach() 调 Session.addToDisplay() 添加 TYPE_WALLPAPER 窗口；relayout() 返回 SurfaceControl。

WallpaperManagerService.java:1164、1170、1174；WallpaperService.java:1174、1435、1195；WMS:2807、2829
5

SystemUI 绘制：首帧完成，App 才返回

            FLAG_SYSTEM | FLAG_LOCK);

// ③ 五参数实现：Binder 只传参数；返回的是写端 FD
public int setBitmap(..., int which, int userId)
        throws IOException {                                // :1744
    validateRect(visibleCropHint);
    final Bundle result = new Bundle();
    final WallpaperSetCompletion completion = new WallpaperSetCompletion();
    try {
        ParcelFileDescriptor fd = sGlobals.mService.setWallpaper(null,
                mContext.getOpPackageName(), visibleCropHint, allowBackup,
                result, which, completion, userId);           // ★ 不传 Bitmap
        if (fd != null) {
            FileOutputStream fos = new ParcelFileDescriptor.AutoCloseOutputStream(fd);
            fullImage.compress(Bitmap.CompressFormat.PNG, 90, fos); // ★ PNG 写入管道
            fos.close();
            completion.waitForCompletion();                    // ★ 等首帧，不是等写完
        }
    } catch (RemoteException e) { throw e.rethrowFromSystemServer(); }
    return result.getInt(EXTRA_NEW_WALLPAPER_ID, 0);
}
注意 压缩发生在调用线程，PNG 数据直接写进 Binder 返回的 ParcelFileDescriptor。所以 setBitmap 既可能有 CPU 开销（压缩），也可能有 I/O 等待（写文件）。

2. system_server：先发 FD，再等文件写完

frameworks/base/services/core/java/com/android/server/wallpaper/WallpaperManagerService.java — setWallpaper
public ParcelFileDescriptor setWallpaper(String name, String callingPackage,
        Rect cropHint, boolean allowBackup, Bundle extras, int which,
        IWallpaperManagerCallback completion, int userId) {       // :2880
    userId = ActivityManager.handleIncomingUser(...);
    checkPermission(android.Manifest.permission.SET_WALLPAPER);

    if ((which & (FLAG_LOCK | FLAG_SYSTEM)) == 0) {
        throw new IllegalArgumentException(...);
    }
    if (!isWallpaperSupported(callingPackage)
            || !isSetWallpaperAllowed(callingPackage)) {
        return null;                                            // 设备策略可能直接拒绝
    }

    // which=SYSTEM 且当前没有独立锁屏壁纸时，先把系统壁纸迁移成锁屏专用
    if (which == FLAG_SYSTEM && mLockWallpaperMap.get(userId) == null) {
        migrateSystemToLockWallpaperLocked(userId);
    }

    wallpaper = getWallpaperSafeLocked(userId, which);           // :3601
    final long ident = Binder.clearCallingIdentity();
    try {
        ParcelFileDescriptor pfd =
                updateWallpaperBitmapLocked(name, wallpaper, extras); // :2977
        if (pfd != null) {
            wallpaper.imageWallpaperPending = true;
            wallpaper.whichPending = which;
            wallpaper.setComplete = completion;                  // 文件写完后的回调
            wallpaper.fromForegroundApp = fromForegroundApp;
        }
        return pfd;
    } finally { Binder.restoreCallingIdentity(ident); }
}
文件名对应关系：wallpaper_orig 是 App 写入的原图；wallpaper 是 WPMS 生成的裁剪图；锁屏对应 wallpaper_lock_orig / wallpaper_lock。

3. FileObserver：真正的「写入完成」信号

WallpaperManagerService.java — WallpaperObserver.onEvent
public void onEvent(int event, String path) {                       // :252
    final boolean moved = (event == MOVED_TO);
    final boolean written = (event == CLOSE_WRITE || moved);     // ★ App close(fd) 后触发
    final File changedFile = new File(mWallpaperDir, path);

    final boolean sysWallpaperChanged = mWallpaperFile.equals(changedFile);
    final boolean lockWallpaperChanged = mWallpaperLockFile.equals(changedFile);

    if (written) {
        SELinux.restorecon(changedFile);
        generateCrop(wallpaper);                                 // :314 原图 → 裁剪图
        wallpaper.imageWallpaperPending = false;
        if (sysWallpaperChanged) {
            IRemoteCallback.Stub callback = new IRemoteCallback.Stub() {
                public void sendResult(Bundle data) {
                    notifyWallpaperChanged(wallpaper);               // 首帧完成后才回调
                }
            };
            // 强制重绑，确保 ImageWallpaper 用新文件重新创建引擎
            bindWallpaperComponentLocked(mImageWallpaper, true,
                    false, wallpaper, callback);                   // :328
        }
        if (lockWallpaperChanged
                || (wallpaper.whichPending & FLAG_LOCK) != 0) {
            // 处理锁屏专用壁纸的清理 / Keyguard 通知
        }
        saveSettingsLocked(wallpaper.userId);
    }
}
为什么用 FileObserver App 通过 FD 写文件，Binder 调用早就返回了；服务端要知道「写完」只能靠文件系统事件。这也解释了为什么写入路径不是一次同步 Binder 调用。

6. 完成回调：为什么 setBitmap 能等到首帧

WallpaperManagerService.java — WallpaperConnection.engineShown
public void engineShown(IWallpaperEngine engine) {                 // :1557
    synchronized (mLock) {
        if (mReply != null) {
            mReply.sendResult(null);                              // :1564 唤醒 App

App 侧的 WallpaperSetCompletion 是一个 IWallpaperManagerCallback.Stub，内部用 CountDownLatch 阻塞；engineShown 最终触发它的 onWallpaperChanged()。所以正常情况下，setBitmap 返回时新壁纸已经画出了第一帧；如果引擎迟迟不画，reportEngineShown 还有 5 秒延迟兜底。

五、最容易误解的五件事

误解 1 「Bitmap 通过 Binder 传给 system_server」
不对。Binder 只传参数和一个写端 FD；Bitmap 由 App 编码成 PNG 后写进文件。大图不会触发 Binder 事务大小限制。
误解 2 「文件写完 setBitmap 就返回」
不对。文件写完只触发 WPMS 裁剪和重绑；App 还要等 engineShown，也就是新壁纸首帧画完。
误解 3 「setBitmap 只改系统壁纸」
默认 which = FLAG_SYSTEM | FLAG_LOCK。如果之前有独立锁屏壁纸，这条路径会清掉锁屏专用记录，让锁屏回退到系统图；只改锁屏才会走 wallpaper_lock_orig 分支。
误解 4 「App 自己把图画到屏幕上」
不对。App 没有 wallpaper surface。真正绘制的是 SystemUI 的 ImageWallpaper，它通过 WallpaperManager 读裁剪图。
误解 5 「设置静态图不会影响动态壁纸」
会。设置成功后 WPMS 会把壁纸组件重绑到 mImageWallpaper，原来的 live wallpaper 服务会被解绑，静态图接管。

六、锁屏、动态壁纸与多用户分支

主线是「系统壁纸」，但 which 一改，后面的路径就分叉。把这张表记住，读源码时就不会迷路。

which写入文件是否重绑 ImageWallpaper锁屏结果
FLAG_SYSTEMwallpaper_orig → wallpaper是若原本没有独立锁屏图，会把旧系统图迁移成锁屏专用
FLAG_LOCKwallpaper_lock_orig → wallpaper_lock否只通知 Keyguard，系统壁纸不变
SYSTEM | LOCK（默认）wallpaper_orig → wallpaper是清掉独立锁屏记录，锁屏回退到系统图
展开：为什么默认路径要「清掉独立锁屏图」？
默认语义是「这张图同时作为系统壁纸和锁屏壁纸」。如果设备上还留着旧的 mLockWallpaperMap，锁屏会继续显示旧图，和「同时设置」矛盾。所以系统在 whichPending & FLAG_LOCK 成立、但本次并没有写锁屏文件时，会移除锁屏专用记录，让锁屏回退到系统壁纸。
展开：动态壁纸是怎么被替换掉的？
setBitmap 只写静态图文件，不会去调用 live wallpaper 的绘制接口。写完后 WPMS 执行 bindWallpaperComponentLocked(mImageWallpaper, force=true, ...)：先 detachWallpaperLocked() 解绑旧的 WallpaperConnection，再绑定 com.android.systemui/...ImageWallpaper。动态壁纸服务失去连接，静态图引擎接管。
展开：多用户 / 多屏时，文件和服务怎么分？
文件按用户分目录：/data/system/users/<userId>/wallpaper_orig。显示侧由 WallpaperConnection.DisplayConnector 按 displayId 管理：connectLocked() 为每个显示创建 token、attach 一个 engine。一个壁纸服务连接可以对应多个显示引擎，所以平板/折叠屏/外接屏要分别看 DisplayConnector。
权限提醒 SET_WALLPAPER 是 normal 级权限，普通 App 通常能拿到；但 isWallpaperSupported() 和 isSetWallpaperAllowed() 还会受设备管理员、用户限制影响，策略禁止时服务端直接返回 null。

自测三问（读完再回答）

1. 为什么 setBitmap 传大图不会触发 Binder 的 TransactionTooLargeException？
因为 Bitmap 不进入 Binder 事务；Binder 只传参数和 FD，像素数据由 App 通过文件描述符写入。

2. 为什么换壁纸后 ImageWallpaper 的引擎像是「重新创建」了？
WPMS 用 force=true 重绑 mImageWallpaper，旧连接被 detach/unbind，新连接 attach 后创建新的 Engine 和 surface。

3. 为什么只改锁屏时不需要重绑系统壁纸？
FileObserver 只在 sysWallpaperChanged 为 true 时调用 bindWallpaperComponentLocked()；锁屏分支只通知 Keyguard 并完成回调。
