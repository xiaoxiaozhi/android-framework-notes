一、从一个日常场景说起

点亮手机屏幕，你看到的不是一个画面，而是许多层"叠"出来的：最底下是壁纸，壁纸上盖着正在看的 App，App 之上可能浮着输入法键盘，键盘之上横着状态栏，忽然来电，来电界面又盖过一切。这些窗口来自不同的进程、不同的 App，甚至系统与三方混在一起，但无论你怎样切换、拖动、分屏，覆盖关系从来不乱——键盘永远不会把状态栏盖住，来电界面永远压住所有 App。

系统靠什么记住"谁盖谁"？如果只是给每个窗口发一个编号，大的在上小的在下，那一维的编号就够了。但真实需求远不止于此：系统要能一次性移动一整层（比如进入单手模式，把除导航栏以外的所有窗口整体下沉、缩小），要能把整片区域调暗或放大（无障碍的放大镜要罩住几乎所有窗口）。这时"编号"就不够用了——你需要一棵树。

本节核心
覆盖关系不是靠单个数值硬排的，而是靠一棵窗口树的结构来决定的。数值只是树内部的"细分规则"。

二、核心模型：DisplayArea 是一棵树

Android 12 把屏幕上所有的窗口容器组织成一棵以 DisplayContent 为根的树。树的中间节点叫 DisplayArea（显示区域），叶子节点是装着真实窗口的槽位——DisplayArea.Tokens 或 TaskDisplayArea。每个窗口最终都挂在某个叶子里，而"谁盖谁"就由树的先后顺序决定：同一父节点下，后加入的兄弟节点（在屏幕上）盖住先加入的。

DisplayContent（根，代表一块屏幕）
├── Dimmable "WindowedMagnification" ────────── 无障碍放大镜的"罩子"（Feature 区）
│   ├── Tokens "Leaf:0:1" ───────────────────── 壁纸
│   ├── Tokens "Leaf:2:2"
│   │   └── TaskDisplayArea "DefaultTaskDisplayArea" ── 所有 App 窗口的家
│   ├── Tokens "Leaf:3:14" ──────────────────── 弹窗、覆盖层等
│   ├── Tokens "Leaf:15:16" ─────────────────── 输入法
│   ├── Tokens "Leaf:17:22" ─────────────────── 状态栏一族
│   └── Tokens "Leaf:23:31" ─────────────────── 导航栏、截屏等
└── Tokens "Leaf:32:36" ─────────────────────── 无障碍覆盖、鼠标指针

读这棵树的规则只有三条：

  1. 纵向是包含：父节点是子节点的"辖区"，子节点永远画在父节点的范围里；父移动，整棵子树跟着移动。
  2. 横向是先后：同一父节点下，兄弟从左到右 = 从下到上叠放；谁排在后，谁盖在前面。
  3. 名字里的数字是窗口层号：Leaf:17:22 表示这个叶子负责 layer 17 到 22 的窗口——数字只是"辖区编号"，真正的盖住关系由树结构决定。
想一下：为什么不用一维的 z 值数组，非要用树？
因为一维数组只能回答"谁在谁上面"，无法表达"这一大群窗口属于同一个整体"。树能表达分组：把放大镜要罩住的几十层窗口放进一个子树，整个子树平移、缩放、调暗，只需要操作一个节点。这就是 Feature 存在的意义（第 5 节展开）。

三、认识树上的节点

树上的所有节点都继承自统一的基类 WindowContainer，它提供了挂孩子、遍历子树、移动子树等公共能力。往下各层分工如下：

类名在树上的角色一句话职责
WindowContainer<T>所有节点的基类提供树的通用操作：增删子节点、遍历、整体移动。
DisplayArea<T>中间容器屏幕上的一块"区域"，把窗口按区域分组，本身不装具体窗口。
DisplayContent树的根代表一块逻辑屏幕，整个窗口树由此长出。
RootDisplayArea根的基类DisplayContent 的父类，缓存了建树时的层号查找表。
DisplayArea.Dimmable可调暗的中间容器能被调暗的 DisplayArea，用于放大镜等需要"罩暗其他窗口"的 Feature。
DisplayArea.Tokens叶子（槽位）直接收纳 WindowToken（窗口容器），大部分窗口的最终落脚点。
TaskDisplayArea叶子（分区）App 窗口的专属区域，分屏时左右各一个，下面挂 Task、ActivityRecord。

注意两个易混点：TaskDisplayArea 只出现在应用层（layer 2），而 DisplayArea.Tokens 负责其余所有层；"Task 树"（Task → ActivityRecord → WindowState）挂在 TaskDisplayArea 下面，与系统窗口的树是两条分支。

四、谁盖谁：先定大类，再定同类

一个窗口最终画在哪里，分两步决定。

1
第一步：按窗口类型查出层号（layer），类型与层号的对应表由 WindowManagerPolicy.getWindowLayerFromTypeLw 定义：壁纸=1，应用=2，输入法=15，状态栏=17，导航栏=24，鼠标指针=35……共 36 层（0~35）。这个层号只是"大类编号"，不是最终顺序。
为什么：层号是系统与三方 App 共同遵守的"宪法"——三方 App 只能拿到 2（应用）和 12（悬浮窗）等少量层，永远摸不到状态栏的 17。先查层号，等于先把窗口归入正确的辖区。
2
第二步：用层号在树里找到叶子槽位，挂进去。同一层号的所有窗口进同一个叶子，它们之间再用"同类规则"排先后——应用层里由 Task 顺序决定，Token 里由加入顺序决定。树的先后已经把不同大类的关系定死，同类内部再用数值微调。
为什么：如果让 36 个层号直接做全局 z 值，系统窗口之间就无法表达"整体移动"。分成两步后，大类关系固化在树结构里，同类窗口内部的排序保持灵活，两头都兼顾。
想一下：应用层里同时有两个 App 窗口（分屏），它们在树上的位置是同一个叶子里的两个 Task。它们的层号都是 2，靠什么分先后？
靠 Task 在 TaskDisplayArea 里的顺序（最近交互的 Task 靠后、盖在上方）。层号只负责把它俩送进同一片区域，区域内的排序是 Task 管理器的职责。

五、两个前置概念：layer 与 Feature

layer（窗口层号）是每个窗口类型出生就带的一个整数，定义在 WindowManagerPolicy.getWindowLayerFromTypeLw。它是"窗口属于哪一大类"的身份证，决定了窗口在树中落脚的辖区：

层号窗口类型典型场景
0（未使用）保留
1TYPE_WALLPAPER壁纸
2APPLICATION_LAYER所有 App 窗口
3~9TYPE_PHONE、TYPE_TOAST 等来电、搜索栏、Toast
10~12TYPE_SYSTEM_ALERT、TYPE_APPLICATION_OVERLAYANR 弹窗、悬浮窗
15~16TYPE_INPUT_METHOD / _DIALOG输入法键盘
17~22TYPE_STATUS_BAR、TYPE_NOTIFICATION_SHADE 等状态栏、通知面板
24~25TYPE_NAVIGATION_BAR / _PANEL导航栏
26~35TYPE_SCREENSHOT、TYPE_POINTER 等截屏、系统错误、鼠标指针
36最大值（getMaxWindowLayer()）圆角遮罩专用

Feature（特性）则是系统功能的"代号"。一个 Feature 声明它作用于哪些层——注意是"层"，不是窗口——建树时系统会为每个 Feature 造出一批 DisplayArea，把这些层罩在里面。默认策略下注册的 Feature 有：

Feature 名作用范围（对层）用途
WindowedMagnification0~31 全部（除 32）窗口放大镜：整个子树整体放大
HideDisplayCutout全部，除导航栏/状态栏一族隐藏挖孔屏的黑边
OneHanded全部，除导航栏一族单手模式：整体下沉缩小
FullscreenMagnification大部分层，除放大镜/输入法/导航栏全屏放大镜
ImePlaceholder仅 15~16输入法占位：系统后续可把键盘移进来
OneHandedBackgroundPanel仅 1（壁纸）单手模式的背景暗化层
类比
把屏幕想成一栋 36 层的大楼，每层住一类窗口（layer = 楼层号）。Feature 则像"物业划分的片区"：物业说"1 到 31 层归 A 片区统一管理"，于是这些楼层的外墙上多了一道共同的闸门。住户（窗口）还是住在各自的楼层里，但片区闸门一动，整片楼层一起动。DisplayArea 树同时记录了楼层（layer）和片区（Feature）两种结构。

六、树是怎么"长"出来的

开机后，每个 DisplayContent 会调用 DisplayAreaPolicyBuilder 来建树，核心是 HierarchyBuilder.build()。它并不直接创建最终的 DisplayArea，而是先用一种"草稿节点" PendingArea 搭出骨架，再统一落成真节点。算法要保证三条性质：每个 Feature 对应一组 DisplayArea；窗口加入后，其所属每个 Feature 的区都是它的祖先；兄弟之间下层的最顶层不高于上层的最底层（Z 序严格）。

1
准备两个数组：PendingArea[] areaForLayer（每层一个"当前槽位指针"，初始全部指向根）和 DisplayArea.Tokens[] displayAreaForLayer（最终落成后每层对应的叶子）。
为什么：areaForLayer 是算法的核心工作区——它记录"每一层现在挂在哪个待定节点下"，新节点据此决定挂在谁下面、能否复用。
2
第一遍扫描：为每个 Feature 造区。按 Feature 定义顺序（先定义的在上）逐个处理；对每个 Feature，从 layer 0 扫到 36：如果该 Feature 覆盖这一层，就看看能否复用上一层的区——只有"上一层也属于这个 Feature 且槽位指针没变"才能复用，否则新建一个 PendingArea 挂在当前槽位指针下，并把指针移到它身上；不覆盖则清空指针。
为什么：一个 Feature 覆盖的层可能被其他 Feature"打断"（比如 15~16 被 ImePlaceholder 占据），于是同一 Feature 会裂成多个区——先定义的 Feature 更靠上，保证 Z 序性质。
3
第二遍扫描：为每层造叶子。再从 layer 0 扫到 36：若本层类型与上一层相同且槽位指针没变，就复用上一个叶子；否则新建叶子。三类叶子：应用层挂 TaskDisplayArea（从 setTaskDisplayAreas 传入），15~16 挂输入法容器，其余建 DisplayArea.Tokens。叶子创建时把它的 mMaxLayer 一路刷到当前层。
为什么：相邻的同类层共用一个叶子，能大幅减少节点数量——36 层最终只浓缩成十来个叶子。
4
落成：对 PendingArea 树做深度优先遍历（instantiateChildren），同一父节点下按最小层号排序后逐个创建真实 DisplayArea，叶子把管辖的每层都写进 displayAreaForLayer 查找表；最后调用 RootDisplayArea.onHierarchyBuilt 把 Feature 列表和查找表缓存在根上。
为什么：先搭草稿再落成，是为了让"挂到哪里"的决策与"创建哪个类的节点"分离，排序也只需在落成时做一次。

七、新窗口如何挂进树里

树建好后就是一棵常青树：每来一个新窗口，系统按固定流程把它挂到对应的叶子下。

1
App 请求加窗口，WindowManagerService 校验后交给所在屏幕的 DisplayContent。
为什么：窗口归属哪块屏幕就挂哪棵树的根，多屏互不干扰。
2
查层号：调用 WindowManagerPolicy.getWindowLayerFromTypeLw(type)，由窗口类型查出 layer（如输入法 → 15）。
为什么：层号是树内寻址的钥匙，下一步直接用它在查找表里定位。
3
查表定位叶子：RootDisplayArea.findAreaForTokenInLayer(token) 用 layer 作下标读 displayAreaForLayer[layer]，直接拿到目标 DisplayArea.Tokens。
为什么：建树时把每层对应的叶子全部预填进数组，运行时寻址就是 O(1) 的数组读——不用每次遍历整棵树。
4
挂入叶子：把窗口的 WindowToken 加到该叶子的子节点列表末尾。
为什么：同一叶子里"加在后面 = 盖在上面"，后来者居上，符合直觉。
特例：子窗口不走树
对话框、下拉面板这类子窗口（TYPE_APPLICATION_PANEL 等）不会单独查层挂树，而是直接挂到父窗口的 WindowState 下面，父子共进退——父窗口被收起，子面板跟着消失。它们的先后由 getSubWindowLayerFromTypeLw 给出的相对层号（正数在上、负数在下）在父窗口内部排序。

建议阅读顺序：

  1. 先看常量：WindowManagerPolicy.getWindowLayerFromTypeLw，把类型→层号这张表印在脑子里。
  2. 再看建树：DisplayAreaPolicyBuilder.HierarchyBuilder.build()，对照第 6 节的两遍扫描。
  3. 回看落成：PendingArea.instantiateChildren，理解草稿如何变成真节点、查找表如何填充。
  4. 最后看挂载：Result.addWindow → findAreaForTokenInLayer，验证运行时 O(1) 寻址。
本节核心
概念与源码一一对应：树 = WindowContainer 家族；建树 = HierarchyBuilder；层号 = WindowManagerPolicy；Feature = DisplayAreaPolicyBuilder.Feature + DisplayAreaOrganizer。

九、自测：7 个问题

Q1：为什么不用一维 z 值数组管理窗口？
提示想想"单手模式要把几十层窗口整体移动"这件事，用数组怎么做？
答案一维数组只能表达顺序，无法表达"群体"。树的一个子树 = 一个可整体操作的单位（移动、调暗、放大都只动一个节点）。这是 Feature 分组机制存在的根本原因。
Q2：layer（层号）与 DisplayArea 树是什么关系？
提示层号是"身份证"，树是"住址结构"。
答案层号由窗口类型决定，是静态的大类编号（0~36）；树才是运行时决定谁盖谁的结构。层号在建树时用于划分辖区（哪个叶子管哪些层），在挂窗口时用于 O(1) 查表定位叶子。
Q3：一个 Feature 为什么可能对应多个 DisplayArea？
提示Feature 声明的层范围可能被别的 Feature"打断"。
答案例如 FullscreenMagnification 覆盖大部分层但排除了 15~16（输入法）和 24~25（导航栏），它的覆盖范围被切成两段，每段各成一个 DisplayArea。建树算法扫描到"不覆盖"的层时会清空复用指针，逼出新的区。
Q4：APPLICATION_LAYER 是多少？为什么 App 窗口不落在 DisplayArea.Tokens 里？
提示App 下面还有 Task、ActivityRecord 一层层结构。
答案APPLICATION_LAYER = 2（定义在 WindowManagerPolicyConstants）。App 窗口需要 Task 组织（最近任务、分屏、多任务切换），所以应用层的叶子是 TaskDisplayArea，下面再挂 Task 树；Tokens 只收纳不需要 Task 概念的系统窗口。
Q5：建树时 areaForLayer 数组是干什么的？
提示它叫"槽位指针"。
答案areaForLayer 记录"当前这一层挂在哪个待定节点下"。新建 Feature 区或叶子时，从它读出父节点并挂上去；判断能否复用上一层节点时，也要比较"指针是否还指向同一个父"。它是两遍扫描算法的工作区。
Q6：对话框这类子窗口如何挂树？
提示它们没有独立查层号。
答案子窗口（TYPE_APPLICATION_PANEL 等）挂在父窗口的 WindowState 之下，不经过 DisplayArea 树的寻址；相对先后由 getSubWindowLayerFromTypeLw 的相对层号在父窗口内部排序。父窗口移动或消失，子窗口跟随。
Q7：为什么运行时给窗口找叶子是 O(1) 的？
提示建树时多做了什么？
答案落成阶段，每个叶子把它管辖的所有层都写进 displayAreaForLayer 数组（第 i 层 → 第 i 项）。运行时拿着层号直接数组下标访问，无需遍历树。
