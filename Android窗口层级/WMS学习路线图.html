一、先立住：四个版本事实

版本陷阱 ⚠ 网上大量 WMS 文章基于 8/9/10/13，类名和职责差别很大。以下四点是本树（android-12.0.0_r32）实测，请先记住，读代码时能少走很多弯路。

  1. 没有 TaskFragment：12 树里不存在 TaskFragment.java（12L/API32 才引入）。任务容器只有 Task（Task.java:252 class Task extends WindowContainer<WindowContainer>）。
  2. WMS 与 ATMS 同包同锁：都在 com.android.server.wm 包；全局锁 mGlobalLock 声明在 ActivityTaskManagerService.java:362（WindowManagerGlobalLock），:370 的 mGlobalLockWithoutBoost 是同一把。
  3. PhoneWindowManager 的位置：在 com.android.server.policy 包（.../server/policy/PhoneWindowManager.java），不是 wm/policy，那个目录不存在。
  4. 动画主力不是 Shell Transitions：12 上转场主线是 AppTransition + SurfaceAnimator(leash) + TaskOrganizer/RemoteAnimation；TransitionController 一整套是 13/14 的主线，别拿新版本文章套 12。另外 SystemUI 侧没有 SystemBars.java。

🐛 实战问题

  • Input dispatching timed out（ANR）：先分清两种——窗口无响应（App 主线程卡死）vs 焦点窗口不存在/未就绪（awaitedFocusedApplication，常见于启动慢）。两者 onAnrLocked 重载不同，dumpsys input 看 connection 的 waitQueue/focus 能直接区分。
  • 触摸点到错误窗口：touchable region 算错（SurfaceView/异形裁剪）、不可见但仍持有 InputChannel 的窗口拦截、FLAG_NOT_TOUCH_MODAL 的区域外放行行为、spy/policy flag。
  • 点了没反应：窗口 NOT_FOCUSABLE 导致按键无焦点、token 已 remove 但 channel 未注销、焦点在另一块 display。
  • 多点触控被“分裂”到两个窗口；模态对话框没拦住下层事件；IME 弹出后触摸宿主变化（与阶段 5 联动）。

🧪 动手实验 ① 开发者选项打开“显示点按操作反馈”，配合 dumpsys input 观察 focusedWindow 与 touchState；② 加一个 FLAG_NOT_FOCUSABLE | FLAG_NOT_TOUCH_MODAL 悬浮窗，分别点窗口内外验证路由；③ adb shell input keyevent/tap 注入，在 dispatchOnceInnerLocked 加 log/断点完整跟一遍。

四、阶段 2：Activity/Task 与窗口生命周期（对应 06–07 篇，建议 1–2 周）

已完成 ✓ 06 篇已完成（窗口的诞生：addView → addWindow → WindowState 上树），见 06 窗口的诞生；本节剩余的「Activity/Task 启动链与回退栈生命周期」内容见 07 篇。

🐛 实战问题

  • 启动黑屏/白屏三种成因，排障点完全不同：starting window 没加上（TaskOrganizer 侧）/ 首帧太晚 isDrawn 迟迟不翻转（App 侧）/ 主题 windowBackground 本身是白色。
  • has leaked window：Activity destroy 时 WindowManager.removeView 没配对（Dialog/Toast 还持有 token）。
  • splash 图标不消失、starting window 残留、冷启动 task snapshot 显示成旧画面。
  • launchMode / taskAffinity / clearTop / 多实例行为与预期不符；后台 Activity 启动被拦（BAL）；showWhenLocked 在锁屏上的显示时机；配置变更期间窗口两次 add/remove 造成闪烁。

🧪 动手实验 ① am start -W -n pkg/.Act 看 WaitTime/TotalTime，配合 tracing 对齐 starting window → 真实窗口的接力点；② 故意在 onCreate 弹 Dialog 后直接 finish，复现 leaked window 并读 WMS 日志；③ 跟一次最近任务恢复，观察快照 surface 与真实 Activity 窗口的替换。

五、阶段 3：布局 / Insets / 旋转与配置（对应 08 篇，建议 1–2 周）

学什么 03 篇学了遍历“怎么跑”，这一阶段学每一遍里“算了什么”：窗口 frame 怎么定、系统栏怎么让位、旋转怎么做到不闪、配置变化怎么沿树传播。

核心锚点（已核实）

布局：DisplayContent.performLayoutNoTrace()（DisplayContent.java:4417）→ 逐窗口回调 mPerformLayout（:781）→ WindowState.computeFrame()（WindowState.java:1274）；策略侧 DisplayPolicy（DisplayPolicy.java:181）的 addWindowLw()（:1070）与 performLayoutLw——系统装饰窗口的 frame 由 policy 先定，再约束应用窗口。
Insets 三件套：InsetsStateController（InsetsStateController.java:64，每屏一份，管所有 source）、InsetsSourceProvider（InsetsSourceProvider.java:68，一个 source = 状态栏/导航栏/IME 之一）、ImeInsetsSourceProvider + InsetsPolicy + InsetsControlTarget（谁拿到系统栏显隐控制权）。客户端对应 WindowInsets / OnApplyWindowInsetsListener / setDecorFitsSystemWindows。
旋转：DisplayRotation（DisplayRotation.java:84）updateRotationUnchecked()（:415）；冻结显示 startFreezingDisplayLocked / stopFreezingDisplayLocked（DisplayContent.java:3008 可见 stop 调用点）——冻结期间用截屏盖住，直到新方向首帧就绪。
配置变更：ActivityRecord.resolveOverrideConfiguration()（:7142）、onConfigurationChanged()（:7697）、ensureActivityConfiguration()（:7950）；Task 同样有 onConfigurationChanged 向下传播。
手动模拟：cmd window user-rotation（ShellCommand:106）、set-ignore-orientation-request（:110）、size/density/reset（:75/:122）。

🐛 实战问题

  • 键盘弹起布局被顶乱：adjustResize/adjustPan 与 WindowInsets(Animation) 冲突；fitsSystemWindows 消费链断裂；IME inset 没收到（ImeInsetsSourceProvider 控制权没给目标窗口）。
  • 沉浸式/手势导航：状态栏隐藏后手势条还在；setSystemBarsBehavior 粘滞模式不生效。
  • 旋转闪一下/截图不更新（freeze 没解除）；传感器旋转与 Activity requestedOrientation 打架。
  • 折叠屏/外屏：screenSize 变化被 manifest configChanges 吃掉但代码没处理；DisplayCutout 安全区与圆角（02 篇最高 layer 36）避让。

🧪 动手实验 ① cmd window size 1080x1920 / density 240 / reset 复现多分辨率；② 强制旋转 + tracing，观察 freeze 截图 surface 与真实 surface 的交接时刻；③ 写一个带 OnApplyWindowInsetsListener 的 demo，弹 IME 后 dump InsetsStateController 状态对照客户端收到的 insets。

六、阶段 4：动画与过渡（对应 09 篇，建议 1 周）

核心锚点（已核实）

转场状态机：AppTransition（AppTransition.java:158）isReady()（:350），默认时长 DEFAULT_APP_TRANSITION_DURATION = 336ms（:167）；Task/ActivityRecord 在切换时设置转场状态，遍历中检查 isReady 后启动动画。
核心机制——leash（缰绳）：SurfaceAnimator.startAnimation()（SurfaceAnimator.java:134）→ createAnimationLeash()（:384）。在目标 Layer 与父 Layer 之间临时插入一个可操控的中间 Layer：动画只动 leash，原 Layer 不动；动画结束销毁 leash、提交最终位置。这是 04 篇的 Surface 树第一次被“动态插节点”，务必读透。
Shell 接管：TaskOrganizerController（TaskOrganizerController.java:69）——SystemUI/Shell 经它接管 Task 层级、starting window、分屏与手势动画；应用侧对应 WindowContainerTransaction 事务 API。
RemoteAnimation：AMS 把转场 leash 交给应用进程（如 Launcher）自己绘制，用于自定义返回桌面等动画。
原 Layer 树 A→B→ reparent B 到 leash→ 事务动画 leash（位移/alpha/裁剪）→ finish 回调：销毁 leash、reparent 回位

🐛 实战问题

  • 动画 leash 泄漏/残留：动画被 cancel 时 finishedCallback 没执行，画面卡在半透明或错位的中间层——Winscope 里能直接看到多出的 leash Layer。
  • starting window 与 app transition 不同步，启动时“闪两次”。
  • 手势返回动画过程中快速操作导致层级状态错乱。
  • 自定义 overridePendingTransition / RemoteAnimation 不生效：被 TaskOrganizer 截胡，或窗口/Task 的前置条件不满足。

🧪 动手实验 ① tracing 录一次 Activity 跳转，在 Winscope 里数出 leash 的创建与销毁时刻；② 开发者选项把“窗口动画缩放”调到 ×10 慢放，对照 AppTransition/SurfaceAnimator 的代码分支看。

七、阶段 4+：vsync 与 Choreographer（对应 10 篇，已落盘）

为什么补这一层 09 篇讲「动画在 vsync-sf 上跑」、04 篇讲「每帧提交 SF」，但 vsync 本身属于显示子系统。10 篇按依赖顺序补齐：VSyncPredictor 模型（中断采样→软件预测→fence 纠偏）→ app/sf 两条相位 → EventThread 按连接分发 → 三层按需（应用 / 分发 / 硬件）→ Choreographer 的 doFrame 五段式 → WMS 在 android.anim 线程用 getSfInstance 接入。

已落盘：10 显示子系统的节拍：vsync 与 Choreographer（锚点 102/102 已核实）

核心锚点：SurfaceFlinger#onComposerHalVsync()（SurfaceFlinger.cpp:1718）→ Scheduler#addResyncSample()（Scheduler.cpp:548）→ VSyncReactor#addHwVsyncTimestamp()（VSyncReactor.cpp:170）→ Choreographer#doFrame()（Choreographer.java:701）→ WindowAnimator#animate()（WindowAnimator.java:128）。

八、阶段 5：IME 与壁纸专项（对应 11 篇，建议 1 周）

为什么单独学 这是 WMS 里唯二“反向跟踪目标窗口”的特殊系统——别的窗口只管自己，IME 和壁纸要先回答“我现在该对着谁”。理解它们，就摸到了 policy 灵活性的上限。

核心锚点（已核实）

IME 服务：InputMethodManagerService.startInputOrWindowGainedFocus()（IMMS.java:3261，焦点变化→重新绑定编辑器）、showCurrentInputLocked()（:3114）。
WMS 侧：ImeContainer（类定义嵌在 DisplayContent.java 内）、IME 目标窗口与相对 Z 序（03 篇 assignRelativeLayerForIme 见过）、ImeInsetsSourceProvider（与阶段 3 同一条线：谁拿到 IME 控制权，谁收到 inset 并能驱动动画）。
壁纸：WallpaperController（WallpaperController.java:60）：壁纸目标窗口选择、与桌面滚动联动（xOffset/yOffset）、壁纸窗口在 layer 表中的固定层（01 篇 wallpaper layer）。

🐛 实战问题

  • 输入法不弹出：焦点没真正切换（startInputOrWindowGainedFocus 没被调到）、mCurToken 为 null、ImeContainer 不可见。
  • IME 盖住输入框：insets 通知没下发或客户端没消费；多屏时 IME 跟错 display。
  • 壁纸纯黑/不跟桌面滑动：wallpaper target 没选对、壁纸进程死了没重连、与 FLAG_SHOW_WHEN_LOCKED 冲突。
  • 第三方键盘/语音输入切换竞态。

九、阶段 6：多显示与多窗口（对应 12 篇，按需，3–4 天）

九、贯穿线：线程与锁模型（建议每个阶段都回看一次）

全局唯一锁：WindowManagerGlobalLock（ActivityTaskManagerService.java:362 声明 mGlobalLock，:370 mGlobalLockWithoutBoost 是同一把）。WMS/ATMS/DisplayContent 几乎所有状态变更都在这把锁内。
三类线程：① Binder 线程持锁执行 addWindow/relayout 等入口；② system_server 的 mH Handler 把收尾工作串行化出锁执行；③ Animation 线程跑 performSurfacePlacement（03 篇 requestTraversal 的 Handler.post 边界）。
输入是另一条“近无锁”链路：InputMonitor 只在持 WMS 锁时快照一份窗口列表交给 native，之后 InputDispatcher 用自己的锁独立分发——所以输入看到的窗口状态可能“略旧”，这是理解焦点/触摸怪问题的关键前提。
实战红线：持 mGlobalLock 时做 Binder 跨进程调用（尤其回调 App）会引入卡顿甚至死锁。源码里大量使用“先清掉待办 → 出锁 → 再回调”的模式，读代码时看到 mH.post / 临时队列要立刻意识到这条边界。
