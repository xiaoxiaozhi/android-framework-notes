一、全景：一次 addView 的两进程旅程

本篇把「一个裸 View 变成树上 WindowState」这条链路走完整：它怎么在 App 进程里登记成一条窗口台账，又怎么跨过 binder 在 system_server 里挂进窗口树。

先记住 上树 ≠ 显示。本篇走完，窗口有了树位、层级、输入通道，但没有 frame、没有 Surface 内容——那要等下一站 relayoutWindow。

🐛 实战 IllegalStateException: View ... has already been added to the window manager。现象：快速 dismiss/show 的 PopupWindow 崩在该异常。因果：同一 contentView 被 add 两次且旧的还没走完 remove；注意 dying 分支只救「remove 已发起」的竞态，没发起过 remove 就是硬异常。怎么查：崩溃栈定位到 show 调用点，检查是否把同一个 View 复用到多个 WindowManager，或 PopupWindow 未先 dismiss 就复用。

🧠 思考（单块） 块 B 对 dying-view 调的是 doDie() 而不是 die(false)。结合 die()（ViewRootImpl.java:8117：非遍历中才同步 doDie，否则只 sendEmptyMessage(MSG_DIE)）想：这里为什么必须同步死，而不能只发 MSG_DIE 排队？

六、跨站闭环：BadTokenException 的完整因果链

线上现象：Activity 在异步回调里 show Dialog，偶现 WindowManager$BadTokenException，dump 显示该 ActivityRecord 已不在树；包一层 runOnUiThread 仍偶发。

① Activity 进入销毁，ActivityRecord 从 Task 摘除（getParent() == null） ② 异步回调（网络/Handler/post）此刻才执行 Dialog.show() ③ App：WindowManagerGlobal.addView → ViewRootImpl.setView └─ session.addToDisplayAsUser ── binder ──▶ system_server ④ WMS.addWindow 块 F 两个返回点之一： · token 查不到 → ADD_BAD_APP_TOKEN · activity.getParent() == null → ADD_APP_EXITING ⑤ 错误码过 binder 返回（全程无异常抛出） ⑥ App：ViewRootImpl.setView 块 D2 res < ADD_OKAY └─ switch(res) 翻译成 BadTokenException 抛出 ⑦ WindowManagerGlobal 块 C catch：removeViewLocked(index, true) 回滚三本账 ⑧ 异常继续抛给业务线程 → 崩溃（或被业务 try/catch 吞掉）

为什么 runOnUiThread 救不了：时序卡点不在「是不是主线程调用」，而在 show 执行那一刻，服务端块 F 的 ActivityRecord 是否还挂在 Task 上。Runnable 排队到主线程，完全可能在 destroy 之后才轮到。正确判据是生命周期状态（isFinishing() || isDestroyed()，Fragment 用 viewLifecycleOwner 的 RESUMED），根治手段是把 UI 操作绑定生命周期（LifecycleObserver / lifecycleScope 自动取消），而不是切线程。

设计回顾「错误码跨进程、异常在客户端抛」是整条链的统一约定——服务端十几种拒绝原因全用整数码，保证绝不留半成品；客户端在块 C 集中回滚台账并抛出带排查文案的异常。排障时务必用服务端返回码区分 ADD_BAD_APP_TOKEN 与 ADD_APP_EXITING，两者修复方向不同（前者多为 token 传错，后者纯生命周期时序）。

🧠 自测（本讲 6 题）

1. 块 B 的 dying-view 分支为何必须同步 doDie，而不能只发 MSG_DIE？
本次 addView 紧接着要在同一下标 new ViewRootImpl 并重新登记（块 C）。若只发 MSG_DIE，旧根要到后续主线程消息轮次才真正 doDie → doRemoveView，届时它会把新根按旧下标从三本账摘掉（三本账按下标对齐，不区分新旧）。同步 doDie 保证「旧根在新根登记前彻底出账」，把下标腾干净。
2. 块 C 为什么先登记后 setView？catch 里为何用旧 index？
(1) setView 内 addToDisplayAsUser 返回后窗口可能立刻收到 relayout/配置/insets 回调，这些回调经 ViewRootImpl 重入 WMG 按 View 反查 root；未登记则反查失败，出现「系统侧已在册、客户端查无此窗」。(2) 回滚语义要对准「本次刚加的那一条」；dying 分支同步清掉旧根后，旧 index 正好等于新根位置，重新查找反而引入歧义。
3. 块 D2 把 ADD_BAD_APP_TOKEN 与 ADD_APP_EXITING 合并成同一文案，怎么区分？
ADD_BAD_APP_TOKEN 在块 F unprivilegedAppCanCreateTokenWith 返回（token 根本查不到）；ADD_APP_EXITING 在块 F activity.getParent() == null 返回（ActivityRecord 已脱离 Task）。二者面向开发者都是「token 不可用」，故合并同一文案。区分：dump 看 ActivityRecord 是否在树（在树但无 parent → EXITING；完全不在 → BAD_APP_TOKEN）；开 ProtoLog 看返回码。
4. 块 G 的 addChild 之后抛异常会怎样？注释保护边界到哪？
树里留下已挂载但后续字段可能未初始化完的 WindowState，而 mWindowMap 尚未 put，成为「在树但查不到、无人回收」的孤儿节点；调用方拿异常而非错误码，块 G 第二段无 try/catch 兜底，异常穿回客户端，服务端不会自动摘除。注释只保证 addChild 之前字段初始化完（使 onDisplayChanged 回调不读到半字段），不保证其后代码不抛异常——这也是 addChild 被放在构造函数极靠后、其后只剩少量注册代码的原因。
5. 块 H「在册但不在树」为何比崩溃更难排查？
mWindowMap 已有该 client→WindowState，后续 relayout/remove/按键投递都能查到它，但它不在任何 WindowToken 的 mChildren 里：不参与布局遍历、层级/Z/可见性计算，dump 窗口树不可见，却占着 client binder（重复 add 撞 ADD_DUPLICATE_ADD）、持有 InputChannel 与死亡监听。它不崩溃、也没有正常路径能清掉（removeWindow 按树查找可能找不到），成为静默泄漏。相比快速崩溃有明确栈和现场，这种「幽灵在册」只表现为后续莫名的重复添加/输入异常，排查成本高得多。所以源码用「no exceptions or errors allowed」把此后全部设计成不可能失败的纯内存操作。
6. ATTACHED_DIALOG 上树后的父节点、Z 序与 frame 分别是什么？
类型落在 FIRST_SUB_WINDOW..LAST_SUB_WINDOW，块 E 经 windowForClientLocked 找到父顶层窗口（hasParent=true），块 F 复用父窗口 token；块 G mIsChildWindow=true，构造函数里 parentWindow.addChild(this, sSubWindowLayerComparator)——所以树父节点是父 WindowState，不是 WindowToken。Z 序由父窗口的 mBaseLayer（getWindowLayerLw × TYPE_LAYER_MULTIPLIER + OFFSET）定大区间、自己的 mSubLayer（getSubWindowLayerFromTypeLw）定区间内次序，再由块 I assignChildLayers() 一次性赋值。此刻 frame 为空（未布局），屏幕位置要到下一站 relayoutWindow → computeFrame 才确定；attached 类型 mLayoutAttached=true，frame 相对父窗口坐标系计算。
