一、全景：布局是「谁给谁量尺寸」

你在 03 篇学过：窗口变了会触发一次遍历（performSurfacePlacement），遍历里会 forAllWindows 走 DFS、会分配 Z 序、会提一笔事务给 SurfaceFlinger。但那篇解决的是「怎么跑」，留下一个问题没答：每个窗口的 mFrame 到底是谁算的、按什么规则算的？

更要紧的是：窗口的尺寸从来不是它自己说了算。一个 App 的 Activity 想要「铺满整屏」，但屏幕上方 100px 被状态栏占了、下方 150px 被导航栏占了、右下角还有手势条、转屏时还要重算一遍——这些「别人占掉的地方」就是 Insets。本篇就是把这条链走完。

类比 03 篇讲的是「装修队怎么进场、按什么顺序施工」；本篇讲的是「每间屋子最终多大」——先由物业（系统装饰窗口）划走楼道、电梯、消防通道，剩下的才是你屋子（App 窗口）的面积；你要是想看图，还得知道那些楼道是谁画的（Insets 来源）、能不能临时拆掉（Insets 控制权）。

二、布局主循环：performLayoutNoTrace 与 mPerformLayout

布局入口在 DisplayContent。注意它的设计：主循环本身很短，真正的活是逐窗口回调 mPerformLayout。

这段在干什么：先判断「这次要不要真布局」，然后自顶向下把所有窗口过一遍回调，最后收尾。

设计意图：自顶向下是布局与 Z 序遍历的关键差异——Z 序要自底向上（先算下面的），布局要自顶向下（先定父的）。同一个 forAllWindows 靠传入不同的回调顺序服务两种目的。

🧠 思考（单块） 如果布局改成自底向上会怎样？想想 06 篇里那个「mLayoutAttached 的子窗口 frame 相对父窗口坐标系计算」——父的 frame 还没定，子的相对位置算得出来吗？

        // as otherwise we'd immediately cause an unnecessary resize.
        if (firstLayout) {
            // … 省略：首布局时对齐 last frame / 触发一次 resize（822-860）
        }
    }
    // … 省略：mLayoutAttached 的子窗口由父窗口带着走，不在这里单独处理
};

这段在干什么：决定这个窗口这轮要不要重排；要的话清标记、预处理，然后把算 frame 的活交给 DisplayPolicy.layoutWindowLw()。

设计意图：frame 计算外包给 policy。因为「状态栏多高、导航栏在哪、IME 是否顶起、屏幕是否圆角/挖孔」这些是设备与厂商策略，WMS 核心不该硬编码——这也是 ROM 定制影响布局的入口。

🐛 实战 窗口 frame 不对（黑边/被状态栏盖住/全屏失效）。因果：isGoneForLayout() 判真 → 直接跳过，frame 保持旧值；常见于窗口刚 add、还没 relayout（呼应 06 篇「上树 ≠ 显示」）。怎么查：dumpsys window windows 看该窗口的 mHaveFrame、mLayoutNeeded、frame= 三项；mHaveFrame=false 说明它从没被真正布局过。DisplayPolicy.layoutWindowLw() 里打断点看它是否被调用。

在主线中的位置：performSurfacePlacement → DisplayContent.performLayoutNoTrace → forAllWindows(mPerformLayout) → DisplayPolicy.layoutWindowLw → WindowState.computeFrame（下一块）。

三、frame 是怎么算出来的：WindowState.computeFrame

上一块把活交给了 policy，policy 最终会调到 WindowState.computeFrame()。这里才是「这个窗口到底占哪块矩形」的收官。

块 C：computeFrame 的入口与前置判断（WindowState.java:1262/1274，裁剪）

WindowState.java:1262-1274（转发）+ 1274-1310（裁剪）
void computeFrameAndUpdateSourceFrame() {
    computeFrame();

    // ① why 两件事：算 frame，再把 frame 同步给 insets 体系（下一节要用）

void computeFrame() {
    if (mWillReplaceWindow && (mAnimatingExit || !mReplacingRemoveRequested)) {
        return;
        // ② why 正在被替换的窗口冻结不动：旧窗口要停在原地等新窗口出现，
        //    否则替换过程会出现两个窗口都在动的画面撕裂
    }
    mHaveFrame = true;
    // ③ ★ 这一行就是「这个窗口真正被布局过」的官方标记——
    //    dumpsys 里的 mHaveFrame 就是它，排障第一眼要看的值

    final Task task = getTask();
    final boolean isFullscreenAndFillsArea = !inMultiWindowMode() && matchesDisplayAreaBounds();
    final boolean windowsAreFloating = task != null && task.isFloating();
    // ④ why 先分清三种处境：全屏铺满 / 多窗口分屏 / 浮动自由窗口——
    //    后面每一个 if 分支都靠这几个布尔量分流，frame 规则完全不同
    final DisplayContent dc = getDisplayContent();
    final DisplayInfo displayInfo = getDisplayInfo();
    final WindowFrames windowFrames = getLayoutingWindowFrames();
    mInsetFrame.set(getBounds());
}

这段在干什么：先排除「正在被替换」的特殊窗口，然后打上 mHaveFrame 标记，再按「全屏 / 分屏 / 浮动」三类处境准备后续分支的输入。

设计意图：mHaveFrame 与 layoutInParentFrame() 两个布尔量决定一切。前者答「布局过没有」，后者答「相对父窗口还是相对屏幕」——这与 06 篇你学过的 mLayoutAttached 是同一套坐标系逻辑。

🐛 实战 分屏/自由窗口下窗口位置错乱。因果：windowsAreFloating 与 isFullscreenAndFillsArea 的分流走错了分支，frame 用了屏幕坐标系而非 Task 坐标系。怎么查：dump 里对比该窗口的 frame= 与所属 Task 的 bounds；自由窗口模式下 frame 应落在 Task 范围内，若等于整屏 bounds 就是分支错了。

🐛 实战 键盘弹起布局被顶乱 / 沉浸式下内容被导航栏盖住。因果：isImeTarget 判真与否决定 frame 是否被 IME 顶起；isFullscreenAndFillsArea 决定用 appRect 还是 Task bounds。怎么查：dump 看该窗口 frame 底边与 dumpsys window displays 里 appRect 的关系；再 dumpsys input 看 IME 目标是不是它。
🧠 思考（需结合：块 B、块 C、块 D） 一个 App 窗口的 frame 最终等于「屏幕 - 状态栏 - 导航栏」，这个减法发生在哪一步？是 computeFrame 里减的，还是它拿到的 appRect 早就减好了？如果状态栏高度在运行中改变（比如隐藏状态栏），这个窗口需要走哪些步骤才能跟着变？

设计意图：三个 Rect 是整套布局的「预算表」。系统装饰窗口（状态栏/导航栏/IME）先在这三个区间里占位，剩下的 nonDecorBounds 就是 App 能用的地方。这也是为什么 ROM 厂商改状态栏高度必须在 policy 层改——改的是这份预算表。

🐛 实战 状态栏隐藏后 App 内容没跟着长高。因果：policy 的 nonDecorBounds 变了，但窗口没被标记 mLayoutNeeded，所以 performLayoutNoTrace 在块 A 的①处直接 return。怎么查：开 cmd window tracing 看布局事件有没有发生；确认 Insets 变化后有触发 requestTraversal()（下一节）。

六、旋转：DisplayRotation 与冻结显示

旋转是布局体系的“极端场景”：屏幕尺寸整个换掉，所有窗口的 frame 都要重算。它最难的地方不是计算，而是怎么让用户看不到中间态。

设计意图：旋转的“计算”很简单，难点全在时序。核心是：不能让用户看到“新旧方向同时存在”的中间帧。所以接下来要冻结。

🐛 实战 旋转不生效 / 转了一半又转回去。因果：rotationForOrientation 的优先级判断——如果 App 在 manifest 里写了 screenOrientation="portrait"，它会压过传感器；或者 mDeferredRotationPauseCount > 0（有窗口请求暂停旋转，常见于视频/相机）。怎么查：开 WM_DEBUG_ORIENTATION ProtoLog，日志里会打印「selected orientation X, got rotation Y」以及每次 return false 的具体原因（注释里那几句 Deferring rotation 就是为排障写的）。

块 H：冻结与解冻（WMS.java:5706 / 5762）

WindowManagerService.java:5706-5730、5762-5795（裁剪）
void startFreezingDisplay(int exitAnim, int enterAnim, DisplayContent displayContent,
        int overrideOriginalRotation) {
    if (mDisplayFrozen || displayContent.getDisplayRotation().isRotatingSeamlessly()) {
        return;
        // ① 幂等：已经冻着就别再冻一次
    }
    if (!displayContent.isReady() || !mPolicy.isScreenOn()
            || !displayContent.okToAnimate()) {
        return;
        // ② if 屏幕没亮/没准备好，不值得冻（否则解冻时机难保证）
    }
    ProtoLog.d(WM_DEBUG_ORIENTATION,
            "startFreezingDisplayLocked: exitAnim=%d enterAnim=%d called by %s",
            exitAnim, enterAnim, Debug.getCallers(8));
    // ③ 打印 8 层调用栈——专门为“谁触发旋转”的排障设计
    mScreenFrozenLock.acquire();
    mAtmService.startLaunchPowerMode(POWER_MODE_REASON_FREEZE_DISPLAY);
    // ④ 冻结期间要提频：旋转会引发大量重绘，不提频会明显卡
    // … 省略：截屏（ScreenRotationAnimation）、冻结 surface
}

void stopFreezingDisplayLocked() {
    if (!mDisplayFrozen) return;
    // … 省略：取出 numOpeningApps / waitingForConfig 等状态
    if (waitingForConfig || waitingForRemoteRotation || mAppsFreezingScreen > 0
            || mWindowsFreezingScreen == WINDOWS_FREEZING_SCREENS_ACTIVE
            || mClientFreezingScreen || numOpeningApps > 0) {
        return;
        // ⑤ ★ 这里是“旋转黑一下”的根源之一：解冻的条件很苛刻——
        //    配置还没发下去、App 还在冻结屏、还有窗口在等首帧……只要有一项没满足，
        //    就继续冻着（用户看到的是那张截屏）。任何一项卡住 = 冻结超时/黑屏
    }
    ProtoLog.d(WM_DEBUG_ORIENTATION, "stopFreezingDisplayLocked: Unfreezing now");
    // … 省略：真正解冻、播动画、释放 mScreenFrozenLock
}

这段在干什么：冻结时截一张屏盖住画面、提频；解冻时检查六个条件全满足才放行。

设计意图：用“截屏 + 冻结”换取“不闪”。旋转时所有窗口都要重算 frame 并重绘，这个过程必然要几十毫秒。与其让用户看到撕裂的中间态，不如冻住旧画面、等新画面准备好再一次性切换——代价是那一瞬间画面是“死的”。

🐛 实战 旋转后一直黑屏 / 卡在旧画面。因果：stopFreezingDisplayLocked 的六个条件里有一项永远不满足。最常见的两个：mAppsFreezingScreen > 0（某个 App 没调 stopFreezingScreen，通常是它自己卡住了）、numOpeningApps > 0（有窗口一直没 drawn，回到 06 篇的“上树≠显示”）。怎么查：开 WM_DEBUG_ORIENTATION，日志会直接打印是哪个条件把解冻挡住的（代码里那行 ProtoLog 就是干这个的）。
🧠 思考（需结合：块 G、块 H） 旋转期间为什么要“截屏”而不是“让旧窗口继续画”？想想如果让旧窗口继续渲染，然后在某一帧突然换成新方向的图层树，用户会看到什么——这能解释 ScreenRotationAnimation 存在的意义。

七、配置变更：谁收到、谁重建

旋转只是配置变更的一种。屏幕上任何影响尺寸/密度/语言/夜间模式的改变，都会走同一条路：计算新配置 → 沿树向下传播 → 决定谁重建。

块 I：配置更新入口（DisplayContent.java:5511 起，裁剪）

DisplayContent.java:5511-5545（裁剪）
boolean updateDisplayOverrideConfigurationLocked() {
    // Preemptively cancel the running recents animation -- SysUI can't currently handle this
    // case properly since the signals it receives all happen post-change
    cancelRecentsAnimation();
    // ① why 先取消最近任务动画：配置变化之后 SystemUI 收到的信号都是“事后”的，
    //    继续跑那个动画会算错位置。这是“手势中旋转”类 bug 的防护

    Configuration values = new Configuration();
    computeScreenConfiguration(values);
    // ② 重新算一份屏幕配置（尺寸/密度/方向/字体缩放等）

    mAtmService.mH.sendMessage(PooledLambda.obtainMessage(
            ActivityManagerInternal::updateOomLevelsForDisplay, mAtmService.mAmInternal,
            mDisplayId));
    // ③ 顺带更新 OOM 等级：屏幕变大了，进程内存阈值也要跟着调

    Settings.System.clearConfiguration(values);
    updateDisplayOverrideConfigurationLocked(values, null /* starting */,
            false /* deferResume */, mAtmService.mTmpUpdateConfigurationResult);
    // ④ 真正下发（重载版在 :5537，内含 deferWindowLayout + 沿树传播）
    return mAtmService.mTmpUpdateConfigurationResult.changes != 0;
    // ⑤ 返回“有没有变化”：调用方据此决定要不要继续重建流程
}

这段在干什么：算出新配置，更新内存阈值，然后沿树把配置传下去。

设计意图：配置在树上是“往下流”的（呼应 01 篇讲的「状态广播」）。每个节点拿到父节点的新配置后，先算自己的 resolved 配置（可能被 override），再传给子节点。这就是为什么改屏幕密度会影响所有 App、但某个 Activity 可以用 configChanges 自己处理掉一部分。

🐛 实战 旋转后 App 一直黑或不刷新。因果：Activity 声明了 configChanges="orientation|screenSize"，但代码里没重排布局——系统不重建，App 自己又没适配，于是画面停在旧尺寸。怎么查：dumpsys activity activities 看该 Activity 的 config 是否已更新；应用侧打日志确认 onConfigurationChanged 有没有被调到。
🧠 思考（闭环·需结合：块 H、块 I、块 J） 一次旋转从 块 G 决定方向，到 块 H 冻结、块 I 下发新配置、块 J 决定重建，最后解冻。请把「谁会阻止解冻」这件事串起来：如果某个 Activity 重建得特别慢，用户看到的是什么？如果它声明了 configChanges 自己处理，又会快在哪一步？

🧠 自测：5 个问题

1. 一个 App 窗口的 frame 最终 = 屏幕减去状态栏和导航栏，这个“减”发生在哪一步？
不是 computeFrame() 里现减的。真正的减法发生在算出 displayInfo.appRect 的那一刻（由 DisplayContent / DisplayInfo 计算），computeFrame() 只是全屏窗口直接取用 appRect 当容身框（WindowState.java:1338 附近那个分支：layoutContainingFrame = layoutDisplayFrame = displayInfo.appRect）。而 appRect 本身是 DisplayPolicy.layoutWindowLw() 里算出的 systemDecorBounds / nonDecorBounds 的结果——所以“谁扣掉系统栏”的答案是 policy 层，不是 WindowState。
2. 为什么布局要自顶向下，而 Z 序遍历要自底向上？
因为两者的依赖方向相反。布局要先把父容器的范围定下来，子窗口才能相对它算位置（mLayoutAttached 的子窗 frame 甚至是相对父窗口坐标系算的）——所以必须自顶向下。Z 序要保证“下面的先分配、上面的后分配”才能得到正确的层叠次序——所以自底向上。（同一个 forAllWindows，靠传入不同遍历方向服务两种目的。）
3. 状态栏隐藏后 App 内容没跟着长高，可能卡在哪三个环节？
按数据流顺序排查：① 输入没变：InsetsStateController.onPostLayout() 里 changed 为 false，没调 notifyInsetsChanged()；② 没触发重布局：Insets 变了但没 requestTraversal()，于是 performLayoutNoTrace 开头 if (!isLayoutNeeded()) return 直接返回；③ 窗口被跳过：窗口在 mPerformLayout 里被判 isGoneForLayout() 真而跳过，frame 保持旧值。三者对应 dump 里不同的字段组合。
4. 旋转时为什么要“冻结显示 + 截屏”，而不是直接让窗口重画？
因为旋转要重算所有窗口的 frame 并全部重绘，这个过程必然持续几十毫秒。如果期间让旧窗口继续渲染，用户会看到新旧方向混杂的中间态（部分窗口已转、部分没转，或画面被拉伸）。冻结 + 截屏的做法是：用一张静态截图盖住整个屏幕，等新方向的首帧准备好再一次性切换。代价是那一瞬间画面是死的（用户感觉“卡了一下”）。ScreenRotationAnimation 就是管这张截屏的。
5. 声明了 configChanges="orientation|screenSize" 的 Activity，旋转时经历了什么不同？
它走的是不重建分支：ensureActivityConfiguration() 比对 manifest 后认为 App 能自己处理这些变化，于是只回调 onConfigurationChanged()（ActivityRecord.java:7697），Activity 实例不销毁、不重新 onCreate、状态不丢——快，但要求代码自己重排布局。
反之未声明时会走 relaunch：Activity 销毁重建、全量重新布局，慢且会闪，但系统兜底保证最终布局正确。这就是「同一次旋转，有的 App 闪、有的不闪」的根本原因。
