〇、我出的题和马老师那套有什么不同

马老师那套（见 实践项目清单）是「别人的 bug，你去修」——优点是贴近真实工作，缺点是依赖现成的复现环境和参考文章，而且你只能沿着他给的路径走。

我给你出的是另一类：「你把系统的一个机制，自己重新造一遍，再拿真机验证」。

马老师型（修 bug）我出的型（造机制）
起点别人踩的坑一条源码机制
动作定位 → 修复预测 → 实现 → 实测 → 对不上就回头
做题时会发现工具不熟自己哪块理解是错的（这就是价值）
对理解的检验强度中（可能靠猜）高（预测错了立刻暴露）
可复现性依赖特定环境/bug随时可做，环境就是你手上的 AOSP 12
产物patch / 报告可运行的工具 / 引擎 / 数据集
一句话区别 马老师教你当医生（病人来了开刀）；我教你当制图师（把整个地形亲自走一遍画出来）。两者都要做——但只做前者，你的理解永远是「碎片 + 补丁」，不成体系。
前提 六题全部基于你手头的 /home/book/aosp12，且每条源码锚点我都已 grep 核实过（见第九章索引），你照做不会扑空。

二、L1 Z 序预言机（构造性 · 最硬核）

一句话 把 WMS 决定「谁盖谁」的那套算法自己实现一遍，然后拿去预测真机上任意窗口组合的最终层级；预测错一个数，就代表你有一处理解是错的理解。

为什么这题值钱

Z 序是 WMS 里最容易被"背下来"却又最容易理解错的部分。你 02/03 篇读过它，但读过 ≠ 能算。这题会逼你分清三件事：

  • mBaseLayer（粗层）怎么来的 —— 由 type 映射 + 乘法偏移
  • mSubLayer（层内细分）只在子窗口场景用
  • 最终 mLayer 是遍历时两趟分配出来的，不是算出来的

源码依据（我已核实）

WindowManagerService.java:343 TYPE_LAYER_MULTIPLIER = 10000； :347 TYPE_LAYER_OFFSET = 1000
WindowManagerPolicy.java:466 getWindowLayerLw(win)；:520 getWindowLayerFromTypeLw(type, canAddInternalSystemWindow, roundedCornerOverlay) —— 那张 switch(type) 大表就是层级字典
WindowState.java:1104 / :1117 子窗口抄父层、否则自己算 mBaseLayer
WindowContainer.java:2290 assignChildLayers(Transaction) —— 两趟循环（第一趟跳过 needsZBoost() 的子节点，第二趟补上），WindowState.java:5648 assignLayer(t, layer)

做什么

1抄字典：把 getWindowLayerFromTypeLw 的 switch 表整理成数据（type → 层号），别用 if-else 硬编码，要能配置。

2实现两级层：mBaseLayer = policyLayer(type) * 10000 + 1000；子窗口改为继承父的 mBaseLayer，自己只填 mSubLayer。

3实现两趟分配：按 DFS 序遍历树，第一趟给「不需要 Z 提升」的节点依次发号，第二趟给 needsZBoost 的补号。这一步是本题的真正考点——很多人第一次写会漏掉 needsZBoost 导致顺序全错。

4喂真实输入：写个解析器，从 dumpsys window windows 里抽出每个窗口的 type / 父子关系 / 当前 mLayer。

5对答案：你的预测序列 vs dump 里的真实 mLayer，逐个比对，要求完全一致（不是"差不多"）。

交付物
  • 一个可运行的「Z 序预言机」（语言随意，Python 够用）
  • 至少 3 组场景的对照表：普通 App / 弹了 Dialog / 有 IME 或状态栏
  • 一份「我错在哪」记录：第一次预测必然有偏差，把每处偏差记下并说明原因（这份记录的价值 > 引擎本身）
🐛 必定会踩 ① 忘了 canAddInternalSystemWindow 会让 alert 类窗口层号发生变化（WindowManagerPolicy.java:520 的第三个参数）；② 误以为 mLayer 是构造时就定好的——它是遍历时由 assignChildLayers 发的；③ needsZBoost 的来源（WindowContainer.java:2318 附近）没搞清。
🧠 做完你就懂了 为什么 WMS 不直接给每个窗口算一个全局 z 值，而是「粗层 + 遍历时局部发号」？—— 想通这个，你对「树」这个数据结构的选择就真理解了（回到 01 篇「为什么非得是树」）。

三、L2 Dump 考古器（工具性 · 最实用）

一句话 现在 dump 里的一个字段，你要问「这是啥意思」只能去翻源码；这题让你建一张「字段 → 哪行代码写的」映射表，让 dump 从「看的」变成「查的」。

为什么这题值钱

B 岗排障时最耗时的动作就是「看到字段 A 不对，但它从哪来？」。这张表建完，你以后查任何窗口问题都快一倍。而且它只能靠真读源码建出来——没法抄。

做什么

1把 dumpsys window windows 的 WindowState 段全字段抓下来（几十个：mLayer / mBaseLayer / mSubLayer / mFrame / mRequestedWidth / isReadyForDisplay / mViewVisibility / mHasSurface / relayoutCalled / isDrawn …）。

2逐个到源码里找「谁给它赋的值」，记下 文件:行号。比如 mLayer → WindowState.assignLayer()（:5648）；relayoutCalled → relayoutWindow 里置位。

3把表做成可查询的：输入字段名，输出「源码位置 + 什么条件下会变成这个值 + 看到异常值说明什么」。

4加一个「红绿灯」判断：哪些字段组合代表异常（例：relayoutCalled=false + isDrawn=false 但 mHasSurface=true）。

交付物
  • 字段字典（≥30 个字段，每个带源码行号）——推荐直接做成你 06 篇的续篇附录
  • 一个 explain-field.py：输入 dump 文件 + 字段名，输出解释
  • 一份「异常字段组合速查」（≥5 条：组合 → 指向的问题）
🐛 坑 别只看声明处（## 字段的诞生要找到真正语义上的「谁决定它」）。例如 mFrame 声明在字段区，但决定它的是 computeFrameAndUpdateSourceFrame()（WindowState.java:1262）→ computeFrame()（:1274）。
🧠 做完了你会得到什么 这张表本身就是你的私人速查手册——以后看任何人的 dump、任何论坛的日志、任何 bugreport，都能立刻翻译成源码语言。

四、L3 What-if 破坏实验室（方法论 · 最提效）

一句话 每次都先写下预测，再改代码、编译、观察，最后解释偏差。这是最反直觉、但学习效率最高的一种练习——因为你亲手制造的「坑」，完全可控、可复现、可反复。

为什么这题值钱

读源码时，我们常有一种自信：「我知道这行是干嘛的」。改掉它、看系统怎么坏——是对这种自信最狠的检验。真到工作时，你对「改这行有多大副作用」的判断力，就是靠这些实验堆出来的。

交付物
  • 「预测 vs 实际」对照表（≥8 行，每行：改了什么 / 我预测 / 实际现象 / 差异原因）
  • 其中至少 2 条是你预测错了——预测全对说明题目选得太简单
  • 一份 git stash 记录（每次实验留下可回滚的 patch）
🐛 坑 ① 一定要先写预测，不然就退化成「随便改改看现象」，学习价值归零；② 改系统导致起不来时，用 adb sync 单模块回滚，别重新全编（aosp12 13 14模拟器如何进行单模块更新 那篇马老师文有讲）。
🧠 进阶 每个实验加一句「这个常量/顺序是为了保护什么」。这句话就是你面试时能讲的设计直觉。

五、L4 窗口泄漏猎犬（实战性 · 最贴近工作）

一句话 把那句人人都见过的崩溃文案 has leaked window，升级成一个能提前告警的检测工具：Activity 反复进出，看窗口树里的节点数是不是只增不减。

源码依据

WindowManagerGlobal.java:480 —— 「… has leaked window …」抛出的位置。围绕它，你能摸出「客户端三本账」和「服务端窗口树」两边的清理时机（呼应 06 篇块 C）。

做什么

1写一个计数脚本：从 dump 里统计 WindowState / ActivityRecord / Task 的数量，按包名分组。

2造一个泄漏：Activity 里 show() 一个 Dialog 但 onDestroy 不做 dismiss，然后反复进出。观察三者的数量曲线。

3对比实验：正常 dismiss vs 不 dismiss，画两条曲线，找出「只增不减」的信号。

4扩大战果：把检测套到别的资源上——SurfaceControl 数、InputChannel 数、Session 名下的 window 计数（windowAddedLocked）。

交付物
  • leak-hound.py：跑一遍输出「可疑只增不减的窗口类对象」
  • 一个你亲手复现的泄漏案例（含最小 demo + dump 证据 + 曲线）
  • 一份「窗口类泄漏的三种成因 + 各自怎么查」
🐛 坑 别把「后台保留的 Task」当泄漏——这正是你在马老师 P1 作业里会看到的现象（后台 kill 后 AR/Task 还在）。先把「设计如此」和「真泄漏」分清，这题才算做对。
🧠 与 P1 的关系 做完 P1（存活策略）再做 L4（泄漏检测），你会同时掌握「什么叫正常的留存」和「什么叫异常的堆积」——这一对概念，是稳定性岗的入门门槛。

六、L5 时序图自动生成器（可视化 · 最好玩）

一句话 你 06 篇里的 addWindow → relayout → finishDraw 时序图是手画的；这题让机器从 trace 里自动画出来。

源码依据

WindowTracing.java:98 startTrace(pw) / :116 stopTrace(pw)；内部用 TraceBuffer mBuffer（:67 / :94）。对应命令：adb shell cmd window tracing start/stop。
（Winscope 用的就是这套 proto trace。）

做什么

1先手工抓一次：开 tracing → 启动一个 App → 关 tracing，拿到原始数据。先看懂它的格式（哪怕只是文本）。

2解析：把「时间戳 + 窗口 + 事件类型」抽成结构化数据。

3生成时序图：输出 Mermaid sequenceDiagram 或纯 HTML（你已有现成页面风格），参与者用【App / Session / WMS / SF】，事件按时间排。

4对照检验：拿自动生成的图和你 06 篇手画的图对比，找出你手画时遗漏或搞错的步骤——这才是本题真正的收获。

交付物
  • 一个 trace2seq.py：输入 trace，输出时序图
  • 至少两份自动生成的时序图（启动一个 App / 弹一个 Dialog）
  • 「手画图 vs 机器图」差异清单——这就是你 06 篇的勘误表
🐛 坑 ① proto trace 是二进制格式，先确认你拿到的是文本还是 proto，别一开始就去写 proto 解析器；② trace 里大量长尾事件会淹没主线，先做「只看关键事件的过滤器」，再加事件。

七、L6 输入命中预言机（进阶 · 闭环 05 篇）

一句话 给定窗口树 + 一个触摸坐标，预测事件会落到哪个窗口；然后用 dumpsys input 对答案。这是 05 篇的实操闭环。

源码依据（我已核实）

InputMonitor.java:270 populateInputWindowHandle(handle, …) —— 把窗口的触摸属性（touchable region / focusable / flags / 父子链）交给 InputDispatcher；
WindowState.java:3649 getTouchableRegion(Region outRegion)；:3713 subtractTouchExcludeRegionIfNeeded()（触摸排除区）。

做什么

1从 dumpsys input 的 window handle 列表里抽出每个窗口的：touchable region、layer、flags（是否 focusable / 是否 not touch modal）。

2实现命中测试：从最上层往下找第一个「包含该点 且 可触摸」的窗口。

3预测 vs 实测：用 input tap x y 真点一下，看事件实际归谁，对比你的预测。

4故意制造反例：加一个 FLAG_NOT_FOCUSABLE | FLAG_NOT_TOUCH_MODAL 的悬浮窗，看它是否只吃自己的区域。

交付物
  • hit-oracle.py：输入 dump + 坐标，输出预期归属窗口
  • ≥ 3 组对比（普通界面 / 有悬浮窗 / 有 IME）
  • 一份「预测错误原因分类」（touchable region 算错 / 排除区 / flag 理解错）
🧠 闭环价值 把 05 篇的「InputDispatcher 怎么找窗口」从描述变成你能算。以后遇到「点了没反应」「点错窗口」这类 bug，你的定位速度会快一个量级。

九、怎么算做完（硬指标）

#指标不达标的样子
1预测准：L1/L6 的预测与实测一致（不是「差不多」）「大体上对，个别差一点」——那就说明理解还不完整
2有代码：产物是可运行的东西，不是一份笔记只有 md 文档
3有差异记录：至少写下一处「我以为 X，实际 Y」全部一次做对（要么题目太简单，要么没认真预测）

最硬的一条 把项目产出写成文章。你已经有 00–06 篇，L1–L6 每个项目天然就是一篇：L1→Z 序篇、L2→dump 字段篇、L3→「如果我改了这行」、L4→窗口泄漏篇、L5→trace 篇、L6→命中测试篇。写完，你的知识就从「知道」变成了「资产」。
