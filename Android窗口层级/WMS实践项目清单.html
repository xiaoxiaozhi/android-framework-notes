〇、为什么「实验」不够，必须做项目

先认错：前面的路线图里给你的都是实验（dumpsys 看一眼、跟一遍堆栈），不是项目。两者差别很大：

实验项目
时长10 分钟几天到两周
产出一条命令的输出、一个「哦原来是这样」可交付的东西：patch / 工具 / 报告 / 功能
会暴露什么几乎没有你的全部知识断口——因为要动手改、要跑通
面试能不能说不能（人人都会）能（「我改过 X，现象是 Y，根因是 Z」）
对应岗位能力无「能改 + 能查」，正好是 B 岗的两个货币
类比 实验 = 看别人游泳的视频；项目 = 自己下水游一趟。WMS 的知识全在「运行时行为」上——不上手改一次，永远不知道自己哪块是空的。

马老师是怎么做的（这就是他课程有效的原因）

翻了一遍本地千里马知识库（850+ 篇），发现他的课程设计有个铁律：每 5–10 个视频就插一个「作业」，而且作业都以「产出物」结尾：

1-6 窗口层级树实战 ────────▶ 作业：自己独立绘制出层级窗口结构树 7-11 addWindow / relayout ──▶ 作业：绘制整个窗口添加的流程图 / trace 图 12-15 日志抓取平台 ─────────▶ 作业：跟着搭建，且可以控制 proto 日志开启 16-25 冻屏 + 闪黑实战 ──────▶ 作业：① 对剩下没有 remove 的图层进行 remove ② 找到/发现一个必现的系统闪黑问题并解决 32-36 activity 启动 ────────▶ 作业：做一个类「App 防沉迷」功能 42-49 动画 / 远程动画 ──────▶ 作业：自己实现简单窗口的远程动画 demo Focus 深入分析 ─────────────▶ 作业：按照案例自己分析一遍 ANR 横竖屏旋转深入分析 ─────────▶ 作业：实战解决小米桌面强制横屏问题
结论 他讲的内容和我们的 00–06 篇高度重合（窗口层级树、addWindow、relayout、finishDraw、动画、旋转），差别就在「有没有作业」。所以下面这套项目清单，就是把你已有的 00–06 篇知识接上作业。

二、P0 窗口树可视化器（热身，1–2 天）

目标：把 dumpsys 的一堆文本，变成一棵能一眼看懂的树。这是所有后续项目的基础工具——你以后每天都要看窗口树。

做什么

1写一个脚本（Python 最顺），拉取并解析：dumpsys window windows / dumpsys activity displays / dumpsys activity activities。

2输出成树：DisplayContent → DisplayArea 链 → Task → ActivityRecord → WindowState，每个节点带关键字段（mBaseLayer / mSubLayer / mFrame / isVisible / relayoutCalled / isDrawn）。

3加一个校验：按 layer 升序排列，看是不是和你 00–02 篇学的树结构、以及 建树模拟器的结果对得上。

4进阶：把输出做成 HTML（你已有现成页面风格），或直接在页面上高亮「刚新增的窗口」。

会碰到的卡点（这才是学到的部分）

  • dumpsys 输出格式在不同 Android 版本不一样，别写死正则，先 dump 下来人工看结构。
  • 为什么同一个 App 的 Activity 在 WindowToken 下面，而系统窗口在 DisplayArea.Tokens 下面？—— 回答不了就回去看 02 篇。
  • dumpsys activity displays 和 dumpsys window 两边的树不完全一样，弄清各看的是什么。
交付物
  • 一个可重复跑的脚本（window-tree.py 之类），输入 adb，输出树
  • 一棵真实窗口树的截图（普通手机 + 平板 density 各一张）
  • 一段自述：树里每个节点类型对应哪个类（带文件名）
🧠 自测 你的脚本能不能正确识别「这个 WindowState 是子窗口、它的父节点是另一个 WindowState 而不是 WindowToken」？—— 这一点答对，说明 02/06 篇真懂了。

三、P1 窗口消亡的三条路径（核心作业，3–5 天）★

这道题来自马老师的真实作业布置（原文：安卓Framework wms ams实战作业布置）。它之所以是最好的第一题，因为只要动手就能看到反直觉的现象，而解释这个现象必须把 WMS + AMS 一起串起来。

现象（马老师的学员首先发现的）

场景 A：在「最近任务」里上划干掉一个 App → 树里 Task / ActivityRecord / WindowState 全部移除 场景 B：App 在后台，用 adb shell kill <pid> 杀进程 → 树里 Task / ActivityRecord 还在，只有 WindowState 被移除 ← 反直觉！ 场景 C：App 在前台被 kill → ？自己测（这就是作业的第一问）

作业要求（马老师原题 + 我补的验收）

1多任务移除 vs 后台命令 kill，各自的移除是被哪个调用触发的？各自打堆栈分析差别。

2进程前台移除 vs 后台移除，区别是什么？同样用堆栈展示。

3（我补的）为什么后台 kill 之后 ActivityRecord 会「赖着不走」？它靠什么被回收？（提示：看 Task 的清理时机，和 AMS 的 cleanUpRemovedTaskLocked 一类逻辑）

怎么动手（不要一上来就翻源码）

1先复现：拿模拟器，在 dumpsys activity activities 里确认 Task=xxx。

2加打印：在 WindowState.removeIfPossible() / removeImmediately()、ActivityRecord 的移除路径、Task 的移除路径，各加一条带堆栈的 Slog（或开 ProtoLog）。

3三种场景各跑一遍，收集堆栈，比对调用链差异。

4画流程图：三条路径各自从哪里进入、在哪里分叉。

交付物
  • 三条路径的对比流程图（手画/Excalidraw 都行，要带类名+方法名）
  • 四个堆栈日志（多任务移除 / 后台 kill / 前台 kill / 正常 finish）
  • 一张表：场景 × 被移除的对象（Task / AR / WS）× 触发函数
🐛 常见翻车 只 dump 不打印堆栈 —— 那你只能看到「结果」，看不到「谁干的」。本作业的核心功夫在堆栈，马老师原文也强调「自己堆栈打印分析能力的锻炼」。
🧠 做成之后的收获 你会第一次真正分清 WindowState（窗口）/ ActivityRecord（页面记录）/ Task（任务栈）三者的生命周期不是绑在一起的。这一条认知直接对应 B 岗面试题 7。

四、P2 Bug 猎手：抓一个真实窗口 bug（1 周）★ 最有岗位价值

目标：完整走一遍「现象 → 复现 → 定位 → 根因 → 修复 → 验证」。这是 B 岗日常工作的全部内容，也是面试最能讲的部分。

从马老师案例库里选一个（四个都适合，按难度排）

#Bug难度学什么
1图库自由窗口划线框显示不全（马老师原文已给完整分析）★★SurfaceView 与 transparentRegionHint；SF 图层与 WMS 树的关系
2隐藏 TaskBar 后手势上滑冻屏（学员作业，aosp14）★★★冻屏类问题；输入与窗口可见性的联动
3横屏分屏黑边 / 分屏黑屏★★★分屏容器、旋转与布局
4壁纸闪黑（马老师原实战：wallpaper add/relayout/detach）★★★★壁纸窗口生命周期；Winscope 分析
📌 建议从 1 开始：它有完整参考分析，你可以「先自己分析 → 再对比原文」——这是最高效的学习方式（见第九章的「先做后看」）。

标准流程（每一步都要留证据）

1复现并录证据：复现步骤写成别人能照着做的 N 步；录屏 + 关键 dump。

2对比法定位：正常场景 vs 异常场景，比 dumpsys window windows 和 dumpsys SurfaceFlinger 的差异。这一招在马老师的图库案例里直接破了案。

3追到根因：差异字段是从哪来的？打堆栈找「谁设置的」。

4出 patch：至少 2 个方案，说明各自代价（马老师原文就给了「单独建 Layer」和「Freeform 模式直接置 0」两案）。

5验证 + 回归：修好后再跑一遍复现步骤，并自问「会不会伤到别的场景」。

交付物
  • 一份 Bug 报告：现象 / 复现步骤 / 对比证据 / 根因（带类名+行号）/ 修复 patch / 验证结果
  • 如果你能在工作中复现并修掉一个，这就是简历上最硬的一条

五、P3 造工具：窗口问题现场抓取器（1–2 周）★ 性价比最高

这道题直接来自马老师的课程项目：12-15 screenshot-dumpsys1~4「实战偶现窗口问题日志抓取平台项目」，作业是「跟着实战搭建，且可以控制 proto 相关日志开启」。

为什么这是性价比最高的 偶现问题（闪黑、冻屏、窗口跳一下）你手动抓不住——发生的时候你不在场。所以专业团队都靠常开的高频日志缓冲 + 出事时一键打包（事实上 Android 自己也是这么做的：WindowTracing / ProtoLog / event log）。这个工具做完，你以后所有 bug 都查得更快。

做什么

1掌握 ProtoLog / WindowTracing：adb shell cmd window tracing start / stop，以及 WindowTracing（可回放窗口树随时间的变化，排查层级/动画问题的第一神器）。

2学会动态开日志：不用重编 ROM 就能打开某个 tag 的日志（isLoggable / ProtoLog group 开关）。马老师专门有一篇 Android ProtoLog动态开启wm logging 讲这个。

3写一个一键打包脚本：按下就抓走——logcat（含 ring buffer）、dumpsys window/activity/input/SurfaceFlinger、Winscope trace、dumpsys dropbox、bugreportz 摘要，打成一个带时间戳的目录/zip。

4加一个环形缓冲思路：让系统后台一直保留最近 N 秒的关键日志，出问题立刻导出，而不是「等你去开日志时问题已经过去了」。

交付物
  • 一个 grab-window-state.sh（或 .ps1/.py），一条命令抓齐现场
  • ProtoLog 动态开关的操作说明 + 验证截图
  • 用这个工具抓到至少一个偶现问题的现场（哪怕是 P2 里那个 bug 的补充证据）
🐛 坑 ProtoLog 默认关闭，开了之后日志量巨大、可能拖慢系统——要能按 group 精细开关，这也是马老师作业强调「可以控制 proto 相关日志开启」的原因。

六、P4 改需求：Freeform / 隐藏系统窗口（2 周）

目标：从「看懂」到「能改」——需求驱动的系统定制，这是厂商/车机岗的日常。

两个候选需求（选一个，或都做）

需求要做的事难点 / 收获
A. 自由窗口 Freeform：给一个 App 加自由窗口模式 + 划线边框（Caption）开 freeform 支持；让 Activity 以自由窗口启动；给窗口加可拖拽边框（CaptionWindow / DecorCaptionView）会见到的坑：划线框画不全（就是 P2 的 bug 1）、Caption 在 aosp13/14 实现差异
B. 隐藏一个系统窗口：比如隐藏 aosp14 的 TaskBar找到该窗口的创建处（TaskbarActivityContext），做隐藏；然后解决由此引发的冻屏极致贴近真实工作：改需求 → 引入 bug → 自己收拾（就是 P2 的 bug 2 的来源）
交付物
  • 可运行的功能（录屏证明）
  • git diff 形式的完整 patch（能直接讲清每处改动为什么必要）
  • 一份「需求实现说明」：改了哪些文件、涉及 WMS / SystemUI / Launcher 哪几层
🧠 关键认知 系统定制的真实工作量不在「实现需求」，而在「需求带来的副作用」。你做完 B 就会体会到：隐藏一个窗口，为什么会把输入搞死——这一课的含金量比看十篇文章都高。

七、P5 综合：Display 多屏与旋转（2–3 周）

来源：马老师的 android framework Display屏幕相关实战作业探讨（单实体屏幕显示两个 Display 的内容）+ 横竖屏旋转深入分析。

三个子任务，难度递增

1单实体屏幕显示两个 Display：用 createVirtualDisplay + Presentation，或 WMS 侧的多 Display 方案，把两个 Display 的内容拼到一块物理屏上。先弄清 DisplayContent 与物理屏的对应关系。

2多屏异显触摸：第二个 Display 上的内容要能被正确触摸（Presentation 相关的 input 路由）。

3旋转与冻结：跟一遍 DisplayRotation.updateRotationUnchecked()，观察旋转期间屏幕是怎么被「冻住」（startFreezingDisplayLocked / stopFreezingDisplayLocked）等新方向首帧准备好的；然后尝试优化旋转闪一下的体验。

交付物
  • 方案说明（为什么这么设计、和原生多屏方案的差异）
  • 实现 + 录屏
  • 旋转过程的 Perfetto trace + 一份耗时分析
🔗 这一项目直接对应路线图阶段 3（布局 / Insets / 旋转），做完可以顺手写 07/08 篇。

八、交付物标准（怎么算「做完了」）

软件行业最容易自欺欺人的一句话是「我大概懂了」。下面四条是可检查的过关线：

#标准反例（不算做完）
1能复现：别人照着你的步骤能重现同样现象「我这里偶尔会」但写不出步骤
2有证据：dump 输出、堆栈、trace、录屏，至少两种只有结论没有日志
3能落到源码：根因能指到具体类 + 方法 + 行为「框架那里有个 bug」
4能讲给别人：不看笔记讲 5 分钟，别人能听懂自己讲着讲着绕回 dump 抄字段
额外一条（B 岗专用） 能把修复讲成「代价权衡」：为什么选方案 A 不选 B，A 会影响哪些场景。这是资深和普通的真正分界线。

九、怎么用马老师文章：先做后看

马老师那些文章是参考答案，不是课本。用错了顺序就没效果。

1只读「现象 + 复现步骤」部分，然后合上文章，自己动手分析。

2卡住了再回去看他的分析路径——重点看他「用了什么工具、按什么顺序怀疑」，而不是记结论。

3对比差异：我和他的分析差在哪一步？是知识缺口还是工具不熟？

4用自己的话重写一遍（写成你自己的文章）——你已经在写 00–06 篇了，把这个习惯用到项目上。

提醒 马老师文章的正文大量是图片，markdown 版只保留了文字，关键分析步骤（截图里的 dump 对比）看不到。所以两张路：① 打开知识库根目录的同名 HTML（有图，需联网）；② 自己动手 dump —— 后者反而收获更大。
注意 他的文章里很多是课程广告尾巴（链接、七件套专题），正文技术内容通常只占前 1/3～1/2，直接跳到「分析过程」和「作业要求」两段看即可。
