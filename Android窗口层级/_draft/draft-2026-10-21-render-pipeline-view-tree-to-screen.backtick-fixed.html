0.0先讲概念：屏幕、帧、树、队列

把 Android 渲染想成一条流水线：UI 线程把界面“录制”成命令清单，RenderThread 把命令清单交给 GPU 画进一块内存，SurfaceFlinger 把多块内存按 Z 序叠成一张图，HWC 再把这张图交给显示控制器逐行扫描到屏幕上。

这条流水线上没有“一个 View 直接对应屏幕上一块像素”这种事。View 只是 App 进程里的对象；真正跨进程流动的是 绘制命令、图形缓冲区 和 同步栅栏。把这三样东西看清楚，渲染链路就通了。

先记住三句话：
① View 树先被录制为 RenderNode / DisplayList 树，不是直接画到屏幕。
② 一个 Window 对应一个 Surface / BufferQueue；SurfaceFlinger 合成的是窗口级 Layer，不是一个个 View。
③ UI 线程负责“录制”，RenderThread 负责“回放与 GPU 提交”，SurfaceFlinger 与 HWC 负责“合成与上屏”。

先纠一个常见误解 “硬件加速”并不是说 View 直接由 GPU 画。准确地说：View 先在 UI 线程被录制为 DisplayList，RenderThread 再让 GPU 回放这些命令。所以 UI 线程的 onDraw 和 GPU 的绘制是两件事，中间隔着一次 RenderNode 树的同步。

两棵树：View 树 与 RenderNode 树

App 侧其实有两棵“同构”的树。第一棵是大家熟悉的 View 树，负责结构与布局；第二棵是 RenderNode 树，负责绘制命令与绘制属性。每个参与硬件加速绘制的 View 都有一个 RenderNode，父 View 的 DisplayList 里保存的是对子 RenderNode 的引用，不是把子 View 的命令复制一遍。

父 DisplayList 里的一条命令：
  drawRenderNode(child.mRenderNode)        // 只存引用，不复制子命令

RenderNode 树不是另一份 UI 结构，它是 View 树的“绘制投影”：只有参与绘制的 View 才有非空 DisplayList；不可见、被裁剪、没有 invalidate 的子树可以整棵复用。也正因为如此，onDraw 不需要每帧执行——只有失效的 View 才重新录制。

另一棵树：SurfaceFlinger 的 Layer 树

SurfaceFlinger 完全不知道 TextView、RecyclerView 这些对象。它看到的是一棵 Layer 树：每个 Window 通常对应一个 BufferLayer，Task/DisplayArea 等对应容器 Layer。App 的一整棵 View 树，最终只变成一块（或少数几块）窗口级 buffer，作为 Layer 的内容参与合成。

surfaceflinger 进程：Layer 树
└─ RootLayer
   ├─ DisplayArea（容器，无 buffer）
   │  ├─ Task（容器，无 buffer）
   │  │  └─ BufferLayer（Window A）        // 一块窗口 buffer，对应 App 的一整棵 View 树
   │  └─ BufferLayer（Window B）           // 另一个窗口，另一块 buffer
   └─ BufferLayer（StatusBar / NavBar 等）

关键边界 View 树在 App 进程内被“压平”成一块窗口 buffer；SurfaceFlinger 只合成窗口级 Layer。例外是 SurfaceView、TextureView、PopupWindow 等会引入额外的 Surface/Layer，所以一个 Activity 可能对应多个 Layer，但绝不会是“一个 View 一个 Layer”。

一条队列：BufferQueue

App 和 SurfaceFlinger 之间不是直接传 Bitmap，而是通过 BufferQueue 传 GraphicBuffer 的槽位（slot）。生产者 dequeue 一个空闲 slot，GPU 画进去，再 queue 回去；消费者 acquire 最新的 buffer，合成完再 release。每个 buffer 带 acquire/release fence，保证 GPU、SF、HWC 不会读到“还没画完”或“已经被复用”的内存。

动作谁做状态变化关键同步
dequeueBufferApp（EGL/ANativeWindow）FREE → DEQUEUED没有空闲 slot 时阻塞，形成背压
queueBufferAppDEQUEUED → QUEUED带 acquire fence，表示 GPU 何时写完
acquireBufferSurfaceFlingerQUEUED → ACQUIRED等待 acquire fence 生效
releaseBufferSurfaceFlingerACQUIRED → FREE带 release fence，表示显示何时用完

二初始化：Renderer、Surface 与 BLASTBufferQueue

渲染链路不是从 onDraw 开始的，而是从 Window 拿到 SurfaceControl、ViewRootImpl 创建 Renderer 开始的。顺序很重要：先有系统侧的 Layer 身份（SurfaceControl），再有 App 侧的 BufferQueue/Surface，最后 Renderer 才能把 EGLSurface 绑到这块 Surface 上。

入口在 ViewRootImpl.setView()（ViewRootImpl.java:993）。它在挂载 View 树时调用 enableHardwareAcceleration(attrs)，决定这个窗口走硬件加速还是软件绘制。硬件加速路径会创建一个 ThreadedRenderer，而 ThreadedRenderer 的父类 HardwareRenderer 会在构造时创建 native 侧的 RenderProxy 和根 RenderNode。

ViewRootImpl.java:1409-1457（裁剪）
private void enableHardwareAcceleration(WindowManager.LayoutParams attrs) {
    mAttachInfo.mHardwareAccelerated = false;
    mAttachInfo.mHardwareAccelerationRequested = false;

    // 兼容模式（mTranslator != null）直接放弃硬件加速
    if (mTranslator != null) return;

    final boolean hardwareAccelerated =
            (attrs.flags & WindowManager.LayoutParams.FLAG_HARDWARE_ACCELERATED) != 0;

    if (hardwareAccelerated) {
        final boolean forceHwAccelerated = (attrs.privateFlags &
                WindowManager.LayoutParams.PRIVATE_FLAG_FORCE_HARDWARE_ACCELERATED) != 0;

        if (ThreadedRenderer.sRendererEnabled || forceHwAccelerated) {
            if (mAttachInfo.mThreadedRenderer != null) {
                mAttachInfo.mThreadedRenderer.destroy();
            }

            final Rect insets = attrs.surfaceInsets;
            final boolean hasSurfaceInsets = insets.left != 0 || insets.right != 0
                    || insets.top != 0 || insets.bottom != 0;
            final boolean translucent = attrs.format != PixelFormat.OPAQUE || hasSurfaceInsets;

            // 【注】这里只是创建 Java 侧 Renderer；native RenderThread 是进程级单例
            mAttachInfo.mThreadedRenderer = ThreadedRenderer.create(mContext, translucent,
                    attrs.getTitle().toString());
            // … 省略：颜色模式、ForceDark、Observer 注册（与本段主线无关）
            if (mAttachInfo.mThreadedRenderer != null) {
                mAttachInfo.mHardwareAccelerated =
                        mAttachInfo.mHardwareAccelerationRequested = true;
                // 【注】把系统侧 Layer 句柄交给 RenderThread，后续事务/属性都走它
                mAttachInfo.mThreadedRenderer.setSurfaceControl(mSurfaceControl);
            }
        }
    }
}

这段在干什么：判断窗口是否允许硬件加速；允许就销毁旧 Renderer、创建新的 ThreadedRenderer，并把 SurfaceControl 交给它。此时还没有真正的 Surface，只有系统侧的 Layer 身份。

设计意图：Renderer 的生命周期跟着 Window/ViewRootImpl 走，而不是跟着某个 View 走；一个窗口一个 Renderer、一个 Surface、一个 BufferQueue，这是后面“窗口级合成”的基础。

实战问题：如果 ThreadedRenderer.sRendererEnabled 为 false（低端机/系统进程策略），或者窗口没带 FLAG_HARDWARE_ACCELERATED，就会落到 drawSoftware() 路径，onDraw 直接画到 Surface.lockCanvas() 返回的 Canvas 上。此时本文后面的 RenderNode/RenderThread 链路不成立，排障时先确认 ViewRootImpl.isHardwareEnabled()。

主线位置：上游 ViewRootImpl#setView()；本方法 ViewRootImpl#enableHardwareAcceleration()；下游 ThreadedRenderer#create() 与 HardwareRenderer 构造。

Surface 从哪里来：BLASTBufferQueue

有了 SurfaceControl，还需要一个 App 能绘制的 Surface。Android 12 走 BLASTBufferQueue：它包住 SurfaceControl，创建一条 BufferQueue，并导出一个生产者 Surface。ViewRootImpl.getOrCreateBLASTSurface() 就是这条路径。

ViewRootImpl.java:1958-1978
Surface getOrCreateBLASTSurface() {
    if (!mSurfaceControl.isValid()) {
        return null;
    }

    Surface ret = null;
    if (mBlastBufferQueue == null) {
        // 【注】BLASTBufferQueue 同时持有 SurfaceControl 和 BufferQueue
        mBlastBufferQueue = new BLASTBufferQueue(mTag, mSurfaceControl,
            mSurfaceSize.x, mSurfaceSize.y,
            mWindowAttributes.format);
        // 【注】createSurface() 返回生产者端；SF 侧对应一个 BufferLayer
        ret = mBlastBufferQueue.createSurface();
    } else {
        // 尺寸/格式变化时只更新队列参数，不重新创建 Surface
        mBlastBufferQueue.update(mSurfaceControl,
            mSurfaceSize.x, mSurfaceSize.y,
            mWindowAttributes.format);
    }

    return ret;
}

这段在干什么：首次调用创建 BLASTBufferQueue 和 Surface；后续只更新尺寸/格式。Surface 是生产者句柄，真正跨进程的 Layer 仍是 mSurfaceControl 指向的那个。

设计意图：把“Layer 的身份/属性”和“像素队列”分开。SurfaceControl 事务负责位置、大小、Z、可见性；BufferQueue 负责 buffer 的生产与消费。BLAST 还把 buffer 提交与事务同步，避免“图层已经移动、buffer 还是旧尺寸”的错位。

实战问题：getOrCreateBLASTSurface() 返回 null 或 Surface.isValid() == false 时，ViewRootImpl.draw() 会在第一行直接返回（ViewRootImpl.java:4283），表现为“窗口在、内容不更新”。这类问题先查 dumpsys SurfaceFlinger --list 有没有对应 Layer，再查 dumpsys window 里该窗口的 SurfaceControl 是否有效。

主线位置：上游 ViewRootImpl#setView() / relayoutWindow 结果；本方法 ViewRootImpl#getOrCreateBLASTSurface()；下游 HardwareRenderer#setSurface() → CanvasContext#setSurface()。

Renderer 的 native 侧：RenderProxy、CanvasContext、RenderThread

ThreadedRenderer.create() 只是 Java 包装。真正的 native 对象在 HardwareRenderer 构造时创建：HardwareRenderer.java:167 的 mNativeProxy = nCreateProxy(!mOpaque, mRootNode.mNativeRenderNode)。RenderProxy 持有一个 DrawFrameTask 和一个 CanvasContext，所有绘制请求都通过 RenderProxy 投递到进程级 RenderThread。

为什么一个进程只有一条 RenderThread：所有窗口共享同一个 GPU 上下文和资源缓存（字体、纹理、Path），这样纹理上传、Shader 编译、Skia 缓存可以复用；代价是任何一个窗口的 RenderThread 任务阻塞，都可能拖慢同进程的其他窗口。CanvasContext 则按窗口隔离，避免不同 Surface 的状态互相污染。

Surface 绑定时发生什么：HardwareRenderer.setSurface() 调 nSetSurface，native 侧最终到 CanvasContext::setSurface()（CanvasContext.cpp:173）。它把 ANativeWindow 包成 ReliableSurface，设置 dequeue 超时，然后 setupPipelineSurface() 让 SkiaOpenGLPipeline 创建/更新 EGLSurface。从这一刻起，EGL 的 back buffer 就来自这个窗口的 BufferQueue。

CanvasContext.cpp:173-187
void CanvasContext::setSurface(ANativeWindow* window, bool enableTimeout) {
    ATRACE_CALL();

    if (window) {
        // 【注】ReliableSurface 负责 dequeue/queue 的错误恢复与超时
        mNativeSurface = std::make_unique<ReliableSurface>(window);
        mNativeSurface->init();
        if (enableTimeout) {
            // 【注】4s 是 dequeueBuffer 的兜底超时，不是帧预算
            ANativeWindow_setDequeueTimeout(window, 4000_ms);
        }
    } else {
        mNativeSurface = nullptr;
    }
    setupPipelineSurface();
}

这段在干什么：把 Java Surface 背后的 ANativeWindow 交给 RT，并重建渲染管线与 EGLSurface。setupPipelineSurface() 会调用 mRenderPipeline->setSurface(...)，失败则 hasSurface 为 false，后续 prepareTree 会把这一帧标记为 skipped。

设计意图：Surface 可能因为窗口尺寸变化、转屏、WMS relayout 而更换；CanvasContext 要能热替换 EGLSurface，而不是重建整个 RenderThread。ReliableSurface 把 dequeue/queue 的异常集中处理，避免每个调用点都写错误恢复。

实战问题：ANativeWindow_setDequeueTimeout(4000ms) 说明 dequeue 卡住时不会立刻失败，而是可能让 RT 停 4 秒；这段时间 UI 线程可能继续跑，但 buffer 很快被填满，最终 UI 线程在 syncAndDrawFrame 里被背压住。看到“应用突然卡几秒又恢复”，要查 dequeueBuffer 是否超时、SF 是否停止消费。

为什么“掉帧”不等于“GPU 慢”

VSync 是截止时间，不是“GPU 画完的时间”。一帧的预算通常是一个 refresh interval（60Hz 约 16.6ms，120Hz 约 8.3ms），但这条预算要分给 UI 线程、RenderThread、SurfaceFlinger 和 HWC。任何一段超时，都会让这一帧错过下一个 VSync。

现象最可能超时的阶段先看什么

DrawFrames 很长，dequeueBuffer 也长RenderThread/GPU 或 BufferQueue 背压Perfetto 的 DrawFrames、dequeueBuffer、queueBuffer
onMessageRefresh 很长，HwcPresentDisplay 异常SurfaceFlinger 合成或 HWCdumpsys SurfaceFlinger、--latency、Winscope
UI 和 RT 都不长，但显示仍旧SF 没 latch、HWC 没 present、buffer 被丢弃dumpsys SurfaceFlinger 的 Layer/Buffer 状态

VSync 的相位 App 的 VSync 与 SurfaceFlinger 的 VSync 通常有相位差：SF 先被唤醒，准备合成；App 稍后收到自己的 VSync，开始录制下一帧。这个相位差是流水线能并行工作的前提，也是“为什么 App 这一帧画完不一定马上显示”的原因。

设计意图：GPU 可能还没画完，queue 时带的 acquire fence 就是“完成凭证”。SF 不能直接读 buffer，必须等 fence；否则会读到半张图。mStateLock 保护 Layer 状态，避免 latch 与事务提交竞争。

实战问题：如果 fenceHasSignaled() 长期不满足，说明 GPU/生产者没有完成，或者 fence 出错；表现为 SF 一直不更新该 Layer。用 dumpsys SurfaceFlinger 看 Layer 的 ActiveBuffer/QueuedFrames，用 Perfetto 看 fenceHasSignaled 和 GPU 完成时间。

主线位置：上游 SurfaceFlinger#onMessageInvalidate() / handlePageFlip()；本方法 BufferLayer#latchBuffer()；下游 SurfaceFlinger#onMessageRefresh() 与 CompositionEngine#present()。

五个常见误区

  1. “View 树直接变成 SurfaceFlinger 的 Layer 树。” 错。View 树先被压平成一块窗口 buffer；SF 只看到窗口级 Layer。
  2. “onDraw 每帧都会执行。” 错。只有 invalidate 的 View 才重录；有效的 DisplayList 会跨帧复用。
  3. “GPU 画完就上屏。” 错。GPU 画完只是 queue buffer；还要 SF latch、合成、HWC present、显示扫描。
  4. “120Hz 屏幕就是每秒渲染 120 帧。” 错。120Hz 是 VSync 频率；实际帧率取决于每帧能否在 deadline 前完成。
  5. “invalidate() 会立刻 draw。” 错。它只是标记失效并安排下一次 traversal；真正绘制在下一个 VSync 回调里。

设计取舍：Android 选择 retained mode + 多缓冲 + 独立合成器，是为了在“UI 结构复杂、窗口多、硬件差异大”的前提下，让 App 和系统解耦。代价是链路长、延迟高、排障需要跨进程看时间线；收益是局部更新、并行流水线、HWC 硬件叠加和统一合成。

🧠 自测：4 个问题

1. 为什么 onDraw 不是每帧都执行？什么情况下会重新录制？
因为硬件加速走 retained mode：每个 View 的绘制命令保存在 RenderNode 的 DisplayList 里。只有 PFLAG_DRAWING_CACHE_VALID 失效、RenderNode 没有 DisplayList、或 mRecreateDisplayList 为 true 时，updateDisplayListIfDirty() 才会重新 beginRecording() 并调用 draw()。普通 invalidate 只标记失效并安排下一次 traversal；如果整棵树都没有失效，甚至 performDraw() 会跳过绘制。
2. UI 线程在 syncAndDrawFrame() 里等什么？为什么不等 GPU 画完？
它等的是 DrawFrameTask#syncFrameState() 完成：RenderNode 树、纹理、动画状态同步到 RT，UI 线程就可以安全地准备下一帧。GPU 绘制在 CanvasContext#draw() 里继续，UI 线程不等待；否则流水线会退化成串行。只有在纹理缓存不足、prepareTextures 返回 false 时，UI 线程才会被留到 RT 画完。
3. 为什么说“View 树不是 SurfaceFlinger 的 Layer 树”？一个 Activity 会有几个 Layer？
SurfaceFlinger 只认识 SurfaceControl/Layer，不认识 View。一个 Window 通常对应一个 BufferLayer，App 的一整棵 View 树被压平成一块窗口 buffer。一个 Activity 至少有一个主 Window Layer；如果用了 SurfaceView、TextureView、PopupWindow、Dialog 等，会额外创建 Surface/Layer。所以是“一个 Window 一个 Layer”，不是“一个 View 一个 Layer”。
4. 用户说“这一帧是黑的/旧的”，你怎么用 trace 和 dumpsys 定位是哪一段的问题？
先看 App 侧：dumpsys gfxinfo <pkg> framestats 是否有 Draw/Sync 异常；Perfetto 看 Choreographer#doFrame、DrawFrames、dequeueBuffer。再看 SF：dumpsys SurfaceFlinger --list 确认 Layer 存在，dumpsys SurfaceFlinger 看 ActiveBuffer/QueuedFrames/fence；Perfetto 看 latchBuffer、onMessageRefresh、HwcPresentDisplay。如果 App 正常 queue、SF 正常 latch、HWC 正常 present，但屏幕仍旧，查显示/背光/刷新率或 Layer 可见性。
