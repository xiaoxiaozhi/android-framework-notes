一、全景：为什么需要 Binder，一次调用穿过哪几层

前面十篇（窗口层级 00–09）里，你反复遇到这样一行：

例子：06 篇里的一次跨进程
res = mWindowSession.addToDisplayAsUser(mWindow, mWindowAttributes, ...);
// ↑ 这行看起来像普通 Java 方法调用，实际上：
//   它把参数序列化 → 交给内核 → 唤醒 system_server 的一个 Binder 线程 →
//   在 WMS 里执行 addWindow → 再把结果序列化回来 → 唤醒当前线程

整条链上的每一跳，都用同一种机制。这篇就是把那个"看起来像普通方法调用"的黑箱拆开。

为什么不直接用 Linux 已有的 IPC？

方案问题
管道 / FIFO单向、无"服务"概念，无法直接调用对方的方法
Socket / Unix Socket两次拷贝（用户→内核→用户）；没有身份传递，安全靠自己实现
共享内存最快，但无同步机制、无"谁在调用"的身份，安全漏洞多
Binder一次拷贝（内核做地址映射）+ 内核携带调用者 UID/PID（不可伪造）+ 面向对象的"调方法"语义
一句话 Binder 的设计目标是三件事同时满足：快（一次拷贝）、安全（内核带身份）、好用（像调本地方法）。这三条决定了它在 Android 里无可替代。

类比 把 Binder 想象成公司的内部邮件系统：
· 你要给隔壁部门发一份表单 —— 序列化（把你脑子里的内容写成标准格式）；
· 前台（内核驱动）负责转交，并且在信封上盖章写上你的工号（UID/PID，不可伪造）；
· 对方部门有个专职收件员轮着班收信（Binder 线程池）；
· 收件员把表单还原成对方能看懂的形式，交给具体经办人（你的服务实现）。

二、客户端路径：BinderProxy 与 Java 侧代理

客户端手里拿到的"服务对象"，实际上是一个代理。理解这个代理的身份，是理解 Binder 的第一步。

块 A：BinderProxy 是什么（BinderProxy.java:48 / 458）

BinderProxy.java:48、458、516
public final class BinderProxy implements IBinder {
    // ① 它是"远端服务的本地代言人"：实现了 IBinder 接口，
    //    但所有方法最终都转成跨进程调用

    private BinderProxy(long nativeData) {
        mNativeData = nativeData;
        // ② 只持有 native 层的指针（BpBinder）：Java 侧不关心"怎么发"，
        //    只负责"发什么"——真正的通信在 native 层
    }

    public boolean transact(int code, Parcel data, Parcel reply, int flags)
            throws RemoteException {
        Binder.checkParcel(this, code, data, "Unreasonably large binder buffer");
        // ③ ★ 先查大小：Binder 事务有硬上限（约 1MB 的缓冲区），
        //    超了就在这里抛 TransactionTooLargeException —— 
        //    这是"传大 Bitmap 崩溃"的源头

        if (mWarnOnBlocking && ((flags & FLAG_ONEWAY) == 0)
                && Binder.sWarnOnBlockingOnCurrentThread.get()) {
            // ④ 提示：从"不该阻塞的进程"发出同步调用时打个警告。
            //    典型场景是 system_server 调 App（应一律 oneway，否则 App 卡住会反拖系统）
            Log.w(Binder.TAG, "Outgoing transactions from this process must be FLAG_ONEWAY");
        }
        // … 省略：tracing 埋点、最终调 transactNative（native 方法）
    }
}

这段在干什么：Java 侧的代理——检查参数大小、给可疑的阻塞调用发警告，然后把活交给 native。

设计意图：Java 层只做"策略"，不做"机制"。大小检查、阻塞警告、tracing 这些是 Java 层能做得更好（能拿到调用栈、能读系统属性）的事；而真正的数据搬运在 native 层（靠近内核、无 GC 干扰）。这是 Android 里很典型的分层原则。

🐛 实战 TransactionTooLargeException。因果：Binder 事务缓冲区约 1MB，且这个额度是整个进程共享的（不是每次调用 1MB）——所以并发调用多时更容易超。怎么查：崩溃栈里看是不是 Binder.checkParcel；排查传参里有没有大对象（Bitmap 应走 ashmem、文件应传 fd）。证据：Binder.checkParcel 抛错的文案就是 "Unreasonably large binder buffer"。

块 B：本地调用不出门（Binder.java:1057）

Binder.java:1057-1068
public final boolean transact(int code, @NonNull Parcel data, @Nullable Parcel reply,
        int flags) throws RemoteException {
    if (data != null) {
        data.setDataPosition(0);
        // ① 读指针归零：调用方可能刚写完数据，位置在末尾
    }
    boolean r = onTransact(code, data, reply, flags);
    // ② ★ 注意：这里直接调 onTransact，没有走任何 IPC！
    //    因为 Binder（基类）代表"服务端对象本身"——
    //    同一个进程内调用自己的服务时，就是一次普通函数调用
    //    （"本地调用不出门"：省掉序列化/内核往返）
    if (reply != null) {
        reply.setDataPosition(0);
    }
    return r;
}

这段在干什么：Binder 基类的 transact 直接调 onTransact——本地直通。

设计意图：统一接口，自动优化。客户端代码永远写 xxx.transact(...) 或 AIDL 生成的代理方法，不需要知道对面是本地还是远端。如果是本地对象（Binder），就直通；如果是代理（BinderProxy），就走 IPC。这让"服务在本进程/在别的进程"对调用方透明——这也是为什么有些 Binder 调用在 trace 里看不到跨进程痕迹。

🧠 思考（单块） 既然 Binder.transact 是直通 onTransact，那么同一个服务对象被 另一个进程调用时，走的是哪个 transact？提示：另一个进程手里拿到的是 BinderProxy 还是 Binder？这解释了两个类为什么必须实现同一个 IBinder 接口。

三、服务端路径：Binder.execTransact 与 onTransact

服务端的入口不在 Java 代码里直接发起——它由 Binder 线程从 native 层唤醒，回调进 Java。

块 C：execTransact——native 回调进 Java 的落点（Binder.java:1136 / 1149）

Binder.java:1136-1200（裁剪）
private boolean execTransact(int code, long dataObj, long replyObj, int flags) {
    // ① 这个方法由 JNI 调用（见第四节），参数是 native 传来的"裸指针编码"
    final int callingUid = Binder.getCallingUid();
    // ② ★ 调用者身份从哪来？不是参数传的，是从当前线程的 TLS 里读的——
    //    这个值由 native 层在收到事务时从驱动拿到并写入。
    //    ★ 这是 Binder 安全模型的基石：UID 由内核提供，调用方无法伪造

    final long origWorkSource = ThreadLocalWorkSource.setUid(callingUid);
    try {
        return execTransactInternal(code, dataObj, replyObj, flags, callingUid);
    } finally {
        ThreadLocalWorkSource.restore(origWorkSource);
    }
}

private boolean execTransactInternal(int code, long dataObj, long replyObj,
        int flags, int callingUid) {
    Parcel data = Parcel.obtain(dataObj);
    Parcel reply = Parcel.obtain(replyObj);
    // ③ 从 native 指针包装出两个 Parcel：data 是请求，reply 是待写的回复
    //    注释里说得很清楚："we just got these from an IPC, so we'll just call it directly"
    //    —— 不重新走 transact，因为数据已经是序列化好的

    boolean res;
    final boolean tracingEnabled = Binder.isTracingEnabled();
    try {
        // … 省略：HeavyHitterWatcher（高频调用监控）、systrace 埋点
        res = onTransact(code, data, reply, flags);
        // ④ ★★ 进入你写的（或 AIDL 生成的）服务实现
        //    —— 到这里，"跨进程"就彻底隐身了，剩下的全是普通 Java 逻辑
    } catch (RemoteException e) {
        // … 省略：只是打日志，不向调用方抛（错误通过返回值/异常码传回）
    } catch (RuntimeException e) {
        // … 省略：本地异常转成异常码写进 reply，由调用方 rethrow
    } finally {
        // … 省略：Parcel.recycle()、释放 TLS、写回 reply 头部
    }
    return res;
}

这段在干什么：从 native 指针包装出 Parcel，读出调用者 UID，然后把控制权交给 onTransact（真正的服务实现）。

设计意图：身份来自 TLS 而非参数。如果 UID 是参数传的，任何进程都能冒充别人调用特权服务。现在 UID 由内核在事务到达时写入线程的 TLS，Java 层只是读——这个设计让"权限检查"变得可信（这也是 checkCallingPermission 系列 API 的根基）。

🐛 实战 服务端抛异常，客户端收到奇怪结果。因果：execTransactInternal 的 catch 分支把异常转成"异常码 + 序列化的异常信息"写进 reply；客户端侧读到异常码再重新抛出 Method.Exceptions。关键差异：如果是 oneway（flags & FLAG_ONEWAY），服务端抛的异常会静默消失（注释原文："If the call was FLAG_ONEWAY then these exceptions disappear into the ether"）。怎么查：服务端加日志；开 Binder 的 tracing（Binder.isTracingEnabled() 那条路径）。
🧠 思考（需结合：块 B、块 C） 块 B 里本地调用直接 onTransact，块 C 里远端调用也最终落到 onTransact。两条路都汇聚到同一个方法——那么服务实现里写的 Binder.getCallingUid()，在本地调用时会返回什么？这解释了一个常见陷阱：为什么有些服务必须检查"是不是本进程调用"。

四、JNI 层：JavaBBinder 打通两个世界

JNI 这一层的任务是：让 C++ 的 BBinder 能调用 Java 的方法，以及反向。所有"魔法"都在这里。

块 D：JavaBBinder 是个 C++ 对象，但握着 Java 引用（android_util_Binder.cpp:340）

android_util_Binder.cpp:340-360、377-410（裁剪）
class JavaBBinder : public BBinder
{
public:
    JavaBBinder(JNIEnv* env, jobject /* Java Binder */ object)
        : mVM(jnienv_to_javavm(env)), mObject(env->NewGlobalRef(object))
        // ① ★ 关键：持有一个 Java Binder 对象的全局引用。
        //    所以 JavaBBinder 是"Java 服务对象的 C++ 化身"——
        //    native 层收到事务后，靠这个引用来回调 Java
    { }

    bool checkSubclass(const void* subclassID) const
    { return subclassID == &gBinderOffsets; }
    // ② 身份校验：确认这个对象确实是从 Java Binder 包装来的

    virtual status_t onTransact(uint32_t code, const Parcel& data, Parcel* reply,
            uint32_t flags = 0) {
        // … 省略：descriptor 校验、权限检查（mObject 是 Java 的）
        jboolean res = env->CallBooleanMethod(mObject, gBinderOffsets.mExecTransact,
        // ③ ★★ 全世界最关键的一行：从 C++ 调回 Java！
        //    调用的是 Java Binder.execTransact（第三节块 C）——
        //    跨进程的"最后一跳"就在这里完成
                (jint)code, (jlong)(uintptr_t)&data, (jlong)(uintptr_t)reply, (jint)flags);
        // ④ 参数传的是 Parcel 的裸指针（编码成 jlong）——
        //    Java 侧 Parcel.obtain(dataObj) 再包装回来（块 C 的 ③）
        //    ★ 这个指针传递技巧避免了数据再拷贝一次
        // … 省略：异常处理、返回值转换
    }
};

这段在干什么：JavaBBinder 是 Java 服务对象在 native 层的"影子"，它收到事务后用 CallBooleanMethod 回调 Java 的 execTransact。

设计意图：为什么要造一个 C++ 影子对象。因为 Binder 的 native 框架（BBinder）是 C++ 的，而服务实现是 Java 的。JavaBBinder 作为适配器：对 native 侧它是个正常的 BBinder（能被 IPCThreadState 处理），对 Java 侧它握着 mObject 能回调。没有这一层，Java 服务根本接不到 native 分发过来的事务。

🐛 实战 服务端崩溃栈里出现 native 帧看不懂。因果：Java 服务在 onTransact 里抛异常时，异常要穿过 JNI 边界回到 native，再由 native 写进 reply。中间任何一环出问题（如 JNI 局部引用溢出）都会表现为"莫名其妙的 native crash"。怎么查：看 tombstone 里有没有 JavaBBinder::onTransact 帧；gcIfManyNewRefs 相关日志（JNI 引用过多会主动 GC）。

五、Native 层：IPCThreadState 与驱动的对话

这是"真正的通信"发生的地方。IPCThreadState 是每个线程一份的（名字里的 ThreadState 就是这个意思），它负责把命令写给驱动、把结果读回来。

块 F：transact——发起一次调用（IPCThreadState.cpp:685）

IPCThreadState.cpp:685-730（裁剪）
status_t IPCThreadState::transact(int32_t handle,
                                  uint32_t code, const Parcel& data,
                                  Parcel* reply, uint32_t flags)
{
    status_t err;
    flags |= TF_ACCEPT_FDS;
    // ① 默认接受文件描述符传递（fd 能跨进程传是 Binder 的重要能力）

    // … 省略：事务日志（IF_LOG_TRANSACTIONS）

    err = writeTransactionData(BC_TRANSACTION, flags, handle, code, data, nullptr);
    // ② 把命令写进 mOut 缓冲区（用户态缓冲区，还没到内核）
    //    命令码 BC_TRANSACTION = "我要发一个事务"

    if ((flags & TF_ONE_WAY) == 0) {
        // ③ ★ oneway 的分水岭：非 oneway 才等回复
        if (reply) {
            err = waitForResponse(nullptr, &acquireResult);
            // ④ 阻塞等待：talkWithDriver 会把自己挂起，
            //    直到驱动唤醒它并送来 BR_REPLY
        }
    } else {
        // ⑤ oneway：写完就走，不等回复（异步）
        err = waitForResponse(nullptr, &acquireResult);
        //    但注意：仍要等 BR_TRANSACTION_COMPLETE——
        //    "驱动已收下"这个回执，否则缓冲区可能被复用覆盖
    }
    return err;
}

这段在干什么：把事务命令写入缓冲区，然后根据是否 oneway 决定等不等回复。

设计意图：oneway 也要等"已收下"回执。这是个容易误解的点：oneway 是"不等业务结果"，但必须等驱动确认数据已被取走。否则函数返回后调用方复用缓冲区，就会覆盖掉还没送达的数据——数据会被悄悄改坏。

🐛 实战 主线程调 Binder 卡住 → ANR。因果：非 oneway 调用会 waitForResponse 阻塞当前线程。如果对端服务卡住（或它自己又在等第三个服务），当前线程就一直等。怎么查：ANR trace 里看主线程栈有没有停在 IPCThreadState::waitForResponse 或 BinderProxy.transact；再用 dumpsys 看对端服务所在进程的状态。

块 G：talkWithDriver——与内核的对话（IPCThreadState.cpp:975）

IPCThreadState.cpp:975-1040（裁剪）
status_t IPCThreadState::talkWithDriver(bool doReceive)
{
    if (mProcess->mDriverFD < 0) {
        return -EBADF;
        // ① 驱动没打开就报错（进程初始化失败/被 seccomp 拦）
    }

    binder_write_read bwr;
    // ② ★ 这个结构体就是与内核的"信封"：
    //    write_buffer 放我要发的命令，read_buffer 收内核给我的命令

    const bool needRead = mIn.dataPosition() >= mIn.dataSize();
    // ③ 输入缓冲区读完了吗？决定这次要不要顺便读

    const size_t outAvail = (!doReceive || needRead) ? mOut.dataSize() : 0;
    bwr.write_size = outAvail;
    bwr.write_buffer = (uintptr_t)mOut.data();
    // ④ 填写待写数据（就是我刚放进去的 BC_TRANSACTION）

    if (doReceive && needRead) {
        bwr.read_size = mIn.dataCapacity();
        bwr.read_buffer = (uintptr_t)mIn.data();
    } else {
        bwr.read_size = 0;
        bwr.read_buffer = 0;
    }
    // ⑤ 填写待读缓冲区（若这次要收）

    // … 省略：do { ioctl(mProcess->mDriverFD, BINDER_WRITE_READ, &bwr); } while (err == -EINTR);
    // ⑥ ★★ 就是对驱动的一次 ioctl —— 真正的"跨进程"发生在这一行之内：
    //    内核里，binder 驱动根据 handle 找到目标进程，
    //    把数据复制进目标进程的缓冲区，并唤醒它的一个 Binder 线程
    //    （如果 read_size > 0 而目标没有数据可给，这里会阻塞睡眠）
    // … 省略：解析 bwr 返回的 consumed 值，更新 mOut/mIn 指针
}

这段在干什么：填好"信封"（binder_write_read），调用 ioctl(BINDER_WRITE_READ) 与驱动交互——这一行之内完成了跨进程数据传递。

设计意图：读写合一减少系统调用。如果是"写一次、读一次"两次 ioctl，开销翻倍。binder_write_read 让一次系统调用同时完成"提交我的请求 + 收下给我的命令"，这在同步调用（发完就等回复）场景下正好匹配。

一次拷贝的真相 驱动做的是 copy_from_user（把发送方数据拷进内核缓冲区）→ 目标进程读时通过 mmap 的映射直接访问内核缓冲区（copy_to_user 被省掉）。对比 Socket 的"用户→内核→用户"两次拷贝，Binder 省掉了一次。这也是为什么 Binder 事务大小受限——内核为每个进程预映射了一块固定大小的缓冲区（约 1MB）。

六、Binder 线程池与 oneway

"服务端谁在执行事务？"——不是主线程，是 Binder 线程池里的线程。

块 H：线程池的诞生（ProcessState.cpp:139 / 45）

ProcessState.cpp:45、139-150 + IPCThreadState.cpp:617-640
// ① 上限定义：
#define DEFAULT_MAX_BINDER_THREADS 15
// 每个进程最多 15 个 Binder 线程（可用系统属性调整）

void ProcessState::startThreadPool()
{
    AutoMutex _l(mLock);
    if (!mThreadPoolStarted) {
        mThreadPoolStarted = true;
        spawnPooledThread(true);
        // ② 先起"主" Binder 线程（isMain=true），其余按需增长
    }
}

// ③ 线程循环本体（IPCThreadState.cpp:617）：
void IPCThreadState::joinThreadPool(bool isMain)
{
    mOut.writeInt32(isMain ? BC_ENTER_LOOPER : BC_REGISTER_LOOPER);
    // ④ ★ 告诉驱动："我加入线程池了"
    //    BC_ENTER_LOOPER = 主线程（驱动会为它多做准备）
    //    BC_REGISTER_LOOPER = 普通池线程

    mIsLooper = true;
    do {
        processPendingDerefs();
        result = getAndExecuteCommand();
        // ⑤ 取一条命令执行（内部就是 talkWithDriver → executeCommand）

        if (result == TIMED_OUT && !isMain) {
            break;
            // ⑥ ★ 池线程超时没活干就退出：线程池会自己收缩
            //    主线程不退出（isMain），保证至少有一个人值守
        }
    } while (result != -ECONNREFUSED && result != -EBADF);
}

这段在干什么：进程启动时起一个主 Binder 线程，之后按需增长（最多 15 个），空闲的池线程会自己退出。

设计意图：弹性线程池是为了"够用又不浪费"。Binder 线程会阻塞（同步调用等待时），所以不能只有一条；但每条线程都占内存（栈），所以不能预先开 15 条。做法是：驱动发现"目标进程所有 Binder 线程都忙"时，会要求它再启一条——这个"按需扩容"是内核与用户进程配合完成的。

🐛 实战 Binder 线程池耗尽（表现为服务"假死"，但对它自己发起的新调用还能响应）。因果：15 条线程全在等（典型：A 服务的 Binder 线程同步调用 B 服务，B 的线程又同步调回 A——环路死等）。这是系统性死锁模式。怎么查：dumpsys 或 /proc/<pid>/task 统计线程名含 Binder: 的数量到没到上限；再抓所有 Binder 线程的栈看是否互相等待。

块 I：oneway 的本质

非 oneway（同步）oneway（异步）
客户端行为阻塞等 BR_REPLY只等 BR_TRANSACTION_COMPLETE
能否拿返回值能不能（reply 参数被忽略）
服务端异常序列化回客户端，客户端 rethrow静默消失（代码注释原话："disappear into the ether"）
谁会用需要结果的查询系统 → App 的通知/回调（避免系统被 App 拖住）
AIDL 里的 oneway 接口或方法上标 oneway，AIDL 生成的代理就会带 FLAG_ONEWAY。注意：oneway 方法不能有返回值、不能用 out/inout 参数（编译期就会报错）——因为它根本不等结果。这个限制在写 AIDL 时会直接遇到。
🧠 思考（需结合：块 F、块 I） 系统向 App 发回调（如 IApplicationThread 的很多方法）几乎都是 oneway。为什么？如果改成同步，服务端会付出什么代价？想想"App 主线程卡住 5 秒"时，同步回调会让 system_server 的 Binder 线程也卡 5 秒——15 条线程能扛几次这样的卡？

//    注释写着 "Local implementation is a no-op." ——
//    本地对象不会"死"（就在本进程），自然不需要通知

设计意图：这是 06 篇那个 mDeathRecipient == null 判断的底层。回顾 06 篇：WindowState 构造函数里 linkToDeath 失败（抛 RemoteException）就说明客户端已经死了，于是构造出一个"半成品"返回。现在你知道为什么那次调用会失败了——因为 linkToDeath 内部要向驱动登记，对端 binder 已经断了。

🐛 实战 内存泄漏：忘记 unlinkToDeath。Binder 驱动会持有你的 DeathRecipient 引用（防止被 GC）。如果不 unlinkToDeath，对象生命周期会被意外延长。怎么查：LeakCanary 报 BinderProxy / DeathRecipient 相关引用链；代码审查时搜 linkToDeath 看有没有配对的 unlinkToDeath。

AIDL 到底生成了什么

写了这么多年 AIDL，它生成的四个东西各自是什么角色？

AIDL 生成代码的结构（以 IMyService 为例）
// 【1】接口本体：继承 IInterface
public interface IMyService extends android.os.IInterface {
    public void doSomething(int arg) throws android.os.RemoteException;
    // 业务方法：两端都实现同一份接口

    // 【2】Stub：服务端基类（你要继承它写实现）
    public static abstract class Stub extends android.os.Binder
            implements IMyService {
        // ★ 它就是第三节说的 Binder 子类——本地直通 + 作为服务端身份

        public boolean onTransact(int code, Parcel data, Parcel reply, int flags) {
            switch (code) {
                case TRANSACTION_doSomething: {
                    data.enforceInterface(DESCRIPTOR);
                    // ★ 校验接口标识：防止"传错对象"（类比：确认收件人是自己）
                    int arg = data.readInt();
                    // ★ 反序列化参数
                    this.doSomething(arg);
                    // ★ 调到你的实现
                    reply.writeNoException();
                    return true;
                }
            }
            // … 缺省走 super.onTransact（处理 INTERFACE_TRANSACTION 等）
        }

        // 【3】asInterface：把 IBinder 包装成接口引用
        public static IMyService asInterface(android.os.IBinder obj) {
            if (obj == null) return null;
            android.os.IInterface iin = obj.queryLocalInterface(DESCRIPTOR);
            if (iin != null && iin instanceof IMyService) {
                return (IMyService) iin;
                // ★★ 同进程：直接返回本地对象（不走 IPC）——块 B 的延续
            }
            return new Proxy(obj);
            // ★★ 跨进程：包装成 Proxy
        }

        // 【4】Proxy：客户端代理（跨进程时用）
        private static class Proxy implements IMyService {
            private android.os.IBinder mRemote;

            public void doSomething(int arg) throws RemoteException {
                Parcel data = Parcel.obtain();
                Parcel reply = Parcel.obtain();
                try {
                    data.writeInterfaceToken(DESCRIPTOR);
                    data.writeInt(arg);
                    // ★ 序列化参数
                    mRemote.transact(TRANSACTION_doSomething, data, reply, 0);
                    // ★ 发起跨进程（回到本篇第二节）
                    reply.readException();
                    // ★ 检查服务端是否抛了异常
                } finally { data.recycle(); reply.recycle(); }
            }
        }
    }
}

这四个东西的分工：Stub（服务端：Binder 子类 + 反序列化 + 分发）、Proxy（客户端：序列化 + transact）、asInterface（决定走不走 IPC）、接口本体（两端共享的契约）。

关键洞察 asInterface 里那个 queryLocalInterface 判断，就是"本地不出门"的唯一开关。它让同一份 AIDL 在"服务在同一进程"和"服务在别的进程"两种情况下都正确工作——这就是为什么很多系统服务在单进程调试时"看起来没有跨进程开销"。

🧠 自测：6 个问题

1. 一次 Binder 调用，数据到底拷贝几次？为什么比 Socket 少？
一次。copy_from_user 把发送方数据拷进内核缓冲区后，接收方通过驱动预先 mmap 好的映射直接读内核缓冲区——省掉了 copy_to_user。
Socket 是"用户→内核→用户"两次拷贝。
代价：内核要为每个进程预留固定大小的缓冲区（约 1MB），所以单次事务大小受限（Binder.checkParcel 在 800KB 就开始警告）。
2. Binder.transact 和 BinderProxy.transact 有什么区别？
Binder.transact 是本地直通：直接调 onTransact，一次普通函数调用，不走 IPC（Binder.java:1057）。
BinderProxy.transact 是跨进程：检查大小 → 调 transactNative → 走 JNI/native/驱动（BinderProxy.java:516）。
两者都实现 IBinder，所以调用方不需要知道对面是本地还是远端——这正是 Binder "像调本地方法"的体现。另外 Binder.linkToDeath 是空实现，BinderProxy 才真登记。
3. 服务端执行事务的是哪个线程？一个进程最多几个？
是 Binder 线程池里的线程，不是主线程。进程启动时 ProcessState::startThreadPool() 起一个"主"Binder 线程（isMain=true），之后按需增长，上限 DEFAULT_MAX_BINDER_THREADS = 15（ProcessState.cpp:45）。空闲的池线程会自己退出（joinThreadPool 里 result == TIMED_OUT && !isMain 就 break）。
扩容是"内核发现所有 Binder 线程都忙 → 要求目标进程再起一条"这种配合机制。
4. 服务端 getCallingUid() 的值从哪来？为什么可信？
从当前线程的 TLS 里读（execTransact 的 Binder.getCallingUid()），而该值由 native 层在收到事务时从内核驱动拿到并写入。
因为 UID 是内核在传递事务时记录在 binder_transaction 结构里的，调用方进程无法伪造（它无法修改内核数据结构）。这是 Binder 安全模型的根基——所有 checkCallingPermission 系列 API 都建立在这上面。
5. oneway 调用，服务端抛异常会怎样？为什么？
异常会静默消失。Binder.execTransactInternal 的代码注释原话："If the call was FLAG_ONEWAY then these exceptions disappear into the ether"。
原因：oneway 不等回复，没有 reply Parcel（客户端传的 reply 被忽略），异常无处可写。
推论：oneway 方法不能有返回值、不能用 out/inout 参数（AIDL 编译期就会报错）。写 AIDL 时标了 oneway 才发现要返回值，这个限制会直接撞上。
6. 为什么 ServiceManager 是特殊的存在？
因为"找服务需要一份目录，但目录本身也是服务"是鸡生蛋问题。
Binder 的解法：内核里预留一个特殊 handle（0），任何进程都能直接拿到它而不需要查找。ServiceManager 进程启动时通过 BECOME_CONTEXT_MANAGER（ProcessState::becomeContextManager()，ProcessState.cpp:149）认领这个位置。Java 侧 getContextObject() 拿到的就是它（ServiceManager.java:110）。
之后所有服务通过它注册/查询；客户端还带一层本地缓存（sCache）省跨进程。
