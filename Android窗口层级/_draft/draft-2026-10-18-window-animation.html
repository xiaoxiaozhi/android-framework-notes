一、全景：动画是窗口树的「第三种改造方式」

你在前八篇里已经见过窗口树的两种改造：

方式篇目树上发生了什么
add02 / 06 篇树上长出新节点（WindowToken / WindowState）
remove06 篇（三条删除路径）树上摘掉节点
动画本篇树上临时插入一个中间节点（leash），让子树可被拖拽；转场结束再抽掉

第三种最难理解，因为它违反直觉：窗口怎么"动"起来？树上的位置是固定的，位置变了不就该重新布局吗？ 答案是：不移动原节点，而是在它上面套一层。这层套子可以随便平移/缩放/旋转/改透明度，被套住的子树整体跟着动——但树的结构、层级、布局一个字节都没变。

类比 想象你要把一幅画从墙上取下来摆到另一面墙。笨办法是重新钉钉子、重新挂（重新布局，代价高、会闪）。
动画的做法是：在画外面套一个画框，把画框连同画一起搬过去。画本身的位置没变，变的是画框。搬完把画框拆掉——画就"落"在了新的地方。
这个画框就是 leash（缰绳）。它的名字也很形象：牵住这棵子树的那根绳。
leash 插入前 vs 插入后 【插入前】 DisplayArea.Tokens └─ WindowToken (App 窗口) └─ WindowState ← mSurfaceControl 直接挂在这里 【插入后（转场中）】 DisplayArea.Tokens └─ WindowToken └─ WindowState └─ SurfaceControl "animation-leash of APP_WINDOW" ← 临时插入 └─ 原有的 surface（被 reparent 进来） 动画操作的是 leash（改它的位置/alpha/crop），而不是 WindowState； 转场结束 leash 被销毁，surface reparent 回原处 —— 树结构恢复如初。
一句话 树定义「谁盖谁」，leash 定义「这一刻谁在哪」。前者是静态的层级真值，后者是转场期间的临时表演层。理解了这句，Winscope 里那些"凭空多出来的 Layer"就再也不会让你困惑了。

二、谁发起：转场状态机 AppTransition

动画不是"窗口自己想起来要动"，而是有人先宣布"接下来要发生一次转场"，然后系统在这个声明期内收集该动谁，最后统一执行。

void prepareAppTransition(@WindowManager.TransitionType int transit,
        int flags, boolean alwaysKeepCurrent) {
    // ① why 先「声明」再「执行」：发起方（AMS/ATMS）此刻只知道要转场，
    //    但还不知道最终有哪些窗口参与——它们要等布局算完才能确定
    //    所以这里只是把意图记在 mAppTransition 里（状态机置位）
    // … 省略：与已有 pending transition 的合并/覆盖判断
}

void executeAppTransition() {
    // ② why 布局之后才执行：此时每个窗口的可见性、frame、目标状态都已确定，
    //    才能正确判断「谁进场、谁退场、谁不动」——这正是 03 篇遍历的末尾阶段
    mAtmService.mWindowManager.mWindowPlacerLocked.requestTraversal();
    // ③ 转场必须触发一次遍历：因为动画要挂在「新一帧的窗口状态」上
}

这段在干什么：prepareAppTransition 宣布意图（记进状态机），executeAppTransition 在布局算完后触发遍历去落实。

设计意图：两段式设计的根本原因是「信息到达顺序」。AMS 决定跳转时，只知道"要从 A 到 B"；但"B 的窗口什么时候真正可见、A 什么时候真正该退场"，必须等 WMS 布局算完。所以意图先存着，等布局的最后一刻再兑现。

🐛 实战 跳转动画不出现 / 只闪一下。因果：prepareAppTransition 被调用但后续没有 executeAppTransition（或中途被 overridePendingTransition(0,0) 置空），意图悬在那里没兑现。怎么查：开 ProtoLog 的 WM_DEBUG_APP_TRANSITIONS，看日志里有没有成对的 prepare/execute；两段之间若隔了很远（几百毫秒），说明中间卡在布局或等 VSYNC。

public class AppTransition implements Dump {
    // ① 这就是 12 上的「转场状态机」本体：它不做动画，只记录
    //    「当前 pending 的转场是什么类型、有哪些窗口在等、准备好没有」

    static final int DEFAULT_APP_TRANSITION_DURATION = 336;
    // ② 默认转场时长 336ms（毫秒）。为什么不是整数 300？
    //    它不是拍脑袋定的，而是和刷新率/帧节奏对齐后的经验值；
    //    开发者选项里的「窗口动画缩放」就是在这个值上乘系数

    boolean isReady() {
        // ③ 就绪判据：所有「参与本次转场的窗口」都已能画（hasDrawn）且
        //    没有窗口还在「等首帧」。任何一方没准备好，
        //    整个转场就得继续等——这就是启动慢时动画迟迟不开始的原因
        // … 省略：mOpeningApps / mClosingApps 的逐个就绪检查（350-386）
    }
}

这段在干什么：AppTransition 是转场状态的记录本：类型、参与者、就绪判断、默认时长。

设计意图：isReady() 是"等齐再动"的闸门。动画最忌讳"动画开始了但内容还没画出来"——那会看到空窗口在滑。所以系统宁可等一下，也要保证参与转场的窗口都已出图。代价就是：启动慢的 App 会让转场整体延后（用户感觉"点了没反应"）。

🐛 实战 点开 App 有"卡一下"才出现动画。因果：isReady() 里某个窗口 hasDrawn 仍为 false（首帧还没画完），转场被挂起等它。这正是 06 篇「上树 ≠ 显示」在动画层的体现。怎么查：dumpsys window windows 看该窗口 isDrawn；配合 Perfetto 看首次绘制的耗时；如果窗口迟迟不 drawn，锅在 App 主线程（不是 WMS）。
🧠 思考（单块） 如果去掉 isReady() 这个闸门、转场一到就立刻开始动画，用户体验会怎样？想想「新窗口还没画出内容，但 leash 已经开始从缩小放大到正常」——你看到的会是什么？

三、核心机制 leash 缰绳：SurfaceAnimator.startAnimation

这是本篇的重心。所有窗口（WindowState）、容器（Task / ActivityRecord）、甚至壁纸的动画，最终都汇聚到同一个类：SurfaceAnimator。每个 WindowContainer 都持有一个 SurfaceAnimator（这解释了 06 篇那个 mWinAnimator 为什么重要）。

块 D：startAnimation 全貌（SurfaceAnimator.java:134 起）

SurfaceAnimator.java:134-180
void startAnimation(Transaction t, AnimationAdapter anim, boolean hidden,
        @AnimationType int type,
        @Nullable OnAnimationFinishedCallback animationFinishedCallback,
        @Nullable SurfaceFreezer freezer) {
    cancelAnimation(t, true /* restarting */, true /* forwardCancel */);
    // ① why 第一件事是取消旧动画：一个窗口同时只能有一个活动动画，
    //    否则两个 leash 会互相打架（画面抖动/卡住）。restarting=true 表示
    //    「这次取消是正常重开，不是被中断」，会走 forwardCancel 通知旧动画收尾

    mAnimation = anim;
    mAnimationType = type;
    mAnimationFinishedCallback = animationFinishedCallback;
    // ② 记下这份动画的身份，后面 dump 和回调都要用

    final SurfaceControl surface = mAnimatable.getSurfaceControl();
    if (surface == null) {
        Slog.w(TAG, "Unable to start animation, surface is null or no children.");
        cancelAnimation();
        return;
        // ③ why 没 surface 就没得动画：leash 要套在一个真实存在的图层上。
        //    这对应「窗口还没 relayout 出 surface」（06 篇的"上树≠显示"）
    }

    mLeash = freezer != null ? freezer.takeLeashForAnimation() : null;
    // ④ why 先问 SurfaceFreezer 要：自适应旋转等场景下，leash 是提前
    //    「冻住」画面时就建好的（截屏当占位），这里直接复用，避免重建和闪屏

    if (mLeash == null) {
        mLeash = createAnimationLeash(mAnimatable, surface, t, type,
                mAnimatable.getSurfaceWidth(), mAnimatable.getSurfaceHeight(), 0 /* x */,
                0 /* y */, hidden, mService.mTransactionFactory);
        // ⑤ ★ 没有现成的就现造：注意尺寸用的是 getSurfaceWidth/Height
        //    （当前图层实际大小），坐标 (0,0)（贴在原位置，不改变外观）
        mAnimatable.onAnimationLeashCreated(t, mLeash);
        // ⑥ 通知宿主「你的 leash 建好了」——宿主借此把子 Layer 挂到 leash 下
        //    （WindowContainer.java:2837 的实现，见下一块）
    }

    mAnimatable.onLeashAnimationStarting(t, mLeash);
    // ⑦ 再通知一次：动画马上要开始，宿主可做最后准备

    if (mAnimationStartDelayed) {
        if (DEBUG_ANIM) Slog.i(TAG, "Animation start delayed");
        return;
        // ⑧ why 支持「延迟启动」：leash 建好但先不播，等外部信号。
        //    用于「先摆好姿势再一起动」的转场（如多窗口同时进入）
    }

    mAnimation.startAnimation(mLeash, t, type, mInnerAnimationFinishedCallback);
    // ⑨ ★ 把 leash 交给具体的 AnimationAdapter 去驱动：
    //    它会在每一帧改 leash 的 position/alpha/crop
}

这段在干什么：一次动画启动的完整准备——取消旧动画、记身份、确认有 surface、拿到或新建 leash、通知宿主挂接、最后把 leash 交给动画驱动器。

设计意图：整个方法是"把树改造好，再把改造后的树交给动画驱动"。仔细看顺序：先建 leash → 再通知宿主把子节点 reparent 进来 → 最后才启动动画。顺序反了的话，动画驱动的就是一棵还没接好线的树。

实战问题：leash 泄漏 / 画面卡在半透明中间层。因果：动画被取消但 mAnimationFinishedCallback 没执行，leash 没被销毁也没 reparent 回去，于是那层永远留在树上。怎么查：Winscope 里看有没有多余的 animation-leash of … Layer；dumpsys window 里搜 mLeash=（SurfaceAnimator.dump() 会打印它）；也可用 adb shell dumpsys SurfaceFlinger | grep leash。

public SurfaceControl.Builder makeAnimationLeash() {
    return makeChildSurface(null)       // 建在「自己」名下，不是建在屏幕下
            .setParent(getSurfaceControl())

public SurfaceControl getAnimationLeashParent() {
    return mParent != null ? mParent.getSurfaceControl() : getSurfaceControl();
    // why 让 leash 的父 = 宿主的父，这样 leash 占据了宿主原本在父容器中的

    // 结果：树形状是 父 → leash → 宿主，视觉与层级完全等价，
    // 但多出一层可自由操作的中间层
}

// ③ 挂接动作：宿主在这里把自己的 surface 塞进 leash（由 createAnimationLeash 里的 reparent 完成）
public void onAnimationLeashCreated(Transaction t, SurfaceControl leash) {
    // … 子类（WindowState / Task 等）各自实现，例如把 IME 相关的相对层级
    //    重新绑定到 leash 上，避免 leash 一插进去 IME 层级就错乱
}

这段在干什么：解答"leash 插在哪一层"——它的父是宿主的父，宿主自己则降到 leash 下面。

设计意图：leash 必须"顶替"宿主原来的图层位。如果 leash 建在宿主内部，那宿主的 alpha/crop 会先作用于 leash 再作用于内容，语义就乱了；相反，让 leash 站在宿主原来的位置、宿主退到下一层，动画操作 leash 就恰好等价于操作整个宿主——这是最干净的实现方式。

四、leash 是怎么插进去的：createAnimationLeash

上一块说「建 leash」，但没图为它到底怎么进树的。这个方法只有二十多行，却把整件事说完了。

块 G：先看插入前的树（ASCII）

插入前： DisplayArea.Tokens (SurfaceControl L1) └─ WindowToken (L2) └─ WindowState (L3) ← mSurfaceControl，直接挂在 L2 下 插入后： DisplayArea.Tokens (L1) └─ WindowToken (L2) └─ leash (L3') ← 新建，父 = WindowToken（即宿主的父） └─ WindowState (L3) ← 原来在 L2 下，现在 reparent 到 leash 下 关键：leash 的父不是 WindowState，而是 WindowState 的父（WindowToken）—— 所以树形状变成 “爷爷 → leash → 孙子”，视觉层级与原来完全等价。

块 H：createAnimationLeash 本体（SurfaceAnimator.java:384）

SurfaceAnimator.java:384-415
static SurfaceControl createAnimationLeash(Animatable animatable, SurfaceControl surface,
        Transaction t, @AnimationType int type, int width, int height, int x, int y,
        boolean hidden, Supplier<Transaction> transactionFactory) {
    if (DEBUG_ANIM) Slog.i(TAG, "Reparenting to leash");

    final SurfaceControl.Builder builder = animatable.makeAnimationLeash()
            .setParent(animatable.getAnimationLeashParent())
            // ① 父的选取是关键：取宿主的父，让 leash 顶替宿主原本的图层位（块 E 已解释）

            .setName(surface + " - animation-leash of " + animationTypeToString(type))
            // ② 名字带 “animation-leash of 类型”——这就是你在 dumpsys SurfaceFlinger
            //    里搜 leash 能直接定位到它的原因，也是排障的第一线索

            // TODO(b/151665759) Defer reparent calls
            // We want the leash to be visible immediately because the transaction which shows
            // the leash may be deferred but the reparent will not. This will cause the leashed
            // surface to be invisible until the deferred transaction is applied. If this
            // doesn't work, you will can see the 2/3 button nav bar flicker during seamless
            // rotation.
            // ③ 这段注释是这个方法的“设计意图说明书”：leash 必须“立即可见”，
            //    因为展示它的那笔事务可能被 defer，但 reparent 不会。
            //    两者的时序差会造成“导航条闪烁”——作者直接把已知坑写在代码里了

            .setHidden(hidden)
            .setEffectLayer()
            // ④ effect layer：标记为“效果层”，不参与某些优化计算（如遮挡）
            .setCallsite("SurfaceAnimator.createAnimationLeash");
            // ⑤ callsite 会记进 SurfaceFlinger，事后能用 dumpsys 反查“这层谁建的”

    final SurfaceControl leash = builder.build();

    t.setWindowCrop(leash, width, height);
    t.setPosition(leash, x, y);
    t.show(leash);
    t.setAlpha(leash, hidden ? 0 : 1);
    // ⑥ 初始化 leash 自身的属性：尺寸/位置/可见/透明度——
    //    这一笔事务执行后，leash 就是一个“与宿主外形一模一样”的空壳

    t.reparent(surface, leash);
    // ⑦ ★ 全篇最关键的一行：把宿主原有的 surface 挂到 leash 下。
    //    执行前树是 L2→L3；执行后是 L2→L3'→L3。视觉上无差别，
    //    但现在改 L3' 的属性等价于改整个 L3 子树

    return leash;
}

这段在干什么：建一个尺寸/位置与宿主一模一样的新图层，改名标记为 leash，然后把宿主原图层挂到它下面。树结构从此多一层。

设计意图：为什么必须“多一层”而不是直接改宿主。因为宿主的 surface 是内容载体——App 会不断往上面画新帧（比如列表滚动）。如果直接把位移写进宿主，那 App 每画一帧都可能把动画位移重置。用 leash 隔开：内容归内容（L3），表演归表演（L3'），两者互不干扰。这是整个动画架构最漂亮的地方。

🐛 实战 动画期间画面闪烁一下。因果：正是注释 ③ 描述的那个时序差——leash 的 show 被 defer 了，但 reparent 已经生效，导致宿主在新旧父子关系间瞬间不可见。怎么查：开 WM_SHOW_TRANSACTIONS ProtoLog 看事务合并情况；用 Winscope 逐帧看 leash 从建立到可见的那几帧。

五、窗口怎么应用动画：applyAnimationLocked

    if (mWin.isAnimating() && mAnimationIsEntrance == isEntrance) {
        // If we are trying to apply an animation, but already running
        // an animation of the same type, then just leave that one alone.
        return true;
        // ① why 已经在播同类动画就不重开：否则每轮布局都重启一遍动画，
        //    表现为“动画卡在开头不动”（永远在从头播）
    }

    // Only apply an animation if the display isn't frozen.  If it is
    // frozen, there is no reason to animate and it can cause strange
    // artifacts when we unfreeze the display if some different animation
    // is running.
    if (mWin.mToken.okToAnimate()) {
        // ② why 冻结显示（旋转中）不播动画：画面本来就是一张静态截图，
        //    再叠动画只会让解冻后出现错位——这是旋转相关 bug 的常见源头

        int anim = mWin.getDisplayContent().getDisplayPolicy()
                .selectAnimation(mWin, transit);
        // ③ policy 先把 transit 映射成一个“动画样式”编号（或 ANIMATION_NONE /
        //    ANIMATION_STYLEABLE）——再次看到“策略在 policy、执行在 WMS”的分工

        int attr = -1;
        Animation a = null;
        if (anim != DisplayPolicy.ANIMATION_STYLEABLE) {
            if (anim != DisplayPolicy.ANIMATION_NONE) {
                a = AnimationUtils.loadAnimation(mContext, anim);
                // ④ 系统预定义的动画（帧动画/补间动画资源），直接加载
            }
        } else {
            switch (transit) {
                case WindowManagerPolicy.TRANSIT_ENTER:
                    attr = ...WindowAnimation_windowEnterAnimation;
                    break;
                case WindowManagerPolicy.TRANSIT_EXIT:
                    attr = ...WindowAnimation_windowExitAnimation;
                    break;
                // … 省略：TRANSIT_SHOW / TRANSIT_HIDE 两个分支（735-745）
            }
            // ⑤ STYLEABLE 的意思是“由主题决定”：去窗口的 windowAnimations 样式里
            //    找 windowEnterAnimation / windowExitAnimation 等属性——
            //    这就是为什么自定义转场动画要在 theme 里写 windowAnimationStyle
            if (attr >= 0) {

                        .loadAnimationAttr(mWin.mAttrs, attr, TRANSIT_OLD_NONE);
            }

    }

这段在干什么：把转场类型翻译成具体的动画对象——要么用系统预定义的，要么从窗口主题样式里取；拿到就交给 WindowState.startAnimation。

设计意图：三级翻译链：transit（转场语义）→ policy.selectAnimation（样式编号或 STYLEABLE）→ 实际 Animation 对象。三级分开是为了让三方各改各的：系统定义默认转场语义、厂商 policy 改映射、App 用主题自定义自己窗口的动画。这就是 overridePendingTransition 能从 App 层影响转场的原理。

六、帧驱动：WindowAnimator 与 Choreographer

leash 建好了、适配器也挂上了——但谁每 16.7ms 去把 leash 往前推一帧？答案是 WindowAnimator，它由 Choreographer 驱动。

类比 Choreographer 是节拍器（跟 VSYNC 对齐），WindowAnimator 是指挥——每次节拍响，它就喊一声“所有还在动的图层，各报各自当前该长什么样”，然后一次性提笔事务。

块 K：动画帧主循环（WindowAnimator.java:128 起，裁剪）

private void animate(long frameTimeNs, long vsyncId) {
    if (!mInitialized) return;

    // Schedule next frame already such that back-pressure happens continuously.
    scheduleAnimation();
    // ① ★ 先排下一帧，再干本帧的活：注释说是为了“持续背压”——
    //    本帧算得慢时，下一帧的请求已经在路上，不会出现“算完才想起要排下一帧”
    //    导致的帧间隔抖动。代价是无动画时也会多跑一拍，所以真无动画时会
    //    被 cancelAnimation 掐掉（下面）

    final RootWindowContainer root = mService.mRoot;
    mCurrentTime = frameTimeNs / TimeUtils.NANOS_PER_MS;
    mBulkUpdateParams = 0;
    root.mOrientationChangeComplete = true;

    ProtoLog.i(WM_SHOW_TRANSACTIONS, ">>> OPEN TRANSACTION animate");
    mService.openSurfaceTransaction();
    // ② 本帧的所有修改聚到一笔事务里——和 03 篇遍历提交同一个套路，
    //    避免每改一个图层就过一次 binder
    try {
        root.handleCompleteDeferredRemoval();
        // ③ 处理被 defer 的删除：动画期间不允许真删窗口（否则 leashed surface 没了），
        //    所以删除请求先挂起，到动画结束才在这里真正执行

        final int numDisplays = mDisplayContentsAnimators.size();
        for (int i = 0; i < numDisplays; i++) {
            final int displayId = mDisplayContentsAnimators.keyAt(i);
            final DisplayContent dc = root.getDisplayContent(displayId);
            // Update animations of all applications, including those associated with
            // exiting/removed apps.
            dc.updateWindowsForAnimator();
            dc.prepareSurfaces();
            // ④ 逐屏两道：先更新窗口的动画状态，再重新准备 surface 参数（位置/alpha/crop）
            //    ——leash 的新属性就是在这两道里被算出来写进事务的
        }
        // … 省略：壁纸动画、无障碍放大、批量参数应用（170-230）
    } finally {
        mService.closeSurfaceTransaction("WindowAnimator");
    }
}

void scheduleAnimation() {
    if (mAnimationScheduled) return;
    mAnimationScheduled = true;
    mChoreographer.postFrameCallback(mAnimationFrameCallback);
    // ⑤ ★ 动画的“心脏起搏器”：向 Choreographer 登记一个帧回调。
    //    Choreographer 会在下一个 VSYNC 到来时唤醒它——
    //    所以动画帧率和屏幕刷新率对齐（60/90/120Hz）
}

这段在干什么：每个 VSYNC 帧，先排下一帧，然后把所有还在动的窗口/壁纸的 leash 参数重新算一遍，打包成一笔事务提交。

设计意图：“先排下一帧”是防掉帧的关键技巧。如果先干活再排下一帧，一旦本帧的计算耗时超过 16.7ms，下一帧就会晚到——表现为顿一下。反过来先把下一帧的请求挂上去，VSYNC 一到就能立刻回调，平滑得多。

🐛 实战 动画掉帧 / 卡顿。因果：animate() 里 updateWindowsForAnimator + prepareSurfaces 是在 system_server 的 UI 线程上跑的，如果同时有很多窗口在动（分屏动画、多屏），这一帧算不完就会错过 VSYNC。怎么查：Perfetto 看 WindowAnimator 的 trace 切片耗时（代码里已埋 Trace.traceBegin）；若超过帧预算，看是不是参与动画的窗口数过多。
🧠 思考（需结合：块 K、块 D） 块 K 里 scheduleAnimation 无条件排下一帧——那系统怎么知道“动画都播完了、可以停下来”？联系块 D 里的 mAnimationFinishedCallback，想想 cancelAnimation 与 mAnimationScheduled 的关系（提示：看 WindowAnimator.java:300 的 cancelAnimation）。

🧠 自测：5 个问题

1. 为什么动画要在树上“插一层 leash”，而不是直接改窗口自己的位置/透明度？
因为窗口的 surface 是内容载体——App 会持续往它上面画新帧。如果动画属性直接写在窗口上，App 的每一帧绘制都可能把动画位移/alpha 重置掉，动画会被“抢断”。用 leash 隔离后：内容层（原 surface）只负责内容，表演层（leash）只负责动画参数，两者互不干扰。另外 leash 让“移动整个子树”（含子窗口、leashed 子节点）变成一个原子操作。
2. leash 的父节点为什么取“宿主的父”而不是宿主本身？
为了让 leash 顶替宿主原本在图层树里的位置。若 leash 建在宿主内部，宿主的 alpha/crop 会先作用于 leash 再作用于内容，语义叠了一层；而让 leash 站在宿主原来那一格、宿主退到 leash 之下，树形状变成「爷爷 → leash → 宿主」，视觉与层级完全等价，动画操作 leash 就恰好等价于操作整个宿主（见 WindowContainer.getAnimationLeashParent() 的注释）。
3. 点开一个 App 有“卡一下”动画才出来，可能的两个不同原因是什么？
① 转场闸门在等：AppTransition.isReady() 要求所有参与窗口 hasDrawn，新窗口首帧没画完就不放行——锅在 App 主线程（这是 06 篇“上树 ≠ 显示”在动画层的体现）。② 动画已开始但被“抢断”：applyAnimationLocked 开头那句 mWin.isAnimating() && mAnimationIsEntrance == isEntrance 判断错误地重开了动画，表现为永远卡在开头。区分方法：开 WM_DEBUG_APP_TRANSITIONS 看 prepare/execute 之间隔了多久。
4. leash 泄漏（画面卡在半透明中间层）怎么查？
三个层次：① dumpsys SurfaceFlinger | grep leash —— 看有没有多余的 animation-leash of … 层（名字由 createAnimationLeash 里 setName() 写入，是唯一可门的指纹）；② dumpsys window | grep mLeash —— SurfaceAnimator.dump() 会打印 mLeash= 与 mAnimationType=；③ Winscope 逐帧回放，看 leash 从创建到销毁的时刻。根因通常是动画被取消但 mAnimationFinishedCallback 未执行，对应 cancelAnimation(…, forwardCancel) 的第三个参数被传了 false。
5. 为什么手势返回动画要交给 SystemUI/App 自己画，而不是 WMS？
因为动画必须跟手。手势返回过程中，手指位置在每个触摸事件里，而触摸事件在 SystemUI/App 进程。若让 system_server 的 WMS 算动画，就得把每个移动事件跨进程送回 WMS，再算一次再发出去——多了一轮往返，动画会明显滞后于手指。交给持有输入的那一方算，动画才能实时跟手。（代价：转场逻辑分散到两进程，调试要同时看两边日志。）
