一、全景：一次 startActivity 的四段旅程

06 篇结尾留了一个悬念：addWindow 里那个 token 是从哪来的？答案在这里——它来自 ActivityRecord，而 ActivityRecord 是 startActivity 一路走来的产物。

一句话 06 篇讲的是「窗口怎么挂上树」（WMS 侧）；本篇讲的是「是谁、什么时候决定该有一个窗口」（ATMS 侧）。两者在 ViewRootImpl.setView 这个点上会合。
一次 startActivity 的四段旅程 【第一段】决策：App 进程 → system_server App: Activity.startActivity() └─ Instrumentation.execStartActivity() └─ ─── binder ───▶ ATMS.startActivity() :1144 └─ ActivityStarter.execute() :611 └─ executeRequest() :811 └─ startActivityUnchecked() :1548 └─ startActivityInner() ★ 决定：复用哪个 Task？要不要新建？ 【第二段】身份：造出 ActivityRecord ActivityRecord extends WindowToken :365 ★ 这一步是本篇的核心：ActivityRecord 本身就是窗口树上的一个容器 ★ 06 篇的 token 就是它（asActivityRecord() 反查的就是这个对象） 【第三段】落地：新进程起来，Activity 实例被创建 系统 → 目标进程 └─ ActivityThread.performLaunchActivity() :3513 └─ Activity.attach() ★ 拿到 ActivityRecord 的 token └─ 走 06 篇的整条链：addView → binder → WMS.addWindow 【第四段】显示：首帧上屏 ViewRootImpl.setView() :993 └─ relayout → 首帧绘制 └─ WindowStateAnimator.commitFinishDrawingLocked() :270 └─ isDrawn() 翻转 ← 启动窗口此时才退场

二、ATMS 入口与 ActivityStarter 决策

先看系统侧的入口。注意 ATMS 与 WMS 同包同锁（都在 wm/ 目录、共用 mGlobalLock）——这是 API 30 之后的重大变化，也是为什么讲 WMS 时总能顺手看到 AMS 的代码。

块 A：ATMS 入口（ActivityTaskManagerService.java:1144 起，裁剪）

ActivityTaskManagerService.java:1144-1200（裁剪）
public final int startActivity(IApplicationThread caller, String callingPackage,
        Intent intent, String resolvedType, IBinder resultTo, String resultWho, int requestCode,
        int startFlags, ProfilerInfo profilerInfo, Bundle bOptions, int userId) {
    return startActivityAsUser(caller, callingPackage, intent, resolvedType, resultTo,
            resultWho, requestCode, startFlags, profilerInfo, bOptions,
            userId, true /*validateIncomingUser*/);
    // ① why 多一层转发：validateIncomingUser 要检查调用方是否有权给这个 userId 启动
    //    （多用户/工作资料场景的安全闸）
}

private int startActivityAsUser(...) {
    // … 省略：权限校验、mAmInternal.handleIncomingUser、计时埋点
    try {
        return new ActivityStarter(mService, mRootWindowContainer, ...,
                new SafeActivityOptions(bOptions))
                .execute();
        // ② ★ 每次 startActivity 都 new 一个 ActivityStarter：
        //    它是个"一次性的决策器"而非长驻服务——用完即弃，
        //    这样决策过程中的临时状态不需要考虑并发保护
    } catch (RuntimeException e) {
        // … 省略：异常转错误码并打日志
    }
}

这段在干什么：入口做权限与 userId 校验，然后造一个一次性的 ActivityStarter 去执行决策。

设计意图：ActivityStarter 是"一次性决策器"。启动决策需要考虑几十个因素（调用方、launchMode、taskAffinity、flags、当前栈状态…），如果做成有状态的常驻服务，并发与状态清理会非常复杂。做成一次性对象后，所有中间状态都随对象死亡而消失，逻辑清爽很多。

🐛 实战 后台启动 Activity 不生效（静默失败）。因果：入口层的 validateIncomingUser 或更下游的 Bal/ABL（Background Activity Launch）检查拒绝——Android 10+ 严格限制后台应用启动 Activity。怎么查：dumpsys activity activities 看不到新 AR；开 ActivityTaskManager 相关 log 看有没有 "Background activity launch blocked" 一类字样。

        //    要不要清栈（clearTop）、要不要新建 Task —— 这里决定 ActivityRecord 的归属

    }
}

这段在干什么：解析 Intent 找到目标 → 创建 ActivityRecord → 进入决策主流程决定它归哪个 Task。

设计意图：先造对象、再决定归属。这看起来顺序奇怪（为什么不先决定放哪、再造对象？），但很合理：决策需要用对象本身的信息（比如它的 taskAffinity、launchMode、intent flags 都来自这个 AR 的字段）。先造出来当"草稿"，决策过程中随时可能被丢弃（abort）——所以后面才有那句注释「Only do the create here (and defer requestStart) since startActivityInner might abort」。

🐛 实战 launchMode 行为不符合预期（例如 singleTask 没有复用实例、singleTop 又起了新的）。因果：startActivityInner 里的复用判断综合了 launchMode + intent flags（FLAG_ACTIVITY_NEW_TASK 等） + taskAffinity + 当前栈状态，任何一个因素不同结果就不同。常见误用：忘了 singleTask 还需要 FLAG_ACTIVITY_NEW_TASK 配合。怎么查：dumpsys activity activities 看目标 AR 落在哪个 Task、Task 的 id 是否变了（变=新建了 Task）；再对照 manifest 的 launchMode 与代码里的 flags。
🧠 思考（单块） 为什么 ActivityStarter 要做成"每次 new"，而不是像 WMS 那样做一个长驻的决策服务？提示：想想决策过程中会产生多少临时状态（mStartActivity / mLaunchTaskBehind / mTargetStack 之类），以及这些状态在并发场景下要花多大代价保护。

三、ActivityRecord 的诞生：它为何就是 WindowToken

这是本篇最需要讲透的一点——它把 06 篇和 AMS 缝合在一起。

块 C：继承链就是答案（ActivityRecord.java:365）

ActivityRecord.java:365 + WindowToken.java:71 + 06 篇的呼应
// ① 这一行就是全部答案：
final class ActivityRecord extends WindowToken
        implements WindowManagerService.AppFreezeListener {

// ② 而 WindowToken 又是窗口容器：
//    WindowToken extends WindowContainer<WindowState>   (WindowToken.java:71)

// ③ 所以在窗口树里的位置是：
//    DisplayArea.Tokens / TaskDisplayArea
//      └─ Task
//           └─ ActivityRecord  ← 它是 Task 的子节点，同时是一个 WindowToken
//                └─ WindowState  ← 06 篇 addWindow 挂进来的窗口
//
// ④ 这就是 06 篇里这两个疑问的答案：
//    · “token 从哪来？” → 来自 ActivityRecord（系统在 startActivity 时创建）
//    · “asActivityRecord() 反查的是什么？” → 就是这个对象
//    · “应用窗口为什么不能伪造容器？” → 因为容器必须由系统在 ATMS 里创建

这段在干什么：用一行继承声明，说明「Activity 在窗口树上的身份就是一个容器」。

设计意图：为什么让 ActivityRecord 直接继承 WindowToken。因为「一个 Activity 的窗口们」天然要共享一份可见性、配置、动画状态——这正是 WindowToken 的职责（06 篇讲过：WindowToken 是窗口树里"一组窗口"的身份单元）。让它继承而不是组合，省掉一层间接，也让所有按 WindowContainer 遍历的逻辑自动覆盖到 Activity。代价是耦合：Activity 的生命周期语义与窗口容器语义混在一个类里（这也是这个文件为什么有上万行）。

🐛 实战 Activity 已 onDestroy 但窗口还在 / 报 leaked window。因果：ActivityRecord（容器）与 WindowState（窗口）的回收不是同时的——容器可以留着等待动画或状态收敛，而窗口该走自己的删除流程（见第七节）。怎么查：dumpsys activity activities 看 AR 是否已从 Task 摘除；dumpsys window windows 看对应 WindowState 是否还在；两者状态不一致时，看谁卡住了。

块 D：桌面/系统窗口也是有 token 的容器（呼应 06 篇块 F）

三类 token 的对照（06 篇块 F 的完整版）
// 【应用窗口】token = ActivityRecord.Token（IApplicationToken）
//   由 ATMS 在 startActivity 时创建，只能由系统创建 → 块 C 的继承链
//   WMS 查到它 → asActivityRecord() 拿到 AR → 有了 Activity 的全部信息

// 【系统窗口】token = 现场 new WindowToken.Builder(...)
//   壁纸 / IME / Toast 等没有 Activity，自带 IBinder 建容器
//   06 篇块 F 的 unprivilegedAppCanCreateTokenWith 就是这道闸

// 【子窗口】token = 父窗口的 IWindow（不是 ActivityRecord！）
//   Dialog/Popup 传的是父窗口的 ViewRootImpl.W.asBinder()
//   WMS 先用它查 mWindowMap 找到父 WindowState，再绕回父的 mAttrs.token 找 AR
//   ——这是 06 篇那个"两路查询"分叉的根本原因

// 一句话：token 的三种身份，对应"窗口归属"的三种来源：
//   有 Activity（应用） / 有主（系统） / 跟着爹（子窗口）

这段在干什么：把 06 篇的三类 token 与 AMS 侧的角色对应起来。

设计意图：安全边界。应用窗口的 token 必须由系统创建（因为它是 Activity 的身份凭证），这从根上杜绝了「App 伪造一个容器把自己挂到别的 Task 上」。系统窗口可以自建（因为系统本身就是可信的），子窗口只能继承父窗口的（因为它的存在依附于父）。

四、Task 与任务栈

ActivityRecord 不能凭空挂在树上，它必须属于一个 Task。startActivityInner 的核心工作就是决定「放进哪个 Task」。

块 E：Task 是什么（Task.java:252）

Task.java:252 + 树上的位置
class Task extends WindowContainer<WindowContainer> {
// ① 注意泛型是 WindowContainer 而不是 WindowState ——
//    Task 的子节点可以是 ActivityRecord（常见的），
//    也可以是另一个 Task（分屏/多窗口时嵌套形成 Task 树）

// ② 它管的东西：一组 ActivityRecord + 自己的 bounds + windowingMode
//    · bounds：这个 Task 占据的屏幕区域（分屏/自由窗口时不是全屏）
//    · windowingMode：fullscreen / freeform / pinned / multi-window
//    —— 08 篇 computeFrame 里的 windowsAreFloating 就是读这个

// ③ 树的形状（含分屏）：
//    TaskDisplayArea
//      ├─ Task (split 左)          ← windowingMode = MULTI_WINDOW
//      │    └─ ActivityRecord
//      │         └─ WindowState
//      └─ Task (split 右)
//           └─ ActivityRecord
//                └─ WindowState
}

这段在干什么：说明 Task 是 ActivityRecord 的上级容器，它自己带 bounds 和 windowingMode。

设计意图：Task 既是"历史记录"又是"几何容器"。作为历史记录，它支撑返回栈（back）和最近任务（recents）；作为几何容器，它决定里面 Activity 的可用区域。这两件事捆在一起是 Android 的历史设计——好处是"一个任务里的页面共享一套几何约束"（分屏时整个任务一起被约束），代价是 Task 类职责偏重。

块 F：决策的四个关键输入

输入在哪作用
launchModemanifest / Intent flagsstandard / singleTop / singleTask / singleInstance —— 决定复不复用实例
taskAffinitymanifest决定"愿意和谁待在同一个 Task"
Intent flags调用方代码NEW_TASK / CLEAR_TOP / SINGLE_TOP / CLEAR_TASK 等——优先级高于 manifest
当前栈状态ATMS 内存目标 Task 是否已存在、栈顶是谁、是否在分屏里
🐛 实战 点通知后 Activity 起在了旧的 Task 上 / 返回键行为异常。因果：从通知、Service、广播启动 Activity 时必须带 FLAG_ACTIVITY_NEW_TASK（因为它们没有 Activity 上下文）。不带要么起不来（抛异常），要么落进一个不符合预期的 Task。怎么查：dumpsys activity activities 观察目标 AR 落在哪个 Task、Task 的 affinity 是什么；对照调用处有没有加 NEW_TASK。
🧠 思考（需结合：块 B、块 F） 块 B 里 ActivityRecord 是"先创建、后决定归属"的。如果一个 singleTask 的 Activity 已经存在于栈中，这次 startActivity 新建的那个 AR 会怎样？——这能解释为什么"startActivity 返回成功"但"没有新建 Activity 实例"。

五、启动窗口：splash 与快照的接力

Activity 决定了，但它的进程还没起来、窗口还没画出来。这几百毫秒里屏幕上显示什么？答案是启动窗口（starting window / splash）。

块 G：两种启动窗口（StartingSurfaceController.java:46 / 60 / 115）

StartingSurfaceController.java:46-130（裁剪）

这段在干什么：两种启动窗口——冷启动用 splash（主题背景），热启动用快照（上次画面）。

设计意图：启动窗口的本质是"掩盖空窗期"。它不是装饰，是性能体验的补丁：App 从进程创建到首帧通常要几百毫秒，这段时间如果屏幕是黑的，用户会以为卡了。Android 用"先画一个占位"把这段时间填上。

📌 AOSP 12 的重要变化：启动窗口的实际绘制已经交给 Shell（SystemUI）——经 TaskOrganizerController.addStartingWindow()（:550，转发到 :134/:316）。WMS 只负责"决定该有一个启动窗"，不再自己画。这条线索在 09 篇（动画与 Shell 接管）里会展开。
🐛 实战 启动黑屏 / 白屏 / 闪两次。这三种现象对应三个不同的锅：
① 黑屏：启动窗口没加上（Shell 侧失败）或主题背景是黑的；
② 白屏：主题 windowBackground 是白色（默认 Theme.DeviceDefault 常见），而 App 真实背景不是——用户看到"白一下再变"；
③ 闪两次：启动窗口退场与真实窗口首帧没对齐（启动窗先没了、真窗口还没画；或反之）。
怎么查：开 cmd window tracing（Winscope）看 starting window 的 surface 何时创建/销毁，与真实窗口首帧的时刻对齐；再查主题的 windowBackground 与 windowSplashScreen* 属性。

六、首帧上屏：isDrawn 翻转

启动窗口什么时候退场？答案是：当真实窗口画完第一帧。这个"画完了"的标记就是 isDrawn。

块 H：三个容易混淆的状态方法（WindowState.java）

WindowState.java:2006 / 2091 / 3160 + WindowStateAnimator.java:270

//    && mDrawState == HAS_DRAWN —— 纯粹的"surface 上真的有过 buffer"

    // … 省略：判断当前 mDrawState
    // 把 mDrawState 从 READY_TO_SHOW（已就绪待显）推进到 HAS_DRAWN（已画过）
    // ★ 这一行执行后，isDrawn()/hasDrawn() 才会返回 true，

这段在干什么：三个状态方法的层次关系，以及"画完了"这个状态是在哪翻转的。

设计意图：为什么要有三个而不是一个。因为它们回答的是不同问题：isReadyForDisplay 是"能不能显示"（用于可见性决策）、isDrawn 是"这一轮画完没"（用于等相关方）、hasDrawn 是"历史上是否真有过帧"（用于最严格的确认）。排障时必须分清——这也是 06 篇「上树 ≠ 显示」的量化答案。

🐛 实战 启动窗口不消失 / 一直显示 splash（马老师 P0 项目里的经典题）。因果：isDrawn() 一直不翻 true，通常因为 App 主线程卡在 onCreate/onResume 里（同步 IO、大计算），或者首帧渲染被 RenderThread 阻塞。怎么查：dumpsys window windows 找该窗口，看 isDrawn=false、mDrawState 的值；再看 App 侧主线程堆栈（adb shell kill -3 <pid> 或 ANR trace）。若 mHasSurface=true 但 isDrawn=false，锅在绘制；mHasSurface=false，锅在 relayout。
🧠 思考（闭环·需结合：块 G、块 H、09 篇） 启动窗口退场与真实窗口进场，需要精确对齐。如果真实窗口的 isDrawn 翻转得比启动窗口退场晚，用户看到什么？如果早呢？想想为什么 09 篇要讲「转场闸门 AppTransition.isReady() 会等所有参与者 hasDrawn」——它正是为了解决这个对齐问题。

七、删除：三条路径的差异

这是本篇的重点章——它也是实践篇 P1 作业的理论基础（马老师那道原题问的就是：多任务移除 vs 后台 kill，为什么树上的残留不一样）。

先立结论 WindowState / ActivityRecord / Task 三者的生命周期不绑定。它们各自有独立的删除触发点，这才是"后台 kill 后 AR 还在"这种反直觉现象的根源。

块 I：三条删除路径的入口（各文件）

WindowState.java:2362/2418 + ActivityRecord.java:3232/3324 + Task.java:972/3211

// WindowState.removeIfPossible()            :2418
//   ├─ 会先 putInTransition 检查：动画没完就不删（等 09 篇的 callback）

// ActivityRecord.destroyImmediately(String reason)   :3232  ← 立刻销毁
// ActivityRecord.removeFromHistory(String reason)    :3324  ← 从历史里摘除

// Task.removeIfPossible()   :972   ← 优先（会检查是否还有未结束的 AR）
// Task.removeImmediately()  :3211  ← 兜底（强制摘树）

// ★ 这两个是"进程死亡后清理历史"的实际执行者

这段在干什么：三类对象各有自己的删除入口，而且每种都有"温和删"（removeIfPossible，等条件）与"强制删"（removeImmediately）两条路。

设计意图：温和/强制两套删除是为了兼顾体验与安全。「温和删」尊重动画与状态收敛（用户看不到突兀消失），「强制删」保证系统不会因为某个对象赖着不走而卡死。系统在正常路径用前者，在异常/超时路径用后者兜底。

块 J：三种场景下被删的东西不同（P1 作业的答案框架）

场景TaskActivityRecordWindowState为什么不同
多任务里上划移除✅ 移除✅ 移除✅ 移除用户显式操作 → 走完整清理流程（removeTask → cleanUpRemovedTaskLocked），三者一起走
后台 kill 进程❌ 保留❌ 保留✅ 移除进程死亡只让窗口失去宿主（binder 断、surface 回收）；Task/AR 是"任务历史"，系统故意保留以便用户还能从最近任务回到它（有些应用会重建进程恢复现场）
前台 kill / 正常 finish看情况✅ 移除✅ 移除正常 finish 走生命周期收尾；前台被 kill 时窗口随进程一起走，AR 随后被清理
核心机制 后台 kill 时 WindowState 掉了但 AR/Task 留着，是因为：
① 窗口挂在进程上——进程死了，binder（IWindow）断连，WMS 的 DeathRecipient 被触发（06 篇块 C 讲的那个 linkToDeath），于是 WindowState 被清理；
② Task/AR 挂在系统上——它们由 system_server 持有，不随 App 进程死亡而消失。系统把"最近任务列表"当作用户可见的历史来维护，进程死了历史还在（这也是最近任务里还能看到那个 App 卡片的机制）。
🐛 实战 判断"真泄漏"还是"设计如此"（这是 L4 窗口泄漏猎犬项目的第一道判据）。因果：后台 kill 后 AR/Task 残留是设计（有 cleanUpRemovedTaskLocked 在合适的时机清理），而非泄漏。真泄漏的特征是"只增不减"：反复进出同一个 Activity，计数曲线单调上升。怎么查：分别统计 dumpsys activity activities 里的 Task/AR 数与 dumpsys window windows 里的 WindowState 数，做进出实验对比两条曲线。
🧠 思考（闭环·需结合：块 C、块 I、块 J） 既然 ActivityRecord extends WindowToken（块 C），而 WindowToken 是窗口的容器——那后台 kill 时 WindowState 被清理了，这个 ActivityRecord 容器岂不是空的？这个"空容器"留在树上会不会导致遍历时出问题？想想 06 篇 WindowToken.addWindow() 里那个 if (!mChildren.contains(win)) 的存在意义。

🧠 自测：5 个问题

1. ActivityRecord 为什么直接继承 WindowToken 而不是组合一个？
因为「一个 Activity 的窗口们」天然要共享一份可见性 / 配置 / 动画状态——这正是 WindowToken 的职责（它是窗口树里"一组窗口"的身份单元）。继承让所有按 WindowContainer 遍历的逻辑自动覆盖到 Activity，省掉一层间接转发。
代价是耦合：Activity 的生命周期语义与窗口容器语义混在一个类里（这就是 ActivityRecord.java 上万行的原因）。
2. 为什么后台 kill 进程后，Task 和 ActivityRecord 还在树上，只有 WindowState 没了？
因为它们的宿主不同：WindowState 的宿主是 App 进程（它持有 IWindow 的 binder，进程死了 binder 断连，06 篇学的 linkToDeath 触发清理）；而 Task/ActivityRecord 由 system_server 持有，代表"任务历史"，系统故意保留它——这样用户还能在最近任务里看到那个应用，点回去时有机会重建进程恢复现场。清理由 cleanUpRemovedTaskLocked 在合适的时机做。
3. 启动窗口（splash）什么时候退场？如果它一直不退，锅在哪？
退场时机是真实窗口的 isDrawn() 翻 true——即 WindowStateAnimator.commitFinishDrawingLocked() 把 mDrawState 推到 HAS_DRAWN。
一直不退通常是这个翻转没发生，排查两个方向：mHasSurface=false → 锅在 relayout（窗口还没拿到 surface，往回查 06/03 篇）；mHasSurface=true 但 isDrawn=false → 锅在绘制（App 主线程或 RenderThread 卡住）。
4. AOSP 12 上启动窗口是谁画的？和 WMS 的关系是什么？
12 上启动窗口的实际绘制已经交给 Shell（SystemUI）：WMS 侧的 StartingSurfaceController 只负责"决定该有一个启动窗"，实际 surface 经 TaskOrganizerController.addStartingWindow()（:550 → :134/:316）转发给已注册的 TaskOrganizer。
所以"启动窗口出问题"这类 bug，可能要看两个进程：WMS 侧看它有没有被请求、SystemUI 侧看它有没有画出来。这也是 09 篇要讲的 Shell 接管的一部分。
5. 怎么区分"窗口类泄漏"和"设计如此的历史保留"？
看趋势而非瞬时值：
· 设计如此：后台 kill 后 AR/Task 保留，但用户下次进入或系统到阈值时会清理——计数是有界波动的；
· 真泄漏：反复进出同一个 Activity，WindowState/ActivityRecord 计数单调上升、不回落。
做法：写脚本定期采样两类计数（dumpsys activity activities 与 dumpsys window windows），做进出实验画曲线。WindowManagerGlobal.java:480 那句 "has leaked window" 是客户端侧的兜底报错，可作为交叉验证。
