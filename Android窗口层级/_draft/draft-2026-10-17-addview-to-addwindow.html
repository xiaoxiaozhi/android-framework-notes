〇、全景：一次 addView 的七跳地图

本篇把两站连成一条完整链路：一个裸 View 怎么在 App 进程里变成“窗口台账”中的一条记录，又怎么跨过 binder 在 system_server 里变成挂在窗口树上的 WindowState。

App 进程 system_server ───────────────────────────────────────────────────────────────────────── WindowManagerImpl.addView WindowManagerImpl.java:131 └─ WindowManagerGlobal.addView WindowManagerGlobal.java:321 ├─ new ViewRootImpl（线程绑定） ViewRootImpl.java:766/781 └─ ViewRootImpl.setView ViewRootImpl.java:1000 ├─ requestLayout()（先排首遍遍历） :1096 └─ mWindowSession.addToDisplayAsUser :1119 ─── binder ────────────────▶ Session.addToDisplayAsUser Session.java:200 └─ WMS.addWindow WMS.java:1457 1. checkAddPermission（锁外） 2. synchronized(mGlobalLock) { Display/重复/父窗口校验 WindowToken 解析或创建 new WindowState ← 子窗口在此上树 openInputChannel win.attach + mWindowMap.put mToken.addWindow ← 顶层窗口在此上树 焦点/IME/Z/输入/insets } 3. return res（错误码，不抛异常）

一句话模型 客户端维护“View ↔ ViewRootImpl ↔ LayoutParams”三本按下标对齐的台账；服务端在一把 mGlobalLock 内完成“准入 → 认容器（token）→ 造对象 → 挂树 → 通知外围”。上树 ≠ 显示：本篇结束时窗口有树位、有层级、有输入通道，但没有 frame、没有 Surface 内容，要等下一站 relayoutWindow。

一、客户端台账：WindowManagerGlobal 的三个并行 List

WindowManagerGlobal 是进程内单例（:172 getInstance()），一个 App 进程的所有窗口都登记在它的四个字段里：

WindowManagerGlobal.java:153-159
private final ArrayList<View> mViews = new ArrayList<>();                 // 每个窗口的根 View
private final ArrayList<ViewRootImpl> mRoots = new ArrayList<>();         // 与 mViews 按下标一一对应
private final ArrayList<WindowManager.LayoutParams> mParams = new ArrayList<>(); // 同样按下标对齐
private final ArraySet<View> mDyingViews = new ArraySet<>();             // 已请求删除、MSG_DIE 还没跑完的 View

这段在干什么：同一下标 i 在三个 List 里描述同一个窗口；mDyingViews 是“正在死”的过渡集合。全篇的异常处理都围绕这套下标对齐展开。

设计意图：mLock（:151）保护的只是 App 进程内这三本账，与 system_server 里 ATMS.java:362 的 mGlobalLock 毫无关系——两把锁分处两个进程，别混淆。

这段在干什么：拒绝重复登记；唯独“旧窗口正在异步死亡”这一种竞态被同步清理后放行。

设计意图：删除路径 removeView → removeViewLocked(index, immediate)（:492）→ root.die()（ViewRootImpl.java:8117）非立即模式只发 MSG_DIE 并把 View 放进 mDyingViews，真正从三本账摘除发生在之后的 doRemoveView（:508）。这个“延迟死亡”就是 dying 分支存在的原因。

🐛 实战 IllegalStateException: View ... has already been added to the window manager：同一 DecorView/Popup 的 contentView 被 add 两次且旧的还没 remove 完。注意 dying 分支只救“remove 已发起”的竞态；没发起过 remove 就是硬异常。快速 dismiss/show 的 PopupWindow、把一个 View 复用加进多个 WindowManager 都会踩。

🧠 思考（单块） 块 B 对 dying-view 调的是 doDie() 而不是 die(false)。结合 die()（ViewRootImpl.java:8117：非遍历中才同步 doDie，否则只 sendEmptyMessage(MSG_DIE)）想：这里为什么必须同步死，而不能只发 MSG_DIE 排队？
参考答案
本次 addView 紧接着就要在同一下标上 new ViewRootImpl 并重新登记（块 C）。若只发 MSG_DIE，旧根要到后续主线程消息轮次才真正 doDie → doRemoveView，届时它会把新根按旧下标从 mRoots/mViews/mParams 里摘掉（三本账按下标对齐，不区分新旧）。同步 doDie 保证“旧根在新根登记前彻底出账”，把下标腾干净。

这段在干什么：创建 ViewRootImpl 并完成线程绑定，先把三本账登记好，最后调 setView 启动窗口；失败则用进入同步块时算好的旧 index 回滚。

设计意图：源码注释 “do this last because it fires off messages” 点明了顺序——setView 之后系统回调随时可能重入，台账必须先就位。这与服务端“先 mWindowMap.put 后挂树”是同一个防御思路在两个进程的对称出现（见第七、八节）。

🧠 思考（单块） 若把三个 add(...) 挪到 setView 成功之后（看似更省回滚），会破坏什么？catch 里为什么用进入同步块时的旧 index，而不是重新 findViewLocked？
参考答案
(1) setView 内 addToDisplayAsUser 返回后，窗口可能立刻收到 relayout/配置/insets 等回调，这些回调经 ViewRootImpl 重入 WMG 按 View 反查 root；若尚未登记，反查失败，出现“系统侧已在册、客户端查无此窗”的不一致。(2) 新登记位置一定在列表尾部，但在 dying-view 竞态 + 列表中还有别的窗口时，重新查找拿到的是新根下标，而需要回滚的正是新根本身——代码用旧 index 在“非竞态的重复添加”场景其实恒为 -1（那条路直接抛异常了），真正走到 catch 的常规路径 index 就是新登记位。关键是回滚语义要对准“本次刚加的那一条”，旧 index 在 doDie 同步清理后正好等于新根位置；重新查找反而引入歧义。

🧠 思考（单块） 若 parentWindow.addChild(this, ...) 成功后构造函数剩余语句抛异常，窗口树会留下什么？WMS 调用方还能靠返回错误码干净回滚吗？注释承诺的保护边界到哪里为止？
参考答案
树里会留下一个已挂载但后续字段（mWinAnimator 等）可能未初始化完的 WindowState，而 mWindowMap 尚未 put（第七节才做），它成了“在树但查不到、无人回收”的孤儿节点。调用方拿异常而非错误码，块 D 第二段没有 try/catch 兜底，异常会直接穿回 binder 给客户端，服务端这一侧不会自动把它从父窗口摘除。注释只保证“addChild 之前字段初始化完，使 addChild 触发的 onDisplayChanged 等回调不读到半字段”，并不能保证 addChild 之后的代码不抛异常——这也是为什么 addChild 被刻意放在构造函数极靠后、其后只剩注册配置监听等少量代码的原因。

🧠 思考（单块） 假如把 mWindowMap.put 之后、mToken.addWindow 之前改回“可失败返回错误码”，客户端 catch 回滚后，服务端会留下什么脏状态？为什么“在册但不在树”比直接崩溃更难排查？
参考答案
mWindowMap 里已有该 client → WindowState，后续 relayout/remove/按键投递都能查到它，但它不在任何 WindowToken 的 mChildren 里：不参与布局遍历、不参与层级/Z/可见性计算、dump 窗口树时不可见，却占着 client binder（重复 add 会撞 ADD_DUPLICATE_ADD）、持有 InputChannel 与死亡监听。它不会崩溃，也没有任何正常路径能把它清掉（removeWindow 按树查找反而可能找不到），成为静默泄漏。相比之下快速崩溃有明确栈和现场，这种“幽灵在册”只表现为后续莫名的重复添加/输入异常，排查成本高得多。所以源码用“no exceptions or errors allowed”把此后全部设计成不可能失败的纯内存操作。

🧠 思考（闭环·需结合：第四节块B、第六节、本节） 一个 TYPE_APPLICATION_ATTACHED_DIALOG 走完本方法后：它在树里的父节点是谁？Z 序由哪两个层级值/comparator 决定？此刻它的 frame 是什么值、屏幕位置要到哪个下游调用才确定？

类型落在 FIRST_SUB_WINDOW..LAST_SUB_WINDOW，第四节块 B 经 windowForClientLocked 找到父顶层窗口（hasParent=true），第五节复用父窗口 token；第六节 mIsChildWindow=true，构造函数里 parentWindow.addChild(this, sWindowSubLayerComparator)——所以树父节点是父 WindowState，不是 WindowToken。Z 序由父窗口的 mBaseLayer（getWindowLayerLw × TYPE_LAYER_MULTIPLIER + OFFSET）定大区间、自己的 mSubLayer（getSubWindowLayerFromTypeLw，ATTACHED_DIALOG 为正值，在父窗口之上）定区间内次序，再由本节 assignChildLayers() 一次性赋值。此刻 frame 为空（WindowState 初始 mRequestedWidth/Height=0，未布局），屏幕位置要到下一站 relayoutWindow → computeFrame（阶段 3 主线）才确定；attached 类型 mLayoutAttached=true，frame 还会相对父窗口坐标系计算。

🐛 实战（闭环·需结合：第七、八节 + 第二节） 加窗口成功但黑屏/ANR、无崩溃：说明已越过不可返回点、树也上了，但 App 主线程迟迟不跑 relayout（典型 onCreate 里同步耗时）。查：dumpsys window windows 找到该 WindowState，看 relayoutCalled=false、isDrawn=false——这两个值把锅精确指向下一站 relayout 而非 addWindow；再 dumpsys input 看焦点是否已指向它（焦点在它、它不响应 → App 主线程卡；焦点没切过去 → 查焦点/可见性路径，两条路查法不同）。

九、跨站闭环：BadTokenException 的完整因果链

线上现象：Activity 在异步回调里 show Dialog，偶现 android.view.WindowManager$BadTokenException，dump 显示该 ActivityRecord 已不在树中。包一层 runOnUiThread 仍偶发。

① Activity 进入销毁，ActivityRecord 从 Task 摘除（getParent() == null） ② 异步回调（网络/Handler/post）此刻才执行 Dialog.show() ③ App：WindowManagerGlobal.addView → ViewRootImpl.setView └─ session.addToDisplayAsUser ── binder ──▶ system_server ④ WMS.addWindow 第五节两个返回点之一： · token 查不到 → ADD_BAD_APP_TOKEN（:1564） · activity.getParent()==null → ADD_APP_EXITING（:1594） ⑤ 错误码过 binder 返回（全程无异常抛出） ⑥ App：ViewRootImpl.setView :1148 res < ADD_OKAY └─ switch(res) 翻译成 BadTokenException 抛出（:1156-1166） ⑦ WindowManagerGlobal 块 C catch：removeViewLocked(index, true) 回滚三本账 ⑧ 异常继续抛给业务线程 → 崩溃（或被业务 try/catch 吞掉）

为什么 runOnUiThread 救不了：时序卡点不在“是不是主线程调用”，而在 show 执行的那一刻，服务端第五节的 ActivityRecord 是否还挂在 Task 上。Runnable 排队到主线程，完全可能在 destroy 之后才轮到执行。正确判据是生命周期状态：activity.isFinishing() || activity.isDestroyed()（Fragment 用 viewLifecycleOwner 的 RESUMED 状态）时不再弹窗；根治手段是把 UI 操作绑定生命周期（LifecycleObserver / lifecycleScope 自动取消），而不是切线程。

设计回顾 “错误码跨进程、异常在客户端抛”是整条链的统一约定：服务端十几种拒绝原因全用整数码（ViewRootImpl.java:1156-1195 逐码翻译），保证服务端绝不留半成品；客户端在块 C 集中回滚台账并抛出带排查文案的异常。排障时务必用服务端返回码区分 ADD_BAD_APP_TOKEN 与 ADD_APP_EXITING，两者修复方向不同（前者多为 token 传错，后者纯生命周期时序）。
