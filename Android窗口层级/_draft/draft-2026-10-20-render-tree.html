一、先看结论：一张图看懂两棵树

这篇只回答一个问题：逻辑窗口树里的一个 WindowState，怎样变成 SurfaceFlinger 里的一块 Layer？ 先把结论画出来，后面再逐层拆。

逻辑树（system_server · Java）Surface 树（SurfaceFlinger · C++）
RootWindowContainer └─ DisplayContent #0 └─ DisplayArea:FeatureRoot └─ TaskDisplayArea └─ Task #42 └─ ActivityRecord (extends WindowToken) └─ WindowState(app) ★ └─ WindowState(sub) ★
Layer "Root" └─ Layer "DisplayArea:FeatureRoot" └─ Layer "TaskDisplayArea" └─ Layer "Task=42" └─ Layer "ActivityRecord" └─ BufferStateLayer "Window{...}" ★ └─ BufferStateLayer "Window{...}" ★
✦ ✦ ✦ 读图四条规则 ✦ ✦ ✦
① 不是每个节点都有 Layer：DisplayContent 的 "Root" 容器图层在构造时就建好（DisplayContent.java:1061-1065）；DisplayArea / Task 等容器只有在需要裁剪、变换或做动画时才通过 makeSurface().setContainerLayer() 建容器图层（WindowContainer.java:2538）。
② 只有 WindowState 必须有 buffer layer：因为只有它要装 App 或系统绘制的内容；容器图层不承载像素，只负责组织层级、裁剪和变换。
③ 应用窗口的 token 就是 ActivityRecord：ActivityRecord extends WindowToken（ActivityRecord.java:365），所以逻辑树里不要再画“ActivityRecord → WindowToken”两层；系统窗口（状态栏、导航栏）才用普通 WindowToken。
④ 两棵树是投影关系，不是复制关系：Surface 树按需生长，父子关系和 Z 序必须与逻辑树一致，但节点数量可以不同。

一句话记住：逻辑树是图纸和管理处，Surface 树是真实舞台。WMS 在逻辑树里做决策，再把决策翻译成 SurfaceControl.Transaction 指令；SurfaceFlinger 只认 Surface 树。

二、为什么需要第二棵树

因为决策者和执行者不在一个进程，也不认同一种对象。WMS 手里是 Java 的 WindowState；SurfaceFlinger 手里是 C++ 的 Layer。两边必须有一棵树来对齐“谁是谁的孩子、谁在谁上面、谁裁剪谁”。

逻辑树（窗口树）Surface 树（图层树）
所在进程system_serverSurfaceFlinger 进程持有实体
节点是什么WindowContainer 子类（Java 对象）Layer（C++ 对象，如 BufferStateLayer）
手里的引用mSurfaceControl客户端侧 SurfaceControl（只是句柄）
决定什么归属、可见性、布局、Z 序策略实际位置、矩阵、Z 值、alpha、Buffer
谁让两者同步WindowContainer.getSyncTransaction() / 全局 Transaction
为什么不能把 Java 对象直接交给 SF？ 三个原因：① 跨进程——SF 不可能持有 system_server 的 Java 对象；② 生命周期——窗口随时可能被销毁，句柄比对象好管理；③ 权限与稳定——App 只能拿到一个受控的 handle，不能直接改 SF 的内部状态。所以 Android 的解法是：对象本体留在 SF，客户端只拿 SurfaceControl 句柄。

三、Surface 树是怎么长出来的

Surface 树不是一次性建好的，而是随着窗口上树、首次布局逐步长出来。按时间顺序看五步：

1屏幕根节点：DisplayContent 建 "Root"
DisplayContent 构造时调用 setContainerLayer()，建出名为 "Root" 的容器图层（DisplayContent.java:1061-1065）。它是整块屏幕 Surface 子树的根，所有窗口图层最终都挂在它下面。
2窗口 token：首个顶层窗口加入时建容器图层
WindowToken.addWindow() 在 mSurfaceControl == null 时调用 createSurfaceControl(true)（WindowToken.java:297-315）。应用窗口的 token 是 ActivityRecord，它继承 WindowToken（ActivityRecord.java:365），addWindow() 里先调 super.addWindow(w)（ActivityRecord.java:3713），所以同样会建出 ActivityRecord 的容器图层。
3容器按需向上递归找父图层
WindowContainer.makeSurface() 返回一个 SurfaceControl.Builder，setContainerLayer() 把它设成容器图层（WindowContainer.java:2188 / 2538）。DisplayArea / Task 等节点只有在需要承接子 Surface 时才建，避免给每个逻辑节点都建一层空图层。
4窗口首次 relayout：建真正的 BufferStateLayer
addWindow 只上树，不建画布。App 首帧 relayout 时，WMS 走 createSurfaceControl()（WindowManagerService.java:2597）→ WindowStateAnimator.createSurfaceLocked()（:304）→ WindowSurfaceController 构造函数（:79）→ b.build()（:109）→ Binder 到 SurfaceFlinger::createLayer()（SurfaceFlinger.cpp:4289），造出一个 BufferStateLayer 并挂进 SF 的 Layer 树。
5句柄回传：App 拿到画布
WindowSurfaceController.getSurfaceControl() 只有一句 copyFrom()（:275-276），把新图层的引用拷进 relayout 的输出参数；Binder reply 回到 App 后，ViewRootImpl.getOrCreateBLASTSurface()（:1958）用这个句柄建 BLASTBufferQueue 和 Surface。到这里，App 才有地方画像素。
WindowSurfaceController.java:91-109（节选）
final SurfaceControl.Builder b = win.makeSurface()
        .setParent(win.getSurfaceControl())      // 挂到父容器图层下
        .setName(name)
        .setBufferSize(w, h)                  // 只有 buffer 图层才有尺寸
        .setFormat(format)
        .setFlags(flags)
        .setMetadata(METADATA_WINDOW_TYPE, windowType);
if (useBLAST) b.setBLASTLayer();            // Android 12 默认走 BLAST
mSurfaceControl = b.build();               // ★ Binder 到 SF 建 Layer

关键边界 addWindow ≠ 显示。上树那一刻，窗口只有逻辑身份、树位、Z 序和输入通道；frame 为空、没有 Buffer。必须等首帧 relayout，Surface 树才长出对应的 buffer layer。

四、谁有 Buffer，谁只是容器

这是整篇最重要的一张表。看树的时候，先问一句：这个节点是“装像素的”，还是“组织像素的”？

位置逻辑树节点Surface 树节点图层类型何时创建带 Buffer？作用
0RootWindowContainer———否全局树根，不直接对应图层
1DisplayContent #0Layer "Root"ContainerLayer构造时否整块屏幕图层子树的根
2DisplayArea:FeatureRootLayer "DisplayArea:..."ContainerLayer按需否按 Feature 分区、裁剪、组织 Z 序
3TaskDisplayAreaLayer "TaskDisplayArea"ContainerLayer按需否应用区容器
4Task #42Layer "Task=42"ContainerLayer按需否任务卡片范围、动画/截图
5aActivityRecord（应用窗口 token）Layer "ActivityRecord"ContainerLayer首个顶层窗口加入时否Activity 级容器；token 本体
5bWindowToken（系统窗口 token）Layer "WindowToken"ContainerLayer首个顶层窗口加入时否一组系统窗口的共同父容器
6WindowState（顶层/子窗）BufferStateLayer "Window{...}"BufferStateLayer（BLAST）首次 relayout是真正承载 App/系统绘制的内容
7动画 leash（临时节点）Layer "animation-leash of ..."ContainerLayer动画期间否只动缰绳，不动原图层（09 篇）
✦ ✦ ✦ 一句话区分 ✦ ✦ ✦
ContainerLayer 是“文件夹”：它可以有子图层、可以裁剪和变换，但自己不放像素。
BufferStateLayer 是“画纸”：它必须有 Buffer，App 或系统把这一帧画进去。
所以看到 dumpsys SurfaceFlinger --list 里一大串 Layer，不要以为每个都在显示内容——大多数只是容器。

五、Z 序：树上的顺序怎么变成整数

Surface 树里没有“兄弟列表顺序”这个概念，只有每个 Layer 的 Z 值。这个整数由 WMS 算好，再通过事务写给 SF。

入口是 WindowContainer.assignChildLayers()（:2290）：它做两趟遍历，第一趟给普通孩子按顺序分配，第二趟给需要 Z-boost 的孩子补到末尾。

WindowContainer.java:2290-2309（节选）
void assignChildLayers(Transaction t) {
    int layer = 0;
    // 第一趟：普通孩子按 mChildren 顺序
    for (int j = 0; j < mChildren.size(); ++j) {
        final WindowContainer wc = mChildren.get(j);
        wc.assignChildLayers(t);
        if (!wc.needsZBoost()) wc.assignLayer(t, layer++);
    }
    // 第二趟：Z-boost 孩子补到末尾
    for (int j = 0; j < mChildren.size(); ++j) {
        final WindowContainer wc = mChildren.get(j);
        if (wc.needsZBoost()) wc.assignLayer(t, layer++);
    }
}

叶子节点由 WindowState.assignLayer()（:5648）接手：先处理 IME 相对层级，再调 super.assignLayer(t, layer)。最终 SurfaceControl.Transaction.setLayer() 把这个整数写给 SF；SF 在 VSYNC 里按 Z 值从小到大叠。

✦ ✦ ✦ 为什么必须“一把事务” ✦ ✦ ✦
如果 100 个窗口的位置、Z 序、可见性一个个单独提交，SF 每收到一个就可能合成一次，用户会看到画面“跳着变”。WMS 在布局遍历结束时打开全局事务，把所有变更合并，再一次性关闭提交（03 篇第七节）。一帧内的中间状态永远不上屏——这就是 openSurfaceTransaction() / closeSurfaceTransaction() 的意义。

六、一帧的生命周期（只看树的变化）

把前面的步骤压成一条时间线，重点看每一步 Surface 树多了什么、谁在改它：

阶段逻辑树侧（WMS）Surface 树侧（SF）关键入口
① addWindowWindowState 挂进树；token 容器图层可能建出新增容器 Layer（如果 token 是首次）WindowToken.addWindow :297
② 首帧 relayout算 frame、可见性；决定建画布新增 BufferStateLayerWMS.createSurfaceControl :2597
③ 句柄回传把 SurfaceControl 交给 AppLayer 本体不动，只回传句柄WindowSurfaceController :275
④ App 绘制—BLASTBufferQueue 在 App 进程 dequeue/queueViewRootImpl :4418
⑤ BLAST 提交—Buffer 打包进 Transaction 送到 SFBLASTBufferQueue :546
⑥ WMS 事务位置/Z/alpha/可见性写入全局事务等待 SF 消费closeSurfaceTransaction（03 篇）
⑦ SF 合成—commit → composite(HWC/GPU) → presentSurfaceFlinger.cpp :3232
两条信息流：WMS 的全局事务带“几何/Z/可见性”；App 的 BLAST 事务带“这一帧的 Buffer”。两条流在 SF 的事务队列里汇合，同一个 VSYNC 原子生效。这就是为什么窗口 resize 时不会出现“新尺寸配旧内容”的半帧。

七、真机对照与六个常见误解

7.1 两条命令，把两棵树抓出来

逻辑树看 WMS，Surface 树看 SF。两条命令的输出可以按窗口名/任务号对上：

adb（设备连接后执行）
# 逻辑树：WindowState、mToken、frame、mLayer
adb shell dumpsys window windows

# 图层树：最快的列表，先看名字
adb shell dumpsys SurfaceFlinger --list

# 图层详情：Z、crop、transform、buffer
adb shell dumpsys SurfaceFlinger

对照技巧：Task.getName() 返回 "Task=" + mTaskId（Task.java:3942），所以 dumpsys SurfaceFlinger --list 里的 Task=42 可以直接对上逻辑树里的 Task #42；窗口图层名通常包含 Window{...}，和 dumpsys window windows 里的 WindowState 一一对应。

7.2 六个常见误解

  1. “每个 WindowContainer 都有 Surface。”错。DisplayArea/Task 等容器按需建，只有 WindowState 必须有 buffer layer。
  2. “SurfaceControl 就是 Layer 本体。”错。它只是指向 SF 中 Layer 的跨进程句柄，Layer 本体始终留在 SF。
  3. “ActivityRecord 下面还有一层 WindowToken。”错。ActivityRecord extends WindowToken（:365），应用窗口的 token 就是 ActivityRecord 本身。
  4. “Z 序就是树的遍历顺序。”错。遍历顺序只是输入，最终是 assignChildLayers 算出的整数 mLayer，由 SF 按整数叠。
  5. “addWindow 就创建了 Surface。”错。addWindow 只上逻辑树；首帧 relayout 才建 buffer layer。
  6. “Surface 树是逻辑树的完整复制。”错。它是投影：父子关系一致，但容器节点可以没有 Layer，数量不必相等。

8.2 自测（5 题）

1. 为什么 DisplayArea 有 Layer 却没有像素？
因为它是 ContainerLayer，只负责裁剪、变换和组织子图层，不承载 Buffer。只有 WindowState 对应的 BufferStateLayer 才装像素。
2. 为什么 ActivityRecord 不是 WindowToken 的子节点？
ActivityRecord extends WindowToken（ActivityRecord.java:365），它是 WindowToken 的一种特化；应用窗口的 token 就是 ActivityRecord 本身。系统窗口（状态栏等）才用普通 WindowToken。
3. SurfaceControl 里到底存的是什么？
指向 SurfaceFlinger 中某个 Layer 的跨进程句柄，不是 Layer 本体，也不是像素。句柄可跨进程传递，Layer 本体始终留在 SF。
4. addWindow 之后到首帧上屏，Surface 树新增了哪些节点？
addWindow：token 容器图层（如果首个顶层窗口）；首帧 relayout：WindowState 的 BufferStateLayer；App 侧另外建 BLASTBufferQueue/Surface，但那是客户端队列，不是 SF 的新 Layer。
5. Z 序由谁决定、谁执行？为什么必须一把事务？
WMS 的 assignChildLayers 算整数 mLayer，写进 SurfaceControl.Transaction；SF 在 VSYNC 里按事务更新 Z 值并合成。一把事务保证一帧内的几何、Z、可见性、Buffer 原子生效，中间状态不上屏。
