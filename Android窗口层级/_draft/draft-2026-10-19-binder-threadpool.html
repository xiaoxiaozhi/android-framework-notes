一、全景：为什么服务端必须有「线程池」

B0 里说过一句话：「服务端执行事务的是 Binder 线程，不是主线程」。但没说清为什么需要「池」、池有多大、谁管扩容。这一篇把这个"看不见的劳动力市场"讲透。

问题的起点：调用会阻塞

如果服务端只有 1 个 Binder 线程会怎样？ A 调用 S.foo()（同步，等结果） │ ▼ S 的 Binder 线程开始执行 foo() ──▶ 需要调另一个服务 T.bar() │ │ 阻塞等待 T 的回复 ▼ ✗ 此时 B 也想调 S.baz() —— 但唯一那条 Binder 线程还卡在 foo() 里 B 的请求只能排队 → B 被拖慢 → 如果 B 是 system_server，全线卡死 所以：必须有多条 Binder 线程，让"阻塞"不传染。

但"多"不能无限——每条线程都要占栈（默认 1MB 虚拟地址）、要被调度。于是有了这套设计：

机制谁负责做什么
初始线程用户态进程启动时起 1 条主 Binder 线程
上限用户态 + 驱动默认 15 条，通过 BINDER_SET_MAX_THREADS 告诉驱动
扩容驱动发起驱动发现"都忙"时下发 BR_SPAWN_LOOPER，用户态收到就起新线程
收缩用户态池线程空闲超时（TIMED_OUT）就退出
饥饿监测用户态忙碌计数触顶超过 100ms 就打 binder thread pool starved
源码边界（同 B1） 「驱动怎么判断"都忙"、什么时候发 BR_SPAWN_LOOPER」这部分在内核 drivers/android/binder.c，不在这棵 AOSP 树里。本篇只讲用户态能看到的：收到命令后怎么起线程、怎么计数、怎么退出。
类比 银行网点：1 号窗口常开（主 Binder 线程）；客户排长队时经理打电话叫人来开新窗口（驱动发 BR_SPAWN_LOOPER）；最多开到 15 个窗口（BINDER_SET_MAX_THREADS）；没人了就关掉多余窗口（空闲超时退出）。
而"15 个窗口全在办大额业务、谁也动不了"就是饥饿/死锁——门口队伍无限长，但你不会收到"网点故障"的报错，只会觉得"怎么这么慢"。
🔗 三篇 Binder 的关系：B0 讲一次调用怎么走完整链路；B1 讲驱动边界与一次拷贝；B2（本篇） 讲"谁来执行、能同时执行几个、卡住了会怎样"。这三篇合起来，你才能解释"Binder 调不通/很慢/莫名 ANR"这类问题。

二、池的诞生：startThreadPool 与 PoolThread

每个进程第一次用 Binder（通常是 ProcessState::self()）时会做初始化，但线程池不是自动起的——要显式调 startThreadPool()。

块 A：起第一条线程（ProcessState.cpp:139 / 339 / 58）

ProcessState.cpp:58-70、139-147、339-347
class PoolThread : public Thread
{
public:
    explicit PoolThread(bool isMain) : mIsMain(isMain) {}
    // ① 只是记下"我是不是主线程"，没有别的状态

protected:
    virtual bool threadLoop()
    {
        IPCThreadState::self()->joinThreadPool(mIsMain);
        return false;
        // ② ★ 线程体就一行：进池子（joinThreadPool 不会返回，直到该退出）
        //    return false 表示"这个 Thread 对象不要循环调用 threadLoop"
    }
};

void ProcessState::startThreadPool()
{
    AutoMutex _l(mLock);
    if (!mThreadPoolStarted) {
        mThreadPoolStarted = true;
        spawnPooledThread(true);
        // ③ ★ 只起 1 条，且标记为"主"（isMain=true）——
        //    主线程的意义见块 C：它不会因空闲而退出
    }
}

void ProcessState::spawnPooledThread(bool isMain)
{
    if (mThreadPoolStarted) {
        String8 name = makeBinderThreadName();
        sp<Thread> t = sp<PoolThread>::make(isMain);
        t->run(name.string());
        // ④ 起线程并命名（名字见下）
    }
}

这段在干什么：起一条（或多条）线程，线程体进入 joinThreadPool 循环。

设计意图：为什么线程体只有一行。因为"当 Binder 线程"这件事的全部逻辑都在 joinThreadPool 里：注册、取命令、执行、判断要不要退出。把 PoolThread 做成极薄的壳，是为了让"起线程"和"跑循环"解耦——加线程时不需要关心循环细节。

块 B：线程名——排障时最有用的一行（ProcessState.cpp:331）

ProcessState.cpp:331-337
String8 ProcessState::makeBinderThreadName() {
    int32_t s = android_atomic_add(1, &mThreadPoolSeq);
    pid_t pid = getpid();
    String8 name;
    name.appendFormat("Binder:%d_%X", pid, s);
    // ① 格式：Binder:<pid>_<序号，十六进制>
    //    例如 Binder:1234_3 —— 1234 是进程 pid，3 是该进程第 4 条（从 1 递增）

    return name;
}
// ② ★ 这个命名是排障的入口：
//    adb shell cat /proc/<pid>/task/*/comm | grep Binder
//    可以直接数出"这个进程当前有几条 Binder 线程"
//    ps -T -p <pid> 也能看到它们各自的 CPU/状态
// ③ 用十六进制序号是为了省字符（线程名上限 15 字符）——
//    pid 最大 7 位 + "Binder:" 7 位 + "_" + 序号，刚好够

这段在干什么：给每条线程起名 Binder:<pid>_<seq>。

设计意图：线程名是唯一能在 /proc 里"按名字筛选"的标识。没有它，你只能靠栈去猜哪条是 Binder 线程。这条信息在诊断"线程池是否打满"时是决定性的——先数出数量，再决定要不要挖栈。

🐛 实战 想知道某个系统进程吃了几条 Binder 线程：
adb shell ps -A | grep system_server 拿 pid，然后
adb shell "cat /proc/<pid>/task/*/comm" | grep -c Binder。
如果接近 15（上限），说明可能已经打满——接着看 §4 的饥饿日志与 §6 的死锁环路。

三、扩容与收缩：BR_SPAWN_LOOPER 与超时退出

池子会自己长大，然后自己缩小。这两件事分别发生在两个地方：长大由驱动"催"，缩小由线程自己"走"。

块 C：线程循环——唯一的进出点（IPCThreadState.cpp:617）

IPCThreadState.cpp:617-650
void IPCThreadState::joinThreadPool(bool isMain)
{
    mOut.writeInt32(isMain ? BC_ENTER_LOOPER : BC_REGISTER_LOOPER);
    // ① ★ 入池登记：主线程报 BC_ENTER_LOOPER，池线程报 BC_REGISTER_LOOPER
    //    驱动据此把它们记到"这个进程的线程池"里——
    //    ★ 只有登记过，驱动才可能给它派活（B1 的 ioctl 就靠这个）
    //    两者的区别：ENTer 的那条在池子里是"常驻"，REGISTER 的会被回收

    mIsLooper = true;
    status_t result;
    do {
        processPendingDerefs();
        // ② 处理积压的对象解引用（释放已经没人引用的 BpBinder 等）

        result = getAndExecuteCommand();
        // ③ ★ 核心：取一条命令并执行（内部 talkWithDriver → executeCommand）
        //    没有命令时，这里会阻塞在 ioctl 上睡眠——不耗 CPU

        if (result < NO_ERROR && result != TIMED_OUT && result != -ECONNREFUSED && result != -EBADF) {
            LOG_ALWAYS_FATAL("getAndExecuteCommand(fd=%d) returned unexpected error %d, aborting",
                  mProcess->mDriverFD, result);
            // ④ 非预期错误 → 直接崩溃（驱动出问题就没有安全退路）
        }

        if (result == TIMED_OUT && !isMain) {
            break;
            // ⑤ ★★ 收缩机制：池线程空闲超时就退出；主线程（isMain）不退出
            //    这保证进程永远至少有 1 条 Binder 线程可用
        }
    } while (result != -ECONNREFUSED && result != -EBADF);
    // ⑥ 驱动 fd 失效（进程要死了）才跳出

    mOut.writeInt32(BC_EXIT_LOOPER);
    mIsLooper = false;
    talkWithDriver(false);
    // ⑦ ★ 离池必须主动注销：告诉驱动"我走了，别再给我派活"
    //    否则驱动仍以为这条线程可用，派过来的事务没人接 → 对端永久等待
}

这段在干什么：线程入池登记 → 循环取活干 → 空闲超时（非主线程）退出 → 离池注销。

设计意图："主线程不退出"是最小可用性的保证。如果所有线程都能空闲退出，那么某个瞬间可能出现"池里 0 条线程"——此时有事务进来，驱动会一直等（或要求新建，但那是异步的，存在窗口期）。保留一条常驻线程消除了这个窗口。代价：每个用过 Binder 的进程至少多一条常驻线程。

🐛 实战 服务"假死"：调用方永远等不到回复。因果：某条 Binder 线程在执行中崩了/被异常路径跳过，没有走到 ⑦ 的 BC_EXIT_LOOPER；驱动以为它还在，把事务派给它 → 无人处理。怎么查：adb shell ps -T -p <pid> 看 Binder:* 线程是否停在奇怪的位置；服务端日志里找有没有 *_LEAVING THE THREAD POOL（LOG_THREADPOOL 宏，需打开日志）。

status_t ProcessState::setThreadPoolMaxThreadCount(size_t maxThreads) {
    LOG_ALWAYS_FATAL_IF(mThreadPoolStarted && maxThreads < mMaxThreads,
           "Binder threadpool cannot be shrunk after starting");
    // ④ ★★ 启动后不允许缩小上限，否则直接 fatal ——
    //    因为已经存在的线程数可能超过新上限，计数逻辑会错乱
    if (ioctl(mDriverFD, BINDER_SET_MAX_THREADS, &maxThreads) != -1) {
        mMaxThreads = maxThreads;
        // ⑤ 同步告诉驱动（驱动据此决定最多催生到几条）
    }
}

这段在干什么：收到 BR_SPAWN_LOOPER 就起一条新池线程；上限通过 ioctl 告知驱动，且启动后不能调小。

设计意图：扩容决策权在驱动，不在用户态。因为只有驱动知道"此刻这个进程有没有空闲线程可接活"——用户态看不到全局队列。这个分工很关键：如果让用户态自己判断"我要不要加线程"，它只能靠猜（比如"我这条线程忙了"），会过度扩容。

🐛 实战 报 Binder threadpool cannot be shrunk after starting 直接崩溃。因果：某个模块在 startThreadPool() 之后调用 setThreadPoolMaxThreadCount() 且传了更小的值（常见于"动态调整上限"的错误实现）。怎么查：搜代码里对该函数的调用点，确认都在启动前；要调大可以（允许），调小不行。

四、忙碌计数与饥饿检测

这一节是 B2 的核心：系统怎么知道"线程池快撑不住了"，以及你为什么会看到那条 starved 日志。

块 E：一次取活前后的计数（IPCThreadState.cpp:519）

IPCThreadState.cpp:519-558（裁剪）
status_t IPCThreadState::getAndExecuteCommand()
{
    status_t result;
    int32_t cmd;

    result = talkWithDriver();
    // ① 阻塞在这里等命令（没有活时睡眠，不耗 CPU）
    if (result >= NO_ERROR) {
        size_t IN = mIn.dataAvail();
        if (IN < sizeof(int32_t)) return result;
        cmd = mIn.readInt32();
        // ② 读出一条命令（BR_*）

        pthread_mutex_lock(&mProcess->mThreadCountLock);
        mProcess->mExecutingThreadsCount++;
        // ③ ★ 开始执行：忙碌计数 +1
        if (mProcess->mExecutingThreadsCount >= mProcess->mMaxThreads &&
                mProcess->mStarvationStartTimeMs == 0) {
            mProcess->mStarvationStartTimeMs = uptimeMillis();
            // ④ ★★ 首次"全忙"时记下时间戳 —— 饥饿计时的起点
            //    注意条件是 >= mMaxThreads：所有线程都在执行才算
        }
        pthread_mutex_unlock(&mProcess->mThreadCountLock);

        result = executeCommand(cmd);
        // ⑤ 真正干活（BR_TRANSACTION → 回调 Java 服务实现）

        pthread_mutex_lock(&mProcess->mThreadCountLock);
        mProcess->mExecutingThreadsCount--;
        // ⑥ 干完：忙碌计数 -1
        if (mProcess->mExecutingThreadsCount < mProcess->mMaxThreads &&
                mProcess->mStarvationStartTimeMs != 0) {
            int64_t starvationTimeMs = uptimeMillis() - mProcess->mStarvationStartTimeMs;
            if (starvationTimeMs > 100) {
                ALOGE("binder thread pool (%zu threads) starved for %" PRId64 " ms",
                      mProcess->mMaxThreads, starvationTimeMs);
                // ⑦ ★★★ 饥饿日志！只在"全忙持续 > 100ms"时打一次
                //    看到这条日志＝你的进程在这段时间内无法接收新事务
            }
            mProcess->mStarvationStartTimeMs = 0;
        }

        // Cond broadcast can be expensive, so don't send it every time a binder
        // call is processed. b/168806193
        if (mProcess->mWaitingForThreads > 0) {
            pthread_cond_broadcast(&mProcess->mThreadCountDecrement);
            // ⑧ 有人在 blockUntilThreadAvailable 里等 → 通知它
        }
        pthread_mutex_unlock(&mProcess->mThreadCountLock);
    }

    return result;
}

这段在干什么：每次执行命令前后各改一次忙碌计数；全忙时开始计时，超过 100ms 就打日志。

设计意图：为什么用"计数触顶 + 100ms"而不是"平均延迟"。因为 Binder 线程池的问题特征是瞬时全忙：平时 1~2 条线程够用，突发时瞬间打满。平均值会把这个尖峰摊平到看不见；而"触顶持续 100ms"能精确抓住这种尖峰，且误报率低（100ms 已远超正常事务处理时间）。

🐛 实战 logcat 里刷 binder thread pool (15 threads) starved for 250 ms。因果：该进程所有 Binder 线程同时被占住 ≥100ms，期间新事务全部排队。三大常见根因：① 某条线程在做同步 binder 调用且对端慢（阻塞传染）；② 某条线程在等锁（Java 层 synchronized 死等）；③ 事务处理里做了重活（大 JSON 解析、数据库批量写）。怎么查：立刻 adb shell ps -T -p <pid> 看 15 条 Binder:* 的状态，再抓 kill -3 拿所有线程栈——看它们卡在 waitForResponse、monitor 还是业务代码。

块 F：等线程可用（IPCThreadState.cpp:504）

IPCThreadState.cpp:504-517
void IPCThreadState::blockUntilThreadAvailable()
{
    pthread_mutex_lock(&mProcess->mThreadCountLock);
    mProcess->mWaitingForThreads++;
    // ① 登记"有人在等"——这个计数决定了块 E 的 ⑧ 要不要广播

    while (mProcess->mExecutingThreadsCount >= mProcess->mMaxThreads) {
        ALOGW("Waiting for thread to be free. mExecutingThreadsCount=%lu mMaxThreads=%lu
",
                (unsigned long)mProcess->mExecutingThreadsCount,
                (unsigned long)mProcess->mMaxThreads);
        pthread_cond_wait(&mProcess->mThreadCountDecrement, &mProcess->mThreadCountLock);
        // ② ★ 全忙就睡在条件变量上，直到有人干完活（块 E 的 ⑧ 广播）
        //    注意：这里会往 logcat 打 WARN —— 也是"线程池紧张"的信号
    }
    mProcess->mWaitingForThreads--;
    pthread_mutex_unlock(&mProcess->mThreadCountLock);
}

这段在干什么：需要"保证有线程可用"的调用方（如 flushCommands、joinThreadPool 的某些路径）在这里等，直到计数降下来。

设计意图：这是线程池的"背压"。当池满时，不是静默排队（那样会无限堆积），而是让调用方显式等待并打 WARN —— 让问题暴露出日志，而不是悄悄变慢。

两条日志的区别 binder thread pool (15 threads) starved for N ms = 事后统计（已经全忙了一段时间，刚恢复）；
Waiting for thread to be free. mExecutingThreadsCount=15 mMaxThreads=15 = 实时事件（此刻正在等）。
前者适合写报告，后者适合抓现场。

五、oneway 洪水与缓冲区耗尽

线程池说的"线程不够"，和 B1 说的"缓冲区不够"，是两种不同的资源耗尽，症状也不同。混淆它们会导致查错方向。

块 G：oneway 的代价（ProcessState.cpp:364）

status_t ProcessState::enableOnewaySpamDetection(bool enable) {
    uint32_t enableDetection = enable ? 1 : 0;

    break;

这段在干什么：驱动可开启"oneway 滥发检测"；疑似滥发时，用户态把当前调用栈打进日志。

设计意图：为什么 oneway 特别危险。同步调用天然限流（一次只能有一个在飞，等回复才能发下一个）；oneway 没有这个约束，一个 for 循环就能把目标进程的缓冲区灌满。而缓冲区是 B1 讲的"进程共享 1MB"——灌满后连正常的同步调用也会失败（BR_FAILED_REPLY）。

块 H：两种耗尽对照表

线程耗尽（本篇 §4）缓冲区耗尽（B1 §4）
本质没人接活没地方放数据
典型原因同步调用阻塞传染、锁等待、重活oneway 洪水、单次大数据、并发多
调用方感受慢（排队，最终可能成功）失败（FAILED_TRANSACTION）
关键日志starved for N ms / Waiting for thread to be freeoneway spamming / TransactionTooLargeException
观测手段数 Binder:* 线程 + 抓栈看 /sys/kernel/debug/binder/stats（需 root）
🐛 实战 「调着调着就失败了」但线程数看起来正常。因果：很可能不是线程问题而是缓冲区问题——特别是你用 oneway 做高频日志上报/事件通知时。怎么查：① 看是否 FAILED_TRANSACTION；② 开 enableOnewaySpamDetection 看有没有 oneway spamming 的栈；③ 把 oneway 改成同步（临时）看是否还失败——如果好了就是缓冲区问题。

六、死锁环路：同步调用的经典陷阱

这是线程池最危险的失效模式：所有线程都在互相等，永远不返回。它不崩溃、不报错，只是"越来越慢直到完全不动"。

块 I：三种经典环路

① 环路型（A→B→A） system_server 的 Binder 线程 1 ──同步调──▶ App 进程的 Binder 线程 X │ └──同步调──▶ system_server（另一服务） │ └─ 需要空闲线程 ✗ 若 system_server 15 条线程都已进入类似的等待 → 没人接 → 永久卡住 ② 自锁型（同一进程内） Binder 线程 1 持有锁 L，然后同步调另一个服务 那个服务的实现也要锁 L → 等 L → 线程 1 持有 L 且在等对方 → 死锁 ③ 线程池互等 进程 P 的 15 条线程，全部在同步调进程 Q 进程 Q 的 15 条线程，全部在同步调进程 P ✗ 两边都没有空闲线程接新事务 → 双向死锁

块 J：为什么"改成 oneway"能救（但要小心）

B0 块 I 的延续：oneway 的取舍
// 【同步调用】调用方线程被占用：
//   Binder 线程 ──transact(flags=0)──▶ 等 BR_REPLY ──▶ 期间不能接新活

// 【oneway】调用方立刻返回（只等"驱动已收下"）：
//   Binder 线程 ──transact(flags=TF_ONE_WAY)──▶ 立刻可接下一个
//   ★ 于是"阻塞传染"被切断 —— 这是系统服务调 App 一律用 oneway 的根本原因

// 【但 oneway 的代价（B0 块 I + 本篇块 G）】
//   ① 拿不到返回值，也收不到服务端异常（异常"disappear into the ether"）
//   ② 不限流 → 可能把对端缓冲区灌满 → BR_FAILED_REPLY
//   ③ 不保证顺序（多线程发送时）

// 【工程结论】
//   · system_server → App：必须 oneway（否则 App 卡住会拖死系统）
//   · App → system_server：通常同步（需要结果）
//   · 高频事件通知：oneway + 自己做节流（合并/丢弃/限速）

这段在干什么：解释为什么"方向上"要用 oneway，但"频率上"必须自己控制。

设计意图：Android 在架构层面就规定了这个方向。回顾 06 篇：WMS 给 App 的所有回调（IWindow 的方法）几乎都是 oneway——因为 system_server 绝不能因为某个 App 卡住而卡住。这条规则不是优化，是生存要求。

🐛 实战 ANR 里看到主线程卡在 BinderProxy.transact → waitForResponse。因果：主线程做了同步 binder 调用，对端慢或死锁。注意：这时不是线程池问题（主线程不是 Binder 线程），而是"调用方进程被阻塞"。怎么查：ANR trace 里顺着栈找到被调的服务，再看那个服务所在进程是否在 starved 或死锁。这条链要跨两个进程看。
🧠 思考（需结合：块 C、块 I） 线程池上限是 15。如果某进程的 15 条线程全部卡在"等另一个进程的回复"，而此时那个进程又想调用本进程——驱动会不会为它新开一条线程（>15）来打破僵局？如果不能，系统该如何设计避免这种互等？（提示：想想为什么 Android 规定"系统调 App 必须 oneway"。）

七、观测与诊断手册

三分钟诊断流程

1确认是不是线程池问题：adb shell "cat /proc/<pid>/task/*/comm" | grep -c Binder。接近 15 就高度可疑。

2看线程都在干什么：adb shell ps -T -p <pid> 看状态（S/D/R）；再 adb shell kill -3 <pid> 拿 Java 栈，或用 debuggerd -b <pid> 拿 native 栈。

3找日志证据：adb logcat -d | grep -E "starved|Waiting for thread to be free|oneway spamming"。

4区分线程问题 vs 缓冲区问题：对照本篇块 H 的表——失败（不是慢）= 缓冲区；慢/排队 = 线程池。

5抓现场：Perfetto 里看 binder transaction 的切片；或 dumpsys 看目标服务状态。

命令速查

WSL / adb —— 线程池相关
# 1) 数 Binder 线程（最常用）
adb shell ps -A | grep <进程名>                      # 先拿 pid
adb shell "cat /proc/<pid>/task/*/comm" | grep -c Binder
adb shell ps -T -p <pid> | grep Binder               # 带状态

# 2) 抓所有线程栈（含 Binder 线程）
adb shell kill -3 <pid>                              # Java 栈 → /data/anr/traces.txt
adb shell debuggerd -b <pid>                        # native 栈

# 3) 关键日志
adb logcat -d | grep -E "starved|Waiting for thread to be free|oneway spamming|Binder"

# 4) 驱动统计（需 root）
adb shell cat /sys/kernel/debug/binder/stats | head -50
adb shell cat /sys/kernel/debug/binder/proc/<pid>    # 单进程细节

# 5) 打开 Binder 详细日志（谨慎，量大）
adb shell setprop log.tag.Binder VERBOSE
💡 先数数量、再看栈、最后看日志——顺序反了容易被海量日志淹死。数量这一步能在 10 秒内告诉你"要不要继续往下查"。

🧠 自测：6 个问题

1. 为什么必须保留至少一条「主」Binder 线程不退出？
因为主线程（isMain=true）在 joinThreadPool 里不会因 TIMED_OUT 退出（IPCThreadState.cpp:640 的 && !isMain）。
如果所有线程都能空闲退出，就可能出现"池里 0 条线程"的窗口——此时有事务进来，驱动要么一直等、要么异步催生（存在时间差），期间调用方无谓等待。保留一条常驻线程消除了这个窗口，代价是每个用过 Binder 的进程至少多一条线程。
2. 线程池是怎么"长大"的？决策权在谁手里？
长大是驱动发起、用户态执行：驱动发现该进程没有空闲线程可派活时，下发 BR_SPAWN_LOOPER；用户态在 executeCommand 的 case BR_SPAWN_LOOPER（IPCThreadState.cpp:1350）里调 spawnPooledThread(false) 起一条新池线程。
决策权必须在驱动，因为只有它能看到全局——用户态看不到"别的线程有没有空闲"。
上限由 BINDER_SET_MAX_THREADS 告知驱动（默认 15），且 启动后不允许调小（ProcessState.cpp:348，否则 fatal）。
3. 看到 binder thread pool (15 threads) starved for 250 ms 意味着什么？怎么查？
意味着该进程所有 Binder 线程同时被占用 ≥100ms，这段时间内新事务全部排队（IPCThreadState.cpp:536-551 的判定：mExecutingThreadsCount >= mMaxThreads 时开始计时，恢复时若 >100ms 就打日志）。
查法：① ps -T -p <pid> 看 15 条 Binder:* 的状态；② kill -3 / debuggerd -b 抓所有栈，看卡在 waitForResponse（阻塞传染）、monitor（锁等待）还是业务代码（重活）。
三大根因：同步调用阻塞传染、锁死等、事务里做重活。
4. 「线程耗尽」和「缓冲区耗尽」怎么区分？
看症状：线程耗尽 = 慢（排队，最终可能成功）；缓冲区耗尽 = 失败（FAILED_TRANSACTION / TransactionTooLargeException）。
看日志：前者是 starved for N ms 或 Waiting for thread to be free；后者是 oneway spamming（带调用栈）或客户端抛 TransactionTooLargeException。
根因不同：线程被"人"占住（同步调用/锁/重活）；缓冲区被"数据"占满（oneway 洪水/大数据/高并发）。
5. 为什么系统服务调 App 一律用 oneway？
切断阻塞传染。同步调用会让 system_server 的 Binder 线程一直等 App 的回复；如果 App 主线程卡住（比如在 onCreate 里做同步 IO），system_server 的那条线程也被拖住。15 条线程经不起几次这样的拖累，最终全线卡死（块 I 的环路型）。
oneway 让调用方只等"驱动已收下"就返回，立刻能接下一个事务。
代价（B0 块 I）：拿不到返回值、服务端异常静默消失、不限流可能灌满缓冲区——所以高频场景要自己做节流。
6. 一条 Binder 线程"在池里但收不到活"，可能是什么问题？
检查它有没有正确入池/离池：
① 入池必须写 BC_ENTER_LOOPER（主）或 BC_REGISTER_LOOPER（池）——没登记的话驱动不会给它派活（IPCThreadState.cpp:621）；
② 离池必须写 BC_EXIT_LOOPER——如果异常路径跳过了这一步，驱动仍以为它可用，派过来的事务无人处理，表现为对端永久等待（块 C 的 ⑦ 与 pitfall）。
排查：ps -T 看线程状态、debuggerd -b 看它停在哪个函数、检查是否有异常吞噬了退出流程。
