一、全景：驱动在中间到底做了什么

先划清源码边界（重要） —— 内核侧的 drivers/android/binder.c 不在这棵 AOSP 树里（本树 kernel/ 只有 configs/ prebuilts/ tests/，没有内核源码）。所以本篇不讲内核函数的行号（讲不了就不编）——只讲用户态能看到的界面：
· 用户态怎么与驱动交互 → frameworks/native/libs/binder/ProcessState.cpp、IPCThreadState.cpp
· 双方约定的数据结构与常量 → bionic/libc/kernel/uapi/linux/android/binder.h（这是内核暴露给用户态的 uapi 头，在这棵树里，可逐行核实）
想看内核实现，请另取内核源码（如 android12-5.10 分支）——但读透本篇的 uapi 边界，已经能解释 90% 的线上问题。

二、进程初始化：open + mmap + 三条 ioctl

任何一个进程想用 Binder，第一步都是"打开驱动、映射一块内存"。这两件事决定了后面所有的性能与限制，值得逐行看。

块 A：open_driver——打开驱动并握手（ProcessState.cpp:379）

frameworks/native/libs/binder/ProcessState.cpp:44-45、379-405（裁剪）
// ① 先看两个宏（同文件 :44-45）——本篇的两个主角：
#define BINDER_VM_SIZE ((1 * 1024 * 1024) - sysconf(_SC_PAGE_SIZE) * 2)
// ② ★ 1MB 上限的真正来源就在这行！注意它不是"正好 1MB"——
//    减掉了 2 个页大小（通常 8KB）。为什么减？见 §4。

#define DEFAULT_MAX_BINDER_THREADS 15
// ③ B0 提过的 15 个线程上限，来源是这里

static int open_driver(const char *driver)
{
    int fd = open(driver, O_RDWR | O_CLOEXEC);
    // ④ 打开驱动节点（通常是 /dev/binder）。O_CLOEXEC 保证 fork+exec 后不被继承

    if (fd >= 0) {
        int vers = 0;
        status_t result = ioctl(fd, BINDER_VERSION, &vers);
        // ⑤ 握手第 1 条：问驱动"你是哪个协议版本"
        if (result == -1) {
            ALOGE("Binder ioctl to obtain version failed: %s", strerror(errno));
            close(fd); fd = -1;
        }
        if (result != 0 || vers != BINDER_CURRENT_PROTOCOL_VERSION) {
            ALOGE("Binder driver protocol(%d) does not match user space protocol(%d)! ...",
                  vers, BINDER_CURRENT_PROTOCOL_VERSION, result);
            close(fd); fd = -1;
        }
        // ⑥ ★ 版本必须严格相等，否则直接失败 ——
        //    这个检查防的是"新用户态 + 旧内核"这种错配（刷机刷一半就会遇到）

        // … 省略：BINDER_SET_MAX_THREADS 设置线程池上限
        size_t maxThreads = DEFAULT_MAX_BINDER_THREADS;
        result = ioctl(fd, BINDER_SET_MAX_THREADS, &maxThreads);
        // ⑦ 握手第 2 条：把"我最多开 15 个 Binder 线程"告诉驱动
    }
    return fd;
}
// ⑧ 三条 ioctl（版本 / 最大线程数 / 后文的 BINDER_SET_CONTEXT_MGR）都是"一次性配置"，
//    之后的高频操作只有 BINDER_WRITE_READ 一条

这段在干什么：打开驱动、核对协议版本、上报线程上限——都是进程级的一次性握手。

设计意图：版本严格相等是刻意的"硬失败"。Binder 协议是内核与用户态的二进制契约：结构体布局、命令编号都不能差。与其容忍错配后出现难查的内存混乱，不如在打开时就报错退出（LOG_ALWAYS_FATAL，见块 B）。这也解释了"刷机刷一半手机会起不来"——system 分区与 boot 分区的 binder 版本不匹配。

🐛 实战 报 "Binder driver protocol(8) does not match user space protocol(7)"。因果：内核里编译进去的 binder 协议版本（BINDER_CURRENT_PROTOCOL_VERSION，uapi binder.h:102/104 有 7 和 8 两个分支）与用户态库不一致。怎么查：确认 boot.img（内核）与 system.img 是不是同一版本；AOSP 12 常见的是 7（老内核）与 8（新内核，支持更多特性）分歧。adb shell dmesg | grep -i binder 能看到驱动的版本打印。

块 B：mmap——那块 1MB 内存（ProcessState.cpp:412 / 428）

frameworks/native/libs/binder/ProcessState.cpp:412-440（裁剪）
// 构造函数初始化列表里 mDriverFD 就是 open_driver 的返回值
ProcessState::ProcessState(const char *driver)
    : mDriverName(String8(driver))
    , mDriverFD(open_driver(driver))
    , mVMStart(MAP_FAILED)
    // … 省略：一堆锁与计数器初始化
    , mMaxThreads(DEFAULT_MAX_BINDER_THREADS)
    , mThreadPoolStarted(false)
{
    if (mDriverFD >= 0) {
        // mmap the binder, providing a chunk of virtual address space to receive transactions.
        mVMStart = mmap(nullptr, BINDER_VM_SIZE, PROT_READ,
                MAP_PRIVATE | MAP_NORESERVE, mDriverFD, 0);
        // ① ★★ 整篇最关键的一行：向驱动 mmap 出一块接收缓冲区
        //    · PROT_READ —— 只读！用户态不能直接写它（写要走 ioctl）
        //    · MAP_NORESERVE —— 不预留物理页，用到才分配（省内存）
        //    · 从 fd 0 偏移 —— 特殊语义：不是在映射"文件"，而是映射驱动的缓冲区

        if (mVMStart == MAP_FAILED) {
            ALOGE("Using %s failed: unable to mmap transaction memory.\n", mDriverName.c_str());
            close(mDriverFD);
            mDriverFD = -1;
            mDriverName.clear();
        }
        // ② 映射失败就整体放弃（连 fd 一起关）——没有缓冲区就无法收发事务
    }
#ifdef __ANDROID__
    LOG_ALWAYS_FATAL_IF(mDriverFD < 0, "Binder driver '%s' could not be opened.  Terminating.", driver);
    // ③ ★ Android 上打不开 Binder 驱动 = 进程直接 abort
    //    （因为整个 Android 的运行都依赖 Binder，没有它什么都做不了）
#endif
}

这段在干什么：向驱动映射一块只读的接收缓冲区，失败就让进程死。

设计意图："只读"这个属性是理解整个一次拷贝的关键。你的进程发数据时走 ioctl（拷贝进内核），收数据时内核直接写进这块已映射的内存——你只管读。接收侧省掉一次拷贝，就是靠这个 mmap。

🐛 实战 进程莫名 abort / tombstone 里有 "could not be opened"。因果：/dev/binder 打不开或 mmap 失败——常见于 SELinux 拒绝、/dev 未挂载、或非 Android 宿主环境。怎么查：adb shell dmesg | grep -i avc 看有没有 SELinux 拒绝；ls -lZ /dev/binder* 看节点与标签。
🧠 思考（单块） 为什么这里 mmap 的是 PROT_READ（只读）而不是读写？如果你能直接写这块内存，会带来什么问题？（提示：设想两个进程同时往同一块区域写，内核还怎么保证事务边界。）

三、一次事务的内核旅程：writeTransactionData 与双命令流

B0 讲到 talkWithDriver() 里的 ioctl 就停了。现在把"进 ioctl 之前"和"出 ioctl 之后"补上——关键是Binder 的命令是双向的、且用同一块缓冲区。

块 C：把事务写进待发缓冲（IPCThreadState.cpp:1082）

IPCThreadState.cpp:1082-1120
status_t IPCThreadState::writeTransactionData(int32_t cmd, uint32_t binderFlags,
    int32_t handle, uint32_t code, const Parcel& data, status_t* statusBuffer)
{
    binder_transaction_data tr;
    // ① 这个结构体就是"事务的元数据"（uapi binder.h:139 定义），
    //    它与真正的负载数据分开：这里只放"发给谁、什么码、多大、在哪"

    tr.target.ptr = 0; /* Don't pass uninitialized stack data to a remote process */
    tr.target.handle = handle;
    // ② ★ 目标用 handle（一个整数索引），不是指针！
    //    这正是"跨进程指针无意义"的体现——见 §5

    tr.code = code;
    tr.flags = binderFlags;
    // ③ code = 方法编号（AIDL 生成的 TRANSACTION_xxx）
    //    flags 里最关键的是 TF_ONE_WAY（oneway 异步）

    tr.cookie = 0;
    tr.sender_pid = 0;
    tr.sender_euid = 0;
    // ④ ★ 这三个"由谁填"很关键：用户态填 0，实际值由驱动写入——
    //    这就是 B0 块 C 说的"UID 从内核来、不可伪造"在数据层面的证据

    const status_t err = data.errorCheck();
    if (err == NO_ERROR) {
        tr.data_size = data.ipcDataSize();
        tr.data.ptr.buffer = data.ipcData();
        tr.offsets_size = data.ipcObjectsCount() * sizeof(binder_size_t);
        tr.data.ptr.offsets = data.ipcObjects();
        // ⑤ ★★ 注意这里传的是用户态缓冲区的指针（ptr）！
        //    也就是说：此刻数据还在你的进程里，还没进内核。
        //    内核收到后会做 copy_from_user（这才是"那一次拷贝"）
    } else if (statusBuffer) {
        tr.flags |= TF_STATUS_CODE;
        *statusBuffer = err;
        tr.data_size = sizeof(status_t);
        tr.data.ptr.buffer = reinterpret_cast<uintptr_t>(statusBuffer);
        tr.offsets_size = 0;
        tr.data.ptr.offsets = 0;
        // ⑥ 序列化时就出错的场景：只把那一个错误码发过去
        //    （TF_STATUS_CODE 标记"这不是正常负载，是错误码"）
    } else {
        return (mLastError = err);
    }

    mOut.writeInt32(cmd);
    mOut.write(&tr, sizeof(tr));
    // ⑦ 写进 mOut：先是命令码（BC_TRANSACTION），再是结构体本身
    //    此时只是"准备好了"，还没送给驱动

    return NO_ERROR;
}

这段在干什么：把「发给谁（handle）+ 什么方法（code）+ 数据在哪（用户态指针）+ 多大」组装成 binder_transaction_data，塞进待发缓冲区 mOut。

设计意图：元数据与负载分离，且指针此时才"过河"。注意 tr.data.ptr.buffer 是用户态地址——内核拿到后会 copy_from_user 把这片内存拷进目标进程的映射区。这就是"一次拷贝"发生的精确时刻：不是在你的 transact() 调用时，而是在内核处理 BC_TRANSACTION 时。

🐛 实战 为什么传指针而不是传数据是安全的？因为这是 ioctl 的同步语义：内核在你的 ioctl 系统调用里直接把数据拷走，返回后你才可以复用缓冲区。但如果中途出错（比如 data.errorCheck() 失败），就要走 ⑥ 那个分支只发错误码——否则接收方会拿到一段没意义的地址。怎么查：如果对端收到奇怪的 "FAILED_TRANSACTION"，看服务端是否在做大对象序列化（序列化失败会走这条路）。

块 D：双命令流——一次 ioctl 收发双向（IPCThreadState.cpp:975-1040）

IPCThreadState.cpp:975-1045（裁剪）
status_t IPCThreadState::talkWithDriver(bool doReceive)
{
    binder_write_read bwr;
    // ① 这是与驱动交互的唯一"信封"（uapi binder.h:90）
    //    结构里有四个关键字段：write_size/write_consumed/read_size/read_consumed

    const bool needRead = mIn.dataPosition() >= mIn.dataSize();
    // ② 输入缓冲读完了吗（读完了才需要这次收）

    const size_t outAvail = (!doReceive || needRead) ? mOut.dataSize() : 0;
    bwr.write_size = outAvail;
    bwr.write_buffer = (uintptr_t)mOut.data();
    // ③ 待发：就是块 C 写进去的 BC_TRANSACTION + 结构体

    if (doReceive && needRead) {
        bwr.read_size = mIn.dataCapacity();
        bwr.read_buffer = (uintptr_t)mIn.data();
    } else {
        bwr.read_size = 0;
        bwr.read_buffer = 0;
    }
    // ④ 待收：留出缓冲接收驱动给的命令（BR_REPLY / BR_DEAD_REPLY ...）

    if ((bwr.write_size == 0) && (bwr.read_size == 0)) return NO_ERROR;
    // ⑤ 没活干直接返回（避免空转系统调用）

    bwr.write_consumed = 0;
    bwr.read_consumed = 0;
    status_t err;
    do {
        if (ioctl(mProcess->mDriverFD, BINDER_WRITE_READ, &bwr) >= 0)
            err = NO_ERROR;
        else
            err = -errno;
        // ⑥ ★★ 就是这一行 —— 一次系统调用同时完成"提交我的请求 + 收下给我的命令"
        //    如果 doReceive 且驱动暂无数据，这里会睡眠（同步调用就阻塞在这）
    } while (err == -EINTR);
    // ⑦ 被信号打断（EINTR）就重试 —— 注意不是失败

    if (err >= NO_ERROR) {
        if (bwr.write_consumed > 0) {
            if (bwr.write_consumed < mOut.dataSize())
                LOG_ALWAYS_FATAL("Driver did not consume write buffer. ...");
            else {
                mOut.setDataSize(0);
                processPostWriteDerefs();
                // ⑧ ★ 驱动收完了才清空 mOut ——"发出去的才能丢"
                //    如果驱动只消费了一部分，直接 LOG_ALWAYS_FATAL 崩溃：
                //    因为这已经是协议级异常，继续跑会更糟
            }
        }
        // … 省略：根据 read_consumed 更新 mIn 的读指针
    }
}

这段在干什么：用 binder_write_read 这一个结构，一次 ioctl 同时"送出去"和"收回来"。

设计意图：读写合一，是为了让"同步调用"只需一个系统调用。典型同步调用是"发出去、等回复"——如果分成"写 ioctl"+"读 ioctl"，就多一次系统调用和一次上下文切换。合一之后：write_size > 0, read_size > 0，内核先处理写、再（若有）填充读；没有读数据时就直接睡眠等。这就是 B0 块 F 里"oneway 也要等 BR_TRANSACTION_COMPLETE"的底层原因——它等的正是这次 ioctl 的 read 部分给出的回执。

🧠 思考（需结合：块 C、块 D） 块 C 里 tr.data.ptr.buffer 传的是用户态指针，块 D 里 bwr.write_buffer 也是用户态指针。既然指针跨进程没意义，为什么这里可以传指针？（提示：这两个指针的使用者是谁——是别的进程，还是内核本身？）

四、一次拷贝的真相，与 1MB 上限从哪来

这是本篇的核心。B0 已经说"一次拷贝"，但没讲清"为什么只能一次"和"为什么必须 1MB"——它们是同一件事的两面。

块 E：三种 IPC 的拷贝次数对比

【Socket / 管道】两次拷贝 发送方用户态 ──①copy_to_user→ 内核缓冲 ──②copy_to_user→ 接收方用户态 （两边的地址空间互不可见，内核必须各拷一次） 【共享内存】零次拷贝，但需自己解决同步与安全 发送方 ──直接写──▶ 共享区 ◀──直接读── 接收方 （谁在写、写到哪、写完没有——全靠自己实现，易错且危险） 【Binder】一次拷贝 —— 关键在"接收方提前 mmap 了内核缓冲" 发送方用户态 ──①copy_from_user→ 内核里的"目标进程缓冲" │ └── 接收方直接读（已 mmap 映射，无需再拷） ★ 省掉的是 ②：因为接收方地址空间里已经映射了那块内核缓冲（块 B 的 mmap）

//    BINDER_WRITE_READ —— 传输就这一条命令
//    BINDER_SET_MAX_THREADS —— 线程数上限（15）

这段在干什么：说明 1MB 不是"随便定的数字"，而是mmap 映射区的固定大小；而 800KB 是用户态的提前警告线。

设计意图：为什么不做成"按需增长"。因为 Binder 追求的是一次 ioctl 完成一次交付（低延迟、可预测）。如果缓冲区动态增长：① 内核要处理"目标缓冲区不够、需要扩容"的复杂失败回滚；② 接收方 mmap 区变化要同步通知；③ 更大的共享区意味着更大的攻击面。固定 1MB + 明确上限是"用可预测性换掉复杂度"——大数据请走 §6 的 fd 传递。

🐛 实战 TransactionTooLargeException 的正确理解（也是 B0 实践题 P2 的答案要点）：
① 不是"传了超过 1MB 才炸"——checkParcel 在 800KB 就警告；而且它是进程级共享的，并发时更容易超；
② 不是"每次都扣 1MB"——缓冲区是复用的，mOut.setDataSize(0) 后就归还；
③ 真正的大数据方案是传 fd（见 §6），不是"压缩后硬塞"。
排查：dumpsys 看不到时，看崩溃栈是否在 Binder.checkParcel；再用 §7 的命令观察有无 oneway 洪水堆积。
🧠 思考（需结合：块 B、块 E、块 F） 块 B 的 mmap 用了 MAP_NORESERVE（不预留物理页）。如果系统内存紧张，这块区域会怎样？这能否解释"内存不足时 Binder 调用更容易 Failed"（BR_FAILED_REPLY）？——这题答出来，你就同时理解了 mmap 语义与线上偶发故障。

五、数据里的"对象指针"：offsets 与 BINDER_TYPE_*

把 Binder 对象（或 fd）塞进 Parcel 传递时，字节流里存的是什么？不是指针，是一个"待翻译的占位"，由驱动在传递时重写。这是 Binder 最精妙的设计之一。

块 G：结构里为什么要"另一份 offsets"（uapi binder.h:90 / 139）

uapi/linux/android/binder.h:56-70、86-100、139-160（裁剪）
// 先看"平铺对象"的结构（uapi :56）——它是塞在数据里的占位符：
struct flat_binder_object {
    struct binder_object_header hdr;   // hdr.type 标明"我是哪种对象"
    __u32 flags;
    union {
        binder_uintptr_t binder;        // ① 本进程内：是真实指针
        __u32 handle;                   // ② 跨进程时：驱动把它换成 handle
    };
    binder_uintptr_t cookie;
};
// ★ 同一个 union，两种含义 —— 取决于"发给谁"

// 再看事务结构里的两个尺寸（uapi :139）：
struct binder_transaction_data {
    // … 省略 target / code / flags / sender_*
    binder_size_t data_size;            // ③ 数据总字节数
    binder_size_t offsets_size;         // ④ ★ 偏移表字节数
    union {
        struct { binder_uintptr_t buffer; binder_uintptr_t offsets; } ptr;
        __u8 buf[8];
    } data;
};
// ⑤ ★★ 为什么需要 offsets？因为数据里混着两类东西：
//    · 普通字节（int/string/byte[]）—— 直接拷就行
//    · 对象占位（Binder/fd）—— 必须在数据里的哪些位置
//    驱动不可能扫描整片数据去找对象（那既慢又不可靠），
//    所以发送方额外给一份"对象在数据中的偏移列表"——就是 offsets

这段在干什么：解释 offsets 的作用——告诉驱动"数据里第 N 个字节处是个对象，需要你翻译"。

设计意图：用偏移表代替"扫描识别"。这既保证了性能（O(对象数) 而非 O(数据大小)），也保证了正确性（避免把恰好长得像对象的普通字节误判）。flat_binder_object.binder/handle 那个 union 则是"翻译"的具体动作：**发给本进程时填真实指针，发给其他进程时换成 handle**。

🐛 实战 序列化 Binder 对象后调用失败 / 拿到 null。因果：如果发送方没正确把这个对象登记进 offsets（比如手工拼 Parcel 时忘了 writeStrongBinder 而直接写了字节），驱动就不会翻译它，对端读出来是个无效值。怎么查：确认用的是 Parcel.writeStrongBinder()（Parcel.java:898）而非写裸字节；服务端 readStrongBinder() 拿到的对象做 asInterface 前先判空。

六、fd 怎么跨进程传

fd（文件描述符）在你进程里只是个小整数——"第 7 号打开文件"。这个数字在别的进程里毫无意义。那 Binder 怎么把"打开的文件"传过去？

块 I：BINDER_TYPE_FD 的秘密

uapi binder.h:57-66 + BinderProxy/Message 侧调用
// 数据里出现的是这个结构（uapi :57）：
struct binder_fd_object {
    struct binder_object_header hdr;   // hdr.type == BINDER_TYPE_FD
    __u32 pad_flags;
    union {
        binder_uintptr_t pad_binder;
        __u32 fd;                       // ① 发送方的 fd 数字
    };
    binder_uintptr_t cookie;
};

// ★ 传递过程（内核做的事）：
//   ① 发送方把 fd 放进 Parcel（Message 里对应 ParcelFileDescriptor）
//   ② 驱动收到后，调用内核的 fd 复制能力（get_unused_fd + fget + fd_install 同类语义）
//   ③ 在目标进程里分配一个新的 fd 号，指向同一个打开文件
//   ④ 目标进程 readStrongBinder/读 Parcel 时，拿到的是它自己的新 fd
// ⑤ 于是两个进程的 fd 数字不同，但都指向同一个"打开文件"

// 【用户态怎么用】
//   写：parcel.writeFileDescriptor(ParcelFileDescriptor) 或 writeRawFileDescriptor
//   读：parcel.readFileDescriptor() → 得到一个 ParcelFileDescriptor
//   然后可以 new FileInputStream(pfd.getFileDescriptor()) —— 直接读对方给的文件！

// 【为什么这也是"大数据"的正解】
//   ashmem / MemoryDealer / 匿名共享内存：
//   创建一块共享内存 → 得到一个 fd → 通过 Binder 传 fd → 双方 mmap 同一块内存
//   于是大数据走共享内存，Binder 只传一个 fd，完全绕开 1MB 上限

这段在干什么：说明 fd 传递的本质是"内核在目标进程复制一份 fd 引用"。

设计意图：这是 Binder 的"逃生舱口"。1MB 限制（§4）本意是"小消息快传"，而大数据用共享内存 + fd 传递解决。框架里到处是这个模式：传 Bitmap（走 ashmem）、传视频帧（GraphicBuffer 的 fd）、传文件（ParcelFileDescriptor）。记住这条，你就不会问"为什么 Binder 只能传 1MB"——因为大东西根本不走 Binder。

🐛 实战 收到 fd 后没关导致 fd 泄漏。因果：跨进程传过来的 fd 是目标进程新增的一个 fd，用完必须自己 close()（或让 ParcelFileDescriptor.close() 处理），否则 fd 数只增不减。怎么查：adb shell ls /proc/<pid>/fd | wc -l 观察是否单调增长；对比 dumpsys meminfo <pkg> 里的 fd 计数。

🧠 自测：6 个问题

1. 打开 Binder 驱动时要过哪几道校验？为什么版本检查是"硬失败"？
三道：① open("/dev/binder", O_RDWR|O_CLOEXEC)；② ioctl(BINDER_VERSION) 核对协议版本，必须严格相等否则关 fd 返回失败；③ ioctl(BINDER_SET_MAX_THREADS) 上报线程上限。
版本检查必须硬失败，因为 Binder 协议是内核与用户态的二进制契约（结构体布局、命令编号），错配会导致难查的内存混乱。这也解释了"刷机刷一半起不来"——boot 与 system 分区的 binder 版本不一致。Android 上打不开驱动更直接：LOG_ALWAYS_FATAL 让进程 abort。
2. 为什么 mmap 出来的接收区是 PROT_READ（只读）？
因为这块内存只用于"接收"：内核把对端发来的数据写进去，本进程只管读。发送走的是 ioctl（内核 copy_from_user 从你的 mOut 拷走），不需要写这块映射区。
如果允许写，就会出现"两个进程同时写同一区域"的竞争，内核也无法保证事务边界。只读 + 统一走 ioctl，是把并发控制完全收回内核——这是 Binder 安全性与一致性的基础。
3. 一次 Binder 调用，数据到底在哪一刻被拷贝？
在 ioctl(BINDER_WRITE_READ) 进入内核、驱动处理 BC_TRANSACTION 时，通过 copy_from_user 把 tr.data.ptr.buffer（这是发送方的用户态地址）指向的内存拷进"目标进程的映射区"。
注意 writeTransactionData 只是记录了指针，此时数据还在原进程。接收侧之所以不需要再拷，是因为目标进程 mmap 过那块区域（块 B），ipcSetDataReference 直接引用（Parcel.cpp:2114）。
4. 1MB 上限是怎么来的？为什么不是"每次调用 1MB"？
来自 BINDER_VM_SIZE = 1MB - 2 页（ProcessState.cpp:44），即 mmap 给每个进程的接收区固定大小（块 F）。
它是进程级共享的缓冲区，不是每次调用独立开销——所以并发调用时更容易撞上限。用户态还有一道提前警告：Binder.checkParcel() 在 800*1024 就抛 TransactionTooLargeException（Binder.java:1087），留出余量。
第二问的"为什么不做成动态增长"见块 F 的设计意图：用可预测性换掉复杂度。
5. binder_transaction_data 里为什么需要 offsets 这个额外字段？
因为负载数据里混着两类内容：普通字节（int/String/byte[]）和对象占位（Binder/fd）。后者必须被驱动"翻译"（本进程指针 ↔ 对端 handle / 新 fd）。
驱动不能扫描整片数据去猜哪些是对象（慢且不可靠），所以发送方额外提供一份偏移列表，精确指出"数据里第 N 字节处是对象"。这样驱动只需 O(对象数) 的处理，且不会误判。
6. 大数据（图片/视频帧）怎么能绕过 1MB？
走 fd 传递 + 共享内存（块 I）：创建 ashmem/匿名共享内存 → 得到一个 fd → 通过 Binder 传这个 fd（BINDER_TYPE_FD）→ 内核在目标进程里分配一个新 fd 指向同一个打开文件 → 双方 mmap 同一块物理内存。
于是 Binder 只传一个 fd 数字，数据本身不进 Binder 缓冲区，完全绕开 1MB。
框架里到处是这个模式：Bitmap 走 ashmem、视频帧走 GraphicBuffer 的 fd、文件走 ParcelFileDescriptor。所以"Binder 只能传 1MB"这句话不完整——大东西根本不走 Binder。
