一、问题所在：树有了，然后呢？

02 篇讲完了一件事：一个新窗口经过 WMS.addWindow()，最终作为 WindowState 挂到了 WindowToken 下，成为窗口树的一片叶子。03 篇又讲了：布局遍历算好每个叶子的 frame，assignChildLayers 算好 Z 序，最后一把事务提交给 SurfaceFlinger。

但这里藏着两个没被回答的问题，正是你现在卡住的地方：

  1. 挂载只挂了"逻辑身份"。WindowState 是 system_server 里的一个 Java 对象，它挂进树里，只是决定了"我是谁、我归谁管、我排第几层"。它本身没有像素，也不是画布。真正能往上画东西的那块"画布"在哪里、谁创建、归谁所有？
  2. 屏幕不认识 Java 对象。物理屏幕只接收合成好的像素扫描信号。system_server 里的一棵树，不可能直接"送"到屏幕。中间一定有另一个子系统接手——那就是 SurfaceFlinger。树的信息和 App 画的像素，是怎么双双流进 SurfaceFlinger，再变成屏幕上的光的？
✦ ✦ ✦ 一句话总览全文 ✦ ✦ ✦
每个窗口在逻辑树上是一个 WindowState，在图形世界里对应一个 SurfaceControl（图层的遥控器）；App 通过它拿到一块 Surface（画布），往里面填 GraphicBuffer（像素）；WMS 用 Transaction（事务） 遥控图层的位置/层级，SurfaceFlinger 收到后把所有图层 合成（composite），交给硬件混叠器 HWC 或 GPU，最终 present（呈现） 到物理屏幕。

这一篇就沿着"画布诞生 → 过河到 App → App 画像素 → 像素送回 → 合成上屏"五步走，每步都绑定真实类名和源码位置。

二、两棵树：WindowContainer 树 与 Surface 树

理解整个图形系统，第一要务是承认系统里存在两棵同构但不同物的树：

窗口树（逻辑树）Surface 树（图层树）
所在进程system_server由 SurfaceFlinger 持有实体，客户端只拿引用
节点是什么WindowContainer 子类（Java 对象）Layer（C++ 对象，如 BufferStateLayer）
手里的引用成员变量 mSurfaceControl客户端侧的 SurfaceControl（只是句柄）
决定什么窗口的归属、可见性、布局、Z 序策略图层实际的位置、矩阵、Z 值、alpha、Buffer
谁让两者同步WindowContainer.getSyncTransaction() / 全局 Transaction 把逻辑树的决定写进 Surface 树

关键认知：逻辑树是"图纸和管理处"，Surface 树是"真实舞台"。WMS 在逻辑树里做完所有决策，并不直接碰屏幕，而是通过 SurfaceControl.Transaction 把决策翻译成对 Surface 树上图层的操作指令。SurfaceFlinger 只认 Surface 树。

两棵树长什么样：一张对照全图

下面把同一块屏幕上的一棵逻辑树和它对应的图层树并排放在一起。左边是 WMS 在 system_server 里维护的 Java 对象树，右边是 SurfaceFlinger 进程里真实的 Layer 树。两边按层级一一对应，但节点不是一一对应：容器节点可能没有 Layer，只有 WindowState 一定有 buffer layer。

逻辑树（system_server · Java）Surface 树（SurfaceFlinger · C++）
RootWindowContainer └─ DisplayContent #0 └─ DisplayArea:FeatureRoot └─ TaskDisplayArea └─ Task #42 └─ ActivityRecord (extends WindowToken) └─ WindowState(app) ★ └─ WindowState(sub) ★
Layer "Root" └─ Layer "DisplayArea:FeatureRoot" └─ Layer "TaskDisplayArea" └─ Layer "Task=42" └─ Layer "ActivityRecord" └─ BufferStateLayer "Window{...}" ★ └─ BufferStateLayer "Window{...}" ★
✦ ✦ ✦ 读图三条规则 ✦ ✦ ✦
① 必有 vs 按需：DisplayContent 的 "Root" 容器图层在构造时就建好（DisplayContent.java:1061-1065）；中间的 DisplayArea / Task 只有在需要裁剪、变换或做动画时才通过 makeSurface().setContainerLayer() 建容器图层（WindowContainer.java:2538），本身不承载像素。窗口 token（ActivityRecord / WindowToken）是例外：它会在首个顶层窗口加入时建容器图层（WindowToken.java:297-315）。
② 只有 WindowState 必须有 buffer layer：因为只有它要装 App 或系统画的内容；没有 Buffer 的容器图层只负责组织层级、裁剪和变换。
③ 名字只是示意：实际 Layer 名由 WindowContainer.getName() 生成（例如 Task.getName() 返回 "Task=" + mTaskId，Task.java:3942），dumpsys SurfaceFlinger --list 里看到的就是这些名字。
④ 应用窗口的 token 就是 ActivityRecord：ActivityRecord extends WindowToken（ActivityRecord.java:365），所以逻辑树里不要再画“ActivityRecord → WindowToken”两层；系统窗口（状态栏、导航栏）才用普通 WindowToken。

不是每个逻辑节点都有 Surface

这是最容易误解的地方。逻辑树上节点很多（DisplayArea、Task、TaskDisplayArea……），但 Surface 是按需创建的：

  • DisplayContent 在构造时就建了一个名为 "Root" 的容器图层（setContainerLayer()），它是整块屏幕 Surface 子树的根。
  • 中间的 DisplayArea、Task 等容器，在需要承接子 Surface 时也会各自有容器型 SurfaceControl（通过 makeSurface() 向上递归创建），它们本身不承载像素，只负责裁剪和变换的层级组织。
  • WindowState 才真正需要一块能装 Buffer 的图层（buffer layer），因为只有它要显示 App 或系统画的内容。

这一节默认你已经具备下面五块前置知识。每题下面是答案与对应篇目；如果连续三题答不上来，先回 01 篇第二节和 03 篇第六、七节，再回来读本节。

1. 为什么 addWindow 成功后屏幕还是黑的？

因为 addWindow 只把 WindowState 挂进逻辑树，建立身份、树位、Z 序和输入通道；此时 frame 为空、没有 Surface、没有 Buffer。要等 App 首帧 relayout，WMS 才建图层，App 才画第一帧。见 06 篇块 I「上树 ≠ 显示」。

2. 为什么 DisplayArea 有 Layer 却没有像素？

因为它是容器图层（ContainerLayer），只负责裁剪、变换和组织子图层，不承载 Buffer。只有 WindowState 对应的 buffer layer 才装像素。

3. SurfaceControl 里到底存的是什么？

存的是指向 SurfaceFlinger 中某个 Layer 的跨进程句柄，不是 Layer 本体，也不是像素。句柄可以跨进程传递，Layer 本体始终留在 SF。见 04 篇第四节。

4. Android 12 的 BufferQueue 在 App 进程还是 SF 进程？为什么？

在 App 进程（BLAST 模式）。BLASTBufferQueue 在 App 侧建本地队列，App 画完 queueBuffer 后，BLAST 把 GraphicBuffer 打包进 SurfaceControl.Transaction 提交给 SF；这样“新 Buffer”和“图层状态变化”能在同一笔事务里原子生效，避免新尺寸配旧 Buffer 的错位。见 04 篇第六节。

5. Z 序由谁决定、由谁执行？为什么必须“一把事务”提交？

WMS 通过 assignChildLayers 算出每个节点的整数 mLayer（WindowState.assignLayer:5648），再通过 SurfaceControl.Transaction.setLayer 把决策写进事务；SurfaceFlinger 在 VSYNC 里按事务更新 Layer 的 Z 值并合成。一把事务保证一帧内的位置、Z 序、可见性、Buffer 原子生效，中间状态不上屏，避免闪烁/撕裂。见 03 篇第六、七节。

三、画布诞生：relayoutWindow 触发 SurfaceControl 创建

窗口被 addWindow 挂树时，并没有立即创建画布。画布的创建被推迟到第一次布局——App 进程的 ViewRootImpl 走完 View 树的 measure 后，调用 IWindowSession.relayout() 向 WMS 要一块与窗口尺寸匹配的 Surface。这是典型的"按需分配"：窗口大小没定下来之前，建了画布也是浪费。

1App 侧发起 relayout
ViewRootImpl.performLayout() 测量 View 树后进入 relayoutWindow()，通过 Binder 调 Session.relayout()，把期望宽高、可见性、一个空的输出参数 mSurfaceControl 一起传过去。
对应源码：ViewRootImpl.java 约 7778 行 mWindowSession.relayout(...)，输出参数 mSurfaceControl 是 new SurfaceControl() 空壳。
2WMS 判断窗口可见且需要 Surface
WindowManagerService.relayoutWindow()（2210 行起）在持有 mGlobalLock 下做策略校正、更新窗口尺寸；当窗口要变为可见（viewVisibility == VISIBLE 等）且尚无 Surface 时，进入创建分支（约 2372 行）。
为什么要在 relayout 而非 addWindow 创建：此时 App 已完成首轮 measure，WMS 也算出了 frame，Surface 的 buffer 尺寸才有意义。
3createSurfaceControl 委托动画器建图层
WMS 的私有方法 createSurfaceControl()（2597 行）调用 winAnimator.createSurfaceLocked(win.mAttrs.type)，由 WindowStateAnimator 真正创建图层。

WindowStateAnimator.createSurfaceLocked — 计算参数

这个方法（WindowStateAnimator.java 304 行）先算清楚新图层的属性：初始一律带 SurfaceControl.HIDDEN 标志（建出来先藏着，等第一帧画完再显示，避免露出空画布）；安全窗口加 SECURE；再通过 w.calculateSurfaceBounds() 算出 buffer 宽高；硬件加速窗口格式统一用 PixelFormat.TRANSLUCENT。然后 new 出 WindowSurfaceController：

WindowStateAnimator.createSurfaceLocked()（节选）
int flags = SurfaceControl.HIDDEN;                 // 先隐藏
if (w.isSecureLocked()) flags |= SurfaceControl.SECURE;
w.calculateSurfaceBounds(attrs, mTmpSize);
final int width = mTmpSize.width(), height = mTmpSize.height();

mSurfaceController = new WindowSurfaceController(
        attrs.getTitle().toString(), width, height,
        format, flags, this, windowType);          // ★ 真正建图层
w.setHasSurface(true);

WindowSurfaceController 构造 — 向 SurfaceFlinger 下单

真正的跨进程调用发生在这个构造函数里（WindowSurfaceController.java 74 行）。它通过 win.makeSurface() 拿到一个 SurfaceControl.Builder，链式设置好父图层、名字、buffer 尺寸、格式、元数据（窗口类型/uid/pid），最后 b.build()：

WindowSurfaceController 构造函数（节选）
final SurfaceControl.Builder b = win.makeSurface()
        .setParent(win.getSurfaceControl())         // 挂到父容器图层下
        .setName(name)
        .setBufferSize(w, h)                         // buffer 图层才有的尺寸
        .setFormat(format)
        .setFlags(flags)
        .setMetadata(METADATA_WINDOW_TYPE, windowType)
        .setMetadata(METADATA_OWNER_UID, mWindowSession.mUid)
        .setMetadata(METADATA_OWNER_PID, mWindowSession.mPid);

if (useBLAST) b.setBLASTLayer();                    // Android 12 默认走 BLAST
mSurfaceControl = b.build();                       // ★ Binder 到 SF 建 Layer

build() 经 JNI 进入 native，最终 Binder 调用 SurfaceFlinger 的 Client.createSurface() → SurfaceFlinger.createLayer()（SurfaceFlinger.cpp 4289 行）。SF 根据 flag 决定图层类型：BLAST 对应 eFXSurfaceBufferState，于是 createBufferStateLayer() 造出一个 BufferStateLayer（C++ Layer），再 addClientLayer() 把它挂进 SF 自己的 Layer 树，并通过 handle 把图层句柄返回给调用方。

✦ ✦ ✦ 此刻发生了什么 ✦ ✦ ✦
SurfaceFlinger 里多了一个真实的 BufferStateLayer 节点，Surface 树长出一片新叶子；system_server 侧拿到的 SurfaceControl 只是指向这个 Layer 的跨进程句柄，并不是图层本体。"逻辑树的一个 WindowState"与"Surface 树的一个 Layer"就此配对成功。

图层建好了，但它还在 system_server 手里。App 才是要画画的一方，句柄怎么过河交到 App 进程？这是第四章。

四、过河：SurfaceControl 怎么跨进程交到 App 手里

难点在于：图层是系统资源，绝不能让 App 随便复制；但 App 又确实需要一个能往上画的接口。Android 的解法是"句柄可跨进程序列化，本体留在 SF"。

1WMS 把句柄拷进输出参数
回到 WMS.createSurfaceControl()：建图层成功后调用 surfaceController.getSurfaceControl(outSurfaceControl)，其实现只有一句 outSurfaceControl.copyFrom(mSurfaceControl, ...)（WindowSurfaceController.java 275 行），把新建图层的引用拷进 relayout 的输出参数。
2Binder 把输出参数回传 App
relayoutWindow 返回后，这个 SurfaceControl 随 Binder reply 回到 App 进程。Binder 传输的不是图层像素数据，而是一个 IBinder 句柄 + 图层标识；App 侧的 SurfaceControl 对象据此在本地重建出一个"指回 SF 那个 Layer"的引用。
3App 用 SurfaceControl 换出一块 Surface
ViewRootImpl 收到后判断 mSurfaceControl.isValid()。Android 12 默认 BLAST，于是走 getOrCreateBLASTSurface()（ViewRootImpl.java 1958 行）：在 App 进程内 new 一个 BLASTBufferQueue，把 SurfaceControl 传给它，再 createSurface() 得到一块 Surface；最后 mSurface.transferFrom(blastSurface)。
ViewRootImpl.getOrCreateBLASTSurface()（节选）
if (mBlastBufferQueue == null) {
    mBlastBufferQueue = new BLASTBufferQueue(mTag, mSurfaceControl,
            mSurfaceSize.x, mSurfaceSize.y, mWindowAttributes.format);
    ret = mBlastBufferQueue.createSurface();          // ★ 画布
} else {
    mBlastBufferQueue.update(mSurfaceControl, ...);   // 尺寸变化只更新
}

这里必须分清三个长得像、职责完全不同的对象——这是全篇最容易混的地方：

对象是什么谁拿着能干什么
LayerSF 里的图层本体（C++）SurfaceFlinger真正参与合成
SurfaceControl图层的"遥控器/句柄"WMS 与 App 各有引用发指令：位置、层级、显示、提交 Buffer
Surface画布的"生产者接口"App（绘制端）dequeue/queue Buffer，往画布填像素
类比：Layer 是银行金库里的真实账户；SurfaceControl 是你手里的网银 U 盾（能发指令、身份校验、可在家人间授权但搬不走账户）；Surface 是专门给"存钱（填像素）"开的存款通道。App 拿到 Surface，只能往里存像素，改不了账户在"图层银行"里的位置——那是 WMS 用它自己的 SurfaceControl 通过 Transaction 决定的。

句柄过了河，画布就位。接下来 App 终于要真正"作画"了。

五、像素生产：App 在画布上画了什么

App 拿到的那块 Surface，本质是 BufferQueue 生产者端的包装。所谓 BufferQueue，是一个典型的生产者-消费者队列：

  • 生产者（App）：通过 Surface dequeueBuffer 申请一块空闲的 GraphicBuffer（一块跨进程共享的图形内存），在上面画，画完 queueBuffer 归还队列。
  • 队列：维护一组 GraphicBuffer，在"空闲 / 已填充待合成 / 正在被合成"几个状态间流转，通常同时保持 2~3 块以形成流水线。
  • 消费者（最终是 SF）：取出已填充的 Buffer 去合成。
为什么用 GraphicBuffer 而不是直接 byte[]：像素数据量大（一帧 1080p 约 8MB），跨进程拷贝不可接受。GraphicBuffer 背后是 gralloc 分配的共享内存，可被 GPU、显示控制器（HWC）、不同进程零拷贝地映射访问。App 在自己这边映射这块内存画，SF 在另一边直接拿同一块物理内存合成，中间没有像素拷贝。

硬件加速窗口：ThreadedRenderer 主导绘制

绝大多数现代窗口带 FLAG_HARDWARE_ACCELERATED，绘制不走软件 Canvas，而是走 硬件渲染管线：

1ViewRootImpl 在收到下一帧绘制信号（VSYNC 驱动的 doTraversal → performDraw）后，调用 mAttachInfo.mThreadedRenderer.draw(mView, mAttachInfo, this)（ViewRootImpl.java 4418 行）。
2HardwareRenderer（native 层是 RenderProxy + DrawFrameTask）在独立的渲染线程执行：先把 View 树录制/同步成 DisplayList（RenderNode 的绘制指令），再通过 GPU（OpenGL ES / Vulkan，经 Skia）把指令渲染成像素。
3渲染目标不是普通显存，而是从那块 Surface（BLAST BufferQueue）dequeue 出来的 GraphicBuffer。GPU 画完后 queueBuffer，一帧像素正式进入队列。

非硬件加速窗口：软件 Canvas

少数窗口（如某些 SurfaceView/老代码）用软件绘制：Surface lockCanvas() 拿到一块可写 Bitmap 内存，CPU 逐像素绘制，unlockCanvasAndPost() 归还。Android 12 里这条路径最终也统一汇到 BufferStateLayer 的 Buffer 更新机制，只是像素由 CPU 产生。

✦ ✦ ✦ 与 View 树的衔接 ✦ ✦ ✦
01 篇区分过"窗口树 vs View 树"。在这一刻两棵树汇合：App 的 View 树被硬件渲染器画进了 Surface 的 GraphicBuffer。View 树描述"画什么"，Surface/Buffer 是"画在哪"，画完这块 Buffer 就代表了这个窗口当前帧的全部像素。

但在 BLAST 模式下，这个 BufferQueue 并不直接长在 SF 里——它运行在 App 进程中。画完的 Buffer 要怎么跨过进程、带着正确的时机回到 SF？这是 BLAST 要解决的核心问题。

六、BLAST 接力：画完的 Buffer 怎么送回 SF

BLAST（Buffer Layer State）是 Android 12 默认的 Buffer 提交机制。理解它要先知道它解决了什么痛点。

旧模式的问题：同步困难

在非 BLAST 的 BufferQueueLayer 模式里，BufferQueue 直接建在 SF 侧。窗口尺寸/裁剪变化（WMS 控制）与 App 提交新 Buffer（App 控制）是两条异步路径，容易出现"新尺寸配了旧 Buffer""画面撕裂或错位"。WMS 想让"图层状态变化"和"新 Buffer"在同一帧原子生效，却很难协调跨进程的两边。

BLAST 的做法：把队列搬到 App 进程，用事务带 Buffer

native 的 BLASTBufferQueue（frameworks/native/libs/gui/BLASTBufferQueue.cpp，构造在 133 行）在 App 进程内创建一套本地 BufferQueue：

  • 构造时 createBufferQueue(&mProducer, &mConsumer)，App 拿 producer 画；consumer 端是一个 BLASTBufferItemConsumer。
  • 当 App queueBuffer，consumer 收到 onFrameAvailable（546 行）回调；BLASTBufferQueue 随即把这块 GraphicBuffer 打包进一个 SurfaceControl.Transaction（setBuffer），连同几何/裁剪信息，提交给那个 BufferStateLayer。
  • 也就是说，Buffer 不再通过单独的队列通道进 SF，而是作为"事务的一部分"提交。这让"新像素"与"图层新状态"天然能在同一笔事务里原子生效。
BLASTBufferQueue 的角色（示意）
App 绘制线程
  │ dequeueBuffer → GPU 画 → queueBuffer
  ▼
BLASTBufferQueue（运行在 App 进程）
  │ BLASTBufferItemConsumer.onFrameAvailable
  │   → Transaction.setBuffer(layer, graphicBuffer)
  │   → transaction.apply()
  ▼ Binder
SurfaceFlinger: BufferStateLayer 收下"带 Buffer 的事务"
  → 该 Layer 下一帧合成时使用这块新 Buffer
同步事务（sync transaction）保证不错位：当窗口正在 resize，WMS/客户端通过 getSyncTransaction() 与 BLAST 协商：WMS 把新尺寸写进同步事务，BLAST 保证新 Buffer 也挂在同一笔事务上，等 Buffer 就绪才一起 apply。这样屏幕上永远是"新尺寸 + 新内容"同时出现，不会有半帧错位。

WMS 这一边在做什么

注意分工：App 的 BLASTBufferQueue 只负责送"我画好的像素"；而图层的位置、Z 序、alpha、显示/隐藏，仍是 WMS 在 03 篇讲的布局遍历里，通过自己的 SurfaceControl + 全局 Transaction 设置的（还记得吗，图层是 HIDDEN 建出来的）。当 App 第一帧 Buffer 画好、WMS 的布局也完成，03 篇那笔全局事务里会同时带上 show 图层和正确的 layer/position——窗口这时才真正可见。两条信息流在 SF 的事务队列里汇合。

✦ ✦ ✦ 两类事务别混 ✦ ✦ ✦
App/BLAST 事务：携带 Buffer（像素），节奏跟随 App 绘制。
WMS 全局事务：携带几何/Z/可见性（03 篇 open/closeSurfaceTransaction），跟随布局遍历。
SF 把这些事务按顺序 apply 到对应 Layer，在下一个 VSYNC 统一消费。像素与"摆放指令"就此在 SF 集齐。

万事俱备：每个图层都有了正确的状态和最新 Buffer。剩下最后一步，把这些图层真正"叠"在一起，推上物理屏幕。

七、合成上屏：SurfaceFlinger 的 commit / composite / present

SurfaceFlinger 由 VSYNC 信号驱动。每个刷新周期（60Hz 约 16.6ms），它在自己的主线程消息回调 onMessageReceived（SurfaceFlinger.cpp 1862 行）里处理两类事，核心可拆成三段：

阶段 A：commit — 收下事务，更新图层状态

commitTransaction()（3232 行）→ commitTransactionLocked() 把这个周期里到达的所有事务（WMS 的几何/Z/可见性 + App/BLAST 的 Buffer）按序应用到对应 Layer：更新 Layer 的位置、矩阵、裁剪、Z 值、alpha，以及待合成的 Buffer。commit 后，Surface 树反映出"这一帧应该是什么样"。

阶段 B：composite — 决定怎么叠

接着进入合成准备。SF 遍历可见 Layer，计算脏区域、被遮挡区域，决定每个可见区域由谁来合成。这里有两个执行者：

合成方式谁执行适用特点
硬件合成 HWC硬件混叠器（HWComposer，经 Composer HAL）能被显示控制器直接叠加的图层省电、不占用 GPU，可多层并行
客户端合成 GPUGPU（经 RenderEngine / GLES）超过 HWC 层数、复杂变换/混合的部分灵活但费电，先画到一块临时 Buffer

SF 会尽量把图层交给 HWC；当层数过多或 HWC 无法处理某些效果时，回退用 GPU 把多个图层先合成成一块（client composition），再交给 HWC。这个决策每帧动态进行。

阶段 C：present — 推到物理屏幕

CompositionEngine 的 Output 抽象表示一个显示输出。Output.present()（CompositionEngine/src/Output.cpp 423 行）先 prepareFrame()（932 行，让 HWC/GPU 为这一帧做准备），随后把各图层 Buffer 提交：HWC 路径通过 Composer HAL presentDisplay 把每层 Buffer 和层叠参数交给内核显示驱动；驱动在后续扫描周期把像素送向显示面板。GPU 合成出的那块 Buffer 同样作为其中一层交给 HWC。

present 完成后调用 postComposition()（SurfaceFlinger.cpp 2235 行）做收尾：释放/回收用过的 Buffer、记录帧时间、通知各生产者 Buffer 已消费（于是 App 那边能 dequeue 出空 Buffer 画下一帧）。

✦ ✦ ✦ 到屏幕的"最后一公里" ✦ ✦ ✦
严格说，presentDisplay 之后像素还在内核帧缓冲/显示控制器手里：显示面板按自己的刷新节奏，从帧缓冲逐行扫描像素、驱动液晶发光。软件到这里就交出控制权了。所以"送到物理屏幕渲染出画面"= SF 合成 → HWC/驱动提交 Buffer → 面板扫描发光。
为什么还要 VSYNC 卡节奏：合成与屏幕扫描必须对齐。SF 在 VSYNC 到来时才合成、present，保证更新的 Buffer 在面板扫描开始前就位，避免画面撕裂，也让多窗口、多 App 的绘制统一收敛到同一个节拍。

至此，逻辑树的决策与 App 的像素，历经跨进程运输，终于变成了你眼睛看到的那帧光。下面用一张时序图把全程串起来。

9.3 自测

1. WindowState 挂树和它拥有画布是同一时刻吗？
不是。addWindow 挂树只建立逻辑身份；画布在首次 relayout（View 已 measure、frame 已确定）时才经 createSurfaceControl 让 SF 建 BufferStateLayer。
2. SurfaceControl、Surface、Layer 三者什么关系？
Layer 是 SF 里的图层本体；SurfaceControl 是跨进程的遥控器/句柄（发几何、层级、提交指令）；Surface 是给绘制端用的生产者接口（dequeue/queue Buffer）。
3. 为什么 Android 12 要把 BufferQueue 放进 App 进程（BLAST）？
让 Buffer 作为 Transaction 的一部分提交，从而和 WMS 设置的几何/裁剪在同一笔事务原子生效，解决旧模式"新尺寸配旧 Buffer"的跨进程同步错位问题。
4. App 画的像素靠什么做到跨进程零拷贝？
GraphicBuffer 由 gralloc 分配为共享内存，可被 App、GPU、HWC 在各自地址空间映射，同一块物理内存被 SF 直接合成，无需拷贝像素。
5. HWC 合成和 GPU（client）合成有何区别，谁决定？
HWC 是显示控制器硬件叠加，省电且可并行多层；GPU 合成灵活但费电，用于 HWC 处理不了的情况。SF 每帧根据层数和效果动态决定，GPU 合成结果再作为一层交 HWC。
6. "送到物理屏幕"在软件上的最后一步是什么？
Output.present → prepareFrame → Composer HAL 的 presentDisplay 把 Buffer 交内核驱动；之后由显示面板扫描帧缓冲发光，软件交出控制权。
