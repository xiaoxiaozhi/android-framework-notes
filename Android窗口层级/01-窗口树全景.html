零、先建立直觉——概念引导（不碰代码）

在读任何源码之前，先回答一个问题：你看到的屏幕画面，是一整张图吗？不是。本节只用两个生活类比建立直觉——后文所有源码细节，都是这些直觉的"实体化"。

0.1 屏幕是"叠"出来的：一张胶片 = 一个窗口

想象屏幕是一张桌子。你能看到的一切——微信界面、状态栏、导航栏、弹窗、输入法键盘、Toast——每一个都是一张独立的透明胶片，按顺序叠在桌子上。上面胶片透明的地方，会透出下面胶片的内容。

每张胶片就是一个窗口（Window），Android 世界里"往屏幕上画东西"的基本单位。它有边界、有大小、有位置，还有一样最容易被忽略的东西——它压着谁、被谁压着。

⚠️ 常见误解：按钮、文字、图片不是窗口，它们画在某张胶片"里面"，属于 View 系统（见第八节）。先记住：一张胶片 = 一个窗口。

0.2 总调度：WMS 管所有胶片

如果大家随意乱放胶片，画面就乱套了。系统里有一位专职管理员——WindowManagerService，简称 WMS。它手里握着一份全系统窗口的清单，负责：

  • 每个窗口放在哪、多大（位置与尺寸）
  • 谁压着谁（叠放顺序，也叫 Z 序）
  • 谁能盖过谁（权限校验，防止恶意 App 造假窗口骗人）
  • 谁和谁同生共死（窗口归属，父窗口没了子窗口必须消失）
✦ ✦ ✦ 关键预告：这份"清单"并不是一张平铺的列表，而是一棵树。为什么 WMS 要自找麻烦用树而不是列表？——这正是第一节要回答的问题，也是全文最重要的问题。

0.3 窗口的三种身份（Window Type）

不是所有窗口地位平等。Android 把窗口分成三大类：

类别例子特点
应用窗口 Activity 的主窗口（微信聊天界面） 应用自己创建，最常见；挂在所属 Task 下面
子窗口 Dialog、PopupWindow、上下文菜单 必须依附某个父窗口，父窗口没了它必须消失——"父子关系"的第一个伏笔
系统窗口 状态栏、导航栏、Toast、输入法、锁屏 系统级创建，Z 序通常更高，普通应用管不着

0.4 两个必须提前认识的名词：Z 序 与 Token

桌面的叠放引入了第三维——Z 轴。这个叠放顺序叫 Z 序（Z-order）：Z 越高的窗口越靠上、越先拿到触摸事件。而每个窗口还带着一个Token（令牌）——它证明"我是谁家孩子"：子窗口靠它证明"我爸是哪个窗口"，系统靠它做权限校验。第七节会专门讲 Token。

  1. 窗口是屏幕上的一层独立"画"，全系统的窗口叠在一起，由 WMS 统一管理。
  2. 叠放顺序叫 Z 序；窗口分应用窗口、子窗口、系统窗口三类。
  3. 窗口之间有父子关系、有归属凭证（Token）——这两点决定了 WMS 必须用"树"来组织它们。
💡 思考题：按一次 Home 键返回桌面，微信的窗口和桌面的窗口，在"窗口树"里发生了什么？

变的是"顺序"，不是"结构"。桌面的 Task 和微信的 Task 是 TaskDisplayArea 下的两个兄弟节点。按 Home 键时，桌面 Task 被移到兄弟列表的尾部（= Z 序最顶层），微信 Task 相应滑到底部——树的样子没变，兄弟顺序变了，于是 DFS 遍历顺序、Z 序、触摸命中顺序全部跟着变。

顺带一提：如果桌面窗口不透明且铺满全屏，还会触发"遮挡检测"——被完全盖住的微信窗口不再参与合成，省电省资源。这个机制在第 03 篇有详细源码拆解。

一、为什么非得是"树"——三个逃不掉的理由

这是全文最重要的一个问题。WMS 完全可以用一个平铺的 List<WindowState> 装下所有窗口，为什么偏偏要设计出一套层层嵌套的 WindowContainer 树？因为有三个需求，平铺列表一个都满足不了。

1.1 理由一：生死绑定——"删一个，带走一整窝"

窗口之间有严格的归属关系：

  • Activity 销毁时，它的 Dialog、PopupWindow、输入法弹窗必须同时消失，一个都不能剩；
  • 一个 App 进程被杀时，它在所有 Task 里的所有窗口必须一起被清掉；
  • 屏幕（Display）拔掉时，挂在这块屏幕上的所有窗口必须整批销毁。

在树结构里，这种需求天然满足：删掉一个节点 = 删掉以它为根的整棵子树。如果换成平铺列表，每次清理都要遍历全表、逐个比对"这个窗口是不是属于要死的那个 Activity"，既慢又容易漏。树的形状本身就是一张"血缘关系图"，清理就是砍树枝。

类比文件系统：删除一个目录，等于删除目录下所有文件和子目录。没有人会主张"文件系统应该把所有文件平铺在一个列表里"——因为目录层级本身就承载了归属信息。窗口树同理。

1.2 理由二：状态广播——配置沿树往下流

旋转屏幕、改分辨率、切深色模式时，配置变化需要通知所有窗口：显示器（DisplayContent）先知道，然后它下面的每个 Task、每个 Activity、每个 WindowState 依次收到并作出反应。

在树结构里，"广播"就是一次从根向叶子的递归——配置像水一样顺着树枝往下流，每个节点只负责通知自己的直接子节点（源码里叫 dispatchConfigurationChanged 之类的 onConfigurationChanged 链）。如果换成平铺列表，又得全表遍历一遍。

1.3 理由三：局部排序拼出全局 Z 序——树让"排序"可维护

这是最精妙的一点。全系统几百个窗口的 Z 序，不可能靠一个大数组反复全量排序来维护——任何一次弹窗、切后台都要动顺序，代价太高。

树把问题分解了：每个父节点只需要保证自己孩子的先后顺序正确，全局 Z 序就自动成立（见第五节，DFS 遍历天然产出全局顺序）。这就像图书馆——不用给全馆图书排一个大序，只要"每个书架上的书排好序、每个房间的书架排好序"就够。局部有序 + 递归组合 = 全局有序。

小结：树不是 WMS 的"优雅选择"，而是刚需——① 级联生命周期（删子树）② 配置/状态传播（沿树广播）③ Z 序的局部维护（每层只排自己的序）。三个需求合力把窗口管理推向了树结构。

二、树长什么样——一棵真实树的全景图

先看整体，再抠细节。下面是一台普通手机上，adb shell dumpsys window 输出简化后的一棵真实窗口树（AOSP 12 结构）：

RootWindowContainer ← 全局唯一（WMS.mRoot），树根 │ └─ DisplayContent #0（内建屏幕） ← 每个显示器一个 DisplayContent │ ├─ DisplayArea:FeatureRoot (0) ← 树根区：手势导航、系统覆盖层 │ ├─ TaskDisplayArea (FEATURE_DEFAULT_TASK_CONTAINER=1) ← ★ 应用区 │ ├─ Task #1（微信） ← 一个"任务"=最近任务里的一张卡片 │ │ └─ ActivityRecord（MainActivity） │ │ ├─ WindowState（主窗口） │ │ └─ WindowState（Dialog） ← 子窗口挂在这 │ └─ Task #2（桌面 Launcher） │ └─ ActivityRecord │ └─ WindowState（主窗口） │ ├─ DisplayArea.Tokens (FEATURE_WINDOW_TOKENS=2) ← ★ 系统窗口区 │ ├─ WindowToken(StatusBar) ← 状态栏 │ │ └─ WindowState（状态栏图标） │ ├─ WindowToken(NavigationBar) ← 导航栏 │ │ └─ WindowState（导航键） │ └─ WindowToken(NotificationShade)← 通知面板 │ └─ WindowState（下拉通知） │ ├─ DisplayArea (FEATURE_ONE_HANDED=3) ← 单手模式 ├─ … (FEATURE_WINDOWED/FULLSCREEN_MAGNIFICATION=4/5, 放大镜) ├─ … (FEATURE_HIDE_DISPLAY_CUTOUT=6, 刘海隐藏) │ ├─ DisplayArea:ImePlaceholders (FEATURE_IME_PLACEHOLDER=7) ← ★ 输入法区 │ └─ ImeContainer │ └─ WindowToken(InputMethod) │ └─ WindowState（键盘） │ └─ DisplayArea (FEATURE_ONE_HANDED_BACKGROUND_PANEL=8) ← 单手背景板

注意三个观察点：

  1. 同一棵树，两类"血统"并存。状态栏、输入法走 WindowToken 直接挂在 DisplayArea.Tokens/ImeContainer 下；而 App 窗口走 Task → ActivityRecord → WindowState 的长链。身份不同，挂的位置就不同。
  2. 编号即楼层。DisplayArea 括号里的 Feature 编号越小越靠底：应用区(1) 在系统窗口区(2) 之下，输入法区(7) 在最上面压着所有人——所以你打字时键盘永远盖住 App。
  3. 兄弟顺序 = 局部 Z 序。Task #1(微信) 排在 Task #2(桌面) 前面，表示微信压在桌面上。每个"目录"内部都是有序列表，这一点是第五节的基石。

四、树的零件与挂载——mChildren / mParent / addChild

整棵树只用两个字段就能描述。打开 WindowContainer.java：

// L156：一个 WindowContainer 持有一个按 Z-Order 排列的子节点列表 protected final WindowList<E> mChildren = new WindowList<E>(); // L145：每个子节点也持有指向父节点的指针 private WindowContainer<WindowContainer> mParent = null;
子列表 + 父指针 = 一棵多叉树。直白点说：mChildren 是文件系统里 ls 出来的目录项列表，mParent 是 ..。而且注意——这个列表是有序的，这正是第 1.3 节"局部排序"的落地点。

4.1 addChild：窗口是怎么"挂"上去的

WindowContainer.java:514-560 定义了 addChild(E child, Comparator<E> comparator)，逻辑如下：

protected void addChild(E child, Comparator<E> comparator) { // 1. 防环检查：不允许把自己挂到自己（或后代）下面 // 2. 用 Comparator 找到 child 在 mChildren 中的 Z 序插入位置 // 3. 插入 mChildren 列表 // 4. 设置 child.mParent = this ← 双向连接 // 5. 触发 onChildAdded() 回调（子类可覆写，如 TaskDisplayArea 记账） }

当 App 通过 Binder 调 WMS.addWindow() 时，链路的概念级走向：

App 通过 Binder 调 WMS.addWindow()，WMS 创建一个 WindowState 对象
校验身份：WindowToken 是否有效？窗口类型是否合法？（Token 不对直接拒绝）
按窗口类型找到父容器：App 窗口 → 它所属 ActivityRecord 名下；系统窗口 → 按类型定位到对应 DisplayArea 的 Token
父容器调用 addChild(windowState)，按 Z 序插入 mChildren，并回填 mParent
创建 SurfaceControl（与 SurfaceFlinger 通信的句柄），通过 Transaction 设置位置/大小/可见性
applyTransaction → SurfaceFlinger 收到通知，下一帧合成时画出这个窗口
树不是"建好再用"的静态结构——它是一边挂载一边生效。每一次 addChild 都在维护"局部有序"这个不变量，全局 Z 序因此永远成立。挂载细节（谁创建父容器、Comparator 怎么定）交给第 02 篇。

五、遍历即 Z 序——forAllWindows 详解

现在回答第一节埋下的问题：为什么"每层排好序"就等于"全局排好序"？答案在遍历方式里。WindowContainer.java:1391-1415 定义了核心递归方法（简化后）：

boolean forAllWindows(ToBooleanFunction<WindowState> callback, boolean traverseTopToBottom) { if (traverseTopToBottom) { // 从列表尾部开始 → 从最上层开始 for (int i = mChildren.size() - 1; i >= 0; --i) mChildren.get(i).forAllWindows(callback, true); } else { // 从列表头部开始 → 从最下层开始 for (int i = 0; i < mChildren.size(); i++) mChildren.get(i).forAllWindows(callback, false); } }

先记住 WindowContainer.java:156 注释里对 mChildren 的定义：

"List is in z-order as the children appear on screen with the top-most window container at the tail of the list."
译文：mChildren 按 Z 序排列——屏幕上越靠上的子节点，越靠近列表尾部。头部 = 最底层，尾部 = 最顶层。

5.1 一个最小例子：看着 DFS 走出 Z 序

拿第二节的树截取两段，标上 DFS 访问顺序。假设 TaskDisplayArea（应用区，Feature 1）在下、DisplayArea.Tokens（系统窗口区，Feature 2）在上：

TaskDisplayArea (Feature 1) DisplayArea.Tokens (Feature 2) ├─ Task #1（微信） └─ WindowToken(StatusBar) │ └─ ActivityRecord │ │ ├─ WindowState A（主窗口） └─ WindowState D（状态栏） │ └─ WindowState B（Dialog） └─ Task #2（桌面） └─ ActivityRecord └─ WindowState C（Launcher） 自下而上遍历（traverseTopToBottom=false）→ A → B → C → D 自上而下遍历（traverseTopToBottom=true） → D → C → B → A

看出门道了吗？每个"目录"内部有序 + 递归地按顺序展开 = 全局唯一的一个 Z 序。这就像合并排序的"合并"步骤：每层都已经排好了，遍历只是在把嵌套的排序展开成一条直线。不需要任何全局排序算法，树的形状 + 局部有序，就决定了全局顺序。

5.2 两个方向对应两个真实场景

遍历方向顺序实际用途
自下而上
traverseTopToBottom=false		 最底层 → 最顶层 绘制/合成顺序：先画下面的，再画上面的，上面的自然盖住下面的（第 03 篇 WindowSurfacePlacer 的布局遍历）
自上而下
traverseTopToBottom=true		 最顶层 → 最底层 触摸命中顺序：先问最上层的窗口"点的是你吗？"，不是再往下问（InputDispatcher 的命中测试逻辑）

5.3 抽象概念实体化：Layer 到底是什么？

"Z 序"听着抽象，它在源码里就是一个 int 层号，由三个具体方法接力算出并下发——全在 WindowContainer.java：

// L2290：父容器给每个子节点"发号"——兄弟顺序就是层号 void assignChildLayers(Transaction t) { int layer = 0; // 第一轮：不需要 Z-boost 的孩子按列表顺序领号 for (int j = 0; j < mChildren.size(); ++j) { final WindowContainer wc = mChildren.get(j); wc.assignChildLayers(t); // 先递归处理孙辈 if (!wc.needsZBoost()) { wc.assignLayer(t, layer++); // ← 层号在这里 +1 分发 } } // 第二轮：需要 Z-boost 的孩子排到最后，层号更大 = 浮在最上 for (int j = 0; j < mChildren.size(); ++j) { final WindowContainer wc = mChildren.get(j); if (wc.needsZBoost()) wc.assignLayer(t, layer++); } } // L2240：真正"写层号"的地方——只有层号变了才动手 void assignLayer(Transaction t, int layer) { final boolean changed = layer != mLastLayer || mLastRelativeToLayer != null; if (changed) { setLayer(t, layer); // → mSurfaceAnimator.setLayer mLastLayer = layer; // 记住旧值，避免每帧重复下发 } } // L2252：相对层级——不写绝对序号，而是"始终贴在 relativeTo 上面" void assignRelativeLayer(Transaction t, SurfaceControl relativeTo, int layer) { ... }

setLayer 一路往下，最终变成 SurfaceControl.Transaction.setLayer(SurfaceControl, int) 这一个 int 参数交给 SurfaceFlinger。也就是说：树上的"Z 序"不是概念，而是一串从根一路 layer++ 分下来的整数。

到窗口这一层，层号拆成三个字段，定义在 WindowState.java:316-317 / 391：

字段行号含义与来源
mBaseLayer316基础层：由 mPolicy.getWindowLayerLw(parentWindow) 按窗口类型给出——状态栏、输入法、应用窗口各有各的层号
mSubLayer317子层偏移：子窗口相对父窗口的微调，来自 getSubWindowLayerFromTypeLw（如菜单面板压在内容之上）
mLayer391最终层号：getSurfaceLayer()（L1486）读的就是它
✦ ✦ ✦ 换用具体类的一句话版：layer = WindowContainer.assignLayer(t, layer) 收到的那个 int，最终存进 WindowState.mLayer，经 Transaction.setLayer 发给 SurfaceFlinger。树排好序、层号按 DFS 分发——这就是"Z 序"的完整实体化。
✦ ✦ ✦ 一句话：DFS 遍历顺序 = 全局 Z 序。树的形状回答了"窗口画在第几层"，遍历方向回答了"先处理谁"。这是整个窗口系统最核心的一个等式，后面两篇（构建、遍历显示）都是围着它转。

六、DisplayArea 的"楼层编号"——mFeatureId 分区

第二节的树里，每个 DisplayArea 都带一个 Feature 编号。为什么？因为不同身份的窗口必须住在不同楼层：App 不能盖住状态栏，键盘必须压住 App，放大镜必须压住一切。与其让每个窗口自己抢位置，不如先按"用途"划好楼层，窗口按身份入住。

DisplayAreaOrganizer.java:39-130 定义了所有 Feature ID：

Feature ID 常量值对应区域（楼层）
FEATURE_ROOT0根 DisplayArea（最低层）
FEATURE_DEFAULT_TASK_CONTAINER1应用任务区 → 实例化为 TaskDisplayArea（你的 App 在这层）
FEATURE_WINDOW_TOKENS2窗口令牌区 → 实例化为 DisplayArea.Tokens（状态栏等系统窗口在这层）
FEATURE_ONE_HANDED3单手模式位移区
FEATURE_WINDOWED_MAGNIFICATION4窗口化放大镜
FEATURE_FULLSCREEN_MAGNIFICATION5全屏放大镜
FEATURE_HIDE_DISPLAY_CUTOUT6刘海隐藏区
FEATURE_IME_PLACEHOLDER7输入法占位区 → 内含 ImeContainer（键盘在这层，压住 App）
FEATURE_ONE_HANDED_BACKGROUND_PANEL8单手模式背景面板（最高层）
DisplayArea 不是按"名字"排队，是按 mFeatureId（楼层编号）排队。DisplayAreaPolicyBuilder 构建时按 Feature ID 升序排列——编号越小越靠底、越大越靠顶。所以"输入法永远压住应用""状态栏永远在 App 之上"这些我们习以为常的现象，源头就是这两行编号。构建细节在第 02 篇完整拆解。

6.1 Feature 不是编号，是一个具体类

每个 DisplayArea 的 mFeatureId 来自一个真实存在的类：DisplayAreaPolicyBuilder.Feature（DisplayAreaPolicyBuilder.java:585）。它是"这棵树该长成什么样"的描述块，四个字段：

字段行号含义
mName586名字，如 "WindowedMagnification"、"ImePlaceholder"（只用于日志和调试）
mId587唯一 id，即上一节的 FEATURE_* 常量（如 FEATURE_IME_PLACEHOLDER = 7）
mWindowLayers588boolean 数组，下标就是窗口 layer 号——标记这个功能圈定哪些窗口类型。Feature 和 Layer 在这里咬合
mNewDisplayAreaSupplier589默认 DisplayArea::new；想要可调暗区域就传 DisplayArea.Dimmable::new

用 Feature.Builder（DisplayAreaPolicyBuilder.java:616）链式圈定范围——all() / and(...) / except(...) / upTo(...) 内部都是在改 mWindowLayers[] 这个布尔数组。来自 DisplayAreaPolicy.java:156 的真实代码：

// 圈定"输入法两层窗口"：TYPE_INPUT_METHOD + TYPE_INPUT_METHOD_DIALOG new Feature.Builder(wmService.mPolicy, "ImePlaceholder", FEATURE_IME_PLACEHOLDER) .and(TYPE_INPUT_METHOD, TYPE_INPUT_METHOD_DIALOG) .build() // 对比：放大镜圈"几乎所有窗口"，再逐个排除 new Feature.Builder(wmService.mPolicy, "FullscreenMagnification", FEATURE_FULLSCREEN_MAGNIFICATION) .all() .except(TYPE_ACCESSIBILITY_MAGNIFICATION_OVERLAY, TYPE_INPUT_METHOD, TYPE_INPUT_METHOD_DIALOG, TYPE_MAGNIFICATION_OVERLAY, TYPE_NAVIGATION_BAR, TYPE_NAVIGATION_BAR_PANEL) .build()

系统默认的整棵功能树，就是在 DisplayAreaPolicy.java:117 的 configureTrustedHierarchyBuilder() 里逐个 addFeature 拼出来的：WindowedMagnification → HideDisplayCutout → OneHandedBackgroundPanel → OneHanded → FullscreenMagnification → ImePlaceholder。每个 Feature 交给 HierarchyBuilder，最终实例化为树里对应的 DisplayArea / RootDisplayArea / TaskDisplayArea 节点。

✦ ✦ ✦ 换用具体类的一句话版：Feature = DisplayAreaPolicyBuilder.Feature 的一个实例，四个字段描述"某类窗口该住哪一层"；树里那些非窗口的组织节点（状态栏区、输入法占位区……）就是它实例化的产物。Layer 给窗口编号，Feature 按编号圈地——这就是树里两个词的关系。构建算法在第 02 篇拆解。

七、WindowToken——窗口的"户口本"

WindowToken.java:71：class WindowToken extends WindowContainer<WindowState>

树上的每个 WindowState 都不是"黑户"——它必须挂在一个 WindowToken 名下。Token 的核心职责：

  • 身份绑定：所有同源的 WindowState（一个 Activity 的主窗口 + 它的 Dialog + 它的 PopupWindow）共享一个 WindowToken。窗口归属谁，Token 说了算
  • 集体清理：Token 被移除 → 递归移除名下所有 WindowState → SurfaceFlinger 同步清除所有 Layer。"注销户口，全家消失"
  • 权限验证：每个 WindowToken 有自己的 client（Binder 连接）。普通 App 无法冒用状态栏的 Token 挂自己的窗口——这就是"系统窗口不能被伪造"的防线
  • ActivityRecord 是 WindowToken 的子类，所以 Activity 天然拥有上述全部能力，还额外带着生命周期管理
✦ ✦ ✦ 一句话：WindowToken = 窗口的"户口本"。户口注销时，所有家庭成员（WindowState）一起消失。ActivityRecord 是户口本的一种特殊类型——它附加了 Activity 生命周期的管理能力，同时身兼 AMS 记录与 WMS 节点两职。

八、别混淆：窗口树 vs View 树（两层结构）

初学最容易栽的坑：把"窗口层级"和"View 层级"混为一谈。它们是两棵完全不同的树，各归各的管家。

窗口树（本专题主角）View 树（窗口内部的骨架）
节点 WindowContainer 家族：Display / Task / Token / WindowState… ViewGroup（容器）和 View（元素）：按钮、文字、图片…
管家 WMS（system_server 进程） ViewRootImpl / LayoutInflater（App 进程内）
根节点 RootWindowContainer（全系统一棵） 每个窗口一棵，根固定叫 DecorView（"装裱好的画框"）
粒度 窗口与窗口之间（谁压谁） 窗口内部元素之间（按钮放哪）

窗口内部的典型结构：

WindowState（窗口） └── DecorView ← 视图树根，窗口的"画框" ├── 系统预留区 ← 状态栏下方的留白 └── 内容区 (ContentView) └── 你的布局：ViewGroup ├── View（按钮） ├── ViewGroup（列表） │ └── View（列表项） └── ...
两棵树的接头点在哪？App 进程里，ViewRootImpl 通过 Session.addToDisplay() 走 Binder 到 system_server，把"我这棵 View 树"注册成一个 WindowState、挂上窗口树；之后 Surface 的提交、触摸事件的下发，都沿这两棵树来回传递。窗口树决定"这一窗画在哪层"，View 树决定"这一窗里面画什么"。

九、和其他系统的关系

AMS

管 Activity 生命周期
创建并持有 Task / ActivityRecord
决定"开哪个界面"

→ 与 WMS 共享 ActivityRecord 对象
WMS

管窗口层级树
持有 RootWindowContainer

SurfaceFlinger

三者之间的数据映射：

  • AMS 的 ActivityRecord ↔ WMS 层级树中的 ActivityRecord（继承 WindowToken）——同一个对象，这是两套系统不打结的关键
  • WMS 的 WindowState → 持有 SurfaceControl → SurfaceFlinger 的 Layer——跨进程 Binder Transaction 映射
  • Activity 销毁时：AMS 移除 ActivityRecord → WMS 连根移除名下的 WindowState → Transaction 通知 SurfaceFlinger 移除 Layer——一次操作沿三层系统瀑布式传导

十一、总结——核心结论

❶ 为什么是树：三个刚需逼出来的——① 级联生命周期（删一个节点带走整棵子树）② 配置/状态沿树广播 ③ 局部排序递归拼出全局 Z 序。窗口层级树不是比喻，是真实的多叉树：所有节点继承自 WindowContainer，靠 mChildren（按 Z 序排列的子列表）+ mParent（父指针）连接。

❷ 树的形状——RootWindowContainer → DisplayContent → 各 DisplayArea（按 Feature 楼层分区）→ Task → ActivityRecord（继承 WindowToken）→ WindowState；系统窗口走 Tokens 区，App 窗口走 TaskDisplayArea 区。

❸ 树的运转 = DFS——forAllWindows 自下而上（绘制合成）或自上而下（触摸命中）遍历，遍历顺序即全局 Z 序：mChildren 头部最底、尾部最顶。

❹ 别混淆两层树——窗口树归 WMS 管"窗口之间谁压谁"；View 树归 ViewRootImpl 管"窗口里面画什么"，两棵树通过 addToDisplay 对接。

❺ 两个抽象词都有实体——Layer 是 WindowContainer.assignChildLayers/assignLayer 从根往下 layer++ 分发的 int 层号（窗口侧拆成 WindowState.mBaseLayer / mSubLayer / mLayer，经 Transaction.setLayer 交给 SurfaceFlinger）；Feature 是 DisplayAreaPolicyBuilder.Feature 的实例（mName / mId / mWindowLayers / mNewDisplayAreaSupplier），用 layer 号圈定楼层、生成对应的 DisplayArea 节点。
