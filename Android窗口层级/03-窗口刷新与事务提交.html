一、全景：从"窗口变了"到"屏幕变了"

上一篇我们讲完了树是怎么建起来的、窗口是怎么挂上去的。这一篇回答下一个问题：树上的一个变化（窗口新增、移除、resize、显示/隐藏），是怎么最终变成屏幕上像素变化的？

先建立一个最重要的直觉：任何变化都不会立刻画屏。系统采用"脏标记 + 批量处理"策略——变化只负责做标记，然后统一安排一次遍历，最后用一笔事务提交：

窗口状态变化
addWindow / removeWindow / relayoutWindow / 动画 → 标记脏
setLayoutNeeded / mWindowsChanged → requestTraversal()
WindowSurfacePlacer 排程 → performSurfacePlacement()
最多循环 6 次 → RootWindowContainer
.performSurfacePlacement() → applySurfaceChangesTransaction()
逐显示器：布局 + 应用状态 → mergeToGlobalTransaction()
合并为一笔全局事务 → SurfaceFlinger
下一个 VSYNC 消费事务 → 上屏
✦ ✦ ✦ 两个贯穿全文的核心思想 ✦ ✦ ✦
① 延迟合并（Defer）：短时间内的一连串变化（比如分屏动画改了几十个窗口），先攒着，最后只做一次布局遍历，避免重复劳动。
② 统一提交（Single Transaction）：所有窗口的新位置、新 Z 序、显示/隐藏，打包成一笔 SurfaceControl 事务原子提交，观众永远看不到"改到一半"的中间状态（避免闪烁）。

读完整篇你会发现，整个流程其实就三件事：遍历树（forAllWindows）→ 算位置（performLayout）→ 分层次（assignChildLayers），最后包起来提交。

二、总调度：WindowSurfacePlacer — 一次布局循环

遍历的总入口不在 WMS 里，而是一个专职小类 WindowSurfacePlacer（AOSP 12 名字；它的前身是 WMS 里的 performLayoutAndPlaceSurfacesLocked）。它的职责写在类注释里：

"Positions windows and their surfaces. It sets positions of windows by calculating their frames and then applies this by positioning surfaces according to these frames."
—— 计算每个窗口的 frame（位置+大小），然后据此摆放对应的 Surface。

2.1 排程：requestTraversal()

WindowSurfacePlacer.java — 请求一次遍历
void requestTraversal() {
    if (mTraversalScheduled) {          // ★ 幂等：已经排了就不用再排
        return;
    }
    mTraversalScheduled = true;
    if (mDeferDepth > 0) {               // ★ 正在 defer：只计数，不执行
        mDeferredRequests++;
        return;
    }
    mService.mAnimationHandler.post(mPerformSurfacePlacement);   // ★ 投递到动画线程的消息队列
}

注意两个细节：

  • 幂等：一帧内无论多少个窗口请求，最终只跑一次遍历（mTraversalScheduled 标志）。
  • 投递到 mAnimationHandler：遍历发生在动画消息队列上，天然和动画节奏对齐；同一队列里后到的遍历请求会被合并。

2.2 defer：把多次变更攒成一次

WindowSurfacePlacer.java — defer 机制
/** Starts deferring layout passes. Useful when doing multiple changes but
 *  to optimize performance, only one layout pass should be done. */
void deferLayout() { mDeferDepth++; }     // 进入延迟区（可嵌套计数）

void continueLayout() {
    mDeferDepth--;
    if (mDeferDepth == 0 && mDeferredRequests > 0) {
        mDeferredRequests = 0;
        performSurfacePlacement();        // ★ 退出延迟区：一次性结算
    }
}

典型场景：分屏拖拽、批量改窗口属性时，WMS 会 deferLayout() 包住整段操作，改完再 continueLayout()——期间所有 requestTraversal 都被计数积压，最后只遍历一次。

2.3 执行：performSurfacePlacement() — 为什么最多 6 次

WindowSurfacePlacer.java — 布局循环
final void performSurfacePlacement(boolean force) {
    if (mDeferDepth > 0 && !force) {        // 延迟中：只记一笔账
        mDeferredRequests++;
        return;
    }
    int loopCount = 6;                      // ★ 与 LAYOUT_REPEAT_THRESHOLD 一致
    do {
        mTraversalScheduled = false;
        performSurfacePlacementLoop();
        mService.mAnimationHandler.removeCallbacks(mPerformSurfacePlacement);
        loopCount--;
    } while (mTraversalScheduled && loopCount > 0);   // ★ 遍历过程中又有新请求 → 再跑一轮
    mService.mRoot.mWallpaperActionPending = false;
}

为什么是循环而不是一次？因为一次遍历的结果可能引发新的布局需求（比如壁纸发现要重调、旋转后要重算）。循环允许"再跑一轮"，但上限 6 次——防止两个窗口互相触发、震荡成死循环。超过 6 次就放弃并打日志。

核心的 performSurfacePlacementLoop() 做了三件事：

WindowSurfacePlacer.java — performSurfacePlacementLoop（节选）
if (mInLayout) { ... return; }                       // ★ 防重入：遍历中禁止再入
if (defaultDisplay.mWaitingForConfig) return;       // 旋转中：配置没就绪先不布局
if (!mService.mDisplayReady) return;                 // 系统没初始化完：不动

mInLayout = true;
try {
    mService.mRoot.performSurfacePlacement();      // ★ 真正的遍历入口：从根节点开始

    mInLayout = false;
    if (mService.mRoot.isLayoutNeeded()) {         // 一轮没摆平？
        if (++mLayoutRepeatCount < 6) {
            requestTraversal();                 // ★ 再请求一轮（呼应外面的 do-while）
        } else {
            Slog.e(TAG, "Performed 6 layouts in a row. Skipping");
            mLayoutRepeatCount = 0;
        }
    }
}
关键字段作用
mTraversalScheduled是否已有遍历在排队（幂等 + 循环条件）
mDeferDepth延迟深度（可嵌套），>0 时不真正执行
mInLayout防重入标志
mLayoutRepeatCount连续布局轮数，≥6 放弃

三、遍历引擎：forAllWindows — DFS 与 Z 序

回顾 01 的结论：mChildren 列表本身就是 Z 序，最顶层节点在列表尾部。源码注释原文：

WindowContainer.java — mChildren 字段注释
// List of children for this window container. List is in z-order as the children appear on
// screen with the top-most window container at the tail of the list.
protected final WindowList<E> mChildren = new WindowList<E>();

有了这个不变量，深度优先遍历（DFS）就有了方向：

WindowContainer.java — 递归遍历器
boolean forAllWindows(ToBooleanFunction<WindowState> callback, boolean traverseTopToBottom) {
    if (traverseTopToBottom) {
        // ★ 从尾部（最顶层）开始，向下遍历
        for (int i = mChildren.size() - 1; i >= 0; --i) {
            if (mChildren.get(i).forAllWindows(callback, traverseTopToBottom)) {
                return true;          // ★ 回调返回 true = 短路，提前结束搜索
            }
        }
    } else {
        // ★ 从头部（最底层）开始，向上遍历
        final int count = mChildren.size();
        for (int i = 0; i < count; i++) {
            if (mChildren.get(i).forAllWindows(callback, traverseTopToBottom)) {
                return true;
            }
        }
    }
    return false;
}

用一棵简化树感受一下访问顺序（数字 = 访问次序，traverseTopToBottom = true）：

RootWindowContainer
 └── DisplayContent (id=0)
      ├── DisplayArea.Tokens "Leaf:0:1"        ④   ← 壁纸（最底层，最后访问）
      │    └── WindowToken → WindowState        ⑤
      ├── TaskDisplayArea                   ③
      │    └── Task → ActivityRecord → WindowState  ③
      ├── DisplayArea.Tokens "Leaf:8:14"     ②   ← Toast 等
      └── DisplayArea.Tokens "Leaf:17:23"   ①   ← 状态栏（最顶层，最先访问）
✦ ✦ ✦ 为什么"遍历顺序"如此重要 ✦ ✦ ✦
全系统的多个子系统共用这同一个遍历器：布局用它、遮挡检测用它、输入事件分发（InputDispatcher 构建窗口命中列表）也用它。
只要大家都按"树的顺序"走，就能保证 眼睛看到的顺序（Z 序）== 手指点到的顺序（命中顺序）。这就是 01 里说的"DFS 遍历天然决定 Z-Order"的威力。

另外注意 ToBooleanFunction 的短路语义：回调返回 true 就停止整棵树的遍历。这被用于"找到第一个可见窗口"之类的搜索（如查找焦点目标）。

四、第一遍遍历：布局（performLayout）

树遍历进来后，第一件事是布局（layout）。注意概念区分：

布局（layout）= 计算 frame：决定每个窗口在屏幕上应该在哪个位置、多大（纯数学计算，只改内存里的矩形）。
摆放（place）= 移动 Surface：把上一步算出的 frame 写进 SurfaceControl.Transaction，真正挪动画面。这是后面第六、七节的事。

4.1 两遍遍历：先根窗口，后附着窗口

DisplayContent.java — performLayoutNoTrace
private void performLayoutNoTrace(boolean initial, boolean updateInputWindows) {
    if (!isLayoutNeeded()) return;      // ★ 没有脏标记就跳过（不浪费遍历）
    clearLayoutNeeded();

    int seq = mLayoutSeq + 1;         // 布局序号：区分"这是第几轮布局"
    mLayoutSeq = seq;

    // ★ 第一遍：布局所有"根窗口"（不依附于其他窗口的）
    forAllWindows(mPerformLayout, true /* traverseTopToBottom */);

    // ★ 第二遍：布局"附着窗口"（子窗口依赖父窗口的位置，必须等父先算完）
    forAllWindows(mPerformLayoutAttached, true /* traverseTopToBottom */);

    // 窗口 frame 可能变了 → 通知输入分发器重建命中区域
    mInputMonitor.setUpdateInputWindowsNeededLw();
    if (updateInputWindows) {
        mInputMonitor.updateInputWindowsLw(false);
    }
}

为什么必须两遍？因为子窗口的 frame 是相对父窗口算的——PopupWindow、Dialog 这类附着窗口，要先知道父窗口定在哪，才能定自己。所以：第一遍所有根窗口（各自独立定位），第二遍所有附着窗口（跟着父窗口走）。

4.2 单个窗口怎么算：mPerformLayout

DisplayContent.java — mPerformLayout 回调
private final Consumer<WindowState> mPerformLayout = w -> {
    final boolean gone = w.isGoneForLayout();   // 即将消失的窗口：跳过，省时省力

    if ((!gone || !w.mHaveFrame || w.mLayoutNeeded) && !w.mLayoutAttached) {
        w.mSurfacePlacementNeeded = true;
        w.mLayoutNeeded = false;
        w.prelayout();                              // ★ 布局前钩子（如隐藏窗口置空 frame）
        getDisplayPolicy().layoutWindowLw(w, null, mDisplayFrames);
                                                   // ★ 核心：计算窗口 frame
                                                   //   → 最终调用 win.computeFrames()，
                                                   //   按窗口类型/Insets/父窗口算出最终矩形
        w.mLayoutSeq = mLayoutSeq;                  // 记录本窗口被第几轮布局过
        ...
    }
};

两个值得记住的字段，之后读源码会反复遇到：

字段含义类比
mLayoutNeeded这个窗口"需要重新布局"待办便签
mHaveFrame这个窗口"已经有一个算好的 frame"已有地址
mLayoutSeq最后一次布局的轮次号盖章日期（判断结果是否过期）

五、布局之后：后置策略收敛、遮挡检测与逐窗口状态应用

布局只是算了位置。算完之后，系统还要回答一堆"副作用"问题：壁纸要不要跟着重排？屏幕方向要不要改？哪个窗口挡住了谁（遮挡检测）？——这些由 DisplayContent.applySurfaceChangesTransaction() 用一个 do-while 循环来收敛：

DisplayContent.java — applySurfaceChangesTransaction（节选）
int repeats = 0;
do {
    repeats++;
    if (repeats > 6) { ... break; }              // ★ 又是 6 次上限：防止震荡

    if ((pendingLayoutChanges & FINISH_LAYOUT_REDO_WALLPAPER) != 0) {
        mWallpaperController.adjustWallpaperWindows();   // 壁纸目标变了 → 重调壁纸窗口
    }
    if ((pendingLayoutChanges & FINISH_LAYOUT_REDO_CONFIG) != 0) {
        if (updateOrientation()) { ... }             // 方向变了 → 旋转 + 通知配置变化
    }
    if ((pendingLayoutChanges & FINISH_LAYOUT_REDO_LAYOUT) != 0) {
        setLayoutNeeded();                              // 要求再来一轮布局
    }

    performLayout(repeats == 1, false);              // ★ 第一遍遍历（上一节）

    pendingLayoutChanges = 0;                         // 清零，然后由策略层重新投票

    // ★ 策略层（PhoneWindowManager）遍历所有窗口，投票决定还需不需要再布局
    mDisplayPolicy.beginPostLayoutPolicyLw();
    forAllWindows(mApplyPostLayoutPolicy, true /* traverseTopToBottom */);
    pendingLayoutChanges |= mDisplayPolicy.finishPostLayoutPolicyLw();
} while (pendingLayoutChanges != 0);   // ★ 还有票 → 再跑一轮，直到稳定

这个循环体现了经典的"布局 → 检查 → 再布局"收敛模型：布局结果可能改变策略判断（如状态栏隐藏导致应用要拉伸、壁纸要跟随），策略判断又要求重布局，反复直到稳定（或 6 次上限）。

5.1 逐窗口应用：遮挡检测

循环收敛后，再用一遍 forAllWindows 从上到下给每个窗口"结算"显示状态，其中最核心的是遮挡检测——决定后面的窗口是否需要调暗（Dim）：

DisplayContent.java — mApplySurfaceChangesTransaction 回调（节选）
private final Consumer<WindowState> mApplySurfaceChangesTransaction = w -> {
    final boolean obscuredChanged = w.mObscured !=
            mTmpApplySurfaceChangesTransactionState.obscured;
    w.mObscured = mTmpApplySurfaceChangesTransactionState.obscured;
                              // ★ 遍历从上到下：更上层窗口先结算，
                              //   后面的窗口若被完全盖住，标记为 obscured

    if (!mTmpApplySurfaceChangesTransactionState.obscured) {
        final boolean isDisplayed = w.isDisplayed();

        if (isDisplayed && w.isObscuringDisplay()) {
            // ★ 这个窗口不透明且铺满全屏 → 它后面的窗口全被遮挡，
            //   不必再画（性能优化：SurfaceFlinger 直接跳过）
            root.mObscuringWindow = w;
            mTmpApplySurfaceChangesTransactionState.obscured = true;
        }
        final boolean displayHasContent =
                root.handleNotObscuredLocked(w, ...);   // 屏幕是否有内容 → 控制熄屏/保活
        ...
    }
};

注意遍历方向的妙用：从顶层往底层走，一旦遇到全屏不透明窗口，后面（更底层）的所有窗口就全被挡住——这正是"最顶层在列表尾部、从尾部开始遍历"这一设计带来的顺理成章的效率。

六、Z 序分配：assignChildLayers 两遍算法

这是本篇的第二个核心。布局定了 (X, Y)，Z 序分配定 Z。回顾 02 的内容：树的形状由 base layer 决定（窗口类型 → 挂在哪个 DisplayArea.Tokens 下），但真正的 Z 值是遍历时按顺序现分的整数。

6.1 入口：谁触发重新分 Z

DisplayContent.java — assignWindowLayers
/** Updates the layer assignment of windows on this display. */
void assignWindowLayers(boolean setLayoutNeeded) {
    assignChildLayers(getSyncTransaction());   // ★ 整棵子树重新分配 Z 值
    if (setLayoutNeeded) setLayoutNeeded();
    scheduleAnimation();   // Z 序变化延迟到动画阶段随事务一起应用（避免闪跳）
}

6.2 两遍算法：普通孩子先分，Z-Boost 孩子殿后

WindowContainer.java — assignChildLayers
void assignChildLayers(Transaction t) {
    int layer = 0;                        // ★ 从 0 开始，自底向上递增

    // 两遍遍历：第二遍把需要 Z-boost 的孩子排到末尾（= 更高 Z）
    for (int j = 0; j < mChildren.size(); ++j) {
        final WindowContainer wc = mChildren.get(j);
        wc.assignChildLayers(t);                 // ★ 先递归分内部
        if (!wc.needsZBoost()) {
            wc.assignLayer(t, layer++);          // 第一遍：普通孩子按顺序拿号
        }
    }
    for (int j = 0; j < mChildren.size(); ++j) {
        final WindowContainer wc = mChildren.get(j);
        if (wc.needsZBoost()) {
            wc.assignLayer(t, layer++);          // 第二遍：Z-boost 孩子拿更大的号
        }
    }
}

needsZBoost() 问的是："这个节点（或它的子孙）是否要求临时'破格'压到兄弟节点之上？"（典型的如某些系统弹窗需要压过应用窗口）。两遍遍历保证：需要破格的节点，Z 值一定比所有普通兄弟大，但又不会搅乱普通兄弟之间的相对顺序。

6.3 叶子节点的特殊处理：WindowState.assignLayer

WindowState.java — assignLayer 覆写
@Override
void assignLayer(Transaction t, int layer) {
    // 输入法的目标窗口：不能只按序号排，要"相对 IME"排
    if (needsRelativeLayeringToIme()) {
        getDisplayContent().assignRelativeLayerForImeTargetChild(t, this);
        return;
    }
    super.assignLayer(t, layer);
}

IME（输入法）是 Z 序里最"不安分"的角色：它必须紧跟目标窗口——目标窗口的兄弟（比如它弹出来的子窗口）要能盖过 IME，但别的窗口不行。所以 IME 相关节点不走普通编号，而走 assignRelativeLayerForIme 的"相对定位"。这解释了为什么 DisplayContent 覆写的 assignChildLayers 开头要先调用 assignRelativeLayerForIme(t, false)。

基类 WindowContainer.assignLayer(t, layer) 也很务实：

WindowContainer.java — assignLayer 基实现
void assignLayer(Transaction t, int layer) {
    // 过渡动画播放期间不抢 Z：避免和动画的 Z 打架（z-order fighting）
    if (mWmService.mAtmService.getTransitionController().isPlaying()) return;
    final boolean changed = layer != mLastLayer || mLastRelativeToLayer != null;
    if (mSurfaceControl != null && changed) {
        setLayer(t, layer);          // ★ 把新 Z 写进事务，等最后统一提交
        mLastLayer = layer;
        mLastRelativeToLayer = null;
    }
}

6.4 base layer：窗口类型的"初始分班"

别忘了树是怎么长成这个形状的：每个窗口类型先被映射成一个 base layer 数字，这个数字决定它挂在哪个 DisplayArea.Tokens 下（02 的 typeOfLayer + areaForLayer 查表）。AOSP 12 的真实映射：

💡 双重理解：base layer 决定树的形状（挂哪个 Tokens）；遍历时按顺序发的连续整数才是真正的 Z 值。前者相对静态，后者每次遍历都可能变。

6.5 数字示例：一棵树的 Z 值长什么样

假设 DisplayContent 下经过 02 的构建算法后得到（示意值，默认 Feature 简化）：

DisplayContent  ── assignChildLayers 从这里开始，layer 从 0 发号
 ├── DA.Tokens "Leaf:0:1"          Z=0   ← 壁纸
 │     └── WallpaperWindowState        Z=0
 ├── TaskDisplayArea               Z=1
 │     └── Task#1 → ActivityRecord
 │           └── WindowState(微信)     Z=1
 ├── DA.Tokens "Leaf:8:14"        Z=2   ← Toast 等
 │     └── ToastWindowState           Z=2
 ├── ImeContainer                  Z=3   ← 输入法（相对层级，示例值）
 ├── DA.Tokens "Leaf:17:23"      Z=4   ← 状态栏 / 通知栏
 └── DA.Tokens "Leaf:24:31"      Z=5   ← 导航栏

看到了吗：Z 值就是"在这棵树的这条路上排第几"。树的形状不变，Z 的绝对数字变了也没关系（比如中间插入一层），因为大家只关心相对关系。这就是层级树设计的优雅之处——结构即顺序。

七、提交：一把事务落地到 SurfaceFlinger

所有遍历做完，新的 frame、新的 Z 值、显示/隐藏状态都写进了事务对象（Transaction）。最后一步是把它合并成一笔全局事务，原子地提交给 SurfaceFlinger：

RootWindowContainer.java — performSurfacePlacementNoTrace（节选）
if (mWmService.mFocusMayChange) {
    mWmService.mFocusMayChange = false;
    mWmService.updateFocusedWindowLocked(
            UPDATE_FOCUS_WILL_PLACE_SURFACES, false);   // ★ 摆放前先解决焦点
}

mWmService.mTransactionSequence++;                       // 事务序号 +1

mWmService.openSurfaceTransaction();                 // ★ 打开全局事务（合并所有子事务）
try {
    applySurfaceChangesTransaction();            // ★ 逐显示器：布局 + Z 序 + 状态（第五、六节）
} finally {
    mWmService.closeSurfaceTransaction("performLayoutAndPlaceSurfaces");
                                   // ★ 关闭 → SurfaceControl.closeTransaction() → 事务上送
}
RootWindowContainer.java — applySurfaceChangesTransaction（节选）
for (int j = 0; j < count; ++j) {
    final DisplayContent dc = mChildren.get(j);
    dc.applySurfaceChangesTransaction();     // 每个显示器各自结算
}
// 给 DisplayManager 一次机会调整旋转等属性
mWmService.mDisplayManagerInternal.performTraversal(mDisplayTransaction);
// ★ 把本进程攒下的事务合并进"全局事务"，等待统一提交
SurfaceControl.mergeToGlobalTransaction(mDisplayTransaction);
✦ ✦ ✦ 为什么必须"一把事务" ✦ ✦ ✦
想象没有原子提交：100 个窗口的位置、Z 序、可见性一个个单独上送，SurfaceFlinger 每收到一个就可能触发一次合成 → 用户看到画面"跳着变"，闪烁（flicker）。
一笔事务 = 一个版本号：SurfaceFlinger 在下一个 VSYNC 一次性消费全部变更，中间状态永远不上屏。这就是 mergeToGlobalTransaction 的意义。

另外注意 getSyncTransaction()（第六节用到）：当窗口与客户端通过 BLAST 同步 Buffer 时，Z 序变化必须和客户端提交新 Buffer 的节奏锁在一起，否则会出现"新窗口用旧 Z 序"的错位。同步事务保证了这一点。

事务提交后，SystemServer 的活儿就干完了：SurfaceFlinger 拿着每层的 SurfaceControl（位置、Z、可见性）+ 每层的 Buffer（应用画的像素），在 VSYNC 到来时逐层合成——这部分是 SurfaceFlinger 的世界，留作下一篇。

从一个应用窗口的 relayout（比如应用请求改变大小）到屏幕更新

━━ 应用进程 ━━
ViewRootImpl.relayoutWindow()          ← 视图树测量/布局后，请求同步窗口
        ↓ Binder 调用
━━ system_server 进程 ━━
WMS.relayoutWindow(session, client, attrs, ...)      ← Binder 入口（本进程内直接调）
  → windowForClientLocked()             查找 WindowState
  → win.setRequestedSize(w, h)          记录应用想要的新尺寸
  → adjustWindowParamsLw(attrs)         策略层校正参数（类型/尺寸限制）
  → createSurfaceControl(...)           ★ 首次：创建 SurfaceControl（真画布）
  → mWindowPlacerLocked.performSurfacePlacement(true)
        ↓
WindowSurfacePlacer.performSurfacePlacement(force=true)
  → performSurfacePlacementLoop()       （最多 6 轮）
  → mRoot.performSurfacePlacement()
       → updateFocusedWindowLocked()    焦点先定
       → openSurfaceTransaction()
       → applySurfaceChangesTransaction()
            → 每个 DisplayContent：
                 ├─ performLayout()            ★ 第一遍遍历：算 frame（两遍 forAllWindows）
                 ├─ postLayoutPolicy 循环   策略投票，最多 6 轮收敛
                 ├─ assignChildLayers()       ★ Z 序：两遍算法（普通 + Z-boost）
                 ├─ forAllWindows(mApply...) 遮挡检测 / 调光 / 显示状态
                 └─ prepareSurfaces()        动画阶段准备（leash 提交等）
       → closeSurfaceTransaction()      关闭全局事务
       → mergeToGlobalTransaction()     合并
        ↓ VSYNC
━━ SurfaceFlinger 进程 ━━
消费事务：更新每层 Surface 的位置/Z/可见性
→ 逐层合成（Composition） → 屏幕显示新画面
三句话复述全文：
① 变化先标记，由 WindowSurfacePlacer 合并排程（defer + 幂等 + 最多 6 轮）。
② 从根节点 DFS 遍历（forAllWindows，mChildren 尾部=顶层）：第一遍算 frame（layout），第二遍算状态（遮挡/调光），中间穿插 Z 序分配（assignChildLayers 两遍算法）。
③ 全部写进一笔事务，原子提交 SurfaceFlinger，下一个 VSYNC 上屏。
