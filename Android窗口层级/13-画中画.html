视频 App 按下 Home 键缩成右下角的小窗，看起来只是“窗口变小了”。实际发生的事要重得多：system_server 把这个 Activity 从原来的 Task 里摘出来，塞进一个新建或复用的 pinned root task；SystemUI 进程里的 WM Shell 接管一条 SurfaceControl leash，把小窗从全屏矩形缩到目标 bounds；最后再通过一次跨进程的配置变更，把“你已经进入 PiP”这个消息送回 App 主线程。入口和状态机在 ATMS，Task 与窗口模式在 WMCore/WMS，动画与菜单在 WM Shell，API 在 android.app——四层各有 owner。本文按事件流走一遍：Activity.enterPictureInPictureMode() → ActivityClientController → ActivityTaskManagerService → RootWindowContainer → PipTransition / PipTaskOrganizer → onPictureInPictureModeChanged()。读懂这条链，才能解释“API 返回 true 但没变小”“多 Activity 的 App 进 PiP 后下面的页面露出来”“旧 PiP 为什么先消失”这些现场问题。

一、全景与归属：PiP 到底属于谁

先破一个常见误解：PiP 不是 WMS 的一个子模块，也不是 SystemUI 的专属功能。它是 Android 的一种窗口模式，代码横跨四个地方；判断归属不要看“代码跑在哪个进程”，要看状态的所有者是谁。

一句话 WMS 提供容器与窗口模式，ATMS 决定“能不能进”，Shell 负责“怎么动”。把 PiP 说成“SystemUI 的功能”，会漏掉 ATMS 的状态机和 WMCore 的 Task 迁移；说成“WMS 的子模块”，又会漏掉 SystemUI 里的全部动画与菜单。

再拆一层：小窗里的三块东西，归属各不相同。上面表里写着“WM Shell 的进程 = SystemUI”，很容易又被读成“PiP 是 SystemUI 画出来的”。实际小窗里叠着三样东西：

位置是什么归属与锚点
小窗里的画面 app 自己的 task surface，只是被搬进 WINDOWING_MODE_PINNED 的容器继续渲染 —— 不是 SystemUI 截屏后塞进自家窗口 app 进程。所以 dumpsys window 里它仍是一个应用窗口，只多出 windowingMode=pinned
缩放 / 边界 / 动画 / 手势 PipTaskOrganizer 拿到这个 task 的 leash，做 relayout、动画与贴边吸附 WM Shell。它是独立 library（frameworks/base/libs/WindowManager/Shell），只是被编译进 SystemUI APK、跑在 systemui 进程里
关闭 / 全屏那个菜单 一个 TYPE_APPLICATION_OVERLAY + PRIVATE_FLAG_TRUSTED_OVERLAY 的 overlay 窗口，内容由 PipMenuView extends FrameLayout 渲染 WM Shell。窗口参数 PipMenuController.java:99、:102；菜单视图 phone/PipMenuView.java:74；靠 attach(SurfaceControl leash)（PipMenuController.java:48）挂到 PiP 的 leash 上，随小窗一起动

因此“跑在 systemui 进程”≠“SystemUI 的功能”：WMShell.java:106 只是在构造时注入 Optional<Pip>，:167 调 initPip()（定义在 :174）把菜单入口接上，真正干活的是 shell 库里的 Pip 实现。判断归属依旧看状态所有者：task 的 windowingMode 是 WMCore 的状态，leash 与 bounds 是 Shell 的状态，菜单窗口是 Shell 自己 addView 出来的 overlay。

顺手验证进 PiP 后跑 dumpsys window windows | grep -i -A3 windowingmode，能看到那个窗口带 app 包名且 windowingMode=pinned；本工程 FramworkContent 的「进入画中画」按钮就是这条链的最小复现。

public boolean enterPictureInPictureMode(@NonNull PictureInPictureParams params) {
    if (!deviceSupportsPictureInPictureMode()) {
        return false;                       // ① 纯客户端特性位，直接 false
    }
    if (params == null) {
        throw new IllegalArgumentException("Expected non-null picture-in-picture params");
    }
    if (!mCanEnterPictureInPicture) {
        throw new IllegalStateException("Activity must be resumed to enter"
                + " picture-in-picture");   // ② 实际只拦"已经 stop"之后的调用
    }
    // ③ 先置 true：保证紧接着的 onPause 里 isInPictureInPictureMode() 已是 true
    mIsInPictureInPictureMode = ActivityClient.getInstance().enterPictureInPictureMode(
            mToken, params);
    return mIsInPictureInPictureMode;       // 这是"受理结果"，不是动画完成
}

        return getActivityClientController().enterPictureInPictureMode(token, params);
    } catch (RemoteException e) {
        throw e.rethrowFromSystemServer();  // binder 死亡直接抛，调用方看到 RuntimeException
    }
}

这段在干什么：进入时是 App 主线程、Activity 还处于 resumed（或至少未 stop）；出去时只是“请求已发出”，UI 还没变。mIsInPictureInPictureMode 被立即写成 binder 的返回值，是为了让紧接着的 onPause() 里 isInPictureInPictureMode() 已经是 true——这是 Android 官方 PiP 指南要求的行为，不是实现随手写的。

设计意图：mCanEnterPictureInPicture 在 performCreate / performRestart / performNewIntent 置 true（Activity.java:8041、8066、8123），在 performStop 才置 false（Activity.java:8263）。所以客户端这个检查实际拦的是“已经 stop 之后”的调用，异常文案里的 “must be resumed” 是历史措辞；真正的 resumed 要求由服务端 checkEnterPictureInPictureState() 判定。

实战现象：调用后立刻返回 false，UI 没反应。因果：客户端只负责特性位；false 可能来自这里，也可能来自 server 的状态门禁。怎么查：先在调用点看 deviceSupportsPictureInPictureMode() 与 mCanEnterPictureInPicture，再看 logcat 里 ActivityTaskManagerService 是否打印拒绝原因；用 adb shell dumpsys activity activities | grep -i pinned 确认当前是否已有 PiP。

// ActivityClientController.java:661-672
public boolean enterPictureInPictureMode(IBinder token, final PictureInPictureParams params) {
    final long origId = Binder.clearCallingIdentity();  // 后续内部调用不记在 App 的 uid 上
    try {
        synchronized (mGlobalLock) {                    // ATMS 全局锁，不是 WMS 的 mWindowMap
            final ActivityRecord r = ensureValidPictureInPictureActivityParams(
                    "enterPictureInPictureMode", token, params);
            return mService.enterPictureInPictureMode(r, params);
        }
    } finally {
        Binder.restoreCallingIdentity(origId);
    }
}
// ActivityClientController.java:717-748
private ActivityRecord ensureValidPictureInPictureActivityParams(String caller,
        IBinder token, PictureInPictureParams params) {
    if (!mService.mSupportsPictureInPicture) {
        throw new IllegalStateException(caller + ": Device doesn't support ...");
    }
    final ActivityRecord r = ActivityRecord.forTokenLocked(token);  // token → AR
    if (r == null) {
        throw new IllegalStateException(caller + ": Can't find activity for token=" + token);
    }
    if (!r.supportsPictureInPicture()) {
        throw new IllegalStateException(caller + ": Current activity does not support ...");
    }
    if (params.hasSetAspectRatio()
            && !mService.mWindowManager.isValidPictureInPictureAspectRatio(
            r.mDisplayContent, params.getAspectRatio())) {
        // … 省略：读 config_pictureInPictureMin/MaxAspectRatio 并抛 IllegalArgumentException
    }
    params.truncateActions(ActivityTaskManager.getMaxNumPictureInPictureActions(mContext));
    return r;
}

这段在干什么：进入时是 binder 线程、手里只有 IBinder token 和一个 PictureInPictureParams；出去时拿到了活的 ActivityRecord r，并且参数已经过一轮“会抛异常”的硬校验。ActivityRecord.forTokenLocked(token) 是 token 到对象的唯一入口；token 失效（Activity 已 finish）时这里直接抛，不会走到 ATMS。

设计意图：Binder.clearCallingIdentity() 不是绕过权限，而是让后续内部调用（WMS 的宽高比检查、Task 操作）以 system 身份执行，不把调用 App 的 uid 带进系统内部。校验分两类：参数/对象非法 → 抛异常（设备不支持、token 找不到、Activity 不支持 PiP、宽高比越界）；运行态不允许 → 返回 false（下一跳 ATMS 的状态机）。这两个语义在排障时必须分开看。

实战现象：崩溃栈里出现 IllegalArgumentException: Aspect ratio is too extreme。因果：App 设了超出 config_pictureInPictureMin/MaxAspectRatio 的比例，在 ACC 就被拒。怎么查：看 PictureInPictureParams.Builder.setAspectRatio() 的入参，对照 frameworks/base/core/res/res/values/config.xml 里的两个 dimen；把比例改到区间内再复现。

块C｜第 3 跳：ATMS 的状态门禁与“搬家 Runnable”

ActivityTaskManagerService.java:3365-3405 ｜ ActivityRecord.java:2663-2710

// ActivityTaskManagerService.java:3365-3405
boolean enterPictureInPictureMode(@NonNull ActivityRecord r, PictureInPictureParams params) {
    if (r.inPinnedWindowingMode()) {
        return true;                                    // 幂等：已经是 PiP 直接成功
    }
    if (!r.checkEnterPictureInPictureState("enterPictureInPictureMode",
            false /* beforeStopping */)) {
        return false;                                   // 状态门禁不允许
    }

    final Runnable enterPipRunnable = () -> {
        synchronized (mGlobalLock) {
            if (r.getParent() == null) {                // 等待期间被销毁
                Slog.e(TAG, "Skip enterPictureInPictureMode, destroyed " + r);
                return;
            }
            r.setPictureInPictureParams(params);       // 参数先落到 ActivityRecord
            final float aspectRatio = r.pictureInPictureArgs.getAspectRatio();
            final List<RemoteAction> actions = r.pictureInPictureArgs.getActions();
            mRootWindowContainer.moveActivityToPinnedRootTask(
                    r, "enterPictureInPictureMode");   // 真正的 Task 搬家
            final Task rootTask = r.getRootTask();
            rootTask.setPictureInPictureAspectRatio(aspectRatio);
            rootTask.setPictureInPictureActions(actions);  // 参数再落到 Task
        }
    };

    if (isKeyguardLocked()) {
        // 锁屏：先请求解锁，成功后在回调里 post；不是同步等
        mActivityClientController.dismissKeyguard(r.appToken, new KeyguardDismissCallback() {
            @Override
            public void onDismissSucceeded() {
                mH.post(enterPipRunnable);
            }
        }, null /* message */);
    } else {
        enterPipRunnable.run();                        // 未锁屏：当前线程直接搬
    }
    return true;                                       // 注意：这里只代表"已受理"
}
// ActivityRecord.java:2663-2710
boolean checkEnterPictureInPictureState(String caller, boolean beforeStopping) {
    if (!supportsPictureInPicture()) return false;
    if (!checkEnterPictureInPictureAppOpsState()) return false;   // AppOps
    if (mAtmService.shouldDisableNonVrUiLocked()) return false;   // VR 模式

    boolean isKeyguardLocked = mAtmService.isKeyguardLocked();
    boolean isCurrentAppLocked =
            mAtmService.getLockTaskModeState() != LOCK_TASK_MODE_NONE;
    final TaskDisplayArea taskDisplayArea = getDisplayArea();
    boolean hasRootPinnedTask = taskDisplayArea != null && taskDisplayArea.hasPinnedTask();
    boolean isNotLockedOrOnKeyguard = !isKeyguardLocked && !isCurrentAppLocked;

    if (beforeStopping && hasRootPinnedTask) {
        return false;                                  // 已有 PiP，不允许自动再进
    }

    switch (mState) {
        case RESUMED:
            return !isCurrentAppLocked
                    && (supportsEnterPipOnTaskSwitch || !beforeStopping);
        case PAUSING:
        case PAUSED:
            return isNotLockedOrOnKeyguard && !hasRootPinnedTask
                    && supportsEnterPipOnTaskSwitch;
        case STOPPING:
            if (supportsEnterPipOnTaskSwitch) {
                return isNotLockedOrOnKeyguard && !hasRootPinnedTask;
            }
        default:
            return false;
    }
}

这段在干什么：进入时是已校验的 ActivityRecord；出去时要么直接返回 false（状态不允许），要么执行 enterPipRunnable：把参数落到 ActivityRecord / Task，调用 RWC 搬家。锁屏是一个异步分叉：先 dismissKeyguard()，解锁成功后在回调里 mH.post(enterPipRunnable)；不锁屏则当前线程直接跑。

设计意图：状态门禁放在 ActivityRecord 而不是 ATMS，是因为它需要读 Activity 自己的状态（mState、AppOps、是否 supportsEnterPipOnTaskSwitch）。beforeStopping 参数是给“自动进入 PiP”用的：Activity 即将 stop 时，如果已经有别的 PiP，就不允许再进；PAUSING/PAUSED 还要求 supportsEnterPipOnTaskSwitch 为 true——这个标志在启动/恢复路径里被置上，表示“这个 Activity 允许在切后台时缩成小窗”。

实战现象：enterPictureInPictureMode() 返回 false，但 App 明明是 resumed。因果：常见是 AppOps 被拒、LockTask（车载/教育模式）、Keyguard 遮挡，或当前已经有 root pinned task。怎么查：adb shell dumpsys activity activities | grep -i -E "pinned|mWindowingMode"；adb shell dumpsys package <包名> | grep -i picture 看 AppOps；再看 adb shell dumpsys activity | grep -i locktask。

// RootWindowContainer.java:2105-2150
void moveActivityToPinnedRootTask(ActivityRecord r, String reason) {
    mService.deferWindowLayout();                       // 先冻住布局，避免半成品上屏
    final TaskDisplayArea taskDisplayArea = r.getDisplayArea();
    try {
        final Task task = r.getTask();
        final Task rootPinnedTask = taskDisplayArea.getRootPinnedTask();
        if (rootPinnedTask != null) {
            rootPinnedTask.dismissPip();                // 同时只允许一个 PiP：旧 PiP 先退出
        }

        // 抑制这次可见性变化的常规转场；真正的窗口模式变化交给下面的 TRANSIT_CHANGE
        r.getDisplayContent().prepareAppTransition(TRANSIT_NONE);

        final boolean singleActivity = task.getChildCount() == 1;
        final Task rootTask;
        if (singleActivity) {
            rootTask = task;                            // 单 Activity：整个 Task 变 PiP
        } else {
            rootTask = new Task.Builder(mService)       // 多 Activity：新建 Task 只装栈顶
                    .setActivityType(r.getActivityType())
                    .setOnTop(true)
                    .setActivityInfo(r.info)
                    .setParent(taskDisplayArea)
                    .setIntent(r.intent)
                    .setDeferTaskAppear(true)
                    .setHasBeenVisible(true)
                    .build();
            r.setLastParentBeforePip();                 // 记录"回来的路"
            rootTask.setLastNonFullscreenBounds(task.mLastNonFullscreenBounds);
            rootTask.setBounds(task.getBounds());
            r.reparent(rootTask, MAX_VALUE, reason);    // 栈顶 Activity 摘出去
            // … 省略：迁移 recents 动画事务、补 TO_BACK 转场（与 PiP 主路径无关）
        }

        // 中间窗口模式要在 reparent 之前取，否则 ActivityRecord 会被设成 fullscreen
        final int intermediateWindowingMode = rootTask.getWindowingMode();
        if (rootTask.getParent() != taskDisplayArea) {
            // pinned task 必须是 DisplayArea 的直接子节点
            rootTask.reparent(taskDisplayArea, true /* onTop */);
        }
// RootWindowContainer.java:2188-2214
        // 把 Task 的窗口模式变化交给 Shell 的 Transitions（12 上没有 TRANSIT_PIP）
        mService.getTransitionController().requestTransitionIfNeeded(TRANSIT_CHANGE, rootTask);

        r.setWindowingMode(intermediateWindowingMode);  // AR 先保持原模式，动画期间不重排
        r.mWaitForEnteringPinnedMode = true;            // 布局冻结闸门（DisplayPolicy 会跳过）
        rootTask.setWindowingMode(WINDOWING_MODE_PINNED); // Task 真正变 pinned
        rootTask.setDeferTaskAppear(false);
        r.supportsEnterPipOnTaskSwitch = false;         // 进来后不再允许"pause 时自动进"
    } finally {
        mService.continueWindowLayout();
    }

    ensureActivitiesVisible(null, 0, false /* preserveWindows */);
    resumeFocusedTasksTopActivities();
    notifyActivityPipModeChanged(r.getTask(), r);       // 通知 AM/监听者
}

这段在干什么：进入时 Activity 还挂在原 Task 上；出去时它已经在（新建或复用的）pinned root task 里，Task 的 windowingMode 已变成 WINDOWING_MODE_PINNED，但 ActivityRecord 自己还保留“中间窗口模式”，等待配置下传。整个过程被 deferWindowLayout() / continueWindowLayout() 包住，避免半成品结构被布局线程看到。

设计意图：

  • 为什么必须是 Task 级：windowingMode 是 WindowContainer 的属性，PiP 是“一个 Task 进入小窗”，不是“某个 Window 变小”。单 Activity 的 Task 可以直接复用；多 Activity 的 Task 不能整栈变 PiP，只能新建一个 Task 把栈顶 Activity reparent 过去，原 Task 留在原地继续显示下面的页面。
  • 为什么先 dismissPip()：系统同时只允许一个 root pinned task。旧 PiP 不退出，新 PiP 就没有位置；dismissPip() 会把旧 Task 的窗口模式恢复为 undefined，并调度旧 Activity 的 PiP 回调（wm/Task.java:7507）。
  • 为什么 prepareAppTransition(TRANSIT_NONE) + requestTransitionIfNeeded(TRANSIT_CHANGE)：前者抑制“这次可见性变化”走常规转场，后者把 Task 的窗口模式变化交给 Shell 的 Transitions 处理。AOSP 12 没有专门的 TRANSIT_PIP，PiP 进入被包装成 TRANSIT_CHANGE；13 才引入独立的 TRANSIT_PIP 和 fromClient 归属判断。
  • 为什么 r.setWindowingMode(intermediateWindowingMode)：让 ActivityRecord 在动画期间仍按原模式布局；真正切 pinned 的是 rootTask。随后 mWaitForEnteringPinnedMode = true，DisplayPolicy.layoutWindowLw() 会直接跳过这个窗口的布局（DisplayPolicy.java:1561-1574），避免客户端在动画中按新尺寸重排、闪一下。

实战现象：多 Activity 的 App 进 PiP 后，下面的页面突然露出来，或者返回时回到了错误的页面。因果：多 Activity 分支新建了 Task 并 reparent 栈顶，原 Task 的剩余 Activity 会被 ensureActivitiesVisible() 重新计算可见性。怎么查：adb shell dumpsys activity activities 看两个 Task 的 Activity 列表与 lastParentBeforePip；返回路径看 Task#dismissPip() 与 lastNonFullscreenBounds 的恢复。

        @PipAnimationController.TransitionDirection int direction,

这段在干什么：进入时 Task 已经出现在 Shell 的 TaskOrganizer 里；onTaskAppeared() 把 RunningTaskInfo、leash、PictureInPictureParams 保存下来，状态置为 TASK_APPEARED，并打点 PICTURE_IN_PICTURE_ENTER。动画结束时，prepareFinishResizeTransaction() 生成一个 WCT：把 Activity 的窗口模式重置为 undefined，把 Task bounds 设为最终小窗 bounds，并通过 setBoundsChangeTransaction() 让 Surface 事务与 bounds 变更同步。

设计意图：“动画”和“最终布局”是两件事。动画期间 WMS 不改 Task bounds（否则会触发客户端重排），只让 Shell 改 leash 的 matrix/crop/alpha；动画结束时才用 WCT 一次性把 Task 落到目标 bounds，并触发真正的 relayout。这样客户端只会在动画结束后收到一次尺寸变化，不会每帧都重排。

一处容易读错的细节： prepareFinishResizeTransaction() 里还调了 wct.scheduleFinishEnterPip()，写进 mPinnedBounds 并置 CHANGE_PIP_CALLBACK（WindowContainerTransaction.java:116-124、 :459、:473）。但在 AOSP 12 的 frameworks/base 里， 这个字段只有定义和 getter，没有读取者 （getPinnedBounds() 全树零调用，见 WindowContainerTransaction.java:601） ——它是一条预留管道，不是 PiP 回调的触发点。 真正的回调在下一节：windowingMode 变化沿配置下传到 Activity 进程。 读到这里不要因为看到 PiP-Callback 字样就以为 WMS 内部有个消费者在派发。

实战现象：PiP 小窗已经出现，但里面的内容还是全屏尺寸，或者黑边。因果：finish WCT 没应用/被取消，Task bounds 没落下去；或 mWaitForEnteringPinnedMode 没清，窗口一直跳过布局。怎么查：adb shell dumpsys window windows | grep -i pip 看 PiP 窗口 frame 与 Task bounds；断点打在 PipTransition#onFinishResize()（PipTransition.java:93）和 ActivityRecord 清 mWaitForEnteringPinnedMode 的那一行。

private void handleWindowingModeChangeIfNeeded(Activity activity,
        Configuration newConfiguration) {
    final int newWindowingMode = newConfiguration.windowConfiguration.getWindowingMode();
    final IBinder token = activity.getActivityToken();
    final int oldWindowingMode = mLastReportedWindowingMode.getOrDefault(
            token, WINDOWING_MODE_UNDEFINED);
    if (oldWindowingMode == newWindowingMode) return;

    // PiP callback is sent before the MW one.
    if (newWindowingMode == WINDOWING_MODE_PINNED) {
        activity.dispatchPictureInPictureModeChanged(true, newConfiguration);
    } else if (oldWindowingMode == WINDOWING_MODE_PINNED) {
        activity.dispatchPictureInPictureModeChanged(false, newConfiguration);
    }

    final boolean wasInMultiWindowMode = WindowConfiguration.inMultiWindowMode(oldWindowingMode);
    final boolean nowInMultiWindowMode = WindowConfiguration.inMultiWindowMode(newWindowingMode);
    if (wasInMultiWindowMode != nowInMultiWindowMode) {
        activity.dispatchMultiWindowModeChanged(nowInMultiWindowMode, newConfiguration);
    }
    mLastReportedWindowingMode.put(token, newWindowingMode);
}
// Activity.java:8340-8352
final void dispatchPictureInPictureModeChanged(boolean isInPictureInPictureMode,
        Configuration newConfig) {
    mFragments.dispatchPictureInPictureModeChanged(isInPictureInPictureMode, newConfig);
    if (mWindow != null) {
        mWindow.onPictureInPictureModeChanged(isInPictureInPictureMode);
    }
    mIsInPictureInPictureMode = isInPictureInPictureMode;  // 这里才与系统真值对齐

这段在干什么：进入时 App 主线程收到新的 Configuration；handleWindowingModeChangeIfNeeded() 用 mLastReportedWindowingMode 里的旧值和 newConfiguration 里的新值比较：新值是 pinned → 派发 dispatchPictureInPictureModeChanged(true)；旧值是 pinned、新值不是 → 派发 false。随后才处理 multi-window 回调，注释明确写着 “PiP callback is sent before the MW one”。

设计意图：回调不是 binder 直接返回的，而是配置变更链路的产物。这样框架只需要在窗口模式真正变化时发一次信号，客户端无论因为配置重建还是自己处理 configChanges，都能在同一条路径上收到。Activity.dispatchPictureInPictureModeChanged() 最后把 mIsInPictureInPictureMode 覆盖成系统真值——这也是为什么 API 返回 true 之后，回调仍可能因为转场取消而永远不来。

实战现象：enterPictureInPictureMode() 返回 true，但 onPictureInPictureModeChanged(true) 一直没来。因果：Activity 在等待期间被销毁（r.getParent() == null）、转场被取消，或进程未 attached（addToPipModeChangedList() 直接跳过）。怎么查：看 adb shell dumpsys activity activities 里该 Activity 是否还在、Task 是否 pinned；logcat 过滤 PipTaskOrganizer 与 ActivityTaskManager；在 updatePictureInPictureMode() 入口打断点确认是否被调用。

七、稳态闭环与退出

一次完整的进入结束后，系统停在一个明确的稳态：一个 root pinned task 存在，里面的 Activity 处于 paused/stopped 之一，Task 的 windowingMode 是 pinned，ActivityRecord 的 mWaitForEnteringPinnedMode 已清，客户端已收到 true 回调。此时再调用 enterPictureInPictureMode() 会在 ATMS 第一行 r.inPinnedWindowingMode() 直接返回 true（幂等）。

状态Task windowingModeActivityRecord客户端
普通全屏fullscreen / undefinedRESUMED/PAUSEDisInPictureInPictureMode() == false
进入中（动画）pinned中间模式 + mWaitForEnteringPinnedMode=trueAPI 已返回 true，回调未到
稳态 PiPpinnedpaused/stopped，flag 已清已收到 true 回调

退出路径不是进入的简单逆运算，但结构对称：用户点关闭/返回、拖到边缘删除、或 App 主动退出时，最终会走到 Task#dismissPip()（wm/Task.java:7507）：在 inSurfaceTransaction 里把窗口模式设回 WINDOWING_MODE_UNDEFINED，把 Task 重新放到顶部，并调用 scheduleUpdatePictureInPictureModeIfNeeded(task, this)。客户端随后收到旧窗口模式与 pinned 不同的配置，handleWindowingModeChangeIfNeeded() 派发 false 回调；如果有 freeform 历史，lastNonFullscreenBounds 会用于恢复。

闭环 进入是“摘 Activity → 建/复用 pinned Task → 播 leash 动画 → 下发 config”；退出是“恢复 Task 模式 → 重新定位 → 下发 config”。两者共用同一条 ActivityRecord.updatePictureInPictureMode() 回调路径，所以 PiP 的状态真值永远在 system_server，客户端只是跟着配置变更走。

🧠 自测：3 个问题

1. 为什么 enterPictureInPictureMode() 返回 true 之后，UI 还可能完全没变化？
因为返回值只代表请求被 ACC/ATMS 受理（Activity.java:2912 立即写入 mIsInPictureInPictureMode），真正的结构变化在 enterPipRunnable 里，动画在 Shell 里，客户端回调要等配置下发。锁屏分支还会先等解锁回调；转场取消时回调可能永远不来。判断是否真的进入，要看 dumpsys activity activities 的 mWindowingMode=pinned 和 onPictureInPictureModeChanged(true)。
2. 多 Activity 的 Task 进 PiP，为什么必须新建 Task 并把栈顶 Activity reparent 过去？
因为 windowingMode 是 Task 级属性。整栈变 pinned 会把下面的页面一起塞进小窗；只有把栈顶 Activity 摘到新的 pinned Task，原 Task 才能继续显示剩余页面。代价是返回路径要处理 lastParentBeforePip 和原 Task 的可见性重算，相关逻辑在 RootWindowContainer.java:2105 的多 Activity 分支与 ActivityRecord.onParentChanged()。
3. PiP 的“进入/退出”回调为什么走配置变更，而不是 binder 直接回调？
因为窗口模式变化本身就是一次配置变化，ActivityThread 已经有现成的 handleWindowingModeChangeIfNeeded() 可以比较新旧模式；走同一条路能保证配置重建、configChanges 自处理等所有情况行为一致。system_server 侧则用 ActivityTaskSupervisor 的 handler 把回调推迟到锁外、配置算完之后，避免持锁跨进程和顺序错乱。
