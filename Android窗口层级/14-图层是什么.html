Trace 里的“图层”，
到底是什么东西？

Winscope 的 SurfaceFlinger trace 里每个图层都有名字和编号。它们不是 UI 控件，也不是 WMS 的 WindowState——而是 SurfaceFlinger 进程里真实存在的 C++ Layer 对象。下面把四个问题一次讲清：是什么、叫什么、编号哪来的、层级树怎么变成图层。

01先给结论

四个问题，四句话。后面的源码和实验都在证明这四句。

图层是什么
SurfaceFlinger 里的一个 Layer 对象：一块可被合成的内容 + 一棵子树 + 一个 Z 值。trace 里是它的序列化快照 LayerProto。
有名字吗
有。LayerProto.name 就是创建 SurfaceControl 时传的名字。WMS 用容器名，WindowState 是 十六进制hash + 窗口标题，重名自动加 #n。
编号哪来的
Layer::sequence，进程内原子自增，从 1 开始。跟 Z、数组下标、WMS hash 都无关；删除不回收，SF 重启才重置。
树能变成图层吗
不是“转换”，是投影：WMS 树在创建 SurfaceControl 时就在 SF 里长出了对应的 Layer 树；trace 只是把这棵树拍下来。
一句话串起来：你在屏幕上看到的每一层，在 WMS 里是一个 WindowContainer，在 SF 里就是一个 Layer；SurfaceControl 是这两棵树之间的“联结点/遥控器”。Winscope 的 SF trace 不读 WMS，它直接 dump SF 自己的那棵树。

先把三个“id”分开

你看到的出处含义会不会重用
LayerProto.id / Winscope 的 id 列Layer::sequenceSF 进程内图层创建序号，从 1 开始不重用；SF 重启归零
LayerProto.zWMS assignChildLayers → setLayer同一父节点下的绘制顺序，越大越靠上每帧/每次 relayout 都可能重排
WMS 里的 System.identityHashCodeWindowState.getName()只用于调试命名，出现在名字前缀里Java 对象回收后可能被复用

02逐条对应源码

2.1 trace 里的一个 layer，就是 LayerProto

Winscope 的 SurfaceFlinger trace 文件是 LayersTraceFileProto，里面按时间戳存了很多帧，每帧一份 LayersProto；LayersProto.layers 的每一项就是 LayerProto。

frameworks/native/services/surfaceflinger/layerproto/layerstrace.protoL27–L50
message LayersTraceFileProto {
  // 一次 trace 里的所有快照
  repeated LayersTraceProto entry = 2;
}
message LayersTraceProto {
  // 时间戳、HWC 信息……
  optional LayersProto layers = 3;   // ★ 这一帧的整棵图层树
}
frameworks/native/services/surfaceflinger/layerproto/layers.protoL30–L46
message LayerProto {
  int32  id = 1;          // unique id per layer ← Layer::sequence
  string name = 2;        // unique name per layer ← SurfaceControl 名
  repeated int32 children = 3;  // 子图层 id 列表（树结构）
  repeated int32 relatives = 4; // Z 相对图层
  uint32 layer_stack = 9;       // 属于哪个 display 的 layer stack
  int32  z = 10;                // 同一父节点下的 Z 序
  int32  parent = 25;           // 父图层 id（根为 0 / 空）
  int32  z_order_relative_of = 26;
}

注意 proto 里同时有 parent 和 children：父子关系被冗余存了两份，Winscope 还原树时用哪个都行，这也是为什么你在面板里点一个节点能立刻展开它的子树。

为什么 trace 里 id 经常不是连续的？因为号是“创建即领取”，已经销毁的图层不会把号还回来。你看到 1、2、7、8，说明中间 3–6 已被销毁；下次再抓还是这几个号，除非 SF 重启。id 永远不要拿来当数组下标用。

2.4 层级树怎么“长”成图层：assignChildLayers 两遍

WMS 每次遍历窗口树时，会给每个父容器的子节点重新分配 Z。这里的“子节点”就是子 WindowContainer，每个容器都有自己的 SurfaceControl，因此也都有自己的 Layer。核心是两遍循环：

frameworks/base/services/core/java/com/android/server/wm/WindowContainer.javaL2290–L2307
void assignChildLayers(Transaction t) {
    int layer = 0;
    // 第一遍：普通子节点先占 Z，并递归处理整棵子树
    for (int j = 0; j < mChildren.size(); ++j) {
        final WindowContainer wc = mChildren.get(j);
        wc.assignChildLayers(t);            // ★ 先下后上（后序）
        if (!wc.needsZBoost()) {
            wc.assignLayer(t, layer++);       // Z = 0,1,2…
        }
    }
    // 第二遍：需要 Z-boost 的子节点统一提到最后
    for (int j = 0; j < mChildren.size(); ++j) {
        final WindowContainer wc = mChildren.get(j);
        if (wc.needsZBoost()) {
            wc.assignLayer(t, layer++);
        }
    }
}
frameworks/base/services/core/java/com/android/server/wm/WindowContainer.javaL2240–L2249
void assignLayer(Transaction t, int layer) {
    ...
    if (mSurfaceControl != null && changed) {
        setLayer(t, layer);        // ★ 最终落到 SurfaceControl.Transaction.setLayer
        mLastLayer = layer;
    }
}
关键：WMS 分配的是“同一个父容器下”的 Z，不是全局 Z。SF 合成时按树做深度优先遍历，父节点和它的子树整体处在某个位置——所以 LayerProto.z 只在兄弟之间有意义，别拿两个不同父节点的 z 直接比大小。

2.5 trace 是怎么把这棵树拍下来的

frameworks/native/services/surfaceflinger/SurfaceFlinger.cppL4949–L4956
LayersProto SurfaceFlinger::dumpDrawingStateProto(uint32_t traceFlags) const {
    const auto display = ON_MAIN_THREAD(getDefaultDisplayDeviceLocked());
    LayersProto layersProto;
    for (const sp<Layer>& layer : mDrawingState.layersSortedByZ) {
        layer->writeToProto(layersProto, traceFlags, display.get());
    }
    return layersProto;
}
frameworks/native/services/surfaceflinger/Layer.cppL2011–L2027
LayerProto* Layer::writeToProto(LayersProto& layersProto, ...) {
    LayerProto* layerProto = layersProto.add_layers();  // 先写自己
    writeToProtoDrawingState(layerProto, ...);
    writeToProtoCommonState(layerProto, ...);

    for (const sp<Layer>& layer : mDrawingChildren) {
        layer->writeToProto(layersProto, traceFlags, display);  // ★ 再递归子树
    }
    return layerProto;
}

于是 trace 里 layers[] 的数组顺序是“先序 DFS”：父在前、子在后；树结构本身靠 parent / children 字段还原。Winscope 读的就是这份数据，跟 WMS 没有直接关系——这也是为什么有时你在 Winscope 里看到的树比 recent tasks 里的层级“多几层”或“少几层”。

03Winscope 面板怎么读

打开 SurfaceFlinger trace 后，左侧是图层树，右侧是选中图层的属性。把面板字段和 proto 对上，就不会再觉得它神秘：

面板里看到对应 proto怎么理解
树节点的 #123 / id 列LayerProto.idLayer 的 creation sequence，稳定主键
节点文字LayerProto.nameSurfaceControl 名，末尾带 #n 去重后缀
缩进关系parent / childrenSF 自己的 Layer 树，不一定等于 View 树
Z / layer stackz / layer_stack兄弟间顺序 + 属于哪个显示设备
时间轴拖动LayersTraceFileProto.entry[]每帧一份快照；id 不变，z/children 可能变
Bounds / crop / transformbounds / crop / transform图层在合成时的几何信息
最快的判断方法：先看名字判断“这是谁”（Display / Task / Window / SurfaceView / StatusBar），再看 id 跟踪“还是不是同一个图层”，最后看 z 和 children 判断“这一帧它被放到了哪”。名字用于识别，id 用于追踪，z 用于排序——三者不要混用。

第 ① 步发生了什么
WMS 为每个 WindowContainer 调用 makeSurface() → SurfaceControl.Builder.build()；SF 侧执行 createLayer()，构造 Layer 时领取 sequence，并把父子关系写进 mDrawingChildren。名字在这里定型。
第 ② 步发生了什么
每个父容器对子节点跑两遍 assignChildLayers：普通节点按顺序拿 0,1,2…，needsZBoost() 的节点跳过第一遍、在第二遍补到末尾。事务提交后，SF 的 z 才更新。
第 ③ 步发生了什么
SF 从 mDrawingState.layersSortedByZ 的根开始，对每棵子树做 writeToProto 先序递归，得到 LayersProto.layers[]。数组顺序 ≠ 合成顺序，树靠 parent/children 还原。
为什么 id 不从 0 开始
Layer::sSequence{1}。0 留给 proto 里“没有父节点”的默认值，因此根图层的 parent 字段读出来是 0，而它自己的 id 是 1。

05四个高频误解

误解一：id 就是 Z，或者就是列表下标。
id 来自 Layer::sequence，只在“创建”时领一次；Z 来自 WMS 的 assignChildLayers，随时可能重排。trace 里 layers[] 的顺序是先序 DFS，和 id 大小没有必然关系。用 id 认身份，用 z 排顺序。
误解二：名字是唯一的，可以直接当主键。
SF 的 getUniqueLayerName 会给重名追加 #1、#2，所以同一时刻名字确实唯一；但名字会随窗口标题/重建变化，跨快照追踪并不可靠。跨帧追踪请用 id。
误解三：WMS 树和 SF 树一定一一对应。
大体对应，但 SF 侧还会出现 WMS 树里没有的图层：动画用的 leash、dimmer、屏幕旋转截图、offscreen 合成层等；反过来，尚未 attach 或没有 SurfaceControl 的容器也不会出现。Winscope 的 SF trace 是 SF 视角的真相，不是 WMS 树的镜像。
误解四：trace 里看到的层级就是 View 树。
View 树在应用进程里，通过 BufferQueue/BLAST 把 buffer 交给一个 SurfaceView 或窗口图层；SF 只认识 Layer。一个 Window 内部的 View 层级不会出现在 SF trace 里，除非它们各自拥有 Surface（如多个 SurfaceView）。
