一、全景：一次触摸的三段旅程

前四篇我们把“树的静态结构”和“树怎么变成像素”讲完了。这一篇回答一个新问题：你手指在屏幕上点一下，系统怎么知道该把这个事件发给哪个窗口？

答案藏在一条跨越三个进程的链路上：内核 → InputReader（system_server 的 InputReader 线程）→ InputDispatcher（同一进程的 InputDispatcher 线程）→ 通过每个窗口专属的管道 InputChannel → App 进程 → ViewRootImpl 派发给 View。而“发给哪个窗口”这个判断，正是建立在窗口树 + 焦点 + 触摸区域之上的。

手指 / 触控芯片→ 内核 evdev→ EventHub→ InputReader→ InputDispatcher
命中测试→ InputChannel→ InputEventReceiver→ ViewRootImpl

把这条链路按“进程”和“谁提供数据”拆开，就是下面这张时间轴。请先记住三个关键角色：WMS（持锁时把窗口的可输入信息快照给输入系统）、InputReader（读设备）、InputDispatcher（做命中测试并分发）。

阶段所在进程 / 线程做什么关键入口（本树已核实）
① 建管道system_server（WMS）每个窗口创建一对 InputChannel，一端留给自己，一端交给 AppWMS.addWindow() :1687 → WindowState.openInputChannel() :2689
② 交底system_server（持 WMS 锁）把“哪些窗口能收事件、区域在哪、能不能聚焦”快照给 InputDispatcherInputMonitor.updateInputWindowsLw() :338 → populateInputWindowHandle() :270
③ 读设备InputReader 线程从 EventHub 取原始 evdev 事件，加工成规范化 MotionEvent / KeyEventInputReader.cpp :108 mEventHub->getEvents()
④ 命中InputDispatcher 线程按窗口表做命中测试，找出目标窗口（或找不到 → ANR）dispatchOnceInnerLocked() :683 → findTouchedWindowTargetsLocked() :1900
⑤ 分发InputDispatcher → App经 InputChannel（socketpair）把事件发给 AppApp：InputEventReceiver → ViewRootImpl.deliverInputEvent() :8520

一句话模型 窗口树决定“有谁是候选”，焦点 / 触摸区域 / 图层遮挡决定“这次事件归谁”。前者在 WMS，后者在 InputDispatcher。二者通过 ② 的“交底”解耦——这也解释了为什么输入系统看到的窗口状态总可能“略旧一点”。

二、接上“电话线”：InputChannel 的建立

一个窗口要被输入系统找到并投递事件，前提是它有一条自己的管道——InputChannel。它不是普通对象，其内部是一对 socketpair（双向管道）：一端归 system_server 的 InputDispatcher，另一端随 Binder 交给 App。

管道在 addWindow 阶段就建好了（还记得 02 篇吗？addWindow 只造逻辑节点、不造 Surface，但会造 InputChannel）。

native 侧建通道：NativeInputManager::createInputChannel()（com_android_server_input_InputManagerService.cpp:511）向 InputDispatcher 申请一个连接（Connection），返回 socket fd。
一端交给 App：addWindow 返回时，App 通过 Binder 拿到那个 fd，包装成 InputChannel，由 ViewRootImpl 创建 InputEventReceiver（InputEventReceiver.java:38）挂在 App 自己的 Looper 上等事件。

🐛 实践含义 没有 InputChannel 的窗口（INPUT_FEATURE_NO_INPUT_CHANNEL，如部分纯装饰窗口）永远收不到输入事件——这也是为什么有的“看得见但点不动”的层不是 bug，而是设计如此。WindowState.java:1932 的 mInputChannel != null && mInputWindowHandle != null 是判断“这个窗口在输入层面是否活着”的条件之一。

三、交底：WMS 把可输入窗口表交给 InputDispatcher

InputDispatcher 不在 WMS 线程里，也不持 WMS 锁。它要判断“点下去该给谁”，就必须拿到一份窗口的“可输入画像”。这份画像由 InputMonitor（InputMonitor.java:72）在持 WMS 锁时生成，然后交给 native。

画像的载体是 InputWindowHandle（android.view.InputWindowHandle，InputWindowHandle.java:33）。每个 WindowState 从出生就带着一个包装：mInputWindowHandle（WindowState.java:606），构造在 :1065 new InputWindowHandleWrapper(new InputWindowHandle(...))，随后逐字段填充 name / 包名 / type / owner uid……

触发时机：任何影响输入的变化（窗口增删、焦点变、布局变、可见性变）都会标记 input windows 需要更新；在遍历收尾阶段（03 篇的 performSurfacePlacement）统一刷一次，避免频繁跨进程。
入口：InputMonitor.updateInputWindowsLw(force)（:338）→ 内部 updateInputWindows(inDrag)（:490）→ 逐窗口 populateInputWindowHandle(handle, w)（:582 / 公共版 :270）。
填什么：populateInputWindowHandle（:270）把窗口的输入属性拷进 handle：touchable region（可点区域）、focusable、可见性、图层 Z（用于遮挡判断）、displayId、owner pid/uid、是否可信 overlay 等。
过河：把整个 handle 列表交给 InputManagerService.setInputWindows，经 JNI com_android_server_input_InputManagerService.cpp（NativeInputManager，:253）→ InputDispatcher。
事务化：输入窗口信息与 Surface 一起走 mInputTransaction（InputMonitor.java:93）——虽然叫 SurfaceControl.Transaction，但 updateInputWindowsImmediately(t)（:360）证明它被用来保证“窗口的可见性变化”与“输入区域变化”原子生效，避免屏幕已经变了但输入区域还是旧的。

为什么解耦 InputDispatcher 每帧都可能做命中测试，不可能每次都去拿 WMS 的全局锁（那会把系统拖垮）。所以采用“快照”策略：WMS 锁内生成，出锁后 native 自己用。代价是——事件到达时看到的窗口表可能是几十毫秒前的。这就是“输入慢半拍”类问题的温床。

四、事件从哪来：InputReader 与 EventHub

链条上游：InputManagerService.start()（InputManagerService.java:476）启动后，native 侧会跑起 InputReader 线程。它循环不已地：

取原始事件：InputReader.cpp 的 loopOnce() 调 mEventHub->getEvents(timeoutMillis, mEventBuffer, EVENT_BUFFER_SIZE)（:108）。EventHub 是本机 evdev 设备的统一入口，负责打开 /dev/input/event*、epoll 等待、设备热插拔。
加工：InputReader 把原始事件交给各 InputMapper（触摸屏→MultiTouchInputMapper、键盘→KeyboardInputMapper、鼠标→CursorInputMapper），归一化成标准 MotionEvent / KeyEvent。
入队：加工后的事件推给 InputDispatcher 的 mInboundQueue，并唤醒 Dispatcher 线程。

这里有一个大量源码/文档都略过、但实际很关键的环节：按键类事件在“入队”之前要先问系统策略——这就是 interceptKeyBeforeQueueing。

🐛 实践含义 音量键/电源键在 App 里 onKeyDown 收不到，就是因为它们在这里被 policy 先截走了。想让 App 收到媒体键，得走 MediaSession，而不是在 View 层监听。同理，“屏幕关闭时触摸唤醒延迟”这类问题往往出在 interceptMotionBeforeQueueingNonInteractive 的非交互路径，而非触摸屏本身。

五、命中测试：事件到底归谁

这是 InputDispatcher 的心脏。一个已入队的事件，经过 dispatchOnceInnerLocked()（InputDispatcher.cpp:683）被取出后，会按类型分成两条路：

按键类（KeyEvent，含方向键/滚轮）：findFocusedWindowTargetsLocked()（定义 :1786，调用点 :1455 / :1562）——只看焦点窗口。
触摸类（MotionEvent）：findTouchedWindowTargetsLocked()（定义 :1900，调用点 :1557）——看坐标落在哪些窗口的可点区域内，并做遮挡与分裂处理。

5.1 触摸命中：touchable region 与“看到却点不到”

每个窗口在交底时带上了自己的 touchableRegion。命中时逐窗口判断：

InputDispatcher.cpp:1013（findTouchedWindowTargetsLocked 内核）
// 窗口若能收触摸：
if (!flags.test(InputWindowInfo::Flag::NOT_TOUCHABLE)) {      // :1013
    // 关键：要么是本窗口内触摸模式（isTouchModal，触摸不会“穿透”到下层）
    // 要么坐标真落在本窗口的可点区域里
    if (isTouchModal || windowInfo->touchableRegionContainsPoint(x, y)) {  // :1016
        ...  // 加入本次触摸的候选目标
    }
}
概念取法实践含义
isTouchModal窗口未设 FLAG_NOT_TOUCH_MODAL模态窗口：区域外的事件也不放行给下层（对话框就靠它拦住背景）
touchableRegion默认=窗口 frame，可被裁切/异形修改圆形/异形窗口、SurfaceView 挖洞靠它；算错就会“点到旁边却命中自己”或“点自己没反应”
NOT_TOUCHABLE窗口设了 FLAG_NOT_TOUCHABLE完全透明不拦截（如纯显示层），但仍可有输入通道

5.2 遮挡：上层盖住了，下层就收不到

InputDispatcher.cpp:2520（遮挡判断）
// 候选窗口是否被更高层的“不可穿透”窗口遮住：
if (... otherInfo->flags.test(InputWindowInfo::Flag::NOT_TOUCHABLE)) {  // :2520
    // 若上面的窗口可触摸（NOT_TOUCHABLE=false）且覆盖了该点，
    // 则下层不能再收——即使它的 touchableRegion 含这个点
}

关键区分 命中测试用的是窗口树 + 图层 Z（与 03 篇 assignChildLayers 算出来的 Z 一致），不是 View 树。一个覆盖在上面的透明悬浮窗（哪怕 View 是空的）只要可触摸，就会把下方 App 的点击吃掉——这是很多人把“点击被拦”当 bug 的根源。

5.3 触摸分裂与多窗口

触摸可能同时落在多个窗口（自由窗口、持续接收触摸的窗口），InputDispatcher 会把一次触摸“分裂”成多个目标（mTempTouchState 管理）。这就是为什么拖拽窗口时，底下的 App 也能同时收到事件（若它被标记为持续接收）。

六、焦点：按键类事件的前提

按键事件没有“坐标”，只能发给当前有焦点的窗口。所以先把焦点算对。

焦点在 WMS 侧维护：DisplayContent.findFocusedWindow()（:3362）从窗口树自顶向下找第一个“可见且可聚焦”的窗口；updateFocusedWindowLocked()（:3387）在窗口可见性/层级变化时重算，并把旧焦点记到 mLastFocus（:503，:3481 mLastFocus = mCurrentFocus）。

谁会赢：可见、可聚焦（非 NOT_FOCUSABLE）、且位于最上层的那个窗口（findFocusedWindowIfNeeded() :3357）。输入法、状态栏等系统窗口也有各自的可聚焦规则。
告知输入系统：焦点变后，除了交底窗口表，还要 setFocusedApplication()（IMS:1735）告诉 InputDispatcher“哪个 App 拥有焦点”。
InputDispatcher 侧：它不问 WMS，直接从“它自己维护的焦点记录”里取——mFocusResolver.getFocusedWindowToken(displayId)（InputDispatcher.cpp:1330），或按事件目标显示取（:1429）。这份记录的来源就是 ② / ⑤ 的交底。
焦点变了都会重算：窗口被移除时（mLastFocus 失效 :1241）、转屏时、输入法弹起时，焦点都可能重算——这也是“输入法弹出后按键跑到了输入法”的原因。

🐛 实战问题 悬浮窗设了 FLAG_NOT_FOCUSABLE，它不会被选为焦点窗口，无法接收按键（不能输入文字），但可以接收触摸。想要“能输入又不抢焦点”的需求，得额外处理（如与输入法交互）——这是 WMS 设计上的硬约束，不是配置坑。

七、分发到 App：从 socketpair 到 ViewRootImpl

命中测试得出目标后，就要把事件顺着 InputChannel 发出去。这一段的调用堆栈（已核实）：

按类型分发：InputDispatcher::dispatchKeyLocked()（:1362，按键）/ dispatchMotionLocked()（:1529，触摸）→ 两者最后都汇到 dispatchEventLocked()（:1671）。
准备发送周期：dispatchEventLocked() :1689 → prepareDispatchCycleLocked()（:2755，检查连接是否可用/ANR）。
入发送队列：enqueueDispatchEntryLocked()（:2844）把事件封入连接的发件箱（逐目标一份，故一次触摸可分发给多个窗口），再 startDispatchCycleLocked()（:3073）真正通过 socketpair 把数据写出去。
App 接收：写入 socketpair 后，App 进程的 InputEventReceiver（InputEventReceiver.java:38，基于自己的 Looper）被唤醒，回调到 ViewRootImpl。
App 派发：ViewRootImpl.enqueueInputEvent()（:8438）→ doProcessInputEvents()（:8493）→ deliverInputEvent()（:8520，走 View 树/手势识别）。
回执：App 处理完会回一个 finish 信号，InputDispatcher 的 finishDispatchCycleLocked()（:3287）→ onDispatchCycleFinishedLocked()（:5473）收尾，然后才发下一个。这就是“输入是同步往返”的含义。

同步往返的含义 InputDispatcher 发完一个事件会等 App 回执再发下一个（同一连接内）。所以 App 主线程卡住，不只是“这一下没反应”，而是后续事件全堆在发件箱里，超过 5 秒就成了输入 ANR。注意：这个“等待”发生在 InputDispatcher 线程，阻塞的是那一条连接，不是整个输入系统。

八、ANR：两种超时，两套重载

输入 ANR（日志里的 Input dispatching timed out）其实分两类，排障时必须先分清：

类型含义触发点日志特征
窗口无响应找到目标窗口了，发出去了，但 App 5 秒内没回执连接超时 → onAnrLocked(Connection) :5515“Waiting because no window has focus…”之外，直接指名窗口 + reason
无焦点窗口事件到达时没有任何焦点窗口（启动/转屏空窗期）processNoFocusedWindowAnrLocked() :614 → onAnrLocked(InputApplicationHandle) :5550“Application is not responding… no focused window”，甩锅给整个 App

ANR 发生后发生什么

native 上报：notifyWindowUnresponsive()（:5642）经 policy 回调回 system_server；无焦点窗口走 NativeInputManager::notifyNoFocusedWindowAnr（native IMS :802）。
WMS 侧处理：WindowManagerService 持有 mAnrController（:772，构造 :1389），焦点变化时处理（:4931 onFocusChanged(newFocus)）；AnrController（AnrController.java:46）决定是否要把超时的 App “切断输入并弹 ANR 框”。
弹框：由 system_server 的 ANR 流程弹出“应用无响应”对话框，同时抓 trace（traces.txt）供分析。

🐛 实战区分 看到 ANR 先看日志抄的是哪一行：窗口无响应→去查那个 App 主线程在干什么（trace 里找 Looper 阻塞）；无焦点窗口→去查为什么启动/转屏时迟迟没有焦点窗口（常见于启动慢、Activity 一直在 stopping、锁屏转场），往往不是输入的问题。

🧠 自测：6 个问题

1. 为什么 addWindow 阶段有 InputChannel，却还没有 Surface？
InputChannel 是输入管道，属于“逻辑身份”的一部分，挂树时就得有；Surface 是图形资源，要到首次 relayout 才向 SF 申请。两者生命周期故意错开：窗口可以先“能接收输入”再“能显示”。
2. 一次触摸能被几个窗口收到？
可以多个。InputDispatcher 在 findTouchedWindowTargetsLocked 里可能得到多个目标（多窗口/持续接收触摸），在 enqueueDispatchEntryLocked 里逐目标各发一份——这就是“触摸分裂”。
3. 按键事件发给谁，由什么决定？
由焦点窗口决定（findFocusedWindowTargetsLocked）。焦点由 WMS 根据“可见且可聚焦且最上层”算出，再交底给 InputDispatcher。
4. 一个透明悬浮窗为什么能吃掉下方 App 的点击？
因为命中测试用的是窗口树 + 图层 Z，不看 View。“可触摸”（NOT_TOUCHABLE=false）的窗口一旦覆盖该点，遮挡判断会让下层收不到——哪怕它是个空 View。解决：给悬浮窗设 FLAG_NOT_TOUCHABLE 或缩小 touchableRegion。
5. 日志里的两种“Input dispatching timed out”怎么区分？
看是窗口无响应（onAnrLocked(Connection)，App 主线程卡了）还是无焦点窗口（processNoFocusedWindowAnrLocked，启动/转屏空窗期）——两者的排查方向完全不同。
6. 为什么输入有时会“慢半拍”？
因为窗口表是 WMS 在持锁时生成的快照，InputDispatcher 用它做命中测试，不实时回查。若屏幕已变但快照未刷，就会出现“点到了旧位置”。排这类问题要拿 Winscope 对齐事件时间戳与层级变化时刻。
