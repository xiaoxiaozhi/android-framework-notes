先把定位钉死：vsync 不属于窗口层级，它属于显示子系统最底下的时间基准；Choreographer 也不属于窗口层级，它是 App 侧（以及 WMS 动画线程）对这个时间基准的消费者与调度器。你在 03/04/09 篇里反复看到的「每帧提交 SF」「动画在 vsync-sf 上跑」「申请一次给一次」，全部是在描述这两个东西的行为，而不是窗口树本身的性质。掉帧与「Skipped N frames」、动画首帧慢半拍、静态界面异常耗电、Perfetto 里对不齐 VSYNC 轨道，这四类现象最后都要落到本文这几条链上。主流程一句话：HWC 中断 → SF 收时间戳 → Scheduler 喂模型 → 模型算节拍、定时器唤醒 → EventThread 按连接分发 → BitTube 送到 App → Choreographer 的 doFrame → traversal。

0.0 名词表

名词一句话解释
vsync面板扫完一帧、回到第一行的那一瞬间。软件里它的形态就是一个纳秒时间戳（nsecs_t），不是事件对象、不是回调。
TE 信号Panel 的 tearing effect 信号，DDIC 每帧发一次给 SoC，是硬件 vsync 的物理来源。
VSYNC-app给 App 用的那条相位。Choreographer.getInstance() 默认连这条。
VSYNC-sf给 SurfaceFlinger 合成用的那条相位。Choreographer.getSfInstance() 与 SF 主循环连这条。
phase offset两条 vsync 相对硬件节拍的提前量，默认各 1ms（VsyncConfiguration.cpp:86-89）。
VSyncPredictor进程内的线性模型：拿历史时间戳拟合出周期与相位，之后不等中断也能算 nextAnticipatedVSyncTimeFrom()。
VSyncReactor看门人：确认周期是否稳定、要不要继续采样、刷新率切换时如何过渡。
VSyncDispatch定时器队列。有人要 vsync 时，按预测时刻用定时器唤醒，不依赖硬件中断。
EventThreadSF 进程里的分发线程，两条（app / appSf），各自维护一串 EventThreadConnection，按需把 vsync 写进各自的管道。
BitTube一对 socketpair，SF 端写、客户端读；vsync 事件就是以 DisplayEventReceiver::Event 结构体从这管道过去的。
Choreographer线程级的帧调度器：把「我想在下一帧做某事」翻译成「申请一次 vsync」，收到后按 input→animation→insets→traversal→commit 的顺序执行回调。
doFrameChoreographer 收到 vsync 后的主函数，一帧的全部回调在这里同步跑完。
vsyncId / FrameTimeline每个 vsync 事件带的 token，用来把 App 的 doFrame、SF 的合成、上屏时间串成一条时间线。
present fence内容真正上屏的信号。SF 用它校正预测：预测偏了就用它触发重新采样。
sync barrierHandler 队列的同步屏障，让异步消息（traversal、vsync）优先于普通消息执行；ViewRootImpl#scheduleTraversals 会先立一道。

摘要

主线：HWC 的硬件 vsync 进入 SF 后只当采样源，Scheduler 用它训练出周期/相位模型；模型学准就关掉硬件中断，由 VSyncDispatch 按预测时刻唤醒 EventThread；EventThread 再按连接把 vsync 写进每个客户端的 BitTube；App 的 Choreographer 收到后跑 doFrame，WMS 的 WindowAnimator 则用另一条 VSYNC-sf 相位推进动画。

  • 采样：onComposerHalVsync 只记录、过滤、喂模型，不合成、不直接发 App；外屏不喂模型。
  • 模型：VSyncReactor 确认周期，VSyncPredictor 用线性回归算周期与相位；needsMoreSamples() 决定硬件中断继续开还是关。
  • 分发：每个客户端一条 EventThreadConnection + BitTube；requestNextVsync 把 vsyncRequest 置为 Single，threadMain 按需投递，postEvent 写管道。
  • 消费：Choreographer 用 mFrameScheduled 保证一帧只申请一次；onVsync 只排消息，doFrame 按 input→animation→insets→traversal→commit 执行。
  • 两条相位：app 与 sf 默认各提前 1ms；WMS 的 WindowAnimator 在 android.anim 线程上用 getSfInstance()，先排下一帧再干本帧。

功能一：硬件 vsync 进 SF —— onComposerHalVsync()

HWC 每来一个硬件节拍，SF 只拿到一个纳秒时间戳。这个函数把它变成三样东西：该屏最近一次硬件 vsync 的记录、一次重复上报的过滤、以及给 Scheduler 的一个样本。它不合成、不 invalidate，也不直接给 App 发 vsync。

HWC HAL onVsync() [vendor thread] // 面板 TE 中断，厂商线程回调 └─ SurfaceFlinger::onComposerHalVsync() [SurfaceFlinger.cpp:1718] // 入口：只收时间戳 ├─ DisplayDevice::onVsync() [DisplayDevice.cpp:211] // 记录该屏最近一次硬件节拍 │ └─ mLastHwVsync = timestamp // 供 getRefreshTimestamp() 推算刷新边界 ├─ HWComposer::onVsync() [HWComposer.cpp:205] // 校验 display、丢重复样本 │ ├─ toPhysicalDisplayId() // display 还活着吗 │ └─ 丢弃灭/亮屏时重复上报的同一时间戳 // 防止同一拍喂两次 ├─ if (外屏) return // 模型只学内屏 └─ Scheduler::addResyncSample() [Scheduler.cpp:548] // 交给模型；见功能二

getHwComposer().onVsync() 返回 false 时直接 return，这不是「这一帧不显示」，而是「这个样本不可信」。外屏也在 addResyncSample 之前返回，因为整个进程只有一个预测模型，它只认内屏的节拍。这样设计把采样和分发彻底分开：采样可以随时关掉，分发只由 EventThread 的按需状态决定。

功能二：把样本喂给模型，并决定硬件 vsync 的生死 —— Scheduler::addResyncSample()

样本进来先看硬件中断是否开着：关着就直接丢弃，避免把陈旧相位喂进已经学准的模型。开着才交给 Reactor；Reactor 返回的布尔量决定接下来是继续开中断，还是立刻关掉。

Scheduler::addResyncSample() [Scheduler.cpp:548] // 入口：一个硬件样本 ├─ lock(mHWVsyncLock) // 只锁状态，不锁 HAL ├─ if (mPrimaryHWVsyncEnabled) // 中断开着才喂；关着说明样本过期 │ └─ VSyncReactor::addHwVsyncTimestamp() [VSyncReactor.cpp:170] // 确认周期、更新模型 │ ├─ periodConfirmed() [VSyncReactor.cpp:142] // 连续间隔稳定？稳定才承认周期 │ ├─ VSyncPredictor::addVsyncTimestamp() [VSyncPredictor.cpp:94] // 样本入历史窗口 │ └─ needsMoreSamples() [VSyncPredictor.cpp:342] // 样本够不够？ ├─ if (needsHwVsync) enableHardwareVsync() [Scheduler.cpp:487] // 还缺 → 继续开中断 └─ else disableHardwareVsync(false) [Scheduler.cpp:496] // 够了 → 关中断，保留重开资格

返回值 needsHwVsync 不是「这一帧要不要画」，而是「模型还缺不缺样本」。缺就继续开中断，不缺就关；关的时候传 false，表示「以后还能再开」，而不是把硬件能力标记为不可用。锁只包住状态变更，HAL 调用放在锁外，否则 SF 主线程会在 setVsyncEnabled 上等 HWC 时被这把锁卡住。

功能三：确认周期、拟合相位 —— VSyncReactor / VSyncPredictor

Reactor 先判断连续样本的间隔是否稳定；稳定才承认周期，然后交给 Predictor 做线性回归。Predictor 保存一组历史时间戳，斜率是周期，截距是相位；样本不够时 needsMoreSamples() 返回 true，模型继续要样本。

VSyncReactor::addHwVsyncTimestamp() [VSyncReactor.cpp:170] // 入口：Reactor 看门 ├─ periodConfirmed() [VSyncReactor.cpp:142] // 周期确认状态机 │ ├─ 连续样本间隔 ≈ 标称周期 // 稳定才承认 │ └─ mPeriodConfirmationInProgress 状态机 // 切换中先存上一个样本 ├─ VSyncPredictor::addVsyncTimestamp() [VSyncPredictor.cpp:94] // 喂给线性模型 │ ├─ validate() / clearTimestamps() // 异常样本丢弃或重学 │ ├─ mTimestamps 环形缓冲 // 保留最近 N 个 │ └─ 线性回归：slope = 周期，intercept = 相位 // 拟合出节拍 └─ VSyncPredictor::needsMoreSamples() [VSyncPredictor.cpp:342] // 样本不足 → 还要采样 VSyncDispatchTimerQueue 排 timer // 预测路径：按模型时刻排定时器 └─ VSyncPredictor::nextAnticipatedVSyncTimeFrom() [VSyncPredictor.cpp:240] // 模型回答「下一拍几点」

周期确认和相位拟合是两件事：Reactor 只回答「这串样本的间隔稳不稳」，Predictor 才回答「下一拍是几点」。模型不需要等硬件中断也能算，所以中断可以在学准后关掉；而 needsMoreSamples() 一旦为 false，采样就停，直到 present fence 或客户端 resync 发现预测偏了，再重新打开。

功能四：开关硬件 vsync —— enableHardwareVsync() / disableHardwareVsync()

模型说还缺样本，就把硬件中断打开；说够了，就关掉。开关本身只改一个布尔量，但重开之前必须先把旧模型作废——周期可能已经变了，否则新样本会被拿去修正一条过期的直线。

Scheduler::enableHardwareVsync() [Scheduler.cpp:487] // 打开硬件中断 ├─ lock(mHWVsyncLock) // 串行化开关 ├─ if (!mPrimaryHWVsyncEnabled && mHWVsyncAvailable) // 没开且能力可用 │ ├─ VSyncPredictor::resetModel() [VSyncPredictor.cpp:347] // 旧模型作废，重新学 │ ├─ mSchedulerCallback.setVsyncEnabled(true) // 回调到 SF │ │ └─ SurfaceFlinger::setVsyncEnabled() [SurfaceFlinger.cpp:1810] // 转给 HWC │ │ └─ HWComposer::setVsyncEnabled() [HWComposer.cpp:433] // 转给 Composer │ │ └─ ComposerHal::setVsyncEnabled() [ComposerHal.cpp:573] // 转给 HWC2 │ │ └─ HWC2::Display::setVsyncEnabled() [HWC2.cpp:469] // 面板 TE 中断 │ └─ mPrimaryHWVsyncEnabled = true // 记下已开 └─ (否则什么都不做) // 已开或不可用 Scheduler::disableHardwareVsync(makeUnavailable) [Scheduler.cpp:496] // 关闭硬件中断 ├─ if (mPrimaryHWVsyncEnabled) // 当前开着才关 │ ├─ mSchedulerCallback.setVsyncEnabled(false) // 落到面板 │ └─ mPrimaryHWVsyncEnabled = false // 记下已关 └─ if (makeUnavailable) mHWVsyncAvailable = false // 灭屏/热插拔：以后也不能开

disableHardwareVsync(false) 只关当前中断，保留「以后还能开」的资格；makeUnavailable=true 才把能力本身置为不可用，通常出现在灭屏或热插拔。重开时先 resetModel() 再 setVsyncEnabled(true)，顺序不能反：模型如果还留着旧周期，第一批新样本会被当成对旧直线的修正，而不是重新学习。

功能五：建客户端连接 —— EventThread::createEventConnection()

每个客户端一条 EventThreadConnection，底层是一对 BitTube socketpair。连接建立时就把缓冲区分配好，接收端 fd 交给客户端，SF 只留发送端；后续每帧投递不再分配、不再走 binder。

SurfaceFlinger::createDisplayEventConnection() [SurfaceFlinger.cpp:1684] // 客户端建连接入口 ├─ 选 app 还是 appSf 句柄 // 两条 vsync 各一条连接 └─ Scheduler::createDisplayEventConnection() [Scheduler.cpp:296] // 按句柄找 EventThread └─ EventThread::createEventConnection() [EventThread.cpp:271] // 真正建连接 └─ new EventThreadConnection() [EventThread.cpp:154] // 连接对象 └─ BitTube::BitTube() [BitTube.cpp:37] // 分配 socketpair └─ socketpair() // 一对 fd，跨进程两端 DisplayEventReceiver::DisplayEventReceiver() [DisplayEventReceiver.cpp:34] // 客户端构造 ├─ ISurfaceComposer::createDisplayEventConnection() // binder 到 SF └─ EventThreadConnection::stealReceiveChannel() [EventThread.cpp:173] // 接收 fd 搬给客户端 └─ 把接收 fd 搬到客户端，SF 只留发送 fd // 管道由此分家

连接建好之后，SurfaceFlinger 侧只保留发送端，接收端已经交给客户端；下面这条链从 SF 的入口一路看到 EventThread 的连接创建，每一层只做自己那一小步，不跨层兜底。

连接是 per-client 的，不是 per-process 的：同一个 App 里两个 Choreographer（app 与 sf）会各自建一条连接，拿到各自的 fd。管道容量在创建时就固定，投递时只写一个固定大小的 Event 结构体；这条路径每帧都走，任何序列化或动态分配都会被 60/120 倍放大。

功能六：按需申请一次 vsync —— EventThread::requestNextVsync()

客户端申请一帧，只把连接上的 vsyncRequest 从 None 改成 Single，然后唤醒 threadMain 重新计算等待条件。申请时顺手校一次模型，但 resync 内部有 750ms 限频，不会每帧都重采样。

申请动作从 Java 侧发出后，经过一次 JNI 转调和一次 binder oneway 才到 EventThread；下面把这三层放在一起看，注意调用方不会等待结果。

申请是异步的：requestNextVsync 走 binder oneway，调用方不会等 EventThread 处理。真正决定「给不给」的是 threadMain 里的汇总和 shouldConsumeEvent 里的状态自减；如果连接已经是 Single，第二次申请会被静默吞掉，所以 App 侧必须用 mFrameScheduled 保证一帧只申请一次。

功能七：分发 vsync —— threadMain() / dispatchEvent() / postEvent()

threadMain 是 EventThread 的主循环：先看有没有待处理事件，再逐条连接判断「谁要、谁该收」，最后把事件交给 dispatchEvent。真正写进客户端管道的是 postEvent；分发层只负责选人，不负责解释 vsync 的含义。

EventThread::threadMain() [EventThread.cpp:403] // 分发主循环 ├─ while (mState != Quit) // 直到线程退出 ├─ mPendingEvents.pop_front() // 取事件：vsync/hotplug/mode change ├─ for each connection: // 遍历所有客户端连接 │ ├─ vsyncRequested |= vsyncRequest != None // 汇总「还有人要吗」 │ └─ shouldConsumeEvent() → consumers // 逐连接过滤、限帧、状态自减 ├─ dispatchEvent(event, consumers) [EventThread.cpp:571] // 给选中的连接投递 │ └─ for each consumer: // 只投给 consumers │ └─ EventThreadConnection::postEvent() [EventThread.cpp:189] // 写客户端管道 │ └─ DisplayEventReceiver::sendEvents() [DisplayEventReceiver.cpp:101] // 转 BitTube │ └─ BitTube::sendObjects() [BitTube.cpp:148] // 真正 send() └─ State transition → mVSyncSource->setVSyncEnabled() // Idle/VSync/SyntheticVSync EventThread 的状态 // 四态决定怎么等 ├─ Idle // 无人申请：wait() 无超时，真休眠 ├─ VSync // 有人要：按预测节拍唤醒 ├─ SyntheticVSync // 灭屏/驱动异常：16ms 自造假 vsync └─ Quit // 线程退出

threadMain 里没有「广播」：它先汇总所有连接的 vsyncRequest，再对每个连接单独调用 shouldConsumeEvent。这一步决定了有人要才醒、没人要就回 Idle；Single 的「投递一次就自减」也藏在这里，不是调用方自觉。

dispatchEvent 只对已经选中的 consumer 逐个投递，所以分发成本与「有多少人在等」成正比，而不是与进程数成正比。EAGAIN 表示管道满，只丢当前帧；EPIPE 才说明连接死了，需要从列表里摘掉。这个区分很重要：主线程偶尔卡一下不应该导致连接被永久移除。

三个状态对应三种等待方式：Idle 是无超时 wait()，这是零唤醒的硬保证；VSync 是 1000ms 超时兜底，防止驱动卡死后客户端永远收不到回调；SyntheticVSync 是 16ms 自造节拍，用于灭屏或驱动异常。状态切换只在跨状态时执行一次 setVSyncEnabled，不会每帧重复开关。

功能八：App 侧排帧 —— Choreographer::postCallback()

App 想在下一次 vsync 做事，先调 postCallback 把回调塞进对应队列；真正申请 vsync 的是 scheduleFrameLocked，它用 mFrameScheduled 保证一帧只申请一次。跨线程调用时，申请消息会被插到队首，避免被已有消息拖延。

App 侧所有重绘最终都汇到 scheduleTraversals 这一个入口；下面看它如何先立屏障、再把 traversal 回调交给 Choreographer，顺序不能反。

mFrameScheduled 是应用层的「按需」开关：一旦为 true，后续所有 postCallback 都只是往队列里加，不会重复申请 vsync；直到 doFrame 把它清回 false，下一次才有资格再申请。延迟回调不会立刻申请 vsync，而是先排一条定时消息——提前申请只会白醒一次。

功能九：App 侧收帧与执行 —— onVsync() / doFrame()

onVsync 只做一件事：把一条异步消息排到 vsync 时间戳上。doFrame 才是真正执行回调的地方，它按 input → animation → insets → traversal → commit 的顺序跑完一帧，并把帧时间吸附到最近的节拍。

onVsync 不直接跑回调，是为了让消息队列先处理掉早于 vsync 时刻的普通消息，避免 vsync 饿死主线程。doFrame 的五段顺序在常量定义处就固定了：输入先消费、动画再算、Insets 在 traversal 前、commit 最后拿真实上屏估计。顺序换一下，动画或布局就会用到过期数据。

功能十：WMS 动画线程 —— WindowAnimator::animate()

WindowAnimator 跑在 android.anim 线程上，用的是 Choreographer.getSfInstance()，也就是 VSYNC-sf 那条相位。它每帧先给自己排下一帧，再干本帧的活；这样即使本帧超时，下一帧的申请也已经在途，表现为持续背压而不是断流。

WindowAnimator::WindowAnimator() [WindowAnimator.java:99] // WMS 动画器构造 ├─ mService.mAnimationHandler.runWithScissors( // 投到 android.anim 线程 │ () -> mChoreographer = Choreographer.getSfInstance()) // 取 VSYNC-sf 实例 └─ mAnimationFrameCallback = frameTimeNs -> { animate(...) } // 每帧回调 WindowAnimator::scheduleAnimation() [WindowAnimator.java:293] // 申请下一帧 └─ Choreographer::postFrameCallback(mAnimationFrameCallback) // 落到 CALLBACK_ANIMATION WindowAnimator::animate(frameTimeNs, vsyncId) [WindowAnimator.java:128] // 每帧推进 ├─ scheduleAnimation() // 先排下一帧，形成背压 └─ updateWindowsForAnimator / prepareSurfaces / ... // 本帧真正推进动画

runWithScissors 把 lambda 投到目标线程并等它执行完，确保 getSfInstance() 在 android.anim 上被调用。线程本身由 AnimationThread 创建，名字与优先级都已核实：super("android.anim", THREAD_PRIORITY_DISPLAY, false)（AnimationThread.java:35）。WMS 侧的 Handler 建在它上面（WindowManagerService.java:766），mAnimator = new WindowAnimator(this) 在 WindowManagerService.java:1248。

功能十一：相位与刷新率 —— VsyncConfiguration / VsyncModulator

app 和 sf 不是同一条 vsync：它们相对硬件节拍各有一个提前量，默认各 1ms。提前量先被换算成 duration，再交给 VsyncModulator 在 early / late 之间切换；early 用于“这一帧要赶早”的场景，late 是常态。

SurfaceFlinger::createEventThread() // 建两条 vsync 的入口 └─ Scheduler::createConnection("app" / "appSf") [SurfaceFlinger.cpp:3178] // 建两条 vsync 连接 ├─ PhaseOffsets::getDefaultOffsets() [VsyncConfiguration.cpp:163] // 取默认提前量 │ ├─ appOffsetToDuration() [VsyncConfiguration.cpp:151] // app 相位换算 │ └─ sfOffsetToDuration() [VsyncConfiguration.cpp:147] // sf 相位换算 └─ VsyncModulator::getNextVsyncConfig() [VsyncModulator.cpp:140] // 选 early/late ├─ earlyGpu / early // 有 early GPU/transaction 帧 └─ late // 常态，默认 1ms/1ms

两条相位是「同一块面板、两个唤醒点」：app 先醒，留出绘制时间；sf 后醒，留出合成时间。提前量不是固定的，刷新率切换或 early 帧会把配置换成另一组 duration，但换算方式不变——都是把 offset 从节拍上减掉，减出负数就补一个周期。

稳态闭环：静止画面为什么一帧都没有

把前面的碎片拼成一次完整循环，就能回答一个最常被问到的问题：屏幕静止时，这套机制到底在干什么？答案是什么都不干，而且是有严格代码依据的「什么都不干」。

1没有新的无效区域。View#invalidate 不产生调用 → ViewRootImpl#scheduleTraversals 不进 → Choreographer 的队列空。
2mFrameScheduled 保持 false。没有 postCallback，就没人调 scheduleFrameLocked（Choreographer.java:636），自然不会有 scheduleVsync()。
3连接上 vsyncRequest 停在 None。mHavePendingVsync 为 false，也没有新的 requestNextVsync（EventThread.cpp:318）。
4EventThread 汇总为 false。vsyncRequested 恒为 false（EventThread.cpp:437），nextState = Idle，触发 mVSyncSource->setVSyncEnabled(false)。
5DispSyncSource 停掉 callback repeater（DispSyncSource.cpp:139），VSyncDispatch 里不再有定时唤醒。
6Scheduler 侧的采样需求也归零。没有 invalidate → 没有 present fence 异常 → 模型无需重采样 → 硬件 vsync 保持关闭（Scheduler.cpp:496）。
7线程真的睡下去。mCondition.wait(lock) 无超时（EventThread.cpp:483），SF 主循环在 pollOnce(-1) 上等唤醒。

反向的启动条件只有一个：任何一方 postCallback / scheduleAnimation。一次点击、一次动画启动、一次窗口属性变化，就会让第 3 步重新发生，整条链被依次点亮。这就是「按需」的全部含义——不是靠某个总开关，而是每一层都在自己的条件满足时自然收敛/展开。

关键认知 vsync 是时间，不是内容：模型只保证「什么时候醒」，醒着的时候有没有事做，由窗口树 / View 树决定。反过来，窗口树只保证「谁盖谁、谁在哪」，什么时候真正上屏，由 vsync 决定。两套系统正交，接口就是这笔「申请一次、给一次」的契约。

🧠 自测：4 个问题

1. 外屏的 vsync 在 onComposerHalVsync 里直接 return，从没喂进 addResyncSample。那外屏的合成靠什么对齐？

靠内屏的模型 + 共享的 dispatch 定时器。预测模型是 per-Scheduler 的（mVsyncSchedule.tracker 只有一个），addResyncSample 只吃内屏样本；外屏只是不贡献样本，它要的节拍仍然由同一个 VSyncDispatch 按内屏周期推算。多屏不同刷新率时，靠 setVsyncPeriod 给模型换周期，并用外屏自己的最近一次 vsync 时间戳（getRefreshTimestamp()）估算该屏的刷新边界，而不是再训一个模型。

关键判据：代码里 if (hwcDisplayId != getHwComposer().getInternalHwcDisplayId()) return; 之后没有任何 per-display 的模型对象。

2. 采样够了就把硬件 vsync 关掉，SF 仍能每 16.67ms 醒一次——是谁算的、靠什么等下去？预测连续偏了，哪一步会把硬件 vsync 重新打开？

算：VSyncPredictor#nextAnticipatedVSyncTimeFrom（VSyncPredictor.cpp:240）用拟合出的周期与相位推算。等：VSyncDispatch 的定时器队列（VSyncDispatchTimerQueue）按该时刻设定时器，到点回调 MessageQueue#vsyncCallback（MessageQueue.cpp:105）→ dispatchInvalidate → SF 主循环醒来合成。

纠偏：实际 present 时间与预测不符时，Scheduler#addPresentFence（Scheduler.cpp:567）调 controller->addPresentFence，返回 true 就 enableHardwareVsync()；后者先 tracker->resetModel() 再 setVsyncEnabled(true)，重新进入采样。此外客户端申请 vsync 会经 resyncCallback 触发 Scheduler#resync（Scheduler.cpp:526，750ms 限频）。

3. 有人把 setVsyncRate(1) 设在一个连接上，为什么安静界面也会持续耗电？请指出这条链上「按需」失效的每一层。

rate=1 对应 VSyncRequest::Periodic（EventThread.h:53-59），于是：①threadMain 里 vsyncRequested |= connection->vsyncRequest != None 恒为 true（EventThread.cpp:437）；②nextState 永远是 State::VSync，setVSyncEnabled(false) 永不执行；③DispSyncSource 的 callback repeater 一直在跑，VSyncDispatch 定时唤醒不止；④SF 每帧被叫醒做一次「没有新内容」的合成尝试。四层全开，与界面是否变化无关。

排查时要注意：Single 会自减成 SingleSuppressCallback 再回 None，是安全的；只有 Periodic 或 rate>1 才是常开。

4.（结合功能六与功能八）「申请一次给一次」在 SF 侧和 App 侧各由哪个状态位保证？如果两侧状态不同步，会发生什么？

SF 侧：EventThreadConnection#vsyncRequest，在 shouldConsumeEvent（EventThread.cpp:518）里投递后从 Single 改 SingleSuppressCallback、再改 None。App 侧：Choreographer#mFrameScheduled（Choreographer.java:636 置 true，在 doFrame 里置 false），以及 mHavePendingVsync（:995 的自检）。

不同步的后果：若 App 侧提前把 mFrameScheduled 复位但 SF 还没投递，App 会再申请一次 → SF 侧仍是 Single，requestNextVsync 的 if (vsyncRequest == None) 不成立，这次申请被静默吞掉，表现为「偶发丢一帧」（EventThread.cpp:318-330）。若反过来 SF 已投递而 App 迟迟不处理，管道满后 postEvent 返回 -EAGAIN，logcat 出现 Failed dispatching。这正是「一帧只申请一次」必须靠两侧闸门共同保证的原因。
