# 实践项目设计：两类模型、已产出清单、硬指标

用途：用户要「实践项目 / 练习项目 / 你没给我出项目」时照此交付。核心结论：**实验不是项目**，交付必须带可验收产物。

## 一、实验 vs 项目（先分清，别拿实验当交付）

| | 实验 | 项目 |
|---|---|---|
| 时长 | 10 分钟 | 几天到两周 |
| 产出 | 一条命令的输出、一个「哦原来是这样」 | **可交付物**：patch / 工具 / 报告 / 功能 |
| 暴露什么 | 几乎没有 | 全部知识断口（因为要动手改、要跑通） |
| 面试能说吗 | 不能（人人都会） | 能：「我改过 X，现象 Y，根因 Z」 |
| 对应岗位能力 | 无 | **能改 + 能查**（B 岗的两个货币） |

## 二、两类项目模型（两类都要给，互补）

**① 修 bug 型（挖现成案例）**：起点是别人踩的坑 → 定位 → 修复。优点是贴近真实工作；缺点是依赖现成复现环境与参考文章。

**② 自造型（自己设计）**：起点是一条源码机制 → **预测 → 实现 → 实测 → 记录偏差**。优点是随时可做（环境就是本机 AOSP 树）、预测错了立刻暴露理解错误；产物是可运行的工具/引擎。

一句话类比（用户认可）：修 bug 型教你**当医生**（病人来了开刀），自造型教你**当制图师**（把地形亲自走一遍画出来）。只做前者，理解永远是「碎片 + 补丁」。

## 三、交付物硬指标（怎么算做完）

1. **能复现**：别人照着步骤能重现同样现象。
2. **有证据**：dump / 堆栈 / trace / 录屏，至少两种。
3. **能落到源码**：根因能指到具体类 + 方法 + 行号（不接受「框架那里有个 bug」）。
4. **能讲给别人**：不看笔记讲 5 分钟。
5. （B 岗专用）**能把修复讲成代价权衡**：为什么选方案 A 不选 B、A 影响哪些场景。

## 六、自造型项目的锚点（WMS 例，已核实）

具体行号见 `android-article-series/references/aosp12-source-map.md` 的「Z 序与层级（L1 预言机用）」「dump 字段」「窗口泄漏」「trace」「输入命中」各节——**直接用，不必重新 grep**。

出题规律（可复用到其他模块）：
- 挑一条**有明确数值或顺序输出**的机制（层级、优先级、状态机）→ 让用户自己重算并和真机对答案，误差为 0 才算过。
- 挑一条**「看起来不可能被改」的常量/顺序** → 让用户先写预测再改掉它，观察系统怎么坏（`TYPE_LAYER_MULTIPLIER`、`addChild` 位置、`mWindowMap.put` 与挂树的先后）。
- 挑一句**人人都见过的报错文案**（如 `has leaked window`）→ 让用户把它做成可量化检测工具。
