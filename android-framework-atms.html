一、它是什么：三个 Binder 接口，别再混着叫

先破一个误解：ATMS 不是「Activity 管理器」。它管的是层级——谁在哪个 Task 里、Task 在哪个 DisplayArea、Activity 该走哪一段生命周期。单个 Activity 里的 UI 状态，它一概不管。

系统里同时存在三个 Binder 接口，各管一块，名字很像，混起来就会得出错误结论：

Binder 接口实现类管什么app 侧怎么拿
IActivityManager ActivityManagerService（am/ActivityManagerService.java:461） 进程、Service、广播、内存/OOM、权限 ActivityManager.getService()
IActivityTaskManager ActivityTaskManagerService（wm/ActivityTaskManagerService.java:302） Task 树、ActivityRecord、生命周期、启动流程 ActivityTaskManager.getService()（core/java/android/app/ActivityTaskManager.java:149）
IActivityClientController ActivityClientController（wm/ActivityClientController.java:101） 反方向：系统 → app 的回调（如生命周期回调、onMovedToDisplay） 不对外，system_server 内部持有
一句话 ATMS 决定「谁活着、排第几」，WMS 决定「长什么样、在哪里」，AMS 决定「进程还在不在」。三条 Binder 接口，三个不同的客户端入口，用错入口就会在错误的服务里找半天。

二、服务结构：六个字段撑起全部

ATMS 这个类有四千多行，但真正撑起结构的只有六个字段。看懂这六个，剩下的都是流程。

字段行号作用
mGlobalLock:371全局锁，WMS 用的是同一把（WindowManagerGlobalLock，定义在 wm/WindowManagerGlobalLock.java）
mTaskSupervisor:380生命周期调度：启动、超时、空闲、ANR
mActivityClientController:381系统 → app 回调的出口
mRootWindowContainer:382整棵 Task / DisplayArea 树的根
mWindowManager:383WMS 引用，直接操作窗口层
mAmInternal:353AMS 的内部接口（要杀进程、查 uid 时用）

外加一个容易被忽略的观察者：

wm/ActivityTaskManagerService.java
464:  private TaskChangeNotificationController mTaskChangeNotificationController;

它负责把「task 变了」这件事广播出去——最近任务列表、Launcher、无障碍服务都从这里收到通知。这也是为什么「最近任务不刷新」有时不在 Launcher 的问题里：通知没发出去，或者发出去没人接。

类比把 ATMS 想成大楼的宿管：手里有一本花名册（Task 树）、一支笔（锁）、一部对讲机（回调）、一个通知板（TaskChangeNotification）。他不装修房间（那是 WMS），也不雇人（那是 AMS），他管的是「谁住哪间、什么时候搬、搬走要登记」。

三、它不拥有树，但持有同一棵树

这是理解 ATMS 最关键的一步，也是最多人搞错的地方：RootWindowContainer 是 WMS 创建的，ATMS 只是引用了同一个对象。

wm/WindowManagerService.java
669:  RootWindowContainer mRoot;
1261: mRoot = new RootWindowContainer(this);      // 树在这里诞生
wm/ActivityTaskManagerService.java
382:  RootWindowContainer mRootWindowContainer;
1024:  mRootWindowContainer = wm.mRoot;            // 不是 new，是引用
对象引用关系（同一个进程，同一个对象）
WindowManagerServicemRoot
ActivityTaskManagerServicemRootWindowContainer
↓ 两个字段指向同一个地址 ↓
RootWindowContainer唯一实例，树的根
DisplayContent一块屏幕
DisplayArea屏幕内的分区／层
Task任务栈，ATMS 真正操作的单位
ActivityRecord一个 Activity 的记录
WindowStateWMS 管
共享：同一个对象 + 同一把锁（mGlobalLock）

这个设计带来三个直接后果，每一个都能解释一类现象：

后果一：Task 变了，WMS 立刻知道，不需要跨进程同步

因为根本就是同一个对象。你在 ATMS 里把 task 的 parent 换掉，下一行代码 WMS 就能读到新的层级——没有 IPC、没有回调、没有延迟。

后果二：同一时刻只能有一个人改它

所以两边的 Binder 入口（ATMS 的 startActivity、WMS 的 addWindow / relayoutWindow）进来第一件事都是抢同一把锁：ATMS 一路走到 ActivityStarter.execute()，开头就是 synchronized (mService.mGlobalLock)（ActivityStarter.java:657）；WMS 的 addWindow（WindowManagerService.java:1498）、relayoutWindow（:2292）也一样。

而且这把锁的归属恰好和树相反：锁是 ATMS 建的，WMS 来取用——mGlobalLock = new WindowManagerGlobalLock()（ActivityTaskManagerService.java:371），WMS 构造时执行 mGlobalLock = atm.getGlobalLock()（WindowManagerService.java:1219）。这也是为什么「ATMS 里的 bug 会让整机卡住」——它拿的是 WMS 也要用的那把锁。

后果三：dumpsys 的两个投影

dumpsys activity activities 和 dumpsys window 看到的是同一份数据的两个视图：前者按 Task 组织，后者按 Window 组织。对着两份 dump 找同一条记录，比读代码快。

坑别在 WMS 里找「Activity 有没有启动」的答案。WMS 只看到 WindowState，它不知道这个窗口对应哪个 ActivityRecord 的生命周期阶段——那个信息只在 ATMS 侧。

三·补、DisplayArea 是什么（忘了看这里）

一句话：DisplayArea 是「一块屏幕上的一个分区／层」，是个纯容器——不放 Activity、不画任何东西，只决定谁在谁上面。

ATMS 的代码里会看到它，只是因为 Task 必须挂在某个 DisplayArea 下面。但 ATMS 真正打交道的是它的子类 TaskDisplayArea：dc.getDefaultTaskDisplayArea()（DisplayContent.java:3086）拿到的是「这块屏上默认放 Task 的那个区域」。

DisplayContent（一块屏） └─ RootDisplayArea [RootDisplayArea.java:40] └─ DisplayArea（各 Feature 层，由 DisplayAreaPolicyBuilder 建） ├─ HideDisplayCutout 挖孔／刘海区 ├─ WindowedMagnification 放大镜 ├─ OneHanded 单手模式 ├─ Tokens 直接挂 WindowToken 的层 [DisplayArea.java:629] └─ TaskDisplayArea 放 Task [TaskDisplayArea.java:73] └─ Task → ActivityRecord → WindowState
  • 它和 Task 是同一套树里的兄弟：DisplayArea extends WindowContainer（DisplayArea.java:71），和 Task / ActivityRecord / WindowState 共用一棵树，所以树序就是 z 序。
  • Task 是「内容」，DisplayArea 是「位置」：Task 里有 Activity、能被用户切走；DisplayArea 没有 Activity 概念，只是屏幕上的一个区域。
  • 层是显式声明的：每个 DisplayArea 带一个 mFeatureId（:75），由 DisplayAreaPolicyBuilder 按 Feature 建层——放大镜、挖孔隐藏、单手模式这类「整层」特性可以自己插进来，而不用改 WMS 的主逻辑（Android 10 之前这些是在层级计算里写死的 if/else）。
记法看到 DisplayArea 就问一句「它是不是 TaskDisplayArea」：是，就往里放 Task（task.reparent(tda, true)）；不是，那是窗口层／特性层，ATMS 一般不直接碰。

① 同线程直接调用 Activity.startActivity() └─ Instrumentation.execStartActivity() └─ ActivityTaskManager.getService().startActivity(...) [ActivityTaskManager.java:149] ② binder 跨进程（system_server） └─ ActivityTaskManagerService.startActivity() [ActivityTaskManagerService.java:1204] └─ ActivityStarter.execute() [wm/ActivityStarter.java:647] └─ executeRequest() [wm/ActivityStarter.java:849] └─ startActivityUnchecked() [定义 :1376，调用 :1227] └─ startActivityInner() [定义 :1543，调用 :1398] ├─ computeLaunchingTaskFlags() [定义 :2397，调用 :1551] ├─ getReusableTask() [定义 :2489，调用 :1567] └─ …（定位 / reparent 完成，进入真正启动） └─ realStartActivityLocked() [定义 ActivityTaskSupervisor.java:766] ③ binder 回到 app 进程（launch） └─ ApplicationThread.scheduleLaunchActivity() └─ ActivityThread.performLaunchActivity() └─ Activity.onCreate() / onStart() / onResume() ④ 首帧回执 └─ ActivityThread.handleResumeActivity() └─ reportFullyDrawn / onEnterAnimationComplete

六、生命周期后半场：删除的三条路径

启动讲得多，删除讲得少，但面试和排障都在这半边。ActivityRecord 消失有三条完全不同的路径：

wm/ActivityRecord.java
3707:  boolean destroyIfPossible(String reason) { ... }   // 正常销毁
3870:  void removeFromHistory(String reason) { ... }      // 从记录里摘掉
路径入口onPause/onStop/onDestroy典型场景
finishapp 调 finish() → destroyIfPossible() :3707都会回调用户点返回、代码主动结束
系统回收removeFromHistory() :3870可能只走 onStop，onDestroy 不一定任务被清理、进程被回收前
force-stopAMS 直接杀进程全部不执行am force-stop、设置里强行停止
坑第三条是经典陷阱题。很多人答「force-stop 会走 onDestroy」——不会。进程都没了，谁来执行回调？所以任何「退出时保存数据」的逻辑都不能依赖 onDestroy，要放在 onPause/onStop。

顺带说清楚一个常被问到的点：Activity 被系统回收后重建，不是「重新启动」。它走的是 ActivityThread 里的恢复流程，savedInstanceState 从 ActivityClientRecord 里来，不经过 ActivityStarter。所以在这种场景下你打启动链的断点，是打不到的。

七、第四条入口：把 task 搬到另一块屏

ATMS 的常驻入口有三个（start / finish / moveTaskToFront），第四个是你要自己加的：把 task 移到另一块屏。它最能说明 ATMS 的职责边界，因为一条链上同时踩到了 Task 树、配置变更、app 回调。

先明确一件事：移的是 task，不是 window

WindowState 的 parent 链固定在某个 DisplayContent 内，单个窗口不能跨屏。能跨屏的最小单位是 Task。这就是为什么所有跨屏方案最后都落到 Task.reparent。

四跳（AOSP 13 已核） 1 按 id 找 task RootWindowContainer.anyTaskForId(int) [RootWindowContainer.java:3255] 2 找目标屏的默认区域 RootWindowContainer.getDisplayContent(int) [RootWindowContainer.java:1342] └─ DisplayContent.getDefaultTaskDisplayArea() [DisplayContent.java:3086] 3 换 parent（跨 DisplayContent） Task.reparent(TaskDisplayArea, boolean onTop) [wm/Task.java:6098] └─ WindowContainer.reparent(WindowContainer, int) [WindowContainer.java:535] 4 配置变更下发到 app ActivityRecord.ensureActivityConfiguration() [ActivityRecord.java:9266] └─ scheduleActivityMovedToDisplay() [定义 :1405，调用 :9454] └─ Activity.onMovedToDisplay(int, Configuration) [Activity.java:3067]

四跳里最容易被忽略的是第 4 跳

很多人做完第 3 跳就以为完事了：dumpsys 里 displayId 确实变了，界面却还是旧尺寸或者直接黑掉。原因是第 4 跳没走完：

  • onMovedToDisplay() 只在 display 变化时回调，不是每次配置变更都调
  • 如果 activity 没声明对应的 configChanges，走的是 重建（onCreate 再来一次），不是 onMovedToDisplay
  • 重建会丢状态，除非你实现了 savedInstanceState 或用了 ViewModel
最小实现（未编译，示意）
// 放在 ActivityManagerShellCommand 或任意系统服务里
Task task = mAtm.mRootWindowContainer.anyTaskForId(taskId);              // :3255
DisplayContent dc = mAtm.mRootWindowContainer.getDisplayContent(displayId); // :1342
TaskDisplayArea tda = dc.getDefaultTaskDisplayArea();                    // :3086
task.reparent(tda, true);                                                 // :6098
实验前提没有双屏设备也能练：adb shell settings put global overlay_display_devices "1280x720/213"。这个 setting 由 OverlayDisplayAdapter 监听（services/core/java/com/android/server/display/OverlayDisplayAdapter.java:58 注释、:159 监听），立刻多出一块虚拟屏。
坑跨屏之后输入焦点不会自动跟过去。每块屏有自己的 input port 与焦点窗口，移动完要主动请求焦点，否则「窗口在那儿，点不动」。这一条在 05 输入分发与窗口命中 里有完整机制。

三个子命令各自看什么

命令看什么典型用途
dumpsys activity activitiesTask 树 + 每个 ActivityRecord 的状态（resumed/paused/stopped）、bounds、displayId「它在哪个 task」「有没有被重建」
dumpsys activity lastanr最近一次 ANR 的现场快照「谁没响应」「当时焦点在哪」

读的顺序（别从头读）

1先定位 Task：grep -n "Task{" 拿行号，再看这一段里的 taskId、affinity、displayId。
2再找 ActivityRecord：grep -n "ActivityRecord{"，看它挂在哪个 Task 下面缩进。
3最后看状态字：mResumed、mVisible、nowVisible、mState=。状态和你想的不一样，这才是线索。
坑dumpsys activity 里混着两个服务的内容：ACTIVITY MANAGER 段来自 ATMS / WMCore，后面的进程与服务列表来自 AMS。看到「进程」「ServiceRecord」就说明已经进入 AMS 的段，别再拿它判断 Task 关系。

九、八个坑（含和 WM Shell 的边界）

#坑正确认识
1把 ATMS 当成「Activity 管理器」它管层级与生命周期，不管 Activity 内部的 UI 状态
2以为 ATMS 拥有窗口树树由 WMS 创建（WindowManagerService.java:1261），ATMS 只是持有同一对象（:1024）
3把 startActivity 返回值当结果返回值只表示受理/拒绝，真正启动在异步链里
4指望 force-stop 走 onDestroy进程被杀，回调不执行；收尾逻辑放 onPause/onStop
5在 WMS 里找「能不能进分屏」门禁在 ATMS（ActivityClientController.java:819 → ATMS），摆放在 WM Shell
6把 WM Shell 当成 SystemUI 的功能它编译进 SystemUI APK、跑在 systemui 进程，但是独立 library（frameworks/base/libs/WindowManager/Shell），是 ATMS/WMS 的客户端，不是下属模块
7认为配置变更一定会重建声明全了 configChanges 就不重建；跨屏是否回调 onMovedToDisplay 取决于 display 是否真的变了
8在 ATMS 里放跨请求的成员状态binder 线程池并发处理请求，成员变量会被并发访问；状态必须挂在 ActivityRecord / Task 上
记住第 6 条「代码跑在 systemui 进程」≠「SystemUI 的功能」。判断归属永远看状态所有者：task 的 windowingMode 归 WMCore，leash 与 bounds 归 Shell，菜单窗口归 Shell 自己 addView 出来的 overlay。

🧠 自测：3 个问题

Q1 ATMS 和 WMS 是两个服务，为什么修改 task 的 parent 之后，WMS 立刻就能看到？
看看答案
因为 RootWindowContainer 只有一个实例：WMS 在 WindowManagerService.java:1261 创建它，ATMS 在 ActivityTaskManagerService.java:1024 直接引用 wm.mRoot。同一个进程、同一个对象、同一把锁（mGlobalLock，:371），所以不存在「同步延迟」这回事。
Q2 用户报告「点了通知，回到的是旧页面，不是通知对应的页面」。你先看哪两个方法？
看看答案
先看 computeLaunchingTaskFlags()（wm/ActivityStarter.java:2397）和 getReusableTask()（:2489）。前者决定意图里该不该 NEW_TASK，后者决定按 affinity 匹配到了哪个现存 task。绝大多数「回错页面」都是 PendingIntent 的 flags 与 taskAffinity 组合问题，而不是 Activity 生命周期问题。
Q3 你把 task 移到另一块屏，dumpsys 显示 displayId 已变，但界面还是旧尺寸。最可能漏了哪一跳？
看看答案
漏了第 4 跳：配置变更下发。看 ActivityRecord.ensureActivityConfiguration()（:9266）有没有走到 scheduleActivityMovedToDisplay()（:9454）。如果 activity 的 configChanges 没覆盖屏幕相关位，走的是重建而不是 onMovedToDisplay()（Activity.java:3067）；如果覆盖了但界面没刷新，检查 app 是否在回调里重新读取了新的 Configuration。
📌 这三题能不能一次答对，是「ATMS 学没学通」的直接判据：Q1 考共享结构，Q2 考决策入口，Q3 考生命周期与配置变更的耦合。
