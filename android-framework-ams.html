一、它是什么：管「生存」，不管「层级」

先破一个误解：AMS 不是「Activity 管理器」。从 Android 10 起，Activity / Task 那部分被拆成了 ATMS。AMS 留下的是更底层的一件事：进程还在不在、能不能被拉起、什么时候该杀。

两者协作方式一句话：ATMS 决定「谁活在哪一层」，AMS 决定「那个进程还活着吗」。ATMS 想启动一个 Activity，先要问 AMS 要进程；AMS 的进程挂了，要通知 ATMS 摘掉它名下的窗口。

Binder 接口实现类管什么
IActivityManager ActivityManagerService（am/ActivityManagerService.java:431） 进程、Service、广播、ContentProvider、崩溃收尾、内存/OOM
IActivityTaskManager ActivityTaskManagerService（wm/ActivityTaskManagerService.java:294） Task 树、ActivityRecord、生命周期、启动流程
IWindowManager WindowManagerService（wm/WindowManagerService.java） Window 树、布局、Surface、输入通道

AMS 的实际职责清单

  • 进程生命周期：按需 fork、attach、保活、杀（本节后半全部讲这个）
  • Service：启动/绑定/前台服务、超时（am/ActiveServices.java:183）
  • Broadcast：有序/无序分发、超时（am/BroadcastQueue.java:79）
  • ContentProvider：发布与查询（am/ContentProviderHelper.java:86）
  • 崩溃与 ANR 收尾：弹窗、日志、杀进程（am/AppErrors.java:74）
  • 内存与 OOM：算 adj、通知低内存杀手（am/OomAdjuster.java:125）
一句话 ATMS 管「层级」，WMS 管「像素」，AMS 管「生死」。三者都在 system_server 里，但只有 ATMS 与 WMS 共享同一把锁——这一点下一节就讲。

二、服务结构：六个字段撑起全部

AMS 有一万四千多行，但结构就是六个字段。看懂这六个，其余都是流程。

字段行号作用
mProcessList:746进程表：名字表、LRU 列表、启动与回收
mServices:1093Service 的启动、绑定、前台化
mBroadcastQueues:621三个广播队列：前台 / 后台 / 离线
mProcessStats:758进程运行时长统计（procstats 数据源）
mBatteryStatsService:1148耗电归因，进程级统计
mActivityTaskManager:1406ATMS 引用：起进程后要它去启动 Activity

反向依赖也存在：ATMS 持有 AMS 的内部接口 mAmInternal（wm/ActivityTaskManagerService.java:344，在 :951 通过 LocalServices 注入）。两个服务互为入口，这是它们「分家但没离婚」的代码证据。

顺带注意 mBroadcastQueues 是长度为 3 的数组（:621），不是单个队列。前台广播、后台广播、离线广播各一条，优先级与超时时间都不同——这就是「广播为什么时快时慢」的根源。

三、锁：AMS 用的是自己那把

这是 AMS 篇最容易搞错、也最值得单独讲的一点。三个服务的锁长这样：

服务锁字段实际是什么
AMSmGlobalLock（:569）ActivityManagerGlobalLock mGlobalLock = ActivityManagerService.this; ——自己
ATMSmGlobalLock（wm/ActivityTaskManagerService.java:362）new WindowManagerGlobalLock() ——自己 new 的一个对象
WMSmGlobalLock（wm/WindowManagerService.java:1211）atm.getGlobalLock() ——拿 ATMS 那把

所以准确的说法是：ATMS 与 WMS 同锁；AMS 独立一把。AMS 的「锁」是它自己（它 implements ActivityManagerGlobalLock，这个接口在 am/ActivityManagerGlobalLock.java 里是个空标记），这样写只是为了配合锁区域注入工具。

为什么这个区别重要

  • 死锁顺序：代码里允许「持 AMS 锁 → 调 WMS」，不允许反向。你如果在 WMS 的持锁区里回调 AMS，就有死锁风险。
  • 性能隔离：AMS 处理进程启停很慢（要等 zygote fork），如果它和窗口共锁，整个 UI 都会被拖住。拆锁是 Android 10 拆服务时的核心收益之一。
  • 排查线索：看 systrace / Perfetto 时，monitor contention 里出现 ActivityManagerService 与 WindowManagerGlobalLock 是两个不同的锁对象，别当成一个。
am/ActivityManagerService.java
// :569  AMS 用自己当锁
final ActivityManagerGlobalLock mGlobalLock = ActivityManagerService.this;
wm/WindowManagerService.java
// :1211  WMS 取的是 ATMS 的锁实例
mGlobalLock = atm.getGlobalLock();
记住「ATMS 和 WMS 同一把锁」成立；「AMS 和 WMS 同一把锁」不成立。这两句话差一个字，排查方向差一整天。

四、进程的诞生：五跳

一个 app 进程从「不存在」到「跑起来」，主线只有五跳。每一跳的职责都很清楚：

AMS.startProcessLocked() am/ActivityManagerService.java:2682 └─ mProcessList.startProcessLocked() :2686 → am/ProcessList.java:2441 └─ startProcessLocked(ProcessRecord…) am/ProcessList.java:1787 └─ Process.start() core/java/android/os/Process.java:657 └─ ZygoteProcess.startViaZygote() core/java/android/os/ZygoteProcess.java:626 └─ socket 请求 zygote fork → 新进程执行 ActivityThread.main()

fork 出来只是「进程有了」，还没有组件。新进程的第一件事是回连 AMS：

ActivityThread.main() └─ attachApplication() → binder └─ AMS.attachApplicationLocked() am/ActivityManagerService.java:4275 ├─ 绑定 ApplicationThread ├─ 建 ProcessRecord 的 binder 关系 └─ 通知 ATMS：可以启动 Activity 了

每跳各自负责什么

跳负责失败会怎样
AMS :2682判断要不要起、起哪个进程名、是否复用已有进程返回 null，调用方拿到 ProcessRecord 为空
ProcessList :2441 / :1787进程名查重、OOM adj 计算、HostingRecord 记录进程重复启动或启动被拒
Process.start() :657把启动参数序列化，交给 zygote抛 ZygoteStartFailedEx
startViaZygote() :626通过 socket 发 fork 请求，读回 pid超时、fork 失败
attachApplicationLocked() :4275建立双向 binder、初始化进程状态、交给 ATMS新进程起来但没界面（典型现象：白屏/闪退）
现象对齐「点应用图标，图标闪一下没了」通常是第 1–2 跳失败（进程没起来）；「白屏很久才出界面」是第 5 跳之后的事——进程起来了，但 Activity 没启动完。

五、进程的状态：ProcessRecord 与 ProcessStateRecord

AMS 用一个对象代表一个进程：ProcessRecord（am/ProcessRecord.java:69）。它自己不存状态，状态在 ProcessStateRecord（am/ProcessStateRecord.java:43）里：

am/ProcessRecord.java
// :511  进程状态被拆成独立对象
mState = new ProcessStateRecord(this);

为什么要拆？因为「进程状态」和「进程身份」的生命周期不同：ProcessRecord 可能被复用，而状态需要独立重置与统计。

两组容易混的状态

概念取值示例决定什么
PROCESS_STATE_*TOP、FOREGROUND_SERVICE、SERVICE、CACHED系统怎么看待这个进程（统计、限制、广播投递）
IMPORTANCE_* / adjFOREGROUND、VISIBLE、SERVICE、CACHED内存紧张时谁先被杀（下一节）

两者相关但不是一回事：一个进程可以是 PROCESS_STATE_SERVICE 却拿 VISIBLE 的 adj——比如它还有一个可见的悬浮窗。看内存问题看 adj，看调度与限制看 procState。

判据adb shell dumpsys activity processes | grep -A3 "ProcessRecord" 里同时能看到 oom: 与 procState= 两个值，对比着看就能判断这次是被「状态限制」还是被「内存压力」影响。

六、OOM adj：谁先死

AMS 不管「杀谁」，它只负责给每个进程打分；真正动手的是 lmkd（低内存杀手，独立进程）与内核。打分逻辑在 OomAdjuster（am/OomAdjuster.java:125）。

触发点（进程状态变化 / 组件增删 / 内存压力） └─ OomAdjuster.updateOomAdjLocked() am/OomAdjuster.java:531 ├─ computeOomAdjLSP() :1499 逐进程算基准 adj ├─ 向上累加依赖（bindService、provider 引用） └─ applyOomAdjLSP() 写回 ProcessRecord、通知 lmkd

adj 的粗粒度顺序（从高到低）

adj典型进程被杀可能性
NATIVE / SYSTEMinit、zygote、system_server几乎不杀
PERSISTENTpersistent 应用极低
FOREGROUND当前前台 app低
VISIBLE / PERCEPTIBLE可见但非前台、播放音乐中
SERVICE后台服务较高
CACHED后台缓存进程最高

关键细节：adj 不是只按「有没有 Activity」算。它还有「依赖传导」——如果你 bind 了一个高 adj 的服务，你的 adj 会被拉高。这就是「为什么我的后台进程没被杀」和「为什么它莫名其妙被杀了」的同一个答案。

别搞混AMS 决定的是 adj 数值；杀进程的决策在 lmkd 与内核内存回收里。所以「内存不足」不是 AMS 报的，AMS 只是把分数交出去。

七、Service、Broadcast、Provider 落在哪

三大组件在 AMS 里各有专属模块，但它们是同一个前提的消费者：进程必须先存在。

组件模块入口
Serviceam/ActiveServices.java:183startServiceLocked() :612，启动实现在 bringUpServiceLocked()（调用点 :934）
Broadcastam/BroadcastQueue.java:79分发主循环 processNextBroadcast() :985；投递入口在 AMS :13562
ContentProvideram/ContentProviderHelper.java:86Provider 发布与查询

Service 的真实路径

Context.startService() └─ binder → AMS.startService() → ActiveServices.startServiceLocked() am/ActiveServices.java:612 ├─ 进程不在？→ AMS.startProcessLocked()（回到第四节） └─ 进程在 → bringUpServiceLocked()（调用点 :934） └─ 回调 app：onCreate → onStartCommand

Broadcast 的真实路径

sendBroadcast() └─ binder → AMS.broadcastIntent() am/ActivityManagerService.java:13562 ├─ 解析目标（静态/动态接收者） ├─ 入队（前台 / 后台 / 离线三条队列） └─ BroadcastQueue.processNextBroadcast() am/BroadcastQueue.java:985 ├─ 有序广播：等上一个 receiver 返回 └─ 无序广播：并行投递

这两条链都回答同一个问题：为什么后台的 Service 启动慢、广播延迟大？因为每一步都要先确保进程存在，而进程存在要走 zygote fork——那是百毫秒级的事。

判据adb shell dumpsys activity services | grep -A3 <pkg> 看 app=ProcessRecord 是否为空；adb shell dumpsys activity broadcasts 看队列里积压了多少条。

八、死亡与回收

进程死亡有四种来源，收尾都汇到一处：

来源触发收尾
用户主动最近任务滑掉 / am force-stop杀进程组
崩溃未捕获异常AppErrors（am/AppErrors.java:74）弹窗 + 记录 + 杀
内存回收lmkd 按 adj 选择binder 死亡通知 → AMS 收尾
系统重启reboot / system_server 崩溃整体重建
进程死亡 └─ binder 死亡通知（linkToDeath） └─ AMS.cleanUpApplicationRecordLocked() am/ActivityManagerService.java:3015 ├─ 清理 ProcessRecord / 统计 ├─ 通知 AMS 内部：Service、Provider、广播 ├─ 通知 ATMS：摘 ActivityRecord └─ 通知 WMS：摘窗口（否则就是你看到过的「幽灵窗口」） └─ Process.killProcessGroup() core/java/os/Process.java:1319（杀进程组，含子进程）

为什么必须杀进程组而不是单个 pid？因为 app 可能 fork 子进程（WebView、渲染线程在独立进程时、厂商 SDK）。只杀主 pid 会留下孤儿，表现为「应用退了但内存没释放、CPU 还在跑」。

典型 BugActivity 已经销毁，但屏幕上还有它的画面——通常是「ATMS 收尾了、WMS 没收到」。此时 dumpsys window 里那个窗口的 mOwnerUid 对应的进程已经不存在，属于泄漏窗口。

九、观测：dumpsys 与 am 怎么用

AMS 相关的输出全在 dumpsys activity 下，但分成几段，先认段再读：

命令看什么典型线索
dumpsys activity processes进程表、adj、procState、LRU 顺序进程为什么被杀、为什么保活
dumpsys activity servicesServiceRecord、绑定关系、前台服务服务起不来、泄漏
dumpsys activity broadcasts三条队列的积压与超时广播延迟、ANR
dumpsys activity providersProvider 发布状态启动时 provider 初始化慢
dumpsys meminfo <pkg>PSS、Dalvik/Native 分布内存占用
dumpsys procstats --hours 3进程运行时长统计（mProcessStats）后台被杀的频率

三个实用命令

shell
# 1. 谁的 adj 最高（最不容易被杀）
adb shell dumpsys activity processes | grep -E "^ +\\*|oom:" | head -40

# 2. 某进程为什么被杀：看 procState 与 lastActivityTime
adb shell dumpsys activity processes | grep -A8 "com.example.framworkcontent"

# 3. 前台服务是否真的在前台
adb shell dumpsys activity services | grep -i "isForeground\|fgRequired"
和 ATMS 的分界dumpsys activity activities 是 ATMS/WMCore 的段，dumpsys activity processes 才是 AMS 的段。两段在同一个输出里，看错段就会得出「进程没了但 Activity 还在」这种自相矛盾的结论。

十、八个坑

#坑正确认识
1把 AMS 当 Activity 管理器Activity/Task 归 ATMS（wm/ActivityTaskManagerService.java:294），AMS 管进程
2以为 AMS 与 WMS 同一把锁AMS 用自己（:569），WMS 用 ATMS 的（wm/WindowManagerService.java:1211）
3以为 startService 会同步拉起进程缺进程时要走 zygote fork，异步且百毫秒级
4把有序广播当普通广播用有序广播要等前一个 receiver 返回，会串行排队
5以为 AMS 决定杀谁AMS 只算 adj，动手的是 lmkd 与内核
6用 dumpsys activity 的 Activity 段查进程进程在 processes 段，两段别混
7只按 procState 判断存活优先级内存回收看 adj，不是 procState
8在 AMS 持锁区做耗时操作AMS 锁被大量路径依赖，持锁 IO 会拖慢整机
记住第 2 条锁的区别不是学术细节：它决定了你排查死锁时该看哪个锁对象，也决定了「为什么改 AMS 会比改 WMS 更容易卡整机」。

三个实践题（不需要编译 framework）

  1. 观测五跳：am start 起一个冷启动 app，同时抓 logcat（Start proc、attachApplication）与 dumpsys activity processes 的两次快照，把五跳对上时间。判据：能说出「哪一跳花了多少毫秒」。
  2. adj 实验：同一 app，分别在前台、退到后台、再 bind 一个前台服务，三次抓 dumpsys activity processes 里该进程的 oom: 值。判据：三次 adj 单调递减，且能解释每一次变化的触发者。
  3. 广播队列实验：发一条有序广播与一条无序广播，各注册两个接收者（一个 sleep 2 秒），比较到达时间。判据：有序广播第二个 receiver 明显延迟，无序广播并行。
📌 这三题的价值在于「可判定」：每题都有一个能写下来对比的数字或时间戳。做完你就有了三条属于 AMS 的实测结论，而不是三条记忆。

🧠 自测：3 个问题

Q1 用户说「应用退了，但任务管理器里还有它的进程」。你先看 AMS 的哪一段？
看看答案
看 dumpsys activity processes，找这个进程的 oom: 与 procState=。如果 adj 是 CACHED，说明这是正常缓存不是泄漏；如果还有 ServiceRecord 或 provider 引用（去 dumpsys activity services 查），那才是真的被绑住了。
Q2 为什么 AMS 与 WMS 不共用一把锁？
看看答案
因为 AMS 的路径里有阻塞操作（等 zygote fork、等进程回连），和窗口共锁会把这些延迟传导给整个 UI。ATMS 与 WMS 共锁（wm/WindowManagerService.java:1211 取 ATMS 的锁）是因为它们操作同一棵 RootWindowContainer（wm/ActivityTaskManagerService.java:976），必须原子。
Q3 「后台服务里的定时任务越来越不准」，最可能是哪三个 AMS 机制在起作用？
看看答案
① 进程被降级到 CACHED 后更容易被回收（adj 上升）；② 广播队列积压导致唤醒延迟（am/BroadcastQueue.java:985）；③ Doze/standby 限制了唤醒窗口。三者叠加，表现为「有时准、有时差几分钟」，而不是「完全不准」。
