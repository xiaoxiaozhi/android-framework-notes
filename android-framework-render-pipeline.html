零、从开机到第一帧：初始化全景

这篇文章从零开始讲渲染，不假设你读过窗口层级系列。你不需要先知道 WMS、SurfaceFlinger 或 Choreographer；下面先把名词定清楚，再从开机讲到第一帧。

一、一分钟建立直觉：渲染到底在干什么

先把“渲染”从黑话还原成一句话：把程序里“要画什么”的描述，变成屏幕上一帧一帧的像素。

Android 里这件事分三段：

  1. 录制（Record）：App 把 View 树（按钮、文字、图片）录成一串绘制命令，叫 DisplayList。
  2. 画布（Draw）：RenderThread 把这串命令交给 GPU，画进一块共享内存 GraphicBuffer。
  3. 合成（Composite）：SurfaceFlinger 把多个窗口的 Buffer 按层级叠起来，交给 HWC/显示驱动，最后面板扫描发光。
✦ ✦ ✦ 三棵树 ✦ ✦ ✦
View 树（App 进程）：画什么。
窗口树（system_server）：每个窗口在哪、谁在前、可见性。
Layer 树（SurfaceFlinger 进程）：真实图层怎么叠、怎么裁剪、Z 值多少。
渲染就是：View 树 → 每个窗口一张 Buffer；窗口树 → Layer 树；SF 把 Buffer 按 Layer 树合成上屏。

60Hz 屏幕每 16.6ms 刷新一次；VSYNC 是节拍。所有绘制、布局、合成都要卡在这个节拍里，否则掉帧。

二、编舞者 Choreographer：每一帧的指挥

Choreographer 不画任何东西。它是 App 进程里每个线程一个的“节拍调度器”：收到 VSYNC 后，按固定顺序执行这一帧该做的事。

为什么叫“编舞者”？因为它决定“谁先动、谁后动”：输入先处理，动画再更新，布局/绘制最后执行，提交收尾。顺序错了就会看到输入延迟、动画跳帧或画面撕裂。

VSYNC └─ Choreographer.doFrame() [:701] ├─ 1. CALLBACK_INPUT (0) [:218] 处理输入 ├─ 2. CALLBACK_ANIMATION (1) [:225] 推进动画 ├─ 3. CALLBACK_INSETS_ANIMATION (2) [:241] Insets 动画 ├─ 4. CALLBACK_TRAVERSAL (3) [:248] measure/layout/draw └─ 5. CALLBACK_COMMIT (4) [:260] 提交
顺序回调类型常量做什么
1INPUTCALLBACK_INPUT = 0（:218）处理输入事件，保证点击/触摸最先响应
2ANIMATIONCALLBACK_ANIMATION = 1（:225）推进动画，算出这一帧的属性值
3INSETS_ANIMATIONCALLBACK_INSETS_ANIMATION = 2（:241）推进 Insets 动画（系统栏/IME）
4TRAVERSALCALLBACK_TRAVERSAL = 3（:248）measure / layout / draw，ViewRootImpl 的主战场
5COMMITCALLBACK_COMMIT = 4（:260）提交这一帧的渲染结果

关键入口：postCallback()（:430）把任务挂到某个回调类型；scheduleFrameLocked()（:636）向系统申请下一个 VSYNC；doFrame()（:701）在 VSYNC 到来时按顺序执行；FrameDisplayEventReceiver.onVsync()（:981）是 VSYNC 的接收口。

一句话：Choreographer 是“帧的指挥官”，不是“画图的人”。它只负责在正确的节拍调用正确的回调；真正画图的是 ViewRootImpl、RenderThread 和 GPU。

二·五、驱动机制：谁在推着这一帧走

Choreographer 只是“节拍器”。真正让一帧开始的是两类信号：内容变了 和 VSYNC 到了。

触发典型来源ViewRootImpl 里的动作结果
invalidate()View 内容变化、动画属性变化标记 dirty，调用 scheduleTraversals()只重画，不一定重新 measure/layout
requestLayout()View 尺寸/结构变化、addView/removeView置 mLayoutRequested，调用 scheduleTraversals()measure → layout → draw 全走
VSYNCDisplayEventReceiverChoreographer.doFrame()按顺序执行本帧回调
invalidate() / requestLayout() [:1770] └─ ViewRootImpl.scheduleTraversals() [:2097] └─ Choreographer.postCallback( CALLBACK_TRAVERSAL, mTraversalRunnable) [:2102] └─ scheduleFrameLocked() [:636] └─ 申请 VSYNC └─ Choreographer.doFrame() [:701] └─ doTraversal() [:2117] └─ performTraversals() [:2510]
ViewRootImpl.java:2097-2115（节选）
void scheduleTraversals() {
    if (!mTraversalScheduled) {                 // 防重入：一帧只排一次
        mTraversalScheduled = true;
        mTraversalBarrier = mHandler.getLooper().getQueue().postSyncBarrier();  // 同步屏障：让 traversal 优先
        mChoreographer.postCallback(                 // 挂到下一帧
                Choreographer.CALLBACK_TRAVERSAL, mTraversalRunnable, null);
    }
}

VSYNC 到来后：Choreographer.doFrame()（:701）→ doCallbacks → mTraversalRunnable → doTraversal()（:2117）→ performTraversals()（:2510）。

✦ ✦ ✦ 为什么要等 VSYNC ✦ ✦ ✦
如果每次 invalidate() 都立刻画，一帧内可能画很多次，浪费 GPU，还会和屏幕扫描不同步。Choreographer 把这一帧内的多次请求合并成一次 traversal，等 VSYNC 来了再统一执行；这样画面更新和屏幕刷新对齐，不会撕裂。

SurfaceFlinger 也有自己的 VSYNC 和调度器：App 画完把 Buffer 交给 SF，SF 在它自己的 VSYNC 里 commit/composite/present。两个循环通过 BLAST 事务和 frame timeline 对齐，不是同一个线程。

四、App 侧：View 树怎样变成 DisplayList

Choreographer 的 TRAVERSAL 回调最终落到 ViewRootImpl.performTraversals()（:2510）。它做三件事：

ViewRootImpl.performTraversals() [:2510] ├─ performMeasure() [:3602] │ └─ 递归测量：每个 View 多大 ├─ performLayout() [:3665] │ └─ 递归摆放：每个 View 在哪 └─ performDraw() [:4128] └─ ThreadedRenderer.draw() [:4418 / :613] ├─ updateRootDisplayList() [:538] │ └─ RenderNode.beginRecording()/endRecording() [:394/426] └─ syncAndDrawFrame() [:634] └─ RenderThread → GPU → GraphicBuffer

DisplayList 里是“画什么”的命令（画矩形、贴图、变换），不是像素。真正的 GPU 绘制发生在 RenderThread：它同步 DisplayList，调用 Skia/GL/Vulkan，把命令画进 GraphicBuffer。

ThreadedRenderer.java:613-634（节选）
void draw(View view, AttachInfo attachInfo, DrawCallbacks callbacks) {
    updateRootDisplayList(view, callbacks);   // ① 录制 DisplayList
    int syncResult = syncAndDrawFrame(frameInfo); // ② 交给 RenderThread
}

DisplayList 里是“画什么”的命令（画矩形、贴图、变换），不是像素。真正的 GPU 绘制发生在 RenderThread：它同步 DisplayList，调用 Skia/GL/Vulkan，把命令画进 GraphicBuffer。

✦ ✦ ✦ 为什么要两个线程 ✦ ✦ ✦
UI 线程负责 measure/layout/录制，RenderThread 负责 GPU 绘制。这样 UI 线程可以继续处理下一帧的输入和布局，不必等 GPU 画完；两块工作流水线化，才能在一帧 16.6ms 内完成。

五、过河：Buffer 怎样到 SurfaceFlinger

RenderThread 画完后，像素在一块 GraphicBuffer 里。它通过 Surface（生产者端）queueBuffer 归还队列；Android 12 默认走 BLAST：

RenderThread → GraphicBuffer └─ Surface.queueBuffer └─ BLASTBufferQueue.onFrameAvailable() [:546] └─ setBuffer + SurfaceControl.Transaction └─ SurfaceFlinger ├─ WMS 几何事务：position / Z / alpha / visibility └─ commitTransaction() [:3232] └─ composite → present

关键 SF 收到的不是“View 树”，而是“哪块 Buffer 放到哪个 Layer 上”。View 的 measure/layout/draw 全部在 App 进程完成。

六、层级树怎样被渲染：从 WindowState 到 Layer

现在回答核心问题：窗口层级树是怎么变成屏幕画面的？ 分两段，不要混在一起：

阶段输入输出谁做
① App 绘制每个窗口的 View 树每个窗口一块 GraphicBufferApp 进程（ViewRootImpl + RenderThread + GPU）
② 图层合成所有窗口的 Buffer + Layer 树一帧屏幕像素SurfaceFlinger + HWC/GPU

关键认知：SurfaceFlinger 完全不知道 View、measure、layout 这些概念。它只看到 Layer 和 Buffer。View 树在 App 进程里已经被“拍平”成一张 Buffer 了。

✦ ✦ ✦ 三棵树的分工 ✦ ✦ ✦
View 树：画什么（按钮、文字、图片）。
窗口树：每个窗口在哪、谁在前、可见性、Z 序策略。
Layer 树：真实图层怎么叠、裁剪、变换、alpha。
渲染 = 每个 WindowState 的 View 树 → 一张 Buffer；WMS 决定 Layer 树；SF 按 Layer 树合成。

所以“层级树渲染”不是把整棵窗口树直接丢给 GPU，而是：

  1. 每个 WindowState 对应一个 BufferStateLayer；
  2. 这个窗口的 View 树在 App 进程画进自己的 Buffer；
  3. WMS 用 assignChildLayers 算出每个 Layer 的 Z 值，写进 Transaction；
  4. SF 按 Layer 树的父子关系和 Z 值，把所有 Buffer 叠成一帧。

把“哪个节点有 Layer、哪个有 Buffer”直接列出来：

逻辑节点Surface 节点有 Layer？有 Buffer？
DisplayContentLayer "Root"必有（容器）否
DisplayArea / Task容器 Layer按需否
ActivityRecord / WindowToken容器 Layer首个顶层窗口加入时否
WindowStateBufferStateLayer必有是
为什么只有 WindowState 有 Buffer：因为只有它承载 App/系统真正绘制的内容；DisplayArea/Task/ActivityRecord 只是容器，负责裁剪、变换、组织 Z 序，本身不装像素。

七、合成与上屏：HWC/GPU 的最后一公里

SurfaceFlinger 拿到所有 Layer 的 Buffer 后，做三件事：

阶段做什么谁执行
commit把事务应用到 Layer：位置、Z、alpha、bufferSF 主线程
composite决定每个可见区域由 HWC 还是 GPU 合成SF + HWC / RenderEngine
present把合成结果交给显示控制器，面板扫描发光HWC / 显示驱动

HWC 能直接叠加的层就硬件合成（省电、快）；层数太多、效果太复杂时，SF 回退用 GPU 先合成成一块 Buffer，再交给 HWC。这个决策每帧动态做。

为什么还会掉帧？ 一帧的预算只有 16.6ms：Choreographer 调度、measure/layout、DisplayList 录制、GPU 绘制、BLAST 提交、SF 合成，任何一段超时，这一帧就赶不上 VSYNC，只能等下一帧。

八、完整时序：一帧的一生

VSYNC │ ▼ Choreographer.doFrame() [App · UI 线程] ├─ CALLBACK_INPUT 处理输入 ├─ CALLBACK_ANIMATION 推进动画 ├─ CALLBACK_INSETS_ANIMATION 推进 Insets 动画 └─ CALLBACK_TRAVERSAL │ ▼ ViewRootImpl.performTraversals() [App · UI 线程] ├─ performMeasure() → performLayout() └─ performDraw() │ ▼ ThreadedRenderer.draw() [App · UI 线程] ├─ updateRootDisplayList() 录制 RenderNode/DisplayList └─ syncAndDrawFrame() 交给 RenderThread │ ▼ RenderThread [App · 渲染线程] └─ GPU 绘制 → GraphicBuffer → queueBuffer │ ▼ BLASTBufferQueue.onFrameAvailable() [App] └─ Buffer 打包进 SurfaceControl.Transaction │ ▼ SurfaceFlinger.commitTransaction() [SF 进程] ├─ 应用 WMS 几何事务 + App Buffer 事务 ├─ composite：HWC / GPU └─ present：交给显示控制器 │ ▼ 面板扫描发光 [硬件]

这张图就是“渲染”的全貌：调度 → 录制 → 绘制 → 过河 → 合成 → 上屏。窗口层级树在中间的角色，是决定“哪块 Buffer 放到哪一层、谁在前”。

八·五、稳态：点击之后，下一帧怎么来

初始化只发生一次；之后屏幕每 16.6ms 重复的是“稳态闭环”。以一次点击为例：

点击 / 输入 └─ ViewRootImpl.dispatchInputEvent() └─ View.dispatchTouchEvent() → onTouchEvent() └─ invalidate() / requestLayout() └─ scheduleTraversals() [:2097] └─ Choreographer → VSYNC └─ doFrame() [:701] └─ doTraversal() [:2117] └─ performTraversals() [:2510] └─ measure → layout → draw └─ RenderThread → GraphicBuffer └─ BLAST → SF commitTransaction() [:3232] └─ composite → present

所以“驱动”不是某个线程从头跑到尾，而是 事件触发 + VSYNC 节拍 + 生产者/消费者事务 三者咬合。

✦ ✦ ✦ 掉帧的因果 ✦ ✦ ✦
一帧预算 16.6ms。measure/layout 太重、DisplayList 太大、GPU 太慢、BLAST/SF 排队，任何一段超时，这一帧就赶不上 VSYNC；屏幕继续显示上一帧，用户看到卡顿。

9.2 自测（5 题）

1. Choreographer 是负责画图的吗？
不是。它是帧调度器：收到 VSYNC 后按固定顺序调用 input、animation、insets animation、traversal、commit 回调；真正画图的是 ViewRootImpl、ThreadedRenderer、RenderThread 和 GPU。
2. 为什么回调顺序是 input → animation → traversal → commit？
输入最先响应，保证点击不延迟；动画先算出这一帧的属性值；traversal 用最新属性做 measure/layout/draw；commit 收尾提交。顺序颠倒会导致输入延迟、动画跳帧或画面撕裂。
3. DisplayList 是像素吗？
不是。DisplayList 是绘制命令（画矩形、贴图、变换），由 RenderNode 录制；RenderThread 执行这些命令后，才由 GPU 产生像素并写进 GraphicBuffer。
4. SurfaceFlinger 知道 View 树吗？
不知道。SF 只认 Layer 和 Buffer。View 树在 App 进程里已经被画成每个窗口的一块 Buffer；SF 只负责按 Layer 树把 Buffer 叠起来。
5. 层级树怎样变成屏幕画面？
每个 WindowState 对应一块 Buffer；WMS 用 assignChildLayers 算出 Layer 的 Z 序并把几何/可见性写进事务；SF 按 Layer 树合成所有 Buffer，交给 HWC/GPU 上屏。
✦ ✦ ✦ 三句话收尾 ✦ ✦ ✦
1. Choreographer 是节拍器，不是渲染器；它按 VSYNC 调度 input → animation → traversal → commit。
2. requestLayout / invalidate 点火，VSYNC 给拍子；一帧内多次请求合并成一次 traversal。
3. View 树在 App 画成 Buffer；WMS 决定 Layer 树；SF 合成上屏。初始化从 SurfaceFlinger/WMS/ViewRootImpl 开始，稳态每 16.6ms 循环一次。
